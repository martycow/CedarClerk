# Десктопное приложение

Решение — ADR-104 (выбор подхода) и ADR-105 (отсутствие синхронизации), `docs/DECISIONS.md`. Причина существования — Asset Manager: индексировать `D:\Projects\MyGame\Assets` умеет только процесс, запущенный на той же машине (ADR-107). Место в очереди работ — `docs/ROADMAP.md`, Phase 13, пункт 2.

> **Построено и проверено 10.08.2026 (T-121).** Оболочка запускается, поднимает сервер на свободном порту, отдаёт SPA, создаёт данные в `%APPDATA%\CedarClerk`, при закрытии окна не оставляет сервер сиротой. Сборка — `.\Scripts\build.ps1`, запуск — `cd CedarClerk.Desktop; npm start`.
>
> **Что из описанного ниже ещё НЕ сделано**: облачный режим (ADR-105 — сейчас работает только локальный), бэкапа локальной базы нет (`T-137`).
>
> **Самообновление добавлено 11.08.2026 (ADR-116).** `.\Scripts\deploy.ps1 -Desktop` собирает инсталлер и кладёт его на сервер, установленная копия обновляется сама — раздел «Как приезжает обновление» ниже.

Этот документ описывает механику: то, что уже реализовано, — как оно устроено; остальное — как строить.

## Общая схема

```
┌─────────────────────── Electron ────────────────────────┐
│  main process                                            │
│   ├─ поднимает CedarClerk.Server.exe на свободном порту  │
│   ├─ ждёт GET /api/health                                │
│   ├─ BrowserWindow.loadURL(http://127.0.0.1:<порт>)      │
│   └─ dialog.showOpenDialog → путь папки                  │
│                    │ IPC (preload, contextIsolation)      │
│  renderer ─────────┴─ тот же Angular SPA, без форка      │
└──────────────────────────────────────────────────────────┘
             │
   CEDAR_DATA_DIR = %APPDATA%/CedarClerk
     ├─ cedar.db
     └─ media/
```

Ни серверный код, ни фронтенд не форкаются (ADR-101). Angular-сборка — та же, что уезжает на прод.

## Структура в репозитории

Новая папка `CedarClerk.Desktop/`:

| Файл | Что в нём |
|---|---|
| `main.js` | Запуск sidecar, ожидание health, окно, меню, завершение процесса |
| `preload.js` | Мост IPC с `contextIsolation: true` — единственный канал между страницей и файловой системой |
| `package.json` | Electron + electron-builder |
| `electron-builder.yml` | Конфиг сборки установщика |

Сборка десктопа — это `Scripts/build.ps1`: `npm run build` (Angular) → `dotnet publish -r win-x64` → копирование SPA в `wwwroot` рядом с exe → `electron-builder`. `Scripts/deploy.ps1` **с флагом `-Desktop`** вызывает его же и после этого публикует результат на сервер (ADR-116); без флага деплой десктопа не касается вообще.

## Запуск сервера

```
dotnet publish CedarClerk.Server -c Release -r win-x64 --self-contained -o desktop-server/
```

Self-contained: на машине пользователя не предполагается установленный .NET. На сервере это не так (там runtime стоит отдельно, `.claude/rules/production-environment.md`) — сборки разные и не должны смешиваться.

**Порт выбирается свободный, не 8080.** Оболочка просит порт у ОС (`net.createServer().listen(0)`) и передаёт его серверу через `Cedar__Urls`.

Это потребовало единственной правки в серверном коде — **сделана 10.08.2026**. Адрес был зашит литералом: `app.Run(Consts.URLs.Localhost)` в конце `Program.cs`. Литерал в аргументе `app.Run` перекрывает `ASPNETCORE_URLS`, поэтому переменной окружения порт задать было нельзя. Теперь: `Cedar:Urls` (`Consts.General.UrlsCfg`), затем `ASPNETCORE_URLS` (через `app.Run()` без аргумента — их может быть несколько через `;`), затем прежнее значение по умолчанию. Ни `dotnet run`, ни прод изменения не замечают. Побочно это починило `Scripts/e2e.ps1`, который выставлял `ASPNETCORE_URLS` и до сих пор молча им не пользовался.

Почему не 8080: у Марти на той же машине регулярно поднят локальный dev-сервер, а на проде 8080 фиксирован конфигом Cloudflare-туннеля. Занятый порт даст непонятную ошибку старта вместо работающего приложения.

**Готовность определяется по `/api/health`**, а не по таймауту: эндпоинт уже есть (`Program.cs:271`) и отдаёт версию — то есть заодно ловит рассинхрон, когда рядом с оболочкой лежит exe от другой сборки.

## Данные

`CEDAR_DATA_DIR=%APPDATA%/CedarClerk` — **та же переменная, что задаётся systemd-drop-in'ом на проде**. Внутри `cedar.db` и `media/`, миграции применяются на старте сами (`Database.Migrate()` в `Program.cs`).

Из этого следует то, о чём легко забыть: **бэкапа у десктопной базы нет.** Раньше здесь стояло «на Pi её копирует ночной cron» — с переездом на DigitalOcean (11.08.2026) не стало и его: у прода теперь только еженедельный бэкап дроплета целиком, у десктопа — по-прежнему ничего. Локальный режим должен либо предложить папку для бэкапов, либо честно сказать, что копий нет — «данные просто есть» здесь неправда.

## Бот выключен, и это не мелочь

Без токена `TelegramBotService.IsRunning` возвращает false by design, публикация в Telegram отвечает 503 с внятным текстом. На десктопе токена нет — значит, ничего настраивать не нужно.

Настраивать при этом **нельзя**: Telegram допускает ровно один процесс, длинно опрашивающий токен, и второй получает 409 (`.claude/rules/telegram-bot.md`). Марти будет запускать десктоп при живом проде, то есть попытка «а давай и здесь бота» уронит продакшен-бота, а не десктопного. В памяти проекта уже два таких инцидента (13.07 и 26.07). Токен в десктопной сборке не поддерживается сознательно, и если поле для него когда-нибудь появится — рядом должно быть это предупреждение.

## Два режима (ADR-105)

При первом запуске выбирается один из двух, и выбранный виден в интерфейсе постоянно:

| Режим | Что происходит | Данные |
|---|---|---|
| **Локальный** | Оболочка поднимает свой сервер | Свой `cedar.db` в `%APPDATA%` |
| **Облачный** | Сервер не поднимается; окно открывает `https://cedarclerk.mooexe.dev` | Данные на сервере |

Синхронизации между ними нет и в v1 не будет. Причина в ADR-105: merge офлайн-правок TipTap-документа — это либо CRDT, либо потеря чужих правок, а проект уже проходил через инцидент потери текста (`T-060`) и построил вокруг него три гарда.

Asset Manager работает в **обоих** режимах: индексируются пути, файлы никуда не копируются (ADR-107), а путь одинаково хорошо уходит и на локальный сервер, и на удалённый. То есть главная причина существования десктопа от выбора режима не зависит.

## Доступ к файловой системе

Единственное, ради чего всё это делается.

1. Renderer просит папку → IPC в main.
2. Main вызывает `dialog.showOpenDialog({ properties: ['openDirectory'] })`.
3. Выбранный путь возвращается в renderer и уходит на сервер как обычный HTTP-запрос индексации.
4. Сервер обходит папку и пишет `AssetEntry`-строки.

`contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` — страница получает ровно те две-три функции, что открыты в preload, и ничего больше. Это не перестраховка: renderer грузит TipTap и пользовательский контент, то есть по нему в принципе может приехать чужой HTML.

**Обход делает сервер, а не Electron.** В облачном режиме сервер удалённый и до папки не дотянется — значит, в облачном режиме обход должен делать main-процесс и отправлять результат списком. Это единственное место, где два режима расходятся по коду, и решать его надо на входе в реализацию, а не по ходу.

## Сборка и запуск

```
.\Scripts\build.ps1                 Angular + сервер + десктоп
.\Scripts\build.ps1 -DesktopOnly    пересобрать только оболочку
.\Scripts\build.ps1 -Installer      плюс CedarClerk-Setup-<версия>.exe
.\Scripts\build.ps1 -RunDesktop     собрать и сразу запустить
cd CedarClerk.Desktop; npm start    запустить уже собранное
```

`Scripts/build.ps1` синхронизирует версию в `CedarClerk.Desktop/package.json` с `Consts.CurrentVersion` — оболочка сверяет её с ответом `/api/health` при старте, и рассинхрон показывается диалогом, а не странным поведением через полчаса.

`CedarClerk.Desktop/server/` — выход сборки (~70 МБ self-contained рантайма), в git не попадает.

## Как приезжает обновление (ADR-116)

```
.\Scripts\deploy.ps1 -Desktop
   │
   ├─ обычный деплой сайта (сборка → архив → swap → health) — сайт уже живой
   ├─ build.ps1 -DesktopOnly -Installer  →  CedarClerk-Setup-<версия>.exe (~119 МБ)
   └─ заливка в  ~/cedarclerk/data/downloads/
         ├─ .exe и .blockmap  →  проверка sha256  →  mv на место
         └─ latest.yml        →  последним
                    │
                    ▼  https://cedarclerk.mooexe.dev/downloads/latest.yml
        установленная копия: проверка при запуске и раз в 4 часа,
        скачивание в фоне, установка при закрытии окна
```

Три вещи, которые здесь неочевидны и стоят каждая своей строки:

- **`latest.yml` пишется последним.** Это единственный файл, который читает установленная копия. Пока его нет, клиенты видят прошлую версию — то есть незаконченная публикация невидима, а не сломана. Обратный порядок дал бы окно, в котором `electron-updater` качает половину файла и падает на проверке sha512.
- **Файлы лежат в `data/`, а не в `app/`.** `app/` деплой сносит целиком при каждом релизе; инсталлер оттуда исчез бы при первом же обычном деплое вместе с манифестом. Это единственное место, где деплой пишет в `data/` (ADR-113 говорил «никогда» — теперь «ровно в `downloads/`»).
- **Версии сайта и инсталлера расходятся, и это нормально.** Сайт едет каждым деплоем, инсталлер — только с `-Desktop`. Деплой печатает в отчёте, какая версия сейчас в `downloads/`; постоянная ссылка — `https://cedarclerk.mooexe.dev/downloads/latest`, она читает версию из манифеста, а не из версии сервера.

**Сервер убивается до установки.** NSIS перезаписывает `resources/server/CedarClerk.Server.exe`, который в этот момент запущен как дочерний процесс, а заблокированный файл сорвал бы установку на середине. Поэтому `stopServer()` синхронный (`spawnSync`) и вызывается до `quitAndInstall()`.

**И перед этим снимает обработчик `exit`.** `taskkill /f` отдаёт убитому процессу код 1, а на `exit` висело «сервер упал неожиданно» с модальным `showErrorBox`. До обновлений это не было видно: все остальные остановки происходят после закрытия окна, что обработчик и проверял. Установка обновления останавливает сервер при живом окне — и модальное окно вставало посреди выхода, блокируя главный процесс. Поймано Марти на первом настоящем обновлении 11.08.2026 («вылетело с exit code 1», при том что инсталлер отработал). Правило, которое из этого следует: **остановка, о которой мы попросили сами, не может быть аварией** — обработчик аварии снимается до, а не после.

**Обновление ставит та версия, которую заменяют.** Установку выполняет старый код, поэтому любая правка пути обновления начинает действовать только со следующего раза, а первое обновление после неё всё ещё идёт по старому пути. Единственный обход — поставить новую версию инсталлятором руками. Это стоит помнить каждый раз, когда чинится что-то в самом обновлении.

**Что происходило, пишется в `%APPDATA%\CedarClerk\update.log`.** У упакованного приложения нет консоли, а обновление заканчивается выходом — то есть без файла диагностировать нечем. Строки короткие: проверка, найденная версия, загрузка, выбор пользователя, передача инсталлятору, ошибки.

**Подписи кода по-прежнему нет, и для обновлений это значит больше, чем для первой установки.** Без сертификата `electron-updater` пропускает проверку подписи и опирается на sha512 из манифеста, полученный по тому же HTTPS. То есть доверие к обновлению равно доверию к `cedarclerk.mooexe.dev`: кто может подменить ответ origin'а или DNS, тот доставляет произвольный exe на машину. При одной своей установке это приемлемо; при первом внешнем пользователе подпись перестаёт быть косметикой против SmartScreen.

В разработке (`npm start`) обновления выключены: рядом с распакованной оболочкой нет `app-update.yml`, и проверка бросила бы исключение вместо того, чтобы промолчать — поэтому `startUpdateChecks()` выходит сразу, если `app.isPackaged` ложно.

## Чем десктопная конфигурация отличается от прода

Оболочка выставляет пять переменных, и они намеренно **раздельные**, а не один флаг «десктоп»:

| Переменная | Что делает | Почему отдельно |
|---|---|---|
| `Cedar__Urls` | Свободный порт от ОС | Два инстанса на машине не могут держать 8080 |
| `Cedar__BotToken=''` | Бот выключен | Два long-poll на один токен = 409 против бота на проде |
| `Cedar__AssetIndex__Enabled` | Разрешает обход диска | **Граница безопасности.** На проде это чтение имён чужих файлов |
| `Cedar__Auth__Upstream` | Вход проверяется на проде (ADR-108) | **Тоже граница.** Определяет, кто решает, что вы — это вы |
| `Cedar__Desktop` | Не отдавать лендинг | **Только оформление.** Флаг про внешний вид не должен открывать ни одну из границ выше |

Первые две — про работоспособность, следующие две — про доступ, последняя — про внешний вид. Смешивать их в один «режим десктопа» нельзя: тогда правка оформления открывала бы доступ к диску.

**`Cedar__Registration__Open` десктоп больше не выставляет.** Он был нужен, пока учётка заводилась локально; с ADR-108 аккаунт создаётся на проде, а локальная регистрация отвечает отказом со ссылкой туда. Сам флаг остался в коде — он всё ещё правильный ответ для установки без upstream.

## Одна учётка, но не одни данные (ADR-108)

Вход на десктопе проверяется на `cedarclerk.mooexe.dev`: логин и пароль те же, что на сайте, и одна почта больше не означает двух разных людей. Локальная строка пользователя заводится под удалённой личностью (`RemoteUserId`), а уже существовавшая локальная учётка с той же почтой **подхватывается**, а не дублируется.

**Данные при этом остаются локальными, и интерфейс обязан это повторять.** В шапке на каждом экране висит метка «данные локальные» с пояснением при наведении. Без неё общая учётка делает путаницу хуже: ожидание, что документы те же самые, становится сильнее, а не слабее.

**Без сети**: уже выданная сессия живёт 30 дней, работать можно. Новый вход требует прод и говорит об этом отдельно — «сервер не ответил», а не «неверный пароль». Это разные вещи, и путать их — худший вид ошибки входа: человек идёт чинить единственное, что не сломано.

## Две вещи, найденные на первом настоящем запуске (Марти, 10.08.2026)

Обе — мои недосмотры: я собрал оболочку и ни разу не попробовал в неё **войти**.

1. **Аккаунт создать было нельзя вообще.** Регистрация закрыта инвайт-кодом, десктоп его не задавал, а из `appsettings.json` он убран (правильно — это секрет). Свежая установка упиралась в «Invalid invite code» без единого способа получить код. Лечится `Cedar:Registration:Open`, и это безопасно ровно потому, что сервер слушает `127.0.0.1`: посторонних, от которых защищает гейт, здесь физически нет. Поле кода на форме регистрации скрывается, подпись «попросите код у Марти» заменяется на «эта учётная запись живёт на этом компьютере».
2. **Приложение открывалось на маркетинговом лендинге с ценами.** Лендинг (`LandingEndpoints.cs`) отдаётся всем, кто не залогинен, — на публичном сервере это правильно, в локальном приложении абсурдно. `Cedar:Desktop` его отключает, и `/` отдаёт SPA.

## `npm start`, а не `electron .`

Бинарник Electron — это по совместительству рантайм Node, и переменная `ELECTRON_RUN_AS_NODE` переключает его в этот режим. Её выставляют в своих встроенных терминалах несколько редакторов (VS Code в их числе), и она наследуется всем, что оттуда запущено. Тогда `electron .` выполняет `main.js` под Node: `require('electron')` возвращает **путь к бинарнику**, а не API, все имена оказываются `undefined`, и первое же использование падает с

```
TypeError: Cannot read properties of undefined (reading 'handle')
```

— сообщением, которое о причине не говорит ничего. Поймано на первом запуске у Марти (10.08.2026) и воспроизведено здесь до совпадения номера строки.

Поэтому `npm start` идёт через `start.js`, который снимает переменную и запускает Electron нормально; а `main.js` в начале проверяет, что `require('electron')` вернул объект, и при обратном печатает, что именно произошло, вместо загадочного TypeError. Запускать напрямую `electron .` можно, но `npm start` не зависит от того, из какого терминала он вызван.

## Что проверено вживую (10.08.2026)

Не «должно работать», а запущено и посмотрено:

- Опубликованный сервер поднимается на **произвольном порту** (проверен 8123 через `Cedar__Urls`) — правка `app.Run` работает.
- `/api/health` отвечает `env: Desktop`, версия совпадает; `/` отдаёт SPA (200).
- В логе старта — **`Cedar:BotToken not set — bot is disabled`**. Это главная проверка: 409 против бота на проде не случится.
- `%APPDATA%\CedarClerk` создаётся с `cedar.db`, `media/`, `dataprotection-keys/`, миграции применяются с нуля.
- Оболочка запускается (Electron + дочерний `CedarClerk.Server`), окно открывается.
- **Закрытие окна не оставляет сервер сиротой** — после закрытия ноль процессов и того и другого. Это проверялось отдельно, потому что осиротевший сервер держит WAL-лок и следующий запуск не открыл бы базу.
- **Регистрация без кода работает, `/` отдаёт SPA** — проверено на настоящей опубликованной сборке (а не на Debug, где нет `wwwroot`): `GET /` → 200 с `<app-root>` и без прайс-таблицы, `POST /api/auth/register` с пустым кодом → 200, `/api/auth/me` отвечает созданным аккаунтом.
- **Прод при этом не изменился**: без флагов `/` по-прежнему отдаёт лендинг с ценами из кода, а регистрация по-прежнему требует инвайт — это держит smoke-сюита (53/53).
- **`npm start` переживает `ELECTRON_RUN_AS_NODE=1`**: с намеренно выставленной переменной приложение поднимается (4 процесса Electron + сервер), а закрытие окна снова оставляет ноль процессов. Прямой `electron .` в тех же условиях печатает объяснение и выходит.

## Риски, каждый с проверкой

| Риск | Проверка |
|---|---|
| Порт занят другим процессом | Взять свободный порт у ОС (`:0`) и передать серверу; проверить с запущенным `dotnet run` на 8080 |
| Antimalware Service тормозит неподписанный exe | Замерить холодный старт на машине Марти; подпись кода — отдельная задача и отдельные деньги |
| Sidecar пережил закрытие окна | Убить дерево процессов на `window-all-closed` и на `before-quit`; проверить диспетчером задач после десяти запусков |
| Рядом лежит exe от другой сборки | Сверять `version` из `/api/health` с версией оболочки, отказываться стартовать при расхождении |
| Размер дистрибутива ~150 МБ | Цена решения, принятая в ADR-104; фиксируем, не боремся |
| Самообновление | Есть с 11.08.2026 (ADR-116): `deploy.ps1 -Desktop` публикует инсталлер, копия обновляется сама. Проверка — что `/downloads/latest.yml` отвечает нужной версией; это делает сам деплой |
| Обновление ставится поверх запущенного сервера | `stopServer()` синхронный и вызывается до `quitAndInstall()` — иначе NSIS упирается в заблокированный `CedarClerk.Server.exe` |
| Обновление приходит с подменённого origin'а | Не закрыто: без подписи кода доверие к обновлению = доверие к домену. Подпись — отдельная задача и отдельные деньги |
| Нет бэкапа локальной базы | См. раздел «Данные» — решить до того, как в локальном режиме появятся реальные данные |

## Что не решено

- **iPad** — строка `T-011` в `docs/BACKLOG.md` про приложение для AppStore. Electron туда не идёт; это отдельное решение, и десктоп его не приближает.
- **macOS/Linux сборки** — технически `electron-builder` умеет, но проверять их некому и не на чем.
- **Подпись кода и нотаризация** — деньги и учётные записи, не техника.
