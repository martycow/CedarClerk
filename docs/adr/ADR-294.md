# ADR-294 — Authentication recovery and provider configuration

## Context

The Google entry URL uses lowercase while the server compares the provider with the
case-sensitive Identity scheme name. Telegram login depends on a BotFather domain
binding, independently of whether the publishing bot runs. The login page has no
password recovery path and uses a placeholder mark.

## Decision

- Normalize the supported Google route to the canonical `Google` scheme. Unknown
  providers remain rejected. OAuth cancellation returns to the login page.
- Read forwarded protocol information only from the default trusted loopback proxy,
  before authentication, so HTTPS OAuth callbacks survive the Cloudflare tunnel.
- Keep the existing signed Telegram widget contract. Domain registration remains a
  BotFather setting; document the current canonical host and expose load failures
  with a retry. Clean up the widget callback when its component is destroyed.
- Add anonymous password request and reset endpoints using Identity tokens. A
  dedicated token provider expires links after one hour. Only confirmed accounts
  with a password receive mail. Unknown, unconfirmed and provider-only accounts get
  the same accepted response. Missing mail configuration returns 503 for every address.
  Transport failures are logged; the form describes a conditional request, not confirmed delivery.
- Limit recovery requests globally to 20 per minute and resets to 60 per minute.
  Tokens remain in the URL fragment, outside HTTP logs and referrers; the form
  removes the fragment immediately. Successful resets rotate the security stamp
  through Identity and do not sign the user in automatically.
- Exclude authentication request and response bodies from the client debug journal.
  Recovery pages neither initialize analytics nor send events to an existing client.
- Reuse existing form controls, localization and paper layout for recovery. Replace
  the placeholder on authentication pages with the approved source logo. Visual
  redesign and the slogan remain subject to the owner's concept selection.

## Validation

Exercise real Identity tokens against SQLite: valid, malformed, expired, wrong-user
and replayed links; verify the old password stops working. Check provider scheme
normalization, recovery feedback, both interface languages and responsive layout.
Use a fake mail transport for tests; a real provider login and delivered mail require
the deployment's credentials and the owner's provider session.
