# ADR-275 — `Draft.LastTelegramSentAt` is the one timestamp "edited since" is measured against (05.09.2026)

**Context.** T-180 lets an edited post be synced to its Telegram message. The editor has to say
whether the post on Telegram is behind the document, and the queue already records
`LastTelegramChatId`/`LastTelegramMessageId` on the draft with no time next to them. `PublishJob`,
`ChannelPost` and `DraftRevision` each carry a moment that is almost the right one, and none of
them is.

**Decision.** A nullable `Draft.LastTelegramSentAt`, written wherever `LastTelegramMessageId` is
written (`TelegramPublishTarget.PublishAsync`) and by the sync itself. Stale is
`UpdatedAt > LastTelegramSentAt`, computed on the list path with no hashing: autosave makes any
edit "stale", the same rule the blog's Update already lives with, and a hash comparison on every
`DraftMeta` row would cost more than the false positive it removes.

**Rejected.** *Deriving the moment from `PublishJob.FinishedAt`* — a scheduled send writes
`ChannelPost` and `ScheduledPost.MessageId` and no job at all, so the derivation has a hole exactly
where the maintainer schedules most posts. *`ChannelPost.PublishedAt`* — one row per part of a
thread, per channel; picking "the one" means the same `max()` over the same ambiguity, and a single
send to a target with no `ChannelId` writes no `ChannelPost`. *`DraftRevision.CreatedAt` for
`Kinds.Telegram`* — a revision is the content baseline (ADR-269), recorded once per publication on
the last part; a sync that Telegram answers "not modified" must still move the timestamp and must
not mint a revision. *Hashing the document against the last revision* — see above.

**Consequence.** Migration `AddDraftLastTelegramSentAt`; rows sent before this ship keep null, and
the editor treats null-with-a-message-id as "unknown", not as stale. The sync endpoint (A2's,
ADR-278) sets the field on every 200, including `unchanged: true`, so a post edited and synced twice
in a minute reads as current after the second call.
