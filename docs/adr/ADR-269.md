# ADR-269 — A publish revision holds the source document, not the wire copy (05.09.2026)

**Context.** `TelegramPublishTarget` swaps each referenced image for its Telegram-safe derivative
before rendering (ADR-031): the wire copy of the document names `photo.tg.jpg` where the draft
names `photo.png`. Since the T-085 move (ADR-078) the target recorded that wire copy as the
`DraftRevision` of kind `telegram` — preserved deliberately then, because the move was promised
to change no behaviour, and written down as T-104. The publish guard (ADR-065) was never affected:
it fingerprints the current document on both sides. What was affected is the diff shown before an
update — every compressed image read as changed, on every publish, whether or not anything was.

**Decision.** The revision recorded after a Telegram publish is the document the author published
— `PublishRequest.CedarJson` — and the rewritten copy exists only for the render. The revision's
purpose is "what would an update overwrite", and the author's answer to that is in source paths.
The same rule already held for the blog target, which never rewrote anything.

**Rejected.** *Rewriting the revision back on read* — a second mapping to keep in step with the
first, and a derivative that was later regenerated under another name would still diff as a
change. *Diffing with media paths masked* — hides a real image swap along with the noise.

**Consequence.** Revisions written before this hold wire paths and will diff once more as "every
image changed" on the next publish; after that publish the baseline is source and the noise is
gone. Nothing is migrated — a revision is a record of what was sent, and rewriting old rows would
make it a record of something else.
