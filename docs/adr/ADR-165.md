# ADR-165 — A screen the kit does not draw takes the bench's materials and keeps its own geometry

**Context.** `project-tasks` is the one screen in Stage 5's table with no pattern behind it. The
three reference screens answer a reading surface, a project bench and a page of a log book; none of
them is a board of columns that a card moves between. `T-229` says so and stops there: a fourth
reference screen is commissioned before the screen is ported.

That leaves the screen in a state nothing else in the app is in. Its palette is the bench's, because
the tokens are in the base blocks and every screen got them at Stage 1. Its controls are not: it
draws `.btn-accent`, `.btn-ghost`, `.icon-btn`, `.status-badge`, a `.chip` row and a two-button
`.view-toggle` — six of the eight duplicated control families `T-230` exists to delete — and its
cards, columns and modal are its own CSS. So the screen reads as the bench and behaves as the app
before the bench, which is the worst of the two states: a reader cannot tell which vocabulary is
authoritative, and every one of those six families has to be deleted anyway.

Waiting for the fourth screen before touching any of it would mean `T-230` either skips this file or
rewrites it twice.

**Decision.** A screen with no kit is ported in two separable halves, and only the first is done now.

**Attribution.** *This is the implementer's split under `T-229`, which names the blocker and not the
interim.* It was not put to Marty as a question. What it does not do is the thing `T-229` forbids.

1. **The materials are not the layout.** Every control on the screen becomes the bench component
   that already exists for it — button, input, index tiles, leaf tag, shelf panel, task tag, stamp
   badge — and every remaining value comes from a token. The *arrangement* is untouched: four
   columns side by side in board view, five columns of a table in list view, a centred modal for the
   card, the same filter strip in the same place. Nothing here decides what a kanban looks like on
   the bench; it decides what its parts are made of, which the design system already answered.

2. **A column is a ShelfPanel and a card is a TaskTag.** Both are the components the kit drew for
   exactly this content — `TaskTag.prompt.md` names the planner board as its first call site, and a
   panel is where a header carries a count and its own command. Using them is not inventing a
   kanban; refusing them and keeping `.column` + `.task-card` would be.

3. **What the kit does not answer stays unanswered.** Drag and drop between columns does not exist
   here today and is not added: a card moves by opening it and changing its status, which is what
   ships. Column width, whether the board scrolls horizontally, what a column does when it holds
   forty cards, and what the whole board becomes when it does not fit — all four are the fourth
   screen's questions, and all four keep the answer they have.

4. **The ask is written as its own brief, not appended to the narrow-screen one.**
   `docs/design/bench-responsive-prompt.md` asks one question — what the existing screens become at
   three widths — and its nine sub-questions are all about the shell's chrome. A board is a missing
   *screen*, at desktop width, with its own content model. Folding it in would produce one run whose
   answers cannot be accepted or rejected separately, and the narrow-screen brief is the one already
   ready to run. `docs/design/bench-board-prompt.md` is the sibling.

5. **The screen's title bar goes, like every other screen's.** The rail already carries the project
   name on its tile and `Tasks` as the crumb, so the page's `<h1>` and its subtitle were a second
   copy of both. The counts they carried — open of total, and how many are overdue — go to the
   RulerBar, where the hub already publishes the same kind of tally (ADR-159 clause 3).

**Rejected.** *Porting the board's layout from the hub's tile wall.* Plates on a wall and cards in
columns look alike and behave nothing alike; the resemblance is exactly the trap `T-229` names.
*Leaving the screen alone until the fourth screen lands.* Six duplicated control families survive
into `T-230`, and the screen keeps looking like the bench while behaving like what preceded it.
*Deleting the list view to make the board the only question.* It is half the screen's use — the
board answers what is happening, the table answers what is due — and a design brief is not a reason
to remove shipped behaviour.

**Consequence.** When the fourth screen arrives, what it changes is arrangement: column widths, the
overflow rule, whether a card can be dragged, what the board becomes when it does not fit. The parts
it arranges are already the bench's, so that port is a template change rather than a rewrite — and
if the design comes back with a component the bench does not have, that component is a new one in
`app/bench/`, not a local class on this page.
