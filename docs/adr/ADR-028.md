# ADR-028 — Debug console panel; Export redesigned as a categorized modal; static HTML export added; social mockups as roadmap placeholders
**Context**: Same session as ADR-027. Marty asked for a bottom, collapsible request/response console (so a slow publish is visibly progressing, not just "maybe stuck"), and separately wanted the export surface redesigned — the old single `.export-popover` panel stacked Telegram, blog, and `.cedar` download in one dense scrolling list with no structure, and Marty wanted it categorized, prettier, with room for future destinations (Twitter/Bluesky/Threads per ADR-021's "cross-posting is a core axis" positioning, plus asked-about Medium/Patreon/Notion/Google Docs) and a real static HTML export.
**Decision** (19.07.2026): Added `DebugLogService`/`debug-log.interceptor.ts` (functional `HttpInterceptorFn`, registered via `withInterceptors` in `app.config.ts`) feeding a new `shared/debug-console.component.ts` — a session-only (no persistence) ring buffer of the last 200 requests, mounted once in `app.html` so it's available everywhere, not just the editor. Extracted the hand-rolled `.modal-overlay`/`.modal-card` pattern (previously duplicated between the AI-edit and re-translate confirm dialogs) into a reusable `shared/modal.component.ts` (`ModalComponent`, Escape/backdrop-close, projected icon/title/body/actions slots); both existing dialogs were migrated to it. The Export trigger now opens `ExportModalComponent`-equivalent markup (kept inline in `editor.component.html` rather than split into a separate component — the existing export logic/signals already live in `EditorComponent` and splitting them out was judged higher-risk than the visual reorg itself needed) as a centered `app-modal` with four sections: **Site/Blog** (existing publish/unpublish logic, plus new informational RU/EN badges linking to `?lang=` variants — blog publish itself stays a single action, since `BlogEndpoints` already serves both languages off one `IsBlogPublished` flag via the `?lang=` query param, confirmed by reading `RenderPostAsync`); **Telegram** (existing channel/language/publish/schedule, unchanged logic); **Other platforms** — Twitter/X, Bluesky, Threads, Medium, Patreon, Notion, Google Docs as inert "Coming soon" rows, no functionality; **File export** — the existing `.cedar` download plus a new real `GET /api/drafts/{id}/export-html?lang=ru|en` (`DraftEndpoints.cs`) that renders the post via the same `CedarToBlogHtmlRenderer` the live blog uses, wrapped in a **new, separate, trimmed-down HTML shell** (`DraftEndpoints.StaticExportHtml`) rather than reusing `BlogEndpoints.PageShell`/`ShellTemplate` — the blog shell wires up comment/reaction `fetch()` calls against a live slug and a theme-toggle button, neither of which makes sense for a file downloaded and opened with no server behind it; the new shell keeps only the CSS needed to render every block type plus a minimal title/date/signature header, and the carousel prev/next/dot script (needed for correct display; without it every carousel image would render stacked, no JS-free fallback exists for that widget).
**Consequence**: The trimmed CSS in `StaticExportHtml` is a **deliberate duplication** of a subset of `BlogEndpoints.ShellTemplate`'s CSS, not a shared constant — `docs/DESIGN.md` already documents CSS as duplicated per-component in this codebase (no tokens file), and a truly standalone single-file HTML export can't `<link>` out to a shared stylesheet regardless, so inlining was required either way. The social-platform rows are pure UI placeholders — no API calls, no settings persisted, no ADR-level design decision made yet about *how* Twitter/Bluesky/etc. would actually be posted to; that remains future work per ADR-021's positioning, not started here. `docs/DESIGN.md`'s "no shared modal component" gap (flagged as known debt) is now partially closed by `ModalComponent`, though `settings.component.css` still has its own independent `.btn-ghost`/`.modal-*` copies, not migrated in this pass.
