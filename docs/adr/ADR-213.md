# ADR-213 — An account can be deleted whole, and what its rows leave behind is swept on demand

**Context.** Multi-tenancy makes deletion a requirement rather than a nicety: an account that can be
created by a stranger has to be removable, and "remove the login and leave the rows" is not removal
when the rows are documents, media, channels and payment records. The existing delete paths were
also incomplete — the draft endpoint cleared five of the thirteen tables that point at a draft, and
production carries 16 rows whose parent is already gone.

**Decision.** Three pieces, none of them clever.

- **One cascade list per parent.** `DraftDeletion` and `ChannelDeletion` hold everything that has to
  go when a document or a channel does, in one place, so the next child table is added there rather
  than forgotten in one of the two endpoints that delete a document.
- **`AccountDeletion` removes the account and everything it owns**, on a platform scope — which is
  what makes it possible and what makes it dangerous, so every statement names `OwnerId` explicitly
  rather than leaning on a filter that is switched off. Rows go before files: a half-finished file
  pass leaves unreferenced bytes on disk, which is recoverable, while the reverse order leaves a
  live account whose pictures have vanished. Stored paths are treated as data and are not trusted to
  stay inside the media directory. The endpoint is admin-only, refuses the actor's own account, and
  writes the audit row *before* the delete, since the account it names will not be there to read
  afterwards.
- **`AdminAuditEntry` survives the account.** It stores both emails as text precisely so it still
  reads once the rows it points at are gone. An audit log that loses the record of a deletion is not
  an audit log.
- **Orphans are counted and removed by two separate calls.** `GET /api/admin/maintenance/orphans`
  and `POST …/orphans/purge`, so the number can be looked at before anything is deleted — the same
  shape ADR-204's refile button uses, and for the same reason: a retroactive sweep that runs without
  being asked is indistinguishable from data disappearing on its own.

**Consequence.** An account leaves nothing behind but its audit trail, and the rows that earlier
incomplete deletes stranded can be found and cleared without a script on the server. The cost is an
irreversible admin endpoint — the only one in the app — which is why it is guarded by the actor
check, the audit row and a warning in the log rather than by a confirmation dialog alone.
