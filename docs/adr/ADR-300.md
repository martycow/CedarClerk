# ADR-300 — A media refusal is never cacheable; a publish warning lands on the target (14.09.2026)

**Status**: DONE

**Context.** Two reports after the LinkedIn deploy. (1) Pictures uploaded into a draft and sent to Telegram "disappeared" on the next visit and were missing from the library — the files were on disk, the `Assets` rows were there, the document still referenced them. Reproduced from the maintainer's own signed-in browser: one anonymous `GET /media/asset_….png` (a draft's picture, claimed by no published post) answers 404 from `MediaOwnershipMiddleware`; Cloudflare caches that 404 by URL and extension (`cf-cache-status: HIT`, `Age` climbing) and adds its default `Cache-Control: max-age=14400` on the way out, so the owner's next request — cookie and all — reads the same 404 from the edge, and the browser keeps it for four hours after that. The editor and the library then draw broken images for a file nothing is wrong with. (2) An X thread went out without its pictures: `/2/media/upload` answered 403 because the connection predates `media.write` (ADR-241). `XPublishTarget` wrote `XMediaScopeMissing` onto `PublishTarget.LastError` and the shared publish path immediately overwrote it with `outcome.Error`, which is null on success — so Settings never showed the reconnect hint and the log was the only witness.

**Decision.**
1. **Every 404 the media gate answers carries `Cache-Control: private, no-store`** (`MediaOwnershipMiddleware.NotFound`), whichever question it failed — unparseable name, no row, another tenant's file, a stranger's request for a gated one. The gate already marked its private 200s `no-store`; the refusals were the gap. Cloudflare honours `no-store` and passes it through, so neither the edge nor the browser keeps a verdict that was given to a different reader. `MediaOwnershipTests.A_refusal_is_never_cacheable` pins all four branches.
2. **`PublishOutcome` carries a `Warning`** — a post that went out with something the author should know — and `PostEndpoints.PublishToTargetAsync` records `outcome.Error ?? outcome.Warning` on the target, so a success no longer wipes what the target just learned. `XPublishTarget.UploadImagesAsync` returns the warning instead of touching the target row; later parts of a thread carry it forward from `LastError`, and an upload that succeeds returns none, which is what clears it. `PublishJobRunnerTests.A_warning_on_a_successful_publish_lands_on_the_target_until_a_clean_one` pins it.

**Consequence.** A 404 already cached at the edge before this deploy expires on Cloudflare's own schedule (minutes) and in a browser after its four hours — a hard reload, or a fresh upload with a new URL, is the way past it; nothing on the server needs purging. Public files (`cf-cache-status: HIT` on a 200) are still edge-cached for the default two hours, which is unchanged and deliberate. The X connection made before ADR-241 has to be reconnected in Settings → Integrations to gain `media.write`; from this release the card says so after the first pictureless send.
