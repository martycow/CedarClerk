# ADR-138 — Surface class: a second density axis, dense chrome and undense paper

**Context.** The app has one density axis: `[data-density="compact"]` on a page root, nine of them
(`admin`, `drafts`, `media-library`, `posts-manager`, `project-assets`, `project-builds`,
`project-planner`, `project-tasks`, `projects`) plus the styleguide's toggle, resolving the
`--dens-*` set declared at `cedarclerk-web/src/styles.scss:89` against the tighter values at
`styles.scss:226`. It is used 240 times across 16 component stylesheets. It works because it is
page-shaped: one screen is a table, another is a sheet, and a component never decides which it is
on (ADR-071 principle 3).

Cedar Bench is not page-shaped. Its density contract
(`.design-sync/ds-v2/guidelines/density-contract.html`, and the readme section that made the V1/V2
merge work) reconciles two incompatible demands — engine chrome wants 11–13px type and 26px rows,
the workshop wants 44px targets and AA — by splitting on **material, not on screen**: wood and
brass may be dense, paper may not. On any bench screen both live at once: a 56px `RailHeader` and a
30px `RulerBar` wrap a 640px reading sheet. No attribute on the page root can express that, and
`data-density` cannot be given a third value without lying, because the two vocabularies interleave
down the tree rather than partitioning it.

Two mechanisms in the app actively break the split if left alone. `[data-density="compact"]` is a
descendant selector, so a compact page root reaches chrome nested inside it. And the touch rule at
`styles.scss:304` — `@media (pointer: coarse) { button, [role="button"], summary, select, a.icon-btn
{ min-height: 44px; min-width: 44px } }` — is global and wins by property rather than by
specificity, which was the point when it was written to rescue a 28px `.mini` button on an iPad. On
a bench screen it would push the ruler from 30px to 44, the drawer lip from 32 to 44, and force the
rail past its own `--bench-rail-h`: the chrome budget the shell exists to buy back would be gone on
the first touch device.

**Decision.**

1. **`data-surface="chrome" | "paper"` is an element-level axis, orthogonal to `data-density`.**
   It is spelled on the bench chrome components (`rail-header`, `hook-rail`, `shelf-panel` header,
   `bench-drawer` lip, `ruler-bar`, `index-tabs`) and on the paper surfaces (worktop sheet, cards,
   forms, task tags, the editor sheet). Chrome inside a compact page is still chrome; paper inside
   comfortable chrome is still paper. The attribute exists rather than the numbers simply living
   inside each component's encapsulated CSS because both the coarse-pointer carve-out and the lint
   need a selector to hang on — an unnamed convention is not enforceable, and this one has to be.

2. **The numbers.** Chrome: minimum control box `--hit-chrome: 30px`, type `--text-chrome` and
   `--text-chrome-sm`, numerals in `--font-mono`. Paper: minimum target `--hit-target: 44px`, type
   from 14px up, reading at `--fs-read`/`--lh-read`. The bench layout tokens
   (`--bench-rail-h: 56px`, `--bench-tool-w: 52px`, `--bench-panel-hd: 30px`,
   `--bench-drawer-lip: 32px`, `--bench-ruler-h: 30px`) are chrome's dimensions and are already
   integers.

3. **Integers only, which is why the mirror's sizes are rounded on the way in.** ADR-071 principle
   7 collapsed 110 measured half-pixel declarations to whole pixels after finding the app's entire
   type hierarchy crowded into a 2.5px band. The mirror carries 63 half-pixel declarations across
   `tokens/`, `components/` and `ui_kits/`: three type tokens (`--text-lg` 16.5px and
   `--text-stamp` 10.5px at `tokens/typography.css:11,18`, `--text-chrome` 12.5px at
   `tokens/bench.css:15`), one 1.5px inset ring inside `--shadow-pine-btn`
   (`tokens/materials.css:12`), and 59 inline in components and kits. (`guidelines/` carries 22
   more; those are documentation of the mirror, not values that port.) The three type tokens port
   as `var(--fs-16)`, `var(--fs-13)` and `var(--fs-11)`, all of which already exist on the scale.
   `--text-readout` (21px) points at a new `--fs-21` rather than a raw value: the scale grows by
   measured, in-use sizes — that is how 10/15/17/18/22 got in — and a semantic role carrying a bare
   pixel number is the debt principle 7 exists to stop. That aliasing runs role → scale, the same
   shape as `--fs-read: var(--fs-17)`, and it is safe here only because neither `--text-readout`
   nor `--fs-21` is on the generator's `WANTED` list. `--fs-read` is broken precisely because its
   role half is — the difference ADR-137 rule 3 turns on.

4. **The two vocabularies never cross.** `[data-density="compact"]` declares no `--bench-*`,
   `--hit-*`, `--text-chrome*` or `--text-readout` token, and `[data-surface]` declares no `--dens-*`
   token. Compact needs no exemption to be contract-compliant: its `--dens-fs` already resolves to
   `--fs-ui` (14px), exactly paper's floor, so compact is at the floor and must not be tightened
   past it.

5. **The coarse-pointer rule is scoped to paper.** Its selector list gains a paper qualifier so
   `[data-surface="chrome"]` and its descendants are exempt. This is a deliberate, named exception
   to WCAG 2.5.5 (Target Size Enhanced, AAA) inside chrome; 2.5.8's 24×24 AA floor is not exempted
   and every chrome control clears it. Reduced-motion and every other global block are untouched.

6. **The split governs size, never contrast.** Chrome type is small, so it is held to 4.5:1 like
   any other body text — the 3:1 large-text relaxation the checker records in its own header
   (≥19px semibold / 24px, `tools/check-contrast.mjs:7-8`) is a convention the tool does not
   implement — its thresholds are attached per pair — and nothing in chrome reaches the size that
   would earn it anyway. Because ADR-136 puts the bench tokens on the bare `:root` and
   `:root[data-theme="dark"]`, chrome pairs are scored by the same run as everything else; there is
   no second pass and no scoped block for the checker to miss.

7. **It is enforced, not trusted: `cedarclerk-web/tools/check-density.mjs`**, exposed as
   `npm run check:density` beside `check:contrast`, and added to `TestPipeline` as a phase so
   `cedar test` runs it. `CedarClerk.Cli.Tests/PipelineTests.cs:335` pins the phase list by value,
   so the phase can be neither added nor dropped silently. What it asserts: no half-pixel
   `font-size` anywhere under `cedarclerk-web/src`; the compact block declares nothing from the
   chrome token families and no `[data-surface]` block declares a `--dens-*`; every `--hit-*` and
   chrome type token resolves to an integer px; the `pointer: coarse` block carries a paper
   qualifier and no bare element selector; and each surface's floors hold — 30px/13–11px for
   chrome, 44px/≥14px for paper.

**Consequence.** A second axis is a second thing to get wrong, and the failure mode is quiet: a
chrome component rendered without the attribute inherits paper's numbers and simply looks loose,
with nothing red. The lint knows the bench chrome components by name and will say so when one loses
its attribute, but it cannot know about a chrome component nobody told it about, and it reads CSS
statically — it scores declared values, never a computed height. Rejected on the way here: a third
`data-density` value, which cannot express two densities on one page and would need all nine
existing page roots redeclared; letting each chrome component hardcode 30px and 13px privately,
which is ADR-071 principle 3's own prohibition restated one level down and invisible to review;
tightening chrome under compact, which would make the same rail two heights on two screens and push
controls under the 24px AA floor; and dropping paper's 44px in favour of that AA floor everywhere,
which trades a real touch affordance for one fewer rule. The honest cost of item 5 is the one to
remember a year from now: on a tablet, bench chrome is a 30px target on purpose, and that decision
was taken with the AAA criterion in front of us.
