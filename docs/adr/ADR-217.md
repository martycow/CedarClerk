# ADR-217 — A project can have collaborators, and a membership opens exactly one door (27.08.2026)

**Context.** `docs/product/INDIEDEV.md` listed multi-user projects under "deliberately not being done": `GameTask.Assignee` is a free-text string, and co-author invitations were called a separate product within the product. The reference board (ADR-218) is the first surface in the module that is worth nothing with one person on it, so that stance had to be decided rather than widened by accident. Tenancy is what makes the widening the hard part: `OwnerId` *is* the tenant id (ADR-206), a tenant context and a platform context compile to two different models (ADR-207), and an unset tenant reads nothing (ADR-208) — a second account cannot see a project's rows by any amount of endpoint code, and `TenantFilterGuardTests` forbids exempting a new table from the filter.

**Decision.**

1. **A membership is a row in the owner's tenant.** `ProjectMember.OwnerId` is the **project owner**; `MemberUserId` is the invited account, null until the invitation is accepted. That split is the whole entity: with the invitee in `OwnerId` the owner could not see who is on his own project, and the member's tenant would own rows it never created. Rejected: adding the canvas paths to `PlatformPaths`, which unfilters the whole request including Identity, and a second `OwnerId`-free schema for shared data.

2. **Access is resolved once, then scoped.** `ProjectAccessResolver.ResolveAsync` does one lookup in a platform scope — a project id is exactly what the caller's own tenant cannot resolve — and hands back the owner id. Every query after it runs inside `CreateTenantScope(access.OwnerId)`, so rows a member writes land stamped with the owner's id and rows a member reads pass the ordinary filter. No filter is loosened anywhere, and reading across owners stays something that has to be said out loud, which is ADR-208's rule rather than a new one.

3. **Two roles, and the owner is not one of them.** `ProjectRoles.Editor`/`Viewer` are strings in `CedarClerk.Core` like `TaskStatuses` — a third role should be a constant and a UI, not a migration. Ownership is identity (`project.OwnerId == callerUserId`) and the owner has no `ProjectMember` row at all: a role column that could hold `owner` would let a row be edited into ownership. A viewer reads the board, sees the other people on it, and writes nothing.

4. **The token is the credential; the address is a delivery route.** An invitation stores a lowercased address and 32 random bytes; accepting fills `MemberUserId`, stamps `AcceptedAt` and clears the token. The accepting account's e-mail is deliberately not compared against the invited one — the same model as `ShowcaseFollower`'s tokens (ADR-216) and for the same reason: an address breaks on aliases and second accounts, an unguessable single-use token does not. The invite URL comes back from the create call whether or not mail is configured, so an owner who can copy a link is never blocked by a missing provider key.

**What a membership does not open.** This is the load-bearing half of the decision, because a quiet widening here is how the feature fails.

- `GET /api/projects` stays the caller's own projects. Projects shared with him are a separate endpoint (`GET /api/projects/shared`) with its own narrow shape, not extra rows in the existing list — one list that means two things is how a tenancy bug gets written.
- The project dashboard (`GET /api/projects/{id}`), rename, archive, delete, showcase settings and every other `ProjectEndpoints` route stay **owner only**. A member who navigates to `/projects/:id` still gets a 404, and the frontend must not offer him the link.
- Tasks, sprints, builds, documents, the asset index and the glossary stay **owner only**. Each has its own visibility question and none of them was asked: a task's description is working material, the asset index is a map of somebody's disk, a document carries the publishing surface. `OwnsProjectAsync` keeps its current meaning and is not "generalised".
- Widening later is one more endpoint; unwinding a widening that shipped is a data question. That asymmetry is the whole argument for starting this narrow.

**Status codes.** The app answers 404 for a row that is not yours, so an id is never confirmed, and that holds for anything the caller cannot read — including a refused `Join` on the hub. It is deliberately not extended to a viewer's refused write: that person is already looking at the board, so a 404 would claim the thing on his screen does not exist. A refused write by a reader is **403**.

**Consequence.** The module gains a second person without gaining a second tenancy model, a notification system, or an invitation to redesign the tracker. A project holds at most ten collaborators. `Assignee` stays free text, because assigning work to an account is a tracker decision and the tracker is not shared. Removing someone leaves his uploaded images on the boards — deleting the bytes would blank a surface that is not his — and account deletion has to sweep memberships in **both** directions, the second of which (my memberships in other people's projects) is the one easily forgotten. Presence, cursors and everything else that exists only while a socket is open belong to ADR-218, not here.

## Addendum — `POST /api/projects/{projectId}/members/{memberId}/resend`

**What it is.** A second route for a pending invitation, not a second meaning for the first one. `POST …/members` answers **409** to an address that already has a row — the unique index on `(ProjectId, Email)` is the rule, and one invitation per address per project is what keeps the People list honest. The panel carries an `inviteResend` button, and a button that says "send again" cannot be backed by a call whose designed answer is a refusal. Recorded here rather than folded into the invite POST: a POST that creates a row on one call and re-mails an existing one on the next means two different things under one verb, and the 409 stops being a rule the moment it is caught and reinterpreted.

**Contract.**

- Owner only, through the same `ProjectAccessResolver` lookup as every member route: a non-owner gets **403**, an unresolvable project **404**.
- The row must be pending — a member who has accepted answers **404**, the same as a row that is not there. There is nothing to resend to somebody already on the board.
- **The token is reused, not rotated.** A resend is usually an answer to "it went to spam"; a mail that did arrive keeps working. A row with no token (none exists today) gets one. `InvitedAt` is stamped with the resend, so the panel's "invited" date is the last attempt.
- Answers `200` with the same shape the invite POST does — `{ member, inviteUrl }` — and, as there, the link comes back whether or not mail is configured, so the owner can copy it by hand.
- Idempotent in effect: two resends produce one row, one token, two mails.
