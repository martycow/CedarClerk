# ADR-093 — X connector: OAuth 2.0 PKCE, "save before use", text+link in v1 (05.08.2026)

**Context**: T-110. The wallet (ADR-092) and `XPostBuilder` are ready; the connector itself is the third `IPublishTarget` implementation. X API v2: posting requires user context (OAuth 2.0 Authorization Code + PKCE, scopes `tweet.read tweet.write users.read offline.access`); an app-only Bearer token cannot post. Config keys: `Cedar:X:ClientId` / `Cedar:X:ClientSecret` (a drop-in on the Pi, gitignored locally — like all secrets).

**Refresh-token rotation is the central risk**: X issues a new refresh token on every refresh and invalidates the old one. For Bluesky, ADR-079 avoided storing tokens at all (a session from the app password on every publish) — there is no such path for X. The rule here: **the new refresh token is saved to the DB BEFORE the new access token is used for the first time**; if the save fails, the publish is not sent. A lost token = "reconnect X" (the same degradation as `TryUnprotect`→null from T-084), not a silently dead target.

**v1 posts text + a link, no media and no threads.** A post on X per ADR-077 is a standalone short post (the author's override or a teaser), the link to the blog leads to the full document with media; uploading images as bytes (up to 4) and a reply chain are separate backlog rows, not blocking the first working post.

**The validator learned about teaser networks** (`PublishCapabilities.DerivesShortPost`): for a network that derives its own short post, `too-long`/`too-many-media` is informational ("will be a teaser"), not a blocker. This also fixes a latent Bluesky bug: the queue would 422 any document longer than 300 graphemes, even though the builder is guaranteed to build a post that fits. Found while building X, not in production — the Bluesky path had not yet been live-verified.

**Credit debit happens after success, anchored on the created post's id** (a refinement of ADR-092, which named PublishJob as the anchor: the post id is even more precise — every post actually created costs a credit, and a queue retry after a failure creates a new post and honestly pays for it). An insufficient balance is a refusal **before** sending (402, not reproducible for the queue — retries are not burned).

**Callback**: `GET /api/targets/x/callback` (exactly the URI entered in the portal). State+PKCE verifier live in process memory for 10 minutes — a single node, a restart only drops unfinished connections.
