# ADR-169 — A pine button as a link is a pine button, and that is the whole of the anchor form

**Context.** ADR-163 ruled that a bench control whose activation is a navigation renders a native
`<a>` carrying its own route, converted `app-module-tile` and `app-task-tag`, and then named a debt
it could not pay: three controls that open a document from a `<button>` — the hub's "Continue", the
hub's document rows and the posts manager's "Open in editor". Two of the three are `app-button`,
which has no anchor form, and the blocker it named was not a component but a question: *what a pine
button looks like when it is a link.*

The mirror does not answer it. `Button.jsx` is `React.createElement('button', …)` with a class per
variant, and `Button.d.ts` offers `onClick` and nothing else — the same shape `ModuleTile.jsx` had
when ADR-163 read it, and the same reason applies: the kit is a drawing of a surface, with no
router, no history and no tab strip, so its choice of tag is not an opinion about navigation.

What the mirror does answer is what a pine button *is*: `border: 1px solid var(--pine-deep)`,
`var(--grad-pine)`, `var(--text-on-pine)` over a text shadow, `var(--shadow-pine-btn)`, and a 2px
press-down. Not one of those is a `<button>` selector. `danger` settles the question from the other
end — the kit already draws it as a dashed-underlined word, which is a link's face on a control that
was never a link.

**Decision.**

1. **The face belongs to the variant, the tag belongs to the consumer.** A pine button as a link is
   pixel-for-pixel a pine button: the same `.btn` class list, the same variant rules, the same
   surface, the same press. The anchor form adds exactly one declaration to the stylesheet —
   `text-decoration: none` on `.btn` — because that is the only part of the face a `<button>` gets
   from the platform and an `<a>` does not. `danger` re-declares its dashed underline below it and
   keeps looking like the link it always looked like.

2. **One input, and it is the route** — ADR-163 rule 1, unchanged: `link` set renders
   `<a [routerLink]>`, unset renders `<button type="button">`. `queryParams` stands beside it for
   the reason `app-task-tag` has one: every destination this form was commissioned for is
   `/editor?draft=…`, and the editor addresses a document by query, never by a path segment
   (ADR-168 clause 3). There is no `fragment` input. The settings screen's chip nav looks like the
   call site that would want one, but `jump()` is a `scrollIntoView` that changes no URL — turning
   it into a navigation is a decision about history entries, not about a tag, and an input added
   against a call site that has not asked is an input nobody can delete.

3. **`disabled` in link form takes the address away rather than painting a dead button.** HTML has
   no disabled anchor. The platform's own model of "not a link" is an `<a>` with no `href`: not
   focusable, not activatable, no context-menu entry and nothing to copy — which is the entire
   content of what `disabled` means on a control whose only job is to go somewhere. So the route is
   dropped and not the element: Angular's `RouterLink` takes `null`, renders no `href` for it and
   returns from `onClick` without navigating. `aria-disabled="true"` carries the state and is also
   what the dimming rule is keyed on, because `:disabled` matches no anchor — and that rule stops
   the pointer as well, since every hover and press rule in the sheet is qualified `:not(:disabled)`
   and an anchor never satisfies it, so a dead link would otherwise still light up under the mouse.

   The tag does **not** flip with `disabled`. Rendering the button form while a busy flag is up
   would swap the element under the user — moving focus and breaking anything standing on it —
   which is a worse failure than the one it avoids.

4. **In link form the control does not emit, and `type` is not written.** The first half is ADR-163
   clause 5: the anchor is the navigation, and a consumer wired to both would go twice. The second
   is that `type` is a `<button>`'s word — a `submit` link is not a thing, so the attribute is
   absent rather than inert.

5. **What falls out of the global touch floor declares its own.** The coarse-pointer rule reaches
   `[data-surface] button`, `[role="button"]`, `summary`, `select` and `a.icon-btn` — a plate that
   becomes a bare `<a>` drops out of it, and ADR-074's exemption is for links in prose, which none
   of these is. `app-button` needs nothing: its `min-height: var(--hit-target)` is on `.btn` and
   unconditional, so it covers both tags already. The two page-level rows converted here say it
   themselves, in a `@media (pointer: coarse)` block scoped to `[data-surface]` so the floor is
   still the nearest surface's — the shape `drafts.component.css` already uses for `.mini`.

6. **All three debts are paid, and the handlers go with them.** The hub's "Continue" becomes the
   first pine link in the app. The hub's document rows and the posts manager's "Open in editor" are
   page markup rather than bench controls, so they take `<a routerLink>` directly instead of being
   dressed as an `app-button` — the class stays, the row keeps its own CSS, and `openDocument()` and
   `openInEditor()` are deleted rather than left unreferenced.

7. **What is deliberately not converted.** *The create-then-navigate actions* — a new document, a
   devlog, a changelog — stay buttons: the id does not exist until the server answers, and a link
   cannot carry an address that has not been assigned. *The `/drafts` rows*, which ADR-163 did not
   name and which are the one open site: all three views open a draft from a `<div>` carrying a
   click, and each row holds a folder picker and three mini buttons, which an anchor may not
   contain. The row can only become a link by giving up the whole-row click or by navigating twice
   from one, and choosing between those is a decision about that board rather than about this
   component (`T-261`). *The planner's and the builds screen's
   Board links*, which ADR-168 clause 6 made text links in a shelf because there was no anchor form;
   the blocker is gone, the shape was also the fit, and a second button face beside a summary is not
   what this form is for. *The settings chip nav* (clause 2) and *the styleguide toggles*, which
   switch state and go nowhere.

**Rejected.** *A `variant="link"` flag*, for ADR-163's reason: two inputs for one fact, with nothing
stopping a link variant that carries no route. *Wrapping the button in an anchor*, which is an
invalid content model, two tab stops and one accessible name read twice. *An `href` input beside
`link`*, for outbound URLs — the app's outbound links are prose or `.state-link`, never a primary
verb, and a component that takes both has to decide which wins. *Leaving `disabled` to `pointer-
events: none` over a live `href`*, which keeps a real address that a keyboard can still reach and a
middle click can still open, i.e. disables the control for exactly the input device that was not
the problem.

**Consequence.** `app-button` now renders one of two elements, so a spec or a smoke selector reading
`querySelector('button')` under one finds nothing when the consumer hands it a route; the three
converted call sites' specs move with the code, and the component's own spec asserts the tag rather
than assuming it. What the board carried as a missing form is now a choice per site — the settings
chip nav is a question about what a jump is, the shelf links are a question about what a summary
holds — and every control that gains a destination from here has ADR-163's rule and no excuse.
