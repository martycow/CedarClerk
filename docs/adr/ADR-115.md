# ADR-115 — On the wire it's always UTC with `Z`, on screen it's always Pacific time (11.08.2026)

**Context**: the server moved to a droplet whose clock runs in UTC (ADR-114), and Marty asked: let the server's time be UTC, and let the sites — the blog and the app — show Pacific time. Reviewing the code showed the request touches more than just output formatting.

**Found while working through it, and this is a bug, not a style issue.** Everything in the database is written in UTC — `DateTime.UtcNow` appears 125 times, `DateTime.Now` doesn't appear once, file dates in the asset index are taken as `LastWriteTimeUtc`. But SQLite doesn't store `DateTimeKind`, EF reads such values as `Unspecified`, and `System.Text.Json` prints them **without a `Z` suffix** — and per spec the browser treats such a string as **local time**. That is, the app was displaying UTC numbers disguised as local time: today that's seven hours ahead. Exactly because of this, two components carried a hand-rolled helper `utcDate()` that appended the `Z` by hand — but it covered two spots out of roughly twenty.

**Decision 1: the instant gets fixed on the wire, not in twenty call sites.** `UtcDateTimeConverter` in `ConfigureHttpJsonOptions` prints any `DateTime`/`DateTime?` as UTC with a `Z`. That's one single point instead of a helper you have to remember in every new component; you can't forget the converter, but you can forget `utcDate()` — and that's exactly what happened eighteen times.

**Decision 2: the zone is `America/Los_Angeles`, not a fixed UTC−8.** Marty said "Pacific Standard Time," but literal PST is winter time; from March to November Los Angeles lives on PDT (UTC−7), and a fixed offset would show an hour off **right today**. The request means "my zone," not "this specific abbreviation," so a named zone with transitions is used, and the label follows reality: PDT in summer, PST in winter. If a genuinely fixed offset is ever needed, that's a single constant.

**Decision 3: the zone is named once on each side.** `Consts.General.DisplayTimeZone` on the backend, `DISPLAY_TIME_ZONE` on the frontend. This isn't done via config: config is needed when a value differs between installations, and today there's only one — and when tenants eventually get their own zone (and with multi-tenancy that's a matter of time), what will need to change isn't the value but the model: the zone will become a per-user field. The two constants are exactly the place that change will land.

**Decision 4: the zone label appears in the blog and not in the app.** The blog is read from anywhere in the world, and "14:05" with no zone shown means something different to different people there. The app is the author's workplace in a single zone, and "PDT" next to every date in a dense interface is noise that says nothing.

**What deliberately doesn't change:**
- **`pubDate` in RSS stays GMT.** RFC 1123 with a correct offset is a machine format for aggregators, not text for a human; "localizing" it would break sorting in readers.
- **Grouping posts by month is computed in the same zone as the month heading.** Otherwise a post from September 1 00:30 UTC (August 31 17:30 PDT) would land in the September group under an August date — a mismatch that looks like a lost post.
- **Scheduler time input stays in the browser's zone.** The `datetime-local` field is read as the machine's local time and converted to UTC on submit. For Marty in the Pacific zone this is the same as the output; a discrepancy would only show up from a laptop in a different zone. That's a separate task (input, not output), and doing it halfway — silently — would be worse than not doing it: there's already a hint next to the field showing the time in other zones, and it would be the first thing to start lying.
