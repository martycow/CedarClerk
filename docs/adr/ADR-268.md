# ADR-268 — The link probe checks every hop and dials only the address it checked (05.09.2026)

**Context.** `LinkCheckService` (T-238) feeds the pre-publish checklist a warning for
every link that answers 4xx/5xx or not at all. It runs on the droplet, where Kestrel listens on
loopback and nothing else is meant to be reachable from the outside, so a link whose host lands
in a private range is refused before any request exists. Two holes were left open by decision in
Wave 2, acceptable while the verdict was a non-blocking warning (T-324):

- the `HttpClient` followed redirects by itself, so `https://public.example/` → `302` →
  `http://169.254.169.254/` was fetched without the second host ever being checked;
- the check resolved the name once and the handler resolved it again to connect, so a DNS answer
  that changed between the two (rebinding) put a checked-public name on a private socket.

**Decision.** Redirects are followed by the service, not the handler (`AllowAutoRedirect = false`),
one hop at a time, each hop's host re-checked against the same private-range rule, at most
`MaxRedirects` (5) hops. A hop into private space reports the *original* link as `blocked`; a
chain longer than the cap, a `Location` off `http`/`https`, or a `3xx` with no `Location` at all
never becomes a fetch. A `3xx` without `Location` counts as a healthy answer.

The address that passed the check travels with the request as an `HttpRequestOptions` value
(`LinkCheckService.PinnedAddress`), and the production `SocketsHttpHandler` connects through a
`ConnectCallback` that dials exactly that address on the request's port — a request without a
pin is refused, never resolved. The name is still what TLS sees (SNI and certificate validation
use the URL's host), so HTTPS links validate as before; only the socket target is pinned. A
pooled connection can be reused for a later request to the same host, which is a connection to an
address that already passed the check.

**Rejected.** *Re-resolving at connect time and comparing* — the second answer is the attack.
*A resolver cache inside the service* — hides the window without closing it, and caches stale
answers for a probe that is meant to be fresh. *Keeping automatic redirects with a
`Location`-header audit after the fact* — the request has already gone out by then.

**Consequence.** A hop that used to be invisible is now a `blocked` verdict on the original link,
and a chain deeper than five is `unreachable`. The per-link cap (5 s) covers the whole chain. The
test for the hanging link asserts that the cap's cancellation reached the handler rather than
timing a stopwatch (T-364) — the old shape raced the cap under a loaded runner. The service
accepts a per-link timeout in its test constructor for exactly that test.
