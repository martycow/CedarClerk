# ADR-127 — Media library v1: the /media page, deletion via scan, paste/drop (18.08.2026)

**Context.** T-177: uploaded files live only inside a specific draft — there is no place to see "all my files," no way to reuse an image without re-uploading it (every paste creates a new `Asset` row and eats into the quota again), and no way to delete anything except by hand on the server. The existing homes don't accommodate an owner-wide library: the export modal's "Files" is per-draft, the Posts Manager is about posts, and the module's project-assets is an index of the game's disk, not of uploads. The v1 scope, per Marty's word: **library + insertion from it + paste/drag&drop**; asset folders/tags/alt — later.

**Decision.**
1. **Reuse = one URL in many documents.** Inserting from the library writes the existing `/media/{LocalPath}` into the new document; there is one `Asset` row, and the quota (`SUM(SizeBytes)`) counts it once. Content-based deduplication on upload (the same file twice = two rows) is deferred — it's an optimization, not a correctness issue.
2. **Deletion — an on-demand scan, not a usage table.** "Who references it" is already handled by `CedarPackage.FindReferencedMediaPaths` — the source of truth for `.cedar` packaging; building a second scanner would create two truths about what counts as a reference. The scan runs over the owner's `Draft.CedarJson` **and all translations** (not just the first — this same commit fixes the latent gap in `GET /drafts/{id}/assets`); an asset in use answers **409 with `[{draftId,title}]`**, and a free one is deleted entirely: file, Telegram derivative, row. The scan's cost is bounded by the owner's document count; a usage table is a follow-up if it becomes slow at real volumes.
3. **New page `/library`** (Angular, authGuard, a link in the shell navigation; **not `/media`** — that prefix already belongs entirely to the URLs of the uploaded files themselves: server static `RequestPath="/media"` and the dev proxy route it to the backend, which the very first e2e run caught) modeled on project-assets' anatomy: a grid/list, type chips with counters, name search, paging, a "used/limit" header — the data arrives via one `GET /api/assets` (skip/take, `q`, type filter; chip counters are over the unfiltered set).
4. **Insertion into the editor — a separate lightweight `media-picker`**, not a reuse of the page: the picker doesn't need delete/usage, and `editor.component` is already huge. A "library" button in the insert rail; insertion by `ContentType` (image/video/audio).
5. **Paste and drag&drop** in the editor: `editorProps.handlePaste` (files from the clipboard → type whitelist → the existing upload with progress → insertion) and `handleDrop` (the same, at the drop point via `posAtCoords`). The progress panel already exists — it's reused.

**Consequence.** `CedarPackage` gets `FindReferencedMediaPathsSafe` (malformed JSON → an empty list, not an exception — the scan must not fail because of one broken document). Deleting a file in use is impossible by construction — first remove it from the documents, then delete it; the 409's wording shows exactly where from. Deferred and recorded on the board: asset folders/tags, alt text, hash-based deduplication, a usage table.
