# ADR-301 — The workshop chrome: a menu bar, a command registry and a shell-level inspector (16.09.2026)

**Status**: DONE

**Context.** Cedar Clerk reads as an admin panel for a blog: everything a user can do is reachable
only by finding the screen that owns it. Three concrete gaps fall out of that. (1) There is no place
that lists what the application can *do* — `Ctrl+K` finds documents (`search-overlay.component.ts`
over `GET /api/search/drafts`) and nothing else, so a command with no button on the current page is
unreachable and undiscoverable. (2) Every inspector in the app is page-local — the editor's
`#editor-inspector`, the Posts Manager's `aside.inspector`, glossary's, teams' — four
`.split-workspace` implementations of the same idea, and none of them survives a navigation, so
there is nowhere for a panel that is *about the session* rather than about one screen. (3) The AI
features that exist (`POST /api/drafts/{id}/ai-edit/…`, auto-translate, glossary translate-all)
leave no record: a job runs, a document changes, and afterwards nothing says which objects were
touched, what it cost, or how to get back. A user cannot trust a bulk edit they cannot inspect.

**Decision.**

1. **A menu bar above the shell — `shell/menu-bar.component.ts`.** `File · Edit · View · Tools ·
   Help`, one row, `data-surface="chrome"`. This **supersedes ADR-239's "nothing above or below the
   sidebar"** for the signed-in shell only: the pre-auth doors and the blog keep the paper-first
   shape. The bar is drawn entirely from the command registry below — it holds no actions of its
   own, so a menu can never drift from what the palette and the shortcuts run. Navigation stays in
   the sidebar: the menu carries commands (Export, Duplicate, Toggle sidebar, Theme), never the
   project tree, because hiding structure inside `File` is the mistake this ADR is trying not to
   make.

2. **One command registry — `core/commands.service.ts`.** An `AppCommand` is
   `{ id, group, label, icon?, shortcut?, run, enabled?, checked? }`. The shell registers the
   account-wide set at boot; a page registers its own on mount and releases them on destroy
   (`register()` returns the disposer). Three surfaces read the same registry and no other source:
   the menu bar, the command palette, and the shell's keyboard handler. That is the point — a
   shortcut, a menu row and a palette hit are one definition, and a command that is disabled is
   disabled everywhere at once.

3. **Commands and objects get separate palettes.** `Ctrl+K` keeps searching documents;
   `Ctrl+Shift+P` opens `shared/command-palette.component.ts` over the registry. They are different
   questions — "which document" and "which action" — and merging them makes both answers worse.
   `ShellOverlay` gains `'commands'`, so the coordinator keeps it exclusive with search, feedback
   and the debug console like any other transient layer.

4. **A shell-level inspector — `shell/inspector-rail.component.ts`**, right side, two modes:
   **Properties** (what the current object is) and **AI** (what an operation would do to it). It is
   collapsible and resizable, and its state lives in `AppearancePrefs`
   (`inspectorOpen` / `inspectorWidth` / `inspectorTab`) so it survives a reload like the sidebar
   mode does. The page-local inspectors stay: the editor's knows about marks and tables, and
   nothing general replaces that. What the rail owns is the *session* scope — the open object and
   the current selection, published by `core/workspace-context.service.ts`, which pages write to and
   the rail and the AI panel read.

5. **The AI panel states its scope before it runs, and every run leaves a record.** The panel shows
   three lines — the objects in scope, the task, and the fields an operation may not touch — and it
   never widens beyond what `WorkspaceContextService` reports; there is no "apply to the whole
   project" path. `core/ai-operations.service.ts` records each run (task, scope, status, changed
   objects, duration, credits) and `/ai` lists them. **The log is client-side for now**
   (`localStorage`, per account) — a durable server-side log needs an `AiOperation` entity and a
   migration, and shipping the record surface first is what makes the shape worth persisting. The
   backlog carries that follow-up.

6. **Undo is not invented here.** An operation's *Undo* is offered only where a real mechanism
   already exists — a draft revision to restore (`POST /api/drafts/{id}/revisions/{rev}/restore`,
   ADR-062's snapshots). Where none exists the button is absent with the reason in its place, rather
   than present and lying. Redo of an applied change never re-runs the model; re-running is a
   separate command with its own cost.

**Consequence.** The signed-in shell is 28px taller. Credits are **not** duplicated: the AI page
links to Settings → Billing, which stays their one home (`#sec-credits`), as does revision history
in the editor — this ADR adds surfaces for concerns that had none, not second homes for concerns
that did. `AppearancePrefs` gains three optional fields, which merge over `DEFAULT_APPEARANCE` like
every field before them, so an account whose stored blob predates this release opens with the rail
closed. Pages that never call `WorkspaceContextService` leave the Properties panel on its empty
state, which is honest: the rail knows what pages tell it.
