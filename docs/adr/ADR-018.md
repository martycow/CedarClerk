# ADR-018 — Telegram send path switched to `InputRichMessage.Blocks` (Bot API 10.2)
**Context**: Marty reported markdown formatting "completely came apart" after posting — a raw `![](url "caption")` string was showing up as literal text in the channel instead of an embedded photo. Investigation (16.07.2026) found Telegram Bot API bumped to **10.2 on 14.07.2026**, introducing a structured `Blocks` model (`InputRichBlock*`/`RichText*` types) alongside the existing free-form `Markdown`/`Html` text fields, plus an `InputRichMessageMedia`/`Media` field with a documented `tg://{kind}?id=` reference convention for embedding media inside that free-form text. `Telegram.Bot` NuGet was one version behind (`22.10.1`, predating the library's own 10.2-aware `22.10.2` release, itself preceded by an interim dev build already patching related bugs).
**What was tried and empirically ruled out** (live-tested against `@testingandfun`, not just reasoned about):
1. Upgrading `Telegram.Bot` to `22.10.2` alone — necessary (new types don't exist below it) but not sufficient.
2. `InputRichMessage.Markdown`/`.Html` + `Media` + a `tg://{kind}?id=` reference in the text (matching the `InputRichMessageMedia.Id` XML doc literally) — **accepted by Telegram with no error, but the media is silently dropped**, not rendered at all.
3. `<photo src="...">` as the Html-mode media tag (introduced by an earlier commit reacting to the same 10.2 change) — **not a recognized tag**; also silently drops the media. Plain `<img>` is correct.
4. Caption via `InputMediaPhoto.Caption` when the photo is referenced inline from Markdown/Html text — **ignored**; renders as nothing. Only visible when the caption text is placed as an ordinary paragraph in the flowing text, and even then it displays as plain body text (no native muted/caption styling), not a real caption.
**Decision**: `PostEndpoints.PublishAsync` now always builds `InputRichMessage.Blocks` via a new `CedarToTelegramBlocksRenderer` (Core) + a mapping layer in `PostEndpoints` (`ToInputRichBlock`/`ToRichText`) — this is the only combination verified to reliably embed media **and** give it a real, natively-styled caption (`InputRichBlockPhoto.Caption` via `RichBlockCaption`). `CedarToTelegramMarkdownRenderer`/`CedarToTelegramHtmlRenderer` are kept (not deleted, still unit-tested) but are **no longer used for sending** — see the "NOT USED" note at the top of each file.
**Consequence**: `CedarClerk.Core` stays free of a `Telegram.Bot` dependency by design — `RichBlockModel.cs` defines a framework-agnostic `CedarRichBlock`/`RichRun` tree, and only `CedarClerk.Server` (which already depends on `Telegram.Bot`) maps it onto the real wire types. `ExportRequest.Format`/`ScheduledPost.Format` (Markdown vs Html) are still accepted for API/DB compatibility but no longer influence what's actually sent — the frontend's format selector is now vestigial; removing it is a follow-up cleanup, not done in this pass. See `.claude/rules/telegram-bot.md` for the operational summary.
