# ADR-091 — The cache-buster stamps our own media URLs only (04.08.2026)

**Context**: the first publish after the disk-full recovery — a text post with one YouTube embed, no local media at all — failed with `failed to get HTTP URL content`. Verified by hand: `img.youtube.com/vi/<id>/hqdefault.jpg` answers `200 image/jpeg`, and the same URL with ADR-087's `?v=<stamp>` appended answers **404** — Google's thumbnail host refuses unknown query strings rather than ignoring them, unlike the CDN behaviour the stamp silently assumed. So the stamp, built to bust Telegram's negative cache of *our* origin, was breaking the one media class that still legitimately travels by URL.

**Decision: `TelegramPublishTarget` stamps only URLs that point into this server's own `/media/`** (the `TryLocalMediaFileName` test ADR-088 already uses for upload eligibility). External URLs go to Telegram byte-for-byte as rendered. The stamp's whole diagnosis (ADR-087) was about our origin behind Cloudflare — a fetch of a foreign CDN was never the thing being defended, and a foreign host's query-string behaviour is not ours to assume. Negative-cache poisoning of an external URL, should it ever happen, is out of our hands either way — the URL has no variant we are entitled to mint.

**Sequence note**: ADR-087 stamped everything, ADR-088 narrowed it to URL-delivered media, this narrows it to URL-delivered media *we serve* — each step shrinking the stamp toward the failure it was actually built for. With ADR-089's file_id path healthy, a stamped URL now occurs only as the per-file fallback when pre-upload is impossible.
