# ADR-265 — `cedar test` builds the front end, and the deploy preflight warns about a stale backup (05.09.2026)

Two guard-rail decisions in the operations console, taken together in the backlog sweep that
closed T-362 and T-195.

## Decision 1 — the production Angular build is a `cedar test` phase (T-362)

**Context.** `cedar test` ran five phases by default — backend, frontend units, icon inventory,
contrast contract, density contract — and every one of them reads source. Nothing in the runner
produced a production bundle. `--smoke` starts the Angular *dev* server through `ng serve`, which
is precisely the compiler that tolerates what the production build rejects. So a build-only
regression — a bundle over the ADR-251 ceiling, a template error the dev build lets through, a
chunk that fails to lazy-load — stayed invisible to the project's own runner until `cedar deploy`
hit it, after the branch guard, at the moment the maintainer had decided to ship. T-362 asked for
either a sixth phase or a stated decision that the build belongs to the deploy alone.

**Decision.** `ng build` is the sixth default phase of `cedar test`, named *Frontend build
(ng build)*. It runs the same invocation `BuildPipeline` uses for the web build —
`BuildPipeline.AngularBuild()` is one method both call — so what the test run proves is what the
deploy ships, and a second command that could drift does not exist.

Order: the five source-reading phases first, the build after them, the smoke suite last and still
only under `--smoke`. The slowest phase goes last, and a template that fails to compile goes red in
about a minute rather than after the browser run has spent five. The phase belongs to the frontend
half of the selector: `--frontend` runs it, `--backend` does not. No new flag.

`--smoke` does not skip the build phase. The smoke harness never builds a production bundle — it
starts `ng serve` for Playwright — so there is no duplicate work to avoid, and the dev compile it
does run is not evidence of anything this phase checks.

**Rejected.** *Leave the build to the deploy* — the deploy is the last place to learn that the
front end does not compile, and it refuses to run from a feature branch, so the failure could not
even be reproduced where the work was done. *Skip the phase under `--smoke`* — it would trade a
minute of `ng build` for a run that proves less. *A separate `cedar build --check`* — a check that
has to be remembered is a check that is not run; the whole point of `cedar test` is one command.

**Consequence.** A bare `cedar test` takes about a minute longer and answers a question it could
not before. The grid draws nothing for this phase — `ng build` names no tests — and the verdict
row reads "no results parsed" with the phase's own exit code, which is the design of ADR-118
decision 8: the exit code decides, the grid only illustrates. `docs/tech/QA.md` and the Key
commands table in `AGENTS.md` list six default phases, seven with `--smoke`.

## Decision 2 — backup freshness is a preflight warning, never a stop (T-195)

**Context.** `cedar deploy --preflight` checked the branch, the tree, the tag, the tools, the
service state and the free disk, and ignored the age of the newest `cedar-*.db.gz` although
`cedar backup verify` and `cedar status` sit next to it and read that directory. The backlog row
was the one real remainder of the "release-guard" idea.

**Decision.** The preflight's single remote round trip gains two read-only lines — the droplet's
own `date +%s` and the mtime of the newest `cedar-*.db.gz` under `{RemoteDataDir}/backups`. Older
than 36 hours, or no copy at all, is a **warning** on the Preflight step, naming the nightly hour
(03:30 UTC) and `cedar backup verify`; inside the limit the age is noted. It is never a
`PipelineStop`, and `--force` has nothing to override.

Warn-only for the same reason the missing-tag check warns: a stale copy is cron's failure, not the
release's. The deploy never touches `data/` — it swaps `app/` — so a stop would keep a hotfix off
production without making the backup any fresher. 36 hours is one missed nightly plus slack;
`cedar backup verify` keeps its own 24/48-hour colouring for the closer look.

Both stamps come from the server clock, so a laptop with a skewed clock cannot age a fresh copy.
The glob is the one `ServerProbe` now holds for all three readers (`status`, `backup verify`, the
preflight): the script's `DEST` and the tool's path are already one fact in two places, and a third
spelling of it would be a third way for them to disagree. The preflight looks at the backup and
never makes one — `cedar` does not create backups (ADR-118 decision 6).

**Rejected.** *A hard stop* — see above; it also contradicts the rule that only the deploy that
would be blocked can fix what the guard complains about. *Reading the backup in a second ssh call*
— latency to fra1 dominates, and the preflight already has one round trip for everything that
decides whether starting is worth it.

**Consequence.** A deploy over a missed nightly says so on the Preflight step and carries on; the
maintainer sees it before answering the "stop production?" prompt, which is the moment the
information is worth having.

## Ported to the Rust console (05.09.2026)

ADR-252 replaced `CedarClerk.Cli` — `TestPipeline.cs` and `DeployPipeline.cs` above — with the
Rust `cedar-cli/` and the `cedar.json` profile the same morning, and the merge dropped both
mechanisms. They are back in the console's own shape. Decision 1 is the last step of the profile's
`test` and `test-frontend` actions: *Angular production build*, `npm run build` in `cedarclerk-web`,
literally the first step of the `build` action, and `config.rs` asserts the two are equal so the step
cannot silently drop. Decision 2 lives in `deploy.rs`: the preflight probe script prints the
droplet's `date +%s` and the `stat -c %Y` of the newest `cedar-*.db.gz`, and `backup_notice` turns
them into a WARNING line (missing, or older than 36 h) or an age note — never a failure. The glob
and the `{remoteRoot}/data/backups` path are `deploy::BACKUP_GLOB` / `deploy::backups_dir`, read by
`cedar backup verify` as well; the age rule is unit-tested at the 36 h boundary, for a missing copy
and for a stamp ahead of the server clock, and the probe script runs for real in
`cedar-cli/tests/deploy_scripts.rs`.
