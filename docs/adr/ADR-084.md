# ADR-084 — A reader's access travels in the link, and the cookie now proves something (T-064/T-023)

**Context** (01.08.2026): a friend of Marty's opened a private post in Telegram's in-app browser, filled in the registration form, then opened the same post in Chrome — and was asked to register again. That was T-064. Reading the code for it turned up T-023 in the same place: the access cookie's value was the string `"1"`. It proved nothing. Anyone who knew a draft's id could write `cedar_access_<id>=1` and read a private post.

Both are the same mistake seen from two sides — the grant lived nowhere but in one browser, and it was not a grant at all.

**Decision**: the cookie carries a **signed** value (DataProtection, the key ring T-074 already put under `CEDAR_DATA_DIR`), and a successful registration mints a **per-reader token** that comes back in the redirect: the reader lands on `/slug?access=…`, which is a link they can send themselves. Per registration rather than per post, which is what makes it revocable without locking out everyone else who registered.

**What this costs, stated rather than hidden**: cookies issued before today stop working. A reader who is already through the gate meets it again once, and passes it again. Keeping the old value working would have meant keeping the forgery open, and a private post whose lock can be picked by typing a cookie is not private.

**What was not built**: the owner-facing revoke button. `IsRevoked` exists and the read path honours it, so revoking is a database update away, but a control for it belongs with the submissions list and its own confirmation — a small feature, not a footnote to this fix.

The test that matters is the incident itself: one browser fills in the form, a second browser that has never seen the post opens the link and reads it, and a third with neither link nor cookie still meets the gate.
