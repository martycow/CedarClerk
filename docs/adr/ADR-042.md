# ADR-042 — Registration form for private posts: locked, not hidden (supersedes part of ADR-041)
**Context**: Brainstorm item B3 (High) — an uninvited visitor of a private post should get a customizable registration form (name, nickname, email, a social link) with optional Google-Forms-style questions, instead of the current 404. That directly contradicts ADR-041's deliberate choice to make a private post indistinguishable from a nonexistent one. Confirmed the trade-off with Marty before building: filling the form **grants access immediately** (it collects an audience, it is not a verification step), the form is configured **per post** (different posts want different questions), and it **replaces the 404** rather than being an optional per-post mode.
**Decision** (26.07.2026):
- `Draft.RegistrationFormJson` (`string?`, migration `AddRegistrationForm`) holds the form definition as a client-authored JSON blob — variable shape (a question list), so the same treatment as `ApplicationUser`'s preference blobs: the server length-checks it (`Consts.RegistrationForm.FormJsonMaxChars`) and never dictates the schema. **Null keeps ADR-041's original behaviour** — no form configured means an uninvited visitor still gets the indistinguishable 404, so the old guarantee is still available, just no longer the only option.
- `RegistrationFormDefinition` (Core, unit-tested) is the single parser both the renderer and the submit-validation read, so the form shown and the rules enforced can't drift. It **degrades rather than throws** on malformed input (corrupt blob → name+email default; unlabelled question → dropped; `choice` with no options → rendered as text), because a hand-edited blob must never take a published post down.
- `CedarToBlogHtmlRenderer.RegistrationFormHtml` (Core, unit-tested) builds the markup, escaping every author-authored string (intro, question labels, choice options) — that's the one new injection surface this feature introduces, and the tests assert it explicitly.
- New `PostRegistration` entity rather than reusing `PostInvite`: the field sets barely overlap (nickname, social link, answers JSON, visitor hash), and folding them together would push half-empty rows of a different kind through the existing invites UI.
- Submission (`POST /api/posts/{slug}/register`) sets **the same** `cedar_access_{draftId}` cookie a valid invite token sets, so everything downstream (`HasPrivateAccess` and its four call sites) is untouched. Required-field and required-question checks are re-run server-side — a form POST is trivially replayable outside the browser.
- **First rate limit in the blog endpoints**: max 3 submissions per `VisitorHash` per post per 24h (429 otherwise). Nothing else on the public blog is throttled, but a public form that hands out access and writes rows is an obvious flood target.
**Consequence**: A private post's existence is now discoverable to anyone with the URL whenever a form is configured — accepted deliberately, that's the point of the feature. The form performs **no email verification**, so a submitter can enter any address; combined with instant access this makes the form an audience-collection tool, not an access-control boundary. Revoking an already-granted access is still impossible (the cookie isn't checked against a live row) — the same limitation invite links already had, but more visible now that anyone can self-serve. Owner-side UI (form editor + submissions list) lives in the Export modal next to the invite list. Not yet live-verified in a browser as of writing.
