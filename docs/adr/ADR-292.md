# ADR-292 — Localization owns language resources and presentation rules

## Context

`CedarClerk.Localization` owns errors and language codes, but UI dictionaries, email text,
reader labels, date formatting and language selection rules live in their consumers.
This makes localization changes require searching unrelated projects.

## Decision

Use `CedarClerk.Localization` as the home for application localization resources and
framework-independent language behavior. Keep its .NET assembly independent of Core,
ASP.NET, Angular, database entities and translation provider SDKs.

- Move email text, reader catalogs, localized value selection, Russian declensions and
  display date/time rules into this project. Core and Server consume it.
- Store TypeScript dictionaries and pure browser localization utilities under its `Web/`
  directory. Angular imports these sources directly through `@localization/*`; retain lazy
  loading of the Russian dictionary and the existing dictionary shape check.
- Share language codes, endonyms and available interface dictionaries through one JSON
  catalog consumed by .NET and TypeScript.
- Keep HTTP/account culture adapters in Server and the signal/DOM adapter in Angular.
  Document/form serialization, translation jobs, provider calls, quotas and persistence
  remain in their domain projects. Their language resources belong to Localization.
- Preserve existing text, language support, fallback rules, escaping, persisted values and
  public URLs. This refactor does not add translations or change account language policy.

## Verification

Run the repository test and production build profiles. Guard shared language metadata,
catalog coverage, formatting/fallback behavior and dependency direction. Existing renderer,
email, profile and locale tests cover consumers after the moves.
