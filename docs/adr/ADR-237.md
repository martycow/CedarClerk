# ADR-237 — Signing in with somebody else's account: a second door, never a side door (01.09.2026)

**Context.** T-003 had been open since the backlog's early numbering, carrying three unanswered questions rather than an implementation problem: which providers, what happens when a provider hands back an address an account already holds, and whether a provider button may create accounts while `/register` is still invite-only. Telegram linking has existed since ADR-009 but is not sign-in — it attaches an identity to a session that already exists.

**Decision.**

1. **Google and Telegram now; Apple deferred to its own row.** Apple is not a third provider of the same size: it needs a paid Apple Developer Program membership, its `client_secret` is a self-signed ES256 JWT that Apple caps at six months so it must be rotated or generated on the fly, its Private Relay hands back `@privaterelay.appleid.com` addresses that only reach us if the sending domain is registered with Apple under SPF/DKIM, and it returns the person's name **only on the first sign-in**. None of that is hard; all of it is separate, and bundling it would have held the two cheap providers behind it.

2. **The invite gate applies to signing up through a provider, exactly as it applies to the password form.** Registration is invite-only, and a Google button that created accounts freely would have opened it to anyone holding a Google account through a door nobody decided to open — leaving the `BUSINESS.md` §1/§2 gates (lawyer, threat model, media into R2) behind the fact. Signing **in** is free; signing **up** goes through the same check. That check moved out of the register handler into `AuthEndpoints.ResolveInviteAsync`, because a rule with two callers written twice eventually disagrees, and the copy that drifts is the one guarding registration.

3. **An address that already belongs to an account is never merged on the provider's word.** The callback sends that person to `/login` with `?external=link`, the password is what proves the account is theirs, and the link is attached immediately afterwards. A provider's `email_verified` is a claim about their world, not ours; treating it as proof of ownership over **our** account is the standard account-takeover path. The cost is one extra step, once, for people who already had a password.

4. **Telegram signs in; it does not sign up.** It carries no email, and the account model needs one — `RequireUniqueEmail` is on, and email is what invitations, receipts and recovery all run through. Inventing an address to satisfy the model would put a fiction in the one field the product must be able to write to, so an unknown Telegram gets a 404 saying so rather than an account. Attaching a Telegram to an existing account is what `/telegram/link` already does.

5. **The server renders nothing in this flow.** Every branch of the callback ends in a redirect to an SPA route carrying an outcome, because the screens that ask for a password or an invite code already exist and there is no reason to grow a second, server-rendered set of them.

6. **The provider identity never travels through the browser.** It lives in Identity's external cookie between the callback and the completion step, and the server reads it back when the form is submitted — so nothing the client posts can change whose account gets created. The cookie is cleared by name (`IdentityConstants.ExternalScheme`) once it has been spent: a bare `SignOutAsync()` would clear every scheme including the application cookie, dropping the session that was just created.

7. **A provider is configured or it does not exist.** Google's scheme is registered only when both the client id and the secret are set, so an install without them answers 501 instead of failing at startup, and the doors draw no button at all — read off `/api/health`, because `/login` and `/register` run before there is a session to ask with. A self-hosted install with neither provider set looks exactly as it did before this shipped.

8. **The last way into an account cannot be removed.** Unlinking a provider is refused when it is the only one and no password is set: an account with neither is unreachable by its owner and recoverable only by hand.

**Consequence.** `AspNetUserLogins` was already in the schema — Identity created it in `InitialCreate` — so **no migration**. Two new front-end surfaces: the provider row on both doors, and `/auth/complete` for a Google sign-in with no account behind it yet. The Telegram widget is a third-party script from `telegram.org`, loaded on the two doors only; it is functionally required to sign in, so it is not behind the ADR-236 analytics consent, which covers measurement rather than the ability to log in.

What this leaves open: **Apple** (its own backlog row, with the four costs above stated), and the fact that a Google account whose address is later changed on Google's side keeps working here — the link is on the provider's subject id, not on the address, which is correct and worth knowing when reading the account list.
