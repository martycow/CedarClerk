# ADR-195 — Blog projects, task files, and Project covers reuse existing primitives

**Context.** The annotated workflow needs a Blog Project, file attachments on GameTask, and a direct
Project-logo upload. Cedar Clerk already has the three storage primitives involved: Project type
selects the starter Document, Asset stores uploaded media and files, EntityLink relates project
objects, and Project.CoverUrl stores the image shown for a Project. The existing `asset` link target
means an indexed `AssetEntry`, whose bytes remain on the author's machine; it cannot also identify an
uploaded `Asset` row without making one type name mean two different entities.

**Decision.**

1. `blog` joins `ProjectTypes`. It starts with a publishable `post` Document and does not restrict
   what the Project may contain afterward, matching every other Project type.
2. GameTask keeps Name and Description as explicit fields. Attachments are ordinary uploaded `Asset`
   rows linked through `EntityLink` using the new string target `attachment`; `asset` remains reserved
   for indexed `AssetEntry`. Creating a task uploads chosen files after the task exists, then links
   them. The task card names, opens, and unlinks those attachments. Deleting an uploaded Asset removes
   its attachment links, while the existing document-reference guard still blocks deletion when the
   bytes are embedded in authored content.
3. A Project logo is an uploaded image Asset whose URL is written to `Project.CoverUrl`. No second
   file store, logo table, or public-media route is introduced. Deleting that Asset clears any
   matching Project cover reference.
4. User-facing copy calls authored content **Document**. Internal names (`Draft`, `DraftTranslation`,
   `/api/drafts`, and CedarJson) remain byte-exact canonical terminology and are not renamed.
5. The writer's Structure starts with a Document root. Clearing the node selection selects that root,
   and the Inspector returns to Document properties.

**Consequence.** No task or cover migration is required: EntityLink target kinds are strings. Adding
`blog` changes validation and starter mapping only. Existing Asset ownership, quotas, document
deletion guard, and EntityLink ordering apply to task files without a parallel store.
