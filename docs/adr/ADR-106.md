# ADR-106 — Task is a separate entity, not a document (10.08.2026)

**Context**: the brief asks for a basic task tracker with Name, Status, Priority, Description, Assignee fields, linked to the rest of the documents. ADR-102 just decided that document types are a column on `Draft`; it's tempting to make a task an eighth document type.

**Decision: `GameTask` — its own entity with fixed columns.** A task has a set of fields that need to be filtered, sorted, and aggregated by ("what's in progress", "what's overdue", "how much is left in the sprint"). Inside `Draft` this would live inside `CedarJson`, meaning every such question would become a full document scan with JSON parsing.

**The boundary between ADR-102 and this decision is simple**: if the content is free text and the surrounding fields are metadata, it's a `Draft` with a type. If the content is a set of fields and the text is just one of them, it's its own entity. `Description` inside a task stays plain text, not a TipTap document — a task that needs formatting, tables, and media is really a document, and it should be created as a document and linked.

**Links — a `TaskLink(TaskId, EntityType, EntityId)` table, not a `DraftId` column.** The brief requires a task to be "somehow linked to other documents," and in practice what needs attaching isn't only documents: an asset, another task, the project itself. A column per link kind means a migration for every new kind; a string `EntityType` doesn't. This is a deliberate trade of FK constraints for extensibility, in the same spirit as `Draft.FolderId`.

**Sprints (`Sprint`) are a separate entity on top of tasks, not a field on a task.** A sprint has its own dates and name, and a task can outlive several sprints.
