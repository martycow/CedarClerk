# ADR-211 — A file inherits the audience of the posts that publish it

**Context.** `/media/*` was a static-file directory: 489 files in one flat folder, served to anyone
with the GUID, on any host. Under one operator that is a deterrent problem at worst. Under many
accounts it is the hole in every other boundary — a private post's page can 404 correctly while its
pictures answer 200 to the same stranger, and one account's host can serve another account's files.

Laying the files out per owner was considered and rejected: moving them means rewriting every stored
reference, including the revision bodies the stale-publish guard fingerprints and channel history
that cannot be edited. So the boundary is a door in front of the directory, not a directory layout.

**Decision.** `MediaOwnershipMiddleware` runs ahead of the ordinary static-file middleware — which
keeps range requests, ETags and conditional GETs exactly as they were — and asks two questions on
every host.

- **Whose file is this, and does this host serve that account?** A host that renders a blog serves
  its own owner's files and nothing else. The application host belongs to no blog and is *not*
  narrowed: it is the origin the server advertises to Telegram's fetcher and to OG scrapers.
- **Is the file gated, and may this reader open it?** A file inherits the audience of the published
  documents that reference it. Referenced by a public post it is public; referenced only by private
  ones it opens to the same signed grant its page needs, or to the owner's own session. This half
  holds on every host, including the application host — otherwise the gate is a property of which
  name the reader typed.

Three details the implementation is bound to. The gate is keyed by **asset**, not by file, so a
Telegram-safe `_tg` derivative cannot be the way around its post's gate. A post already sent to a
channel counts as public whatever its blog page says, because channel history cannot be edited.
And every refusal is a **404, never a 403** — a 403 confirms the file exists for somebody else.

The answer is computed for a whole account in one pass and held 30 seconds: a blog page asks about
every image on it at once, and a per-file question would scan the account's documents each time.
That lifetime is also how long publishing takes to open a gated post's images and unpublishing takes
to close them. A file name that parses but belongs to nobody is cached as a miss on the same terms
(ADR-212), so a crawler's guesswork costs a query per name per interval rather than one per request.

**Consequence.** Media stopped being the exception to tenancy: it is filtered by host owner and
gated by audience, and the live three-tenant matrix confirms both for published posts, derivatives,
grants and scraper user-agents.

**The rule as implemented does not cover the whole surface, and shipped that way.** The gate is
derived only from `IsBlogPublished` drafts, so a private post that is unpublished — or has never been
published — contributes no gate and its media becomes anonymously readable (`T-284`): taking a post
down is what opens its pictures. And the host narrowing keys on the resolved blog owner, which is
null for any Host header the router does not recognise, so an arbitrary `Host:` switches narrowing
off (`T-285`), which also leaves project attachments, avatars and project covers ungated on the
application host, since no published post references them. Both are disclosure defects on the board,
not accepted costs of this decision.
