# ADR-277 — The project journal is a union of timestamps the module already writes, and the nudge is one date on the list (05.09.2026)

**Context.** ADR-160 §7 left the hub's chalk edge with "the last activity the API does report",
and `app-log-line` was ported with nothing to draw. Documents, tasks, builds, channel posts and
queue jobs each carry a timestamp already; `GET /api/projects` carries `lastActivityAt`, which is
the newest *edit* and says nothing about publishing. T-249 asked for a feed, T-166 for "days since
the last post". Both are read shapes over rows that exist.

**Decision.**

1. **`GET /api/projects/{id}/activity?take=` is an in-memory union, not a table.** Ten fixed
   `kind` strings (`ProjectEndpoints.ActivityKinds`), one item shape `{at, kind, title, subtitle,
   href, actor}`, newest first. Each source is queried with its own `Take(take)` before the union,
   so the cost is bounded by `take` (1…100) rather than by the project's size. Nothing is written:
   an event table would be a second copy of dates the entities already hold, and it would start
   empty on the day it shipped while the union answers from history.
2. **Two collapses keep the journal honest.** A document's `UpdatedAt` counts as an update only
   when it is more than a minute past `CreatedAt` — the starter template's first save is not an
   edit. Telegram parts of one send (same draft, same channel, within fifteen minutes) are one
   `telegram-published` item pointing at the first message; a twelve-part thread is one event, and
   the channel-post source is over-fetched so the collapse cannot starve it.
3. **Members read it.** The route resolves through `ProjectAccessResolver` and reads under the
   owner's tenant, the same door the canvas opened in ADR-217 — a viewer on the hub sees the same
   journal as the owner. Every source query still carries the explicit owner predicate, so a row
   filed under the project id by another tenant never appears even through an unfiltered context.
4. **`lastPublishedAt` lives on the project list projection** — the newest of `Draft.BlogPublishedAt`,
   `ChannelPost.PublishedAt` and a succeeded `PublishJob.FinishedAt` across the project's documents,
   null when nothing was ever published. On the list because the hub already derives its summary
   from it; not on `/api/stats/publishing`, which is the account's streak and which ADR-160 §3 keeps
   off a project screen.

**Rejected.** *A persisted activity table* — a write path for every module action, empty history,
and a second truth for dates the rows already carry. *Per-part Telegram items* — the journal names
what the author did, and the author sent one post. *A `lastPublishedAt` on the detail only* — the
hub would need a second request for a number the list query can answer in three grouped reads.

**Consequence.** Ten kinds are a contract the client's `projects.hub.journalKinds` map must cover
one for one; adding an eleventh means a row in both. The `href` for `blog-published` depends on
the owner having a tenant username, and is null otherwise, as every blog link is. The failed-job
subtitle carries the network and the stored error verbatim, which is the same text the queue
already shows the owner.
