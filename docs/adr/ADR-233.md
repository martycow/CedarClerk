# ADR-233 — A preset is a named starting point; a document type's "meaning" is the preset that carries it (31.08.2026)

**Context.** Two coupled asks. T-331: the New-project dialog's types are presets in fact, and the
maintainer wants a Preset Manager — and eventually presets for documents and export too. T-355:
the Document Type (`post`/`design`/…) carries no behaviour of its own, so the maintainer's ruling
was "give it real meaning" rather than making the raw type string user-editable.

**Decision.** One entity answers both: `Preset { OwnerId, Kind, Name, ConfigJson, SortOrder }`.
`Kind` is `document` today; `project` and `export` are the same table later, each validating its
own `ConfigJson`. A **document preset** bundles what a bare type never did: a base type (which
built-in `DocumentTypes` value it publishes as), an icon, and a heading skeleton the new document
is born with (`DocumentPresetConfig`, in Core, shared by validation and skeleton generation).

Two commitments make this safe:

1. **A preset never mints a new stored type string.** `documentType` on `Draft` stays one of the
   frozen `DocumentTypes` values, because publishability keys on it and it lives in SQLite forever.
   A preset's `baseType` is validated against `DocumentTypes.IsKnown` and falls back to `post`. So
   "give the type meaning" is done by *bundling behaviour behind a named choice*, not by letting
   the type itself become arbitrary — the byte-exact contract holds.
2. **The skeleton is applied server-side at creation, once.** `POST /api/projects/:id/documents`
   takes an optional `presetId`; when set, the server reads the preset, sets the draft's type to
   its base type and its body to the skeleton. After that the document is an ordinary draft — a
   preset is a starting point, never a live link, so editing or deleting the preset never touches
   documents already made from it.

**Consequence.** One table, one migration (`AddPresets`), a Preset Manager screen (`/presets`, off
the tray like Glossary), and document presets offered as dashed cards beside the built-in types in
the New-document dialog. The built-in types stay in code as the always-present baseline; presets
are additive. Project and export presets, and letting a project preset drive the New-project
dialog, are the next slices on the same table — deliberately not built until they are needed, so
the config shapes are designed against real use rather than guessed.
