# ADR-279 — The Stats tab asks the server for one aligned window; selection reaches it, and the window delta replaces Δ7d (05.09.2026)

**Context.** ADR-161 rule 5 had the tab fan out on the client — `GET /api/blog/stats` plus one
`GET /api/channels/{id}/stats` per channel, every range — and align the answers itself: the window
start, the carry-forward through days with no snapshot, and the display-zone day keys were all
computed in `stats.component.ts`. Two costs were recorded there and never resolved. A leaf toggling
cost no request because everything was already fetched, which was the rule's whole argument; and
the readout cards took the server's `deltaWeek*`, computed over the API's own window rather than the
aligned one, so a card and the chart could disagree when snapshots were sparse (T-242). The rule
also left X and Bluesky with no leaf at all (rule 4): no snapshot existed for either, and the client
had no way to learn of one (T-241). The kit's CSV action had been moved into the chart panel's
header by ADR-148 §4 and had nowhere to go, because nothing wrote CSV (T-243).

Wave 2 gives the server `GET /api/stats/series?days=&sources=` (contract §2): the **selected**
source ids in, one aligned window out — dense `days`, per-source `values` already carried forward,
`current` and `delta` over those same days, `publishDays`, and `available[]`, the list of every
source the account has whether selected or not. `GET /api/stats/series.csv` is the same matrix as a
file.

**Decision.**

1. **Selection reaches the server, superseding ADR-161 rule 5.** `StatsComponent.load()` makes one
   request carrying the selected ids for the chosen range; `toggle()`, `showAllSources()` and the
   period picker each refetch. A failed refetch keeps the previous answer on the board and clears
   `pending`; an answer overtaken by a newer request is dropped. The metric strip and the chart/table
   strip are still the client's own and cost nothing — they choose what to draw from an answer, not
   what to ask for. What is traded away is rule 5's "a toggle cannot fail": a toggle is now one cheap
   request, and its failure mode is stated above rather than impossible.

2. **The client draws what the response carries and aligns nothing.** `sources()` is `available[]`
   joined to `series[]`; `days`, `labels`, the table rows, the readout sparkline and the publish
   markers all read the response's arrays as they are. `normalize()`, `axis()`, `carryForward()` and
   the display-zone day keying are gone from the component — the day keys arrive as calendar days
   in `zone`, which is the same zone ADR-115 gave `formatInZone`. Rules 2 and 3 of ADR-161 (the
   window starts at the latest first reading, gaps carry forward, `openTail` is false) are unchanged
   in meaning and moved in place: they are now the server's, tested in `StatSeriesAlignerTests`.

3. **The readout delta is `series[].delta` and nothing else — "over the window", not Δ7d.** It is the
   window's last value minus its first, computed by the server over the same days the chart is drawn
   from, so a card and the chart cannot disagree; the disagreement ADR-161 recorded is closed by
   removing the second number rather than reconciling two. `stats.perWeek` is deleted with it.

4. **The leaf strip is `available[]` verbatim** (ADR-161 rule 4, now satisfied by construction). A
   source is offered the moment the server lists it and dried until its `firstDay` is set or while
   the picked metric is not in its `tracked` list; an X or Bluesky account (`target:{guid}`) arrives
   with its brand mark (`app-brand-icon`) and a network word, named by `available[].name`. Slots
   stay the entity's: the blog keeps ink blue, channels then targets take the rest in `available`
   order. A switched-off source is absent from `series[]`, so the number its leaf showed while it was
   drawn is remembered on the client — the current value is the latest reading, which no window
   changes — and a source never drawn in this session shows its name alone.

5. **A fresh open may cost two requests, and that is the price of the server owning the list.** With
   no saved selection the client cannot name a target before the server has listed it, so the first
   request selects the blog and every channel; if `available[]` names a source that request did not,
   the client selects everything and asks once more. A saved selection (`?statsSources=`) is sent as
   it is, one request.

6. **CSV is an anchor in the chart panel's header** (ADR-148 §4): `<a download>` to
   `seriesCsvUrl(days, selectedIds)` after the two `app-index-tabs`, wearing the global `.btn sm`
   face — `app-button` cannot carry a `download` attribute onto its inner anchor, and a second
   button component for one attribute is the wrong trade. Same-origin cookie auth, no fetch; with
   nothing drawn the address goes and the element stays (`aria-disabled`, ADR-169), because an empty
   selection would download a header row.

**What was rejected.** *Keeping the fan-out and adding the series endpoint only for CSV* — two
alignments of one matrix, one of them on the client, is exactly the two-sources-of-truth the delta
disagreement came from. *Sending `sources=all`* — not in the contract, and the server would then
have to define "all" separately from the list it already returns. *Caching every source's series on
the client so a toggle stays free* — that is the fan-out again, one request later. *Guessing a
target's id on the client* to avoid the second cold-start request — the client would be constructing
source ids the server owns, the thing rule 4 forbade.

**Consequence.** `ChannelsService.getStats()`, `getBlogStats()`, `ChannelStats`, `BlogStats` and
the two snapshot DTOs leave the client API — nothing else read them; `GET /api/channels/{id}/stats`
and `GET /api/blog/stats` stay on the server for the post-details chart. The freshness note no
longer carries a snapshot's clock time (the response has none) and states the window's last day and
zone instead. The audience shelf rides every response, so it no longer depends on the blog being
fetched separately. `ChannelsService.series()` / `seriesCsvUrl()` and the `StatsSeries` types are
the client's mirror of contract §2–3; the stub in `stats.component.spec.ts` answers the way the
server does, so every test asserts the component renders exactly what a response carries.
