# ADR-126 — Metrics event dictionary: a contract before the analytics provider (18.08.2026)

**Context.** T-153 (analytics) is stalled on choosing a provider (Plausible/Umami/GA4 — affects `/privacy`), but no dictionary of product events exists anywhere, and that's a separate problem: the first day of connected analytics will collect the wrong events, and there's no going back to collect them retroactively — a principle already recorded on the snapshot entities themselves (`DraftStatSnapshot`, `BlogViewGeoDaily`: "History starts the day this ships"). The four metrics in `docs/product/BUSINESS.md` §4 are today computed however each one happens to be: three from the database, activation halfway. The panic of "every day without a dictionary is lost data" is overstated — registration is closed, there's no funnel — but the dictionary must exist **before** T-153 (T-193).

**Decision.**
1. **`docs/product/METRICS.md` is the single source of truth for events and metrics**: what is already written to the database (and by which entity), what is not written (and therefore cannot be mined retroactively), and how each of the four §4 metrics is derived from what already exists. BUSINESS §4 stays the owner of the list of "which metrics matter"; METRICS answers "exactly how are they computed".
2. **Event names are a stable contract.** The provider from T-153 only transports events under these names; changing providers does not change the dictionary. Names are `snake_case`, the action's object comes first: `signup_completed`, `draft_created`, `post_published_first`.
3. **Activation is already derivable retroactively** — with no explicit event: a join of `AspNetUsers.CreatedAt` × min(`PublishJob.FinishedAt` with `Status=Succeeded`, `Draft.BlogPublishedAt`) per owner. `PublishJob` is a complete append-only publish log with no retention, `BlogPublishedAt` has first-publish semantics; so "first publish" is mineable across the whole history, and a `post_published_first` event in the provider is an optimization, not a data rescue.
4. **The no-cookie stance is fixed before the provider is chosen**: our own blog statistics already work without cookies (`VisitorHash` with a salt, ADR-016; `BlogViewGeoDaily` is an aggregate, not a trail), and the provider must not make that worse — a consent-banner option is accepted only by Marty's deliberate decision, never by default.

**Consequence.** Onboarding the provider (T-153) starts with mapping the dictionary, not inventing events; events "not in the database" (the signup funnel, feature usage) will only start existing from the moment it's connected — METRICS.md honestly marks them as non-mineable. The file must be updated in the same commit that adds or renames an event.
