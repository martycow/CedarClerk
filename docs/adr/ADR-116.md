# ADR-116 — Desktop updates itself, the installer serves our own server, deploy carries it behind a flag (11.08.2026)

**Supersedes** the line "Self-update — not in v1, updating means reinstalling" in the risk table of `docs/DESKTOP.md`, and part of ADR-113 ("deploy never touches `data/`" — now it touches exactly one subdirectory of it, see below).

**Context**: the installer was only ever built manually with the flag `.\Scripts\build.ps1 -Installer`, lived in `CedarClerk.Desktop/dist/` on Marty's machine, and went nowhere. That is, desktop had neither a delivery mechanism nor an update mechanism: any server change — and the server ships inside the install, self-contained — meant "build, send the file over, reinstall by hand." While there's only one install and it's Marty's own, that's tolerable; as soon as there are two, versions will drift apart silently, and a shell/server mismatch is only caught by a dialog at startup.

**Decision 1: updating is done by `electron-updater`, provider `generic`, not GitHub Releases.** The project already has a public HTTPS origin with its own static file serving; GitHub Releases would require a public repo (there isn't one) or a token in the client (not allowed). `publish: {provider: generic, url: https://cedarclerk.mooexe.dev/downloads}` — and the whole update protocol comes down to three files in one folder: `latest.yml` (a manifest with the version and sha512), `CedarClerk-Setup-<version>.exe`, and its `.blockmap`. No server-side logic at all: updates are served by the same `UseStaticFiles` that serves media.

**Decision 2: the files live in `data/downloads/`, not next to the app.** `app/` gets wiped and recreated by deploy on every release — an installer placed there would disappear on the very next ordinary deploy, taking `latest.yml` with it and leaving installed copies pointing at a manifest that leads nowhere. `data/` survives a deploy by construction (ADR-113). The price of this is exactly that exception to "deploy never touches `data/`": the script writes to exactly `data/downloads/` and nowhere else, and that folder's contents are the only thing in `data/` that gets recreated by a build — so losing it costs one `deploy -Desktop`, not data.

**Decision 3: building and uploading happen behind the `-Desktop` flag, not on every deploy.** `electron-builder` is minutes of work and ~130 MB on top of the usual ~50 MB deploy, over the home upstream channel. An ordinary deploy fixes the server and frontend, which will arrive in desktop anyway with the next desktop build; there's no reason to pay for that on every deploy. The cost of this decision is stated honestly: **production's version and the latest installer's version can drift apart**, and that's visible in the deploy report (it prints what version is currently in `downloads/`) rather than being discovered later.

**Decision 4: uploading uses the same mechanism as the release itself, and `latest.yml` is written last.** The same `Send-Tail` with resume and the same sha256 verification (ADR-113) — 130 MB over a channel that breaks, otherwise it wouldn't make it at all. The order is mandatory: `.exe` and `.blockmap` are uploaded to a temporary subdirectory, verified, moved with `mv` into `downloads/`, and **only then** does `latest.yml` appear. The manifest is the only thing clients read; while it's absent or stale, installed copies see the previous version, not a broken new one. The reverse order would mean a window where `electron-updater` downloads half a file and fails on sha512.

**Decision 5: there's no code signing, and that changes the trust model, not just SmartScreen.** `publisherName` isn't set in the config, so `electron-updater` skips signature verification and relies on the sha512 from `latest.yml`, fetched over the same HTTPS as the file itself. Practical meaning: **trust in an update equals trust in `cedarclerk.mooexe.dev`** — whoever can spoof the origin's response or the DNS can deliver an arbitrary exe to the machine. With one user and our own domain this is acceptable; with the first external desktop-build user, signing stops being cosmetic (SmartScreen) and becomes a security boundary. Recorded here so the decision is made consciously, not by default.

**Decision 6: the server is killed before installation.** NSIS overwrites `resources/server/CedarClerk.Server.exe`, and at that moment it's running as a child process — a locked file would abort the install midway. So `stopServer()` is called before `quitAndInstall()`, rather than relying on `before-quit`.

**Found on the first real update (Marty, 11.08.2026), and this is a property, not a one-off: the update is installed by the version being replaced.** The code performing the install is the old code; the new code only takes effect starting from the next time. Practical consequence: any change to the update path must be tested on the "previous version → this one" cycle, and the first update after such a change still goes through the old, broken path. There's exactly one way around it — install the new version by hand with the installer, bypassing self-update. This also means the update path is the one place in the project where a bug lives one version longer than its fix.

The specific bug was in the same spirit: `taskkill /f` returns exit code 1 to the process it killed, and the server's exit handler had "the server crashed on its own" wired to it, showing a modal `showErrorBox`. Before updates existed this never showed up — every other stop happens after the window closes, and the handler was checking exactly that. Installing an update stops the server **while the window is still alive**, in the middle of the exit sequence, and the modal window blocked the main process. Fixed by having the deliberate stop remove the handler first: something we asked for ourselves cannot, by definition, be a crash.

**The shell speaks English.** The app's interface is translated, the shell isn't, and translating it halfway would be worse than not translating it: an update dialog in Russian next to an English "Version mismatch" reads as a bug, not as care. Decided by Marty on 11.08.2026, when the first Russian update dialog turned out to be the only Russian text in the shell.

**What stays the same**: `Scripts/build.ps1 -Installer` still builds the installer locally and sends it nowhere — deploy reuses it (`-DesktopOnly -Installer`) rather than duplicating the build logic. The shell version is still kept in sync with `Consts.CurrentVersion`; what's new here is that deploy **refuses** to run with mismatched versions, rather than silently patching the file in the working tree along the way.
