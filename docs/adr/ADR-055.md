# ADR-055 — NF5: polls, blog-only, no new form/preset entity
**Context** (28.07.2026): idea #22/NF5 — a poll content block. `docs/BACKLOG.md` recorded Marty's suggestion to build it on the existing form-preset entity, since the question/choice model already exists there. Marty's explicit decision this session: **polls render on the blog only** — no Telegram surface at all (not even a degraded link), which removes the biggest open question NF5 carried (Blocks has no native poll support).

**Decision**:
- **Not built on `RegistrationFormDefinition`/`FormPreset` after all.** That entity models a per-*draft* access-gate form (name/email/questions to unlock a private post) — a fundamentally different thing from an in-content block any reader can vote on inline, registered or not. Reusing it would have meant threading poll semantics through access-control code that has nothing to do with polls. Instead: a new TipTap node (`poll-node.ts`, `cedarclerk-web/src/app/tiptap-extensions/`) storing `id`/`question`/`options` as node attrs (no content — there's nothing here that's itself rich text), following the exact node-view pattern `toggle-node.ts` already established (hand-built DOM via `addNodeView`, patched back into the doc via `setNodeMarkup`).
- **Genuinely blog-only, enforced by omission, not a guard.** No `case "poll"` was added to either Telegram renderer (`CedarToTelegramBlocksRenderer`/`CedarToTelegramMarkdownRenderer`) or to `CedarToTelegramHtmlRenderer`. A poll node has no content, so those renderers' existing "unknown block type → render children" default (the same fallback `annotation` already relies on) naturally produces nothing at all — the blog-only behavior falls out of the node shape, it isn't special-cased per renderer.
- **Votes are a new `PollVote` table** (`DraftId`, `PollId`, `Option`, `VisitorHash`, `CreatedAt`), same anonymous-visitor-hash shape as `Reaction` (ADR-016) rather than anything tied to an account — a poll on a public blog post has to accept votes from anyone, the same way a like does. One vote per `(poll, visitor)`; changing your answer updates the row (no "unvote" — a poll has no meaningful blank state to return to, unlike a like toggle). Tallies piggyback on the existing `GET /{slug}/annotations` bootstrap fetch (a `polls` dict alongside `article`/`annotations`) rather than a separate round-trip, since every real post page already makes that call.
- **Results only show after voting**, not live before — the rendered markup ships zero-width bars and no percentages; the client script only paints real numbers once `myVote` is set. A `.zip`/`.cedar` static export still gets the same markup (a poll is post *content*, unlike the page-level reactions/comments chrome those exports never included) — the vote buttons simply have no server to call from a downloaded file, the same inherent limitation any interactive feature has in a static export, not something special-cased for polls.

**Consequence**: migration `AddPollVotes`; new route action `poll` in `BlogEndpoints.HandleRequest`'s slug-scoped dispatcher (`POST /api/posts/{slug}/poll`), alongside `react`/`comments`/`register`. `CedarToBlogHtmlRenderer` gained a `poll` case with the same "drop entirely if nothing to show" rule as an empty carousel/collage (ADR-019). `dotnet test` 353/353 (2 new `BlogHtmlRendererTests` cases, 1 new `BlocksRendererTests` case confirming the Telegram side renders nothing). `ng build`/`ng test` clean. Not yet live-verified in a browser; the migration has not been applied against production.
