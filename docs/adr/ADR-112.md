# ADR-112 — Project glossary is a column, build is an entity (11.08.2026)

**Context**: T-125 and T-126, the last two MUSTs of Phase 13. The brief phrases them as: "`Glossary` stays where it is for now but should work globally for posts. I need to be able to set up a local glossary scoped to a project" and "Tagging builds and versions. And, accordingly, a proper tag system."

**Decision 1 (T-125): `GlossaryTerm.ProjectId` — a nullable column, `null` = a global term.** Exactly the same move as `Draft.ProjectId` (ADR-102): a project term and a global term have the same shape — word, description, synonyms, image, language — and differ only in the one question of "where does it apply." A separate entity would mean a second table with the same nine columns and no way to move a term from a project into the shared glossary without re-entering it.

**What a document sees**: global terms **plus** terms of its own project. Not "or": "Unity" is global, "ferry" is specific to one game, and an article about that game needs both. A project's term never leaks into a document outside it — otherwise "local" wouldn't mean anything.

**Order on a clash**: if the same term is defined both globally and in a project, the project one wins. A narrower scope is a more precise definition — that's exactly why a local glossary is set up in the first place.

**Decision 2 (T-126): a build is its own entity, `Build`, not a tag.** The brief's "proper tag system" describes the desired result, not the mechanism. A version has a number, a release date, notes, and a composition; a flat `Draft.Tags` string stores none of those fields and can't answer "what went into 0.4.2" except by a full scan with string parsing. This is the same boundary ADR-106 drew for the task: a set of fields is an entity, free text is a tag.

**The link to a task is the `GameTask.BuildId` column; the link to a document is `EntityLink`.** The asymmetry is deliberate and follows from the questions being asked: a task ships **in one** build ("which one?"), and that field needs to be filterable and aggregatable — that's a column, like `SprintId`. A document, on the other hand, relates to a build loosely and not necessarily in one direction: the version's changelog, a devlog about it, a game-design document it implements. Adding a column on `Draft` for this would mean growing an entity that already has about thirty-five fields and a recorded tech-debt item to split it (ADR-102).

**A changelog is generated as a document, not as text.** `POST /api/builds/{id}/changelog` creates a real document of type `changelog` inside the project, listing the build's closed tasks — and from there it lives an ordinary document's life: it's edited, translated, published, versioned. Returning a copy-paste string instead would mean building a generator whose output has nowhere to live.

**What is deliberately not done**: a build isn't linked to git, doesn't read repository tags, and knows nothing about builds in the CI sense. It's a version record the author maintains — and pretending it's a CI integration that doesn't exist would be worse than honestly being a record.
