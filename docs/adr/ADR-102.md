# ADR-102 — Document type is a column on `Draft`, not a new entity (10.08.2026)

**Context**: the brief introduces documents of different types — post, game design, script, changelog — and "post" becomes one of many. The straightforward move is a new `Document` entity, into which `Draft` migrates over time.

**Decision: `Draft.DocumentType` (string, default `post`) and `Draft.ProjectId` (`Guid?`).** Existing rows become `post` without a data migration: the default value is exactly the truth about them. `ProjectId` is a plain scalar with no FK or nav property, exactly like `Draft.FolderId` (`Entities.cs:275`) and for the same recorded reason.

**There's already a precedent in the code**: `IsTemplate` (`Entities.cs:285`) — a post template was built exactly this way, as a flag on `Draft`, and Marty's wording in `docs/BACKLOG.md` about "the cheapest honest form" referred to exactly that choice. Document type is a generalization of the same move, not a new technique.

**Why not a separate entity**: `Draft` isn't "a post", it's "a TipTap document with autosave, version history, translations, tags, and a folder." Everything listed is needed by a game-design document verbatim. A new entity would mean duplicating `DraftTranslation`, `DraftRevision`, autosave with the ADR-065/066 guards, and optimistic concurrency — that is, repeating the most expensive and most burned part of the codebase (incident of 29.07 — `T-060`).

**The cost is accepted explicitly**: `Draft` grows to roughly 35 fields, and the publishing fields (`BlogSlug`, `IsBlogPublished`, `WatermarkText`, `LastTelegram*` and others) mean nothing for a document of type `design`. This is tech debt — "extract the publishing fields into `DraftPublishing`" — logged as a line in `docs/BACKLOG.md`, not a reason to build a second hierarchy now: today, zeros in unused columns cost less than a join on every document read.

**Added during implementation (10.08.2026, T-120):**

**Not every document type gets published.** `DocumentTypes.IsPublishable` is a pure function in Core: `post` and `changelog` yes, `design`/`script`/`plot`/`note` no. A game-design document or a plot outline is working material, and sending one to a channel is never intentional; the honest answer to that request is a refusal, not a post. The check sits on the shared path `PostEndpoints.PublishToTargetAsync(Draft, …)`, meaning it applies to every network at once, not to whichever one someone happened to remember. Existing content's behavior doesn't change: everything written before types existed is `post`.

**The column's default must be declared in the model, not in the property initializer.** When generating the migration, EF **does not read** `= DocumentTypes.Post` in the field declaration and generated `defaultValue: ""` — meaning an `ALTER TABLE ADD COLUMN` would have filled every existing draft with an empty string. An empty type passes neither `IsKnown` nor `IsPublishable`, so **every already-written post would have refused to publish on the very next deploy**. Fixed with `builder.Entity<Draft>().Property(d => d.DocumentType).HasDefaultValue(DocumentTypes.Post)` in `OnModelCreating` — in the model, not by hand-editing the migration file, so that regenerating it doesn't silently lose the default. The first migration was deleted and regenerated; the `A_null_type_still_publishes` test guards this boundary.
