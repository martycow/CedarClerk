# ADR-236 — Analytics is PostHog, recorded where it happens, behind a consent nobody assumed (01.09.2026)

**Context.** T-153 had been stalled on the provider since 13.08.2026. ADR-126 had already done the part that could be done without one: `docs/product/METRICS.md` fixes the event names, and clause 3 established that activation is derivable retroactively from `AspNetUsers.CreatedAt` × `PublishJob`/`BlogPublishedAt`, so nothing was being lost by waiting. What was still open was the choice itself, which is not a script include: it decides what `/privacy` has to say.

Two facts narrowed it. **Seven of the nine dictionary events already exist in the database**, so the provider is not where product metrics come from — it is where the funnel before an account exists (`signup_started`, traffic source) and a live dashboard come from. And **blog readers are out of scope**: their statistics are already ours and cookie-free (`VisitorHash` with a salt, ADR-016; `BlogViewGeoDaily` as an aggregate), so no third-party script goes on `*.cedarclerk.app` and the volume the provider ever sees is the landing plus the app.

**Decision.**

1. **The provider is PostHog, EU cloud.** Free to a million events a month, which this install will not approach, and it computes funnels, cohorts and retention directly — three of the four `BUSINESS.md` §4 metrics are those shapes. Umami and Plausible were the cookie-free alternatives and were not chosen; Cloudflare Web Analytics cannot transport a custom event at all, so it could not carry the METRICS dictionary. Self-hosting was refused outright: the droplet is 1 vCPU / 2 GB **with no swap**, and standing a ClickHouse or a second Postgres next to the app trades a few dollars for an out-of-memory kill that takes the service down.

2. **Events are recorded at the point they happen, not swept out of the database afterwards.** A batch job over `Payment`/`PublishJob`/`CreditEntry` was the alternative and would have bought retroactive history through PostHog's `historical_migration`; it was not taken. The eight call sites are visible where the thing they describe occurs, which is the property that keeps them from drifting away from it.

3. **`ProductAnalytics` is the only way an event reaches the provider, and it never throws.** It sits inside billing, publishing and registration, and a metric is not worth failing a payment over. It is a no-op when unconfigured — a local run and a self-hosted install carry no client at all, because the provider is registered only when `Cedar:Analytics:Enabled` and a project key are both present.

4. **The names live in `Consts.Analytics.Events`.** ADR-126 clause 2 made them a contract; a contract spread across eight string literals is one a rename silently breaks.

5. **`ai_used` is recorded on refusal as well as on success.** Every AI call funnels through `ChargeAiOrRefuseAsync`, so the event carries `outcome` — `charged`, `no_credits`, `daily_limit`. "Asked and was turned away" is the half of AI spend that says whether the limits are set where they should be.

6. **No third party sees anything that identifies a person.** The distinct id is the account id, an opaque key; email and display name are never sent, and post content never is. Owner, never payer, on a Stars purchase — a transferable invoice link means the two can differ (T-359 finding 7).

7. **Consent is asked, and it is the maintainer's deliberate decision to ask it.** ADR-126 clause 4 permitted a consent banner only that way, and this is that decision: PostHog's default cookie is kept, and a banner with Accept and Decline stands in front of it. **Nothing from the provider loads until the answer is yes** — the SPA imports the library dynamically and the landing appends the script tag only after an accept, so an unasked visitor has no provider code running at all. That is stronger than initialising it opted-out, and it is what makes the banner an honest question. The answer lives in one `cedar_consent` cookie read by both surfaces, so answering on either settles both.

8. **The landing decides in the browser, not on the server.** It is served `Cache-Control: public, max-age=300`, so a server-rendered banner would hand one visitor's choice to the next out of the edge cache. The markup ships with the banner hidden and a small inline script reveals it or loads the provider — the document stays identical for everyone and still correct for each of them.

9. **The project key rides `/api/health`.** It is public by construction (it ships inside the page script), and the frontend already calls that endpoint at startup for the version. Building it into the bundle instead would leave a self-hosted install unable to turn it off.

**Consequence.** `/privacy` gains a section naming PostHog, the EU region, the cookie and its year, and states the two exclusions explicitly: post content is never sent, and blog readers are never counted this way. That section is part of what goes to the lawyer under the `BUSINESS.md` §2 gate, not a separate errand. The banner is a new global UI element on both surfaces and is inventoried as such.

What this does **not** buy: history before the day it ships. Clause 2 chose call sites over a backfill, so `signup_started` and traffic source begin now, exactly as METRICS.md already warned for the events it marks non-mineable. The four §4 metrics remain derivable from the database regardless — that was ADR-126 clause 3 and it is unaffected by the provider being here.
