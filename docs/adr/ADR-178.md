# ADR-178 — The server-rendered pages are served the faces they name, from stable URLs (22.08.2026)

**Context.** ADR-143 kept the four faces self-hosted and refused the mirror's Google `@import`, and
its consequence section named the hole it left open: *"The server-rendered surfaces name a face they
do not serve."* `--font-sans` and `--font-serif` reach `DesignTokens.generated.cs`, `BlogEndpoints`
and `LandingEndpoints` paint with them, and `@fontsource` puts its `@font-face` rules in the Angular
bundle only — which the blog host never loads. A reader has been getting `system-ui` and Georgia
under names that say *Source Sans 3* and *Literata* ever since. ADR-143 also named why the obvious
repair fails: the build content-hashes the files
(`publish/wwwroot/media/caveat-latin-500-normal-XNJ4DF4N.woff2`), so a hand-written URL dies at the
next build.

Porting the blog to Cedar Bench turns that from a divergence into a blocker. Half of what the kit is
made of is type: Vollkorn cut into every sign tile, stamp and title, Literata carrying the reading
column at 17/1.75. A blog on the bench palette in `system-ui` is the colour half of a port, and
`docs/design/UI-V2-PLAN.md` records what a half-port of the blog costs — it is the surface that fell
a shade behind the app and stayed there until the generator existed.

The hash is the whole problem, and it belongs to one pipeline: the Angular bundler hashes what it
bundles. `angular.json` already copies `public/**/*` verbatim into the output, unhashed — that is how
`/assets/forest/tex-paper.svg` is reachable, on the blog host included, because `UseStaticFiles` runs
before the blog's `MapWhen` and serves `wwwroot` for every host.

**Decision.**

1. **The woff2 files the server-rendered pages need are copied into the build output at
   `assets/fonts/`, by `angular.json` asset entries reading `node_modules/@fontsource/*/files`.**
   Copied, not committed: the packages are already a dependency, the version already pinned in
   `package.json`, and a binary in the repo would be the second copy of a file `npm` owns. Copied
   verbatim, so the names are stable and a URL written by hand survives every build — which is the
   one property ADR-143 said a fix would need.

2. **The `@font-face` rules live in `CedarClerk.Core.DesignTokens.FontFaces`, beside the tokens, and
   every server-rendered page inlines them.** The blog, the landing page and the single-file export
   name the faces through the same generated file; they get the faces from it too. It is a plain
   constant rather than generated output: it declares URLs the build guarantees, not values read out
   of `styles.scss`, and generating it would mean reading the bundler's manifest at commit time.

3. **Each rule carries an explicit `unicode-range`.** `@fontsource`'s per-subset stylesheets
   (`latin-400.css`, `cyrillic-400.css`) carry none — only its `index.css` does — so two subsets of
   one family and weight declared without one do not compose: the later rule shadows the earlier for
   the whole range, and every glyph missing from the surviving subset falls through to the next
   family in the stack. The ranges are taken from the package's own `index.css`, which is where the
   values are maintained.

4. **The set served is narrower than the app's sixteen, and the difference is stated rather than
   inherited.** Vollkorn 600/700, Source Sans 3 400/600, Literata 400/600 — latin and cyrillic each,
   twelve files, about 158 KB on disk and far less on the wire, since a range a page has no glyphs in
   is never fetched. Source Sans 3 700 is not served: the rail's lettering is Vollkorn, and nothing
   the server renders asks for a heavy sans. Caveat is not served at all — the margin note is the one
   place it appears in the kit and no server-rendered page has one. Both are additions of one line if
   a call site arrives.

**Rejected.** *Committing the woff2 into `public/assets/fonts/`.* Works, and duplicates 158 KB of a
package's own files into git, where the next `@fontsource` bump silently leaves them behind. *Linking
the app host's stylesheet from the blog.* The bundle's name is hashed, it carries the whole app's CSS
to read one post, and it puts a second origin on the critical path of a page that has one.
*Generating the `@font-face` block from the build manifest.* It would track the hashed names
correctly and make the blog's type depend on a build artefact being read at the right moment; an
unhashed copy has no moment to get wrong. *Taking ADR-143's other exit and importing from Google.*
Its clause 3 is unchanged and this decision does not reopen it — one origin, no visitor IP handed to
a third party on a public page.

**Consequence.** The blog and the landing page render in the product's own faces, and ADR-143's open
consequence is closed for the server surfaces. The app is untouched: its sixteen `@fontsource`
imports still feed the bundle, and it now ships twelve of those files a second time, unhashed, for a
host that could not read the hashed ones. That duplication is on disk only — the two hosts are
different origins and would not have shared a cache entry in any case.

One thing this decision *found* and does not fix: the app's own imports have the clause 3 problem.
`styles.scss` `@use`s each face's `latin-*.css` and then its `cyrillic-*.css`, neither of which
carries a `unicode-range`, so the cyrillic rule shadows the latin one for the whole range and Latin
text in the app is drawn by whatever the fallback stack offers. It is the same defect this clause
avoids on the server side, it is one line per import to close, and it is on the board rather than in
this decision, because the app's type is not what this decision is about.
