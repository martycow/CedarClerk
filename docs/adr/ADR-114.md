# ADR-114 — Production moved to DigitalOcean, and not everything moved with it (11.08.2026)

**Context**: production had lived on a Raspberry Pi 4 at Marty's home for two months. Three pressures built up at once: disk space (27 GB, of which 6 free — the 10.08 deploy failed with zero space left, because of 13 GB of cloudflared logs), the end of Raspbian Bullseye security support ≈August 2026 (`T-070`), and the fact that a public SaaS depended on home electricity and a home internet connection. The move checklist was written on 11.08 from the machine's actual state, and executed in full by Marty that same day.

**Decision: a droplet, not another Pi and not a PaaS.** `cedarclerk-periwinkle`, fra1, Ubuntu 24.04.4 LTS, x86_64, 1 vCPU / 2 GB, 48 GB disk. Everything that was on the Pi was reproduced one-to-one: the same paths (`~/cedarclerk/app`, `~/cedarclerk/data`), the same unit with the same `ExecStart`, the same drop-ins with secrets, the same Cloudflare tunnel on `127.0.0.1:8080`, the same single Kestrel process serving two hosts. The application didn't notice the platform change.

**Why this turned out to be copying rather than porting**: the server is published **framework-dependent, with no RID** — portable IL. That's exactly why armhf → x86_64 required neither a rebuild for a different architecture nor a code change. This property didn't exist for the sake of the move — it existed because the Pi builds nothing — and it paid off on the day it was needed.

**Decision: `raspberrypi.local` is no longer production's address.** `Scripts/deploy.ps1` now targets `martycow@deploy.mooexe.dev` by default; in the rules, `ARCHITECTURE.md`, `CLAUDE.md`, `AGENTS.md`, `DESKTOP.md` and the Pi scripts it's replaced with the server/droplet. **`CHANGELOG.md` and this file were not edited**: they record how things were at the time, and rewriting history to match today's machine would mean losing why those decisions were made the way they were.

**Decision (and this is the most honest part): backups got worse, and that's recorded, not papered over.** On the Pi there was a nightly `sqlite3 .backup` + rsync to a microSD, 14 dated copies. The droplet has neither a crontab nor `~/bin` — the script didn't move over. In its place, DigitalOcean's paid **weekly droplet backup** is enabled. This is not an equivalent, and the difference is exactly in three places:

1. **The loss window grew from a day to a week.** A failure the day before a snapshot costs six days of posts, media and accounts.
2. **Restore is all-or-nothing.** The image returns the whole machine; there's physically nothing to "restore yesterday's database while keeping today's code" with.
3. **The copy lives in the same account as the original.** An accidental destroy, non-payment, or a hijacked login takes it along with the droplet. A card in a different device didn't have this property — and it's been lost, not gained.

None of the three points makes the situation an emergency, and none is a reason to postpone: `sqlite3` is already installed on the droplet, a nightly cron is ten lines, exporting outside the account is `T-071`, raised to High. **Until this is done, the phrase "the data is backed up" is only true in the weekly, single-account, whole-machine sense** — and any note about backups must say exactly which sense it means.

**Found during the review, not done**: the unit is `disabled`. DigitalOcean reboots droplets for host maintenance, and after a reboot the site won't come back up on its own (`T-143`). Fixed with a single command, but it requires the sudo password, which automation doesn't have by design of the permissions: `NOPASSWD` is deliberately scoped to exactly `systemctl start|stop|restart cedarclerk`.

**What the move closed by itself**: `T-070` (migrating the Pi's OS for arm64 and a newer .NET) — the new host is already a 64-bit supported Ubuntu; the disk shortage (45 GB free instead of 6); and the coordination with the Freenove projects on the same machine.
