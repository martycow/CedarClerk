# ADR-110 — "Where the post went" is read from the publish queue, not a new table (11.08.2026)

**Context**: Marty published a 25-part thread to X and reported two things — no progress was visible, and he couldn't find links to the created posts anywhere. A check against the production database: all 25 parts `Succeeded`, each with a `PublicUrl` recorded, the whole thread went out in **17 seconds**. So the backend did its job completely, and both symptoms were in the frontend.

**Three defects were found, and none of them is about publishing itself:**

1. **Progress tracking wasn't updating at all.** `awaitJobs` accepts an `onProgress` callback that redraws the part chips on every poll — and the Telegram path passes it, but the short-network path (X, Bluesky) **never did**. The chips were drawn once, all "pending," and flipped over all at once at the end. The `reflectJobs` helper could also only address `tg-<lang>` rows, so there was nothing to pass the callback into anyway — now it addresses rows by step id and works for any network.
2. **The "7/25" counter was invisible in both themes.** `.pr-count` was colored with `--alt`, which is a **surface** token, not a text one — #EFECE4 on #FCFBF8 in light mode, #2F2C23 on #2B2820 in dark mode. The automated contrast check didn't catch this because it checks the declared role pairs, not arbitrary combinations in CSS.
3. **Links disappeared.** The result toast lives **inside** the export dialog, the progress dialog sits on top of it, and the toast removed itself after 10 seconds. So watching the publish through to the end and closing the checklist meant seeing nothing. Ten seconds isn't enough to read a link — it's barely enough to notice it.

**Decision: "where the published content lives" is read from `PublishJobs`, not a new entity.** Every queue row already stores the `PublicUrl` the network returned. Adding a "published posts" table alongside it would mean writing the same thing a second time and ending up with two sources of truth that diverge at the first error. The new `GET /api/publish/published` returns one row per place a version went out to, and the Posts Manager reads it — the one place that survives closing the editor.

**Only part 0.** A thread's public address is its head; 25 links to a single thread are not a list of posts, they're a list of replies. `PartCount` rides alongside it so the UI can say "a thread of 25 messages."

**The newest entry wins** for each (draft, network, language, account) pair: from a reader's perspective a republish replaces the post, so five attempts would otherwise give five links to the same tab.

**A success with no public address doesn't make the list** — a Telegram channel with no `@username` was published but can't offer a link, and a row with an empty `href` would be a dead button. This is exactly the case ADR-065 already found reads as "never published"; here it reads as "published, no link."

**A lesson worth more than the three fixes**: publishing had no place at all that survived closing the modal. Progress, result, and links only lived inside that dialog — and the dialog closes. Value created by an action must have an address it can be found at the next day.
