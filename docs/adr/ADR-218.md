# ADR-218 — The reference board is one server-owned surface, last writer wins, and the socket is SignalR (27.08.2026)

**Context.** `T-129` (a moodboard gallery) and `T-155` (a Miro-like whiteboard) had both stood on the board with a note that they were probably one thing and that two must not be built. They are one thing. It is also the module's first screen where two people are on the same pixels at the same moment, and the application has no precedent for that: everything shipped so far is a request and a response, with the durable `PublishJob` queue as the only asynchrony. The board therefore forces a realtime model to be chosen rather than inherited.

**Decision.**

1. **One surface: a board of items.** `CanvasBoard` per project, `CanvasItem` on it, four kinds — image, note, frame, link. A moodboard is a board whose items happen to be images, which is why `T-129` does not survive as a screen of its own.

2. **Geometry is columns; kind-specific data is one JSON payload.** `X Y Width Height Rotation` are `double` columns and `Z` is an `int`, because a drag writes numbers and render order has to be sortable in SQL (`ORDER BY Z, CreatedAt, Id` — total and stable; ties under concurrency are harmless). A frame's title and an image's natural size are not comparable across kinds, so they live in one `Payload` string that is replaced whole and never patched field by field. An unknown property in a payload is rejected rather than ignored: a payload that silently loses a field is worse than a refusal.

3. **The server is the source of truth and the conflict rule is last-writer-wins.** Every write from a permitted writer is accepted — the server bumps `Version`, stamps `UpdatedAt`, and broadcasts the result to the board's group including the sender, which needs the authoritative version for its optimistic row. **The server never refuses a write for being stale.** `Version` is not optimistic locking; it exists so a client can discard an echo older than the state it already holds, whether from out-of-order delivery or from its own optimism. Rejected: version-checked writes, because a refusal arrives while the user is still holding the mouse and there is nothing honest to do with it; and OT or a CRDT, because the price is a library and a new class of bug, and what it buys back is a keystroke when two people type in one sticky note in the same second.

4. **SignalR, not raw WebSockets and not polling.** Polling cannot express "someone else is dragging this right now" at all, and a cursor at poll rate is either visibly late or a request every 100 ms per person against one vCPU. Raw WebSockets would mean hand-writing the reconnect loop, the group fan-out, the transport fallback and an auth handshake — which is precisely what SignalR already is: `withAutomaticReconnect`, `Clients.Group`, its own negotiation, and the Identity cookie this app issues anyway, since a hub is an ordinary `[Authorize]` endpoint. It also costs no dependency: the server half is in the shared framework and `@microsoft/signalr` is already in `package.json`.

5. **What crosses the socket and what reaches the disk are different lists.** `DragItems` broadcasts at pointer rate and persists nothing; the pointer-up sends one `UpdateItems` that does. Writing every frame is roughly twenty writes a second per user against SQLite on a 1 vCPU / 2 GB droplet with no swap. Cursors, selection and presence are held in memory in the hub and are never rows at all: they are meaningless one second after a connection drops, and a row per cursor move would be the heaviest write in the application.

6. **Reconnect is a fresh `Join`, and the snapshot replaces local state.** There is no delta log, no replay and no tombstone: a late joiner and a reconnecting client take the same full snapshot, which is also why an item is hard-deleted. Optimistic writes that never landed roll back out of that same snapshot — one reconciliation path rather than two. Nothing is persisted on disconnect, because the last `UpdateItems` is already the truth.

7. **The hub is the only write path for items; REST owns boards and reads.** Two write paths would mean two validators and two broadcast points. `GET /api/canvas/{boardId}` returns the same snapshot `Join` does and `/export` hands it back as a file, so a board is never hostage to a socket.

8. **The viewport is per person.** Pan and zoom live in `localStorage` and are never sent anywhere; a shared viewport — "follow me" — is a different feature with a different contract.

**Consequence.** Presence lives in one process's memory, so **this is the one part of the application that does not scale out by starting a second instance**: a second Kestrel would need a backplane (Redis) before it could serve a board at all, and production is deliberately a single process behind a single tunnel. A hub invocation does not run the request pipeline, so the hub's injected scope carries no tenant and must open the project owner's scope per call (ADR-217) — an added row with no `OwnerId` throws rather than leaking, which is a behaviour to rely on rather than to remember. The accepted losses are stated rather than designed around: two people dragging one item is self-correcting, two people typing in one note lose a keystroke, and a board four people edit for an hour is still one row per item with no history behind it.
