# ADR-226 — CTA buttons are a send setting on the post, never a node in the document (29.08.2026)

**Context.** Bot API 10.3 (Telegram.Bot 22.10.3, Wave 2) lets a rich message carry a native button row — `InputRichBlockButtons` — and every competitor's "add a button under the post" lives in their composer. The obvious build here would be a TipTap `buttons` node. But the architecture's core rule is one CedarJson rendered by every renderer: a node in the document is a promise to the blog renderer, the Steam and itch renderers, the micro-thread splitter and the `.cedar` export, each of which would have to either draw a URL-button row it has no native form for or carry an explicit skip — and the renderer invariants demand a unit test per node per renderer either way. A button row is not content. It is Telegram furniture.

**Decision.** The buttons live on the post: `Draft.CtaButtonsJson` — a JSON array of `{ "text", "url" }`, at most 3, text ≤ 32 characters (Telegram's own cap), http(s) URLs only, normalized and validated on save (`DraftEndpoints.NormalizeCtaButtons`, public and static so a unit test pins the wire contract; null means no buttons). They are edited in the export modal's Telegram panel, not the editor sheet, and appended **at the wire level only**: `TelegramPublishTarget` adds one `InputRichBlockButtons` after the rendered blocks of the **last part** of the publication — the same close-the-post placement as the signature. The stored document, the blog, `.cedar` and every other network never see them.

**Consequence.** CedarJson's schema is untouched, no renderer gains a node it cannot honestly draw, and clearing the buttons is a PATCH with an empty list rather than a document edit. The stated costs: the editor's sheet cannot preview the buttons (the export modal is where they exist), and if another network ever grows native buttons it gets its own mapping from the same stored JSON, not a shared abstraction invented today.
