# ADR-186 — The bench remembers which project is open, and the tile is a real switcher (22.08.2026)

**Context.** ADR-139 gave the rail a project tile and the wall a Board hook, and both of them are
honest about a gap the port could not close: nothing in the app knows which project you are working
on unless the URL says so.

`bench-shell.component.ts` states it twice, in comments written when the code was. The tile: *the
switcher is account-scoped wherever the project is unknown, which is every screen but
`/projects/:id` — `DraftMeta` carries no `projectId`, so a draft, a post or a library asset cannot
say which project it belongs to.* The Board hook: *without a project in the URL the board has no
owner to open, so the hook lands on the hub.*

Both fall out the same way in use, and both are on Marty's list. The tile reads **All Projects** on
nine screens out of eleven, which is not a switcher — it is a sign, and pressing it goes to a list.
The Board hook goes to the hub, so the wall has a station labelled *Board* that never once opens a
board.

The missing piece is not `projectId` on `DraftMeta`. It is that "which project" is a property of the
**session**, not of the row on screen: you open a project and then work on things belonging to it,
and the one place that answer is currently held is the address bar, which throws it away the moment
you navigate to `/drafts`.

**Decision.**

1. **`CurrentProjectService` holds the open project and outlives the URL.** Id and name, written
   whenever a `/projects/:id` route resolves, persisted in `localStorage['cedar-project']` so it
   survives a reload, and cleared when the session ends — a remembered project belongs to the
   account that opened it. It is validated against the project list on load: an id that no longer
   exists is forgotten rather than turned into a link that 404s.

2. **The tile is a switcher.** `RailHeader` takes a project list and draws a menu under the tile;
   each entry is an `<a routerLink>`, so a middle click still opens a project in a tab — the reason
   ADR-139 made the tile an anchor is kept where it actually matters, on the destinations. The last
   entry is the hub, which is where **All Projects** used to send you. With no list handed in, the
   tile stays exactly the plain link it is today.

   This is not the menu ADR-183 removed from this component. That one was *overflow* — the rare rest,
   which belongs where screens are chosen. This is the switcher `RailHeader.prompt.md` names in its
   own description of the rail, and a switcher that cannot switch is the defect being fixed.

3. **The Board hook opens the remembered board.** `/projects/<current>/tasks` when a project is
   known from the URL or from memory, the hub only when none has ever been opened — which is true
   exactly once per account, on the screen where you pick one.

**Rejected.** *Putting `projectId` on `DraftMeta` and every other row.* It is a real feature and it
is `T-241`'s neighbourhood, but it answers a different question — *what does this row belong to* —
and it would still leave the tile with nothing to say on `/settings`. *Deriving the project from the
last visited URL in the router history.* The router's history is not readable across a reload, and
"last URL that happened to contain a project" is a different fact from "the project I am working
on". *A project selector on every page that needs one.* Eleven copies of one piece of state, which
is the shape `.claude/rules/ui-changes.md` rule 1 exists to refuse.

**Consequence.** The rail says which project you are in on every screen, not on two, and the wall's
Board hook opens a board. The service is one small piece of session state with one writer, so the
question *which project* now has an answer that a future feature — a draft filtered by project, a
default project for a new document — can read instead of re-deriving. `DraftMeta` is unchanged and
this decision does not pre-empt what `T-241` does about it.
