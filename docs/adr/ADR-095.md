# ADR-095 — Connections live only in Settings → Integrations (07.08.2026)

**Context**: Marty's request. The "Integrations" panel has existed since I12, but knows only three things: whether a Telegram account is linked, whether the bot is alive, and how many channels are connected — with a "manage in the editor" link. All the actual connecting grew up inside the export window instead: connecting a Telegram channel (N4/FI2.9 — "the moment you need an account is the moment you publish"), Bluesky login via app password (T-089), the X OAuth button (T-110). Across three connectors, rule N4 stopped working: the export window became half an account-settings window, and the panel that's supposed to own integrations by name went stale and showed neither Bluesky nor X.

**Decision: connecting an account is a settings matter, not a publishing step.** Settings → Integrations becomes the only place where an account is connected and disconnected: Telegram account, bot, Telegram channels (list of known chats, manual @name/id entry, disconnecting), Bluesky (handle + app password), X (OAuth), and the list of planned networks. The export window only **selects** from what's already connected, and where there's nothing connected shows a "Connect →" link into Settings, not a form.

**Why N4 is retired rather than refined**: the rule was born when there was one network and "connect" meant "paste in the channel id." With three different flows (bot-membership discovery / app password / a redirect to x.com and back), the publish window stopped being a place you can leave for a third-party site and return to. The OAuth redirect is the argument itself: the whole page navigates away, the draft is left behind, and there is nowhere to return to the modal from.

**Consequence**: `GET /api/targets/x/callback` now returns the browser to `/settings?tab=account&x=connected` (it was `/?x=connected`, and no screen read that parameter — connecting looked like "nothing happened"). An error is `?x=error` at the same place.
