# ADR-161 — One chart needs a metric control, one axis needs a shared window, and a leaf must not promise a line

**Context.** ADR-148 fixed where the metrics screen lives (a tab body in the Posts Manager) and ADR-149 fixed its two controls (the legend is the filter; the 7…180-day slider survives, the kit's period segments do not). Neither answers what happens when the port collapses `stats.component`'s **four** single-metric charts into the one `app-growth-chart` that Stage 4 built. Three questions fall out of that collapse, and each has a way to get it wrong that reads as a working screen:

- Four charts drew Subscribers, Views, Likes and Comments at once. One chart draws one quantity, so the metric becomes a *selection* that did not exist before, and it needs a home and a material.
- `GrowthChartComponent` takes `series[].points` as parallel arrays over one x-axis, and its own point count is `min()` over them. The app's sources do not share an axis: `GET /api/blog/stats` and `GET /api/channels/{id}/stats` each return the most recent `days` **rows**, a channel connected last week has seven of them, and the blog's on-demand snapshot lands at a different hour from the nightly job's.
- `openTail` is `input.required` on that component. There is no default to fall back to, so this screen has to answer it in a sentence that is true.

The kit also draws two leaves — `X` and `Bluesky`, the second one `dried` and reading `не подключён` — and a rail-level `Выгрузить CSV`. ADR-148 already moved the export down and noted it does not exist; the leaves have not been ruled on.

**Decision.**

1. **The metric is a control on the panel's header, not a strip on the paper.** `app-index-tabs` is the app's only tile strip and its jurisdiction is exactly this — it switches what a panel *shows* and never navigates (ADR-139/`IndexTabs.prompt.md`) — so the metric strip and the chart/table strip are both `[actions]` on the chart `ShelfPanel`'s header. That is also where they are made of the right material: an index tile is a painted wooden tile on a shelf edge, and the filter strip above the chart is paper. The strip that selects the *query* (sources, period) is paper because it is a form; the strips that select the *view* are chrome because they are shelf furniture.

2. **The x-axis is the window in which every drawn line has a reading, and a gap holds the last reading rather than dropping to zero.** Points are keyed by calendar day in the display zone (ADR-115's `formatInZone`, so the key and the axis label are the same day) and the window runs from the **latest first reading among the selected sources** to the latest reading overall. Inside that window a source with no snapshot for a day carries its previous value forward.

   Both halves are load-bearing. Starting earlier would need a value for a source before it had one, and the only available inventions are a zero — drawing a launch ramp that never happened — or the first value stretched backwards, which draws a flat history that was never measured. Carrying forward inside the window invents nothing: the series are cumulative readings, and the last reading is what is known until the next one is taken. The window therefore **moves with the selection**, which is why the panel's counter states it (`N points · d MMM — d MMM`) instead of leaving it to be inferred from the axis.

3. **`openTail` is false on this screen, and the reason is the shape of the data, not the hour of the day.** Every snapshot is a running total read at the moment it was taken — `Draft.ViewCount` to date, the channel's member count now — not a sum over a bucket that has to close. A partial day understates a *bucket*; it cannot understate a *reading*. The day this screen ever plots day-over-day deltas, that answer flips, and this clause is what has to be revisited.

4. **A source that the API cannot draw gets no leaf.** The kit's `dried` state says "no data", and `LeafTag` documents it as "no data or switched off, **never** an error". A dried X leaf would therefore be honest about today and dishonest about tomorrow: it implies a line that appears once X is connected, and no snapshot entity for X or Bluesky exists anywhere in the repository — connecting one changes nothing on this screen. So X and Bluesky are absent until they have data to be absent *of*, and they arrive with the board row that builds their snapshots. `dried` is spent on what it can honestly say: a real source with no readings yet, and a real source that does not track the selected metric (a blog has no subscriber count — ADR-030), each with the reason where the kit put its word.

5. **The fetch fans out on the client; no endpoint is invented, and the fan-out is not the filter.** Blog stats plus every connected channel's stats are requested in parallel for the selected range, and a leaf toggling only changes what is drawn. Two consequences are deliberate: toggling a source costs no request and cannot fail, and blog stats are fetched even when the blog leaf is off, because the audience shelf is blog data (ADR-097) and would otherwise blank out whenever the user looked at a channel. One request per source per range is the honest cost of a client fan-out and the reason the multi-source endpoint keeps its board row.

6. **The second view is the same dataset, not a second one.** The chart/table pair shows the aligned series as a picture and as a table of the same numbers. The kit's second tab is a per-post breakdown; per-post-per-day-per-source numbers do not exist (`Draft.ViewCount` is one lifetime total with no history — the inventory's own note on the activity cell says so), so that tab is a board row, not a rename of this one.

**What was rejected.** *Keeping four charts and stacking them.* It is the one option that needs no metric control, and it is what the task removes: four axes, four scales, and no way to see two sources against each other, which is the entire point of a multi-series chart. *A metric strip on the paper filter row.* It reads as a form control for a query, and it would put wooden index tiles on paper stock; the two materials are the port's way of saying which half of the screen a control belongs to. *Intersecting the window over **all** sources rather than the selected ones.* One channel connected yesterday would then cut every other line back to yesterday, including lines it is not drawn beside. *Zero-filling before a source's first reading.* It draws growth that did not happen, and it is exactly the shape of lie ADR-158 wrote `openTail` to refuse. *Rendering X and Bluesky dried, as the kit does.* Covered above.

**Consequence.** The screen's axis is no longer a fixed period: it is a function of the selection, and a user who adds a young channel will watch the chart's history shorten. That is visible, stated in the panel counter, and reversible by unticking the young source — but it is new behaviour with no precedent elsewhere in the app, and it is the first thing to look at if the chart ever "loses" history.

The Δ7d numbers on the readout cards keep coming from the server's `deltaWeek*` fields, which are computed over the API's own window and not over the aligned one; a readout and the chart can therefore disagree about how far back seven days reaches when a source's snapshots are sparse. Recomputing the delta from the aligned series was rejected as a second source of truth for one number, but the disagreement is real and is recorded here rather than discovered.
