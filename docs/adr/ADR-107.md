# ADR-107 — Asset Manager indexes paths, not copies files (10.08.2026)

**Context**: the code already has `Asset` (`Entities.cs:590`) — an uploaded file living under `CEDAR_DATA_DIR/media`, counted against the plan quota (200 MB on Free) and served publicly via `/media/*`. A game project's asset is a different animal: it weighs gigabytes, lives inside a Unity project folder, changes outside of Cedar Clerk, and must never be publicly accessible.

**Decision: a new entity `AssetEntry` — metadata and a path, no byte copying.** The existing `Asset` stays exactly what it was (post media) and is untouched. Indexing walks the given folder, records name, size, type, modification time, and hash, and stops there.

**Why not reuse `Asset`**: it is defined by the fact that the file lives inside `CEDAR_DATA_DIR` and is served over HTTP. Detaching it from that would mean breaking the plan quota, `/media/*`, and Telegram pre-upload (ADR-088/089) for the sake of an entity with a different lifecycle. Two entities here are cheaper than one with two modes.

**This is exactly why desktop is a MUST, not a MIGHT.** The web version can only show what was uploaded into it; indexing a local game-project folder (`MyGame/Assets`) can only be done by a process running on the same machine. The ordering in `docs/INDIEDEV.md` follows from this: the desktop shell comes before the Asset Manager, because without it the Asset Manager degenerates into the same file upload that already exists.

**What is left undecided and gets resolved during implementation**: previews (where to generate and store them — next to the database, not next to the source), reaction to a disappeared file (mark it, don't delete the row — otherwise an unplugged external drive would wipe the index), and the size of the index on a real Unity folder, which could run into hundreds of thousands of rows and require extension filters on the way in, not on the way out.

**Implemented 10.08.2026 (T-122), with four refinements:**

**1. Indexing is a second, separate capability, off by default.** The endpoint makes the **server** walk **its own** disk on the tenant's request. On a laptop that's exactly the point of the feature; on the Pi, where a single process serves every account, it's a way to list `/etc` and read file names. So a module flag isn't enough: it needs `Cedar:AssetIndex:Enabled`, which only the desktop shell sets for its own single-user process. Production doesn't set it and answers 403 with a clear message; **viewing an already-indexed list still works** — the rows are owner-scoped, and a project indexed on desktop must still open from the web.

**2. One root per project, not `RootPath` on every row.** The initial draft put the root on `AssetEntry`; at tens of thousands of rows that's the same string repeated tens of thousands of times, and "Change folder" in the design replaces the whole root anyway. The root lives on `Project.AssetRootPath`; the row only carries `RelativePath` with a `/` separator.

**3. The walk is hand-written, not `Directory.EnumerateFiles(.., AllDirectories)`.** That method throws on the very first folder it can't open, and throws away everything after it — one folder without permissions would abort the whole scan. The hand-written walk skips such a folder, counts it, and continues; the number of unreadable folders is shown, not swallowed. It also skips, by name, `Library/`, `Temp/`, `node_modules/`, `.git/`, `Intermediate/`, and other engine caches — these hold more files than the project itself and none of them are authored content.

**4. File type is a guess from the extension, and the UI doesn't pretend it's more than that.** Opening every file in a folder of a hundred thousand items is not an option. There is **no** separate "Music" kind, even though the design has a chip for it: telling a music track apart from ambient by extension is impossible, and a chip stuffed with guesswork is worse than no chip at all. Everything audio is one kind, `audio`.

**Verified by running it, not by reading it**: a scan of a real folder (41 files: 26 images, 15 texts, recursion, `.exe` and `Library/` skipped); deleting a file marks the row and **keeps** it; the file's return clears the mark; with the flag off, `POST /index` answers 403 while the list keeps working.

**Extended 10.08.2026 (T-140/T-141): previews, metadata, and links.**

**Thumbnails live under `CEDAR_DATA_DIR/thumbs/`, not next to the source.** The indexed folder belongs to someone else's game project, usually under version control; writing files into it would be both a surprise and a diff. They are generated **on request**, not during the scan: a scan that decodes every image takes minutes for previews almost nobody will look at. The cache is invalidated by the file's `ModifiedAt` — a replaced sprite doesn't show its predecessor. They are served by an authorized, owner-scoped endpoint, **not through `/media/*`**: the public path is for what the author decided to publish, and the index is for what's sitting on their disk.

**Metadata is read only for new and changed files.** Reading a header is cheap, but a hundred thousand times on every rescan is not. `MetadataForModifiedAt` is set even when the header said nothing, otherwise such a file would be reopened forever.

**`.blend` gets its own parser (Marty's request).** It's the main file of many game projects and the one file no graphics library will open. Blender puts an RGBA preview in the `TEST` block inside the file, and `CedarClerk.Core/BlendThumbnail.cs` pulls it out: a 12-byte header, a walk over the blocks, a pixel copy. Only the first megabyte is read — the block sits near the start, while the scene itself can weigh hundreds of megabytes. Rows are stored bottom-up (as OpenGL emits them), so the image is flipped. A compressed `.blend` (zstd since 3.0, gzip before that) **fails honestly**: the preview is in there, but pulling in a decompressor just for a thumbnail isn't worth the cost.

**What counts as "preview possible" is decided by extension, not by kind.** `image` covers both a PNG and a Photoshop document: the first decodes, the second doesn't. The list of allowed extensions is explicit, because the alternative is a grid of broken-image icons wherever the decoder gives up.

**The format set is extended for real game dev (Marty's request).** Engine files (`.unity`, `.prefab`, `.uasset`, `.tscn`), DCC source files (`.blend`, `.ztl`, `.sbsar`, `.aseprite`, `.kra`), DAW projects (`.rpp`, `.flp`, `.als`, `.bank`), shaders and scripts. Engine files stay kind `other`: a Unity scene is not a picture and not a document, and filing it under "text" just to put it somewhere would be a lie of convenience.

**`EntityLink` instead of `TaskLink` — a refinement of ADR-106.** That row was conceived as "task → anything"; as soon as a second pair of entities needed linking, it would have become two tables doing the same job. A task's link is an `EntityLink`, one side of which is the task. The pair is **ordered** (`LinkTargets.Order`) before being written: without a fixed A→B / B→A order, two rows would describe the same fact, and no unique index could tell them apart.

**Links are set by hand, and that's not a shortcut.** An indexed file lives outside Cedar Clerk; no TipTap document can reference it — the editor's images are uploaded media under `/media/`. There's nothing to search for, so "used in" can't be discovered, only asserted. The label reflects that: "Linked documents," not "Used in."

**Verified by running it (T-140/T-141)**: a scan of a fixture folder — PNG dimensions (256×16, 64×32), WAV duration and sample rate (2:14 · 48 kHz), previews from `.blend` and `.blend1` (128×96 and 64×64, JPEG generated), `.fbx` honestly with no thumbnail, `.exe` and `Library/` skipped; linking a document to an asset works, adding it again doesn't create a second row, removing it returns an empty list.

**What is still unverified**: the orientation of a preview from a **real** `.blend`. The flip follows Blender's documented behavior (bottom-up rows), but was verified only on a synthetic file — Marty has Blender, and one real file will settle this.
