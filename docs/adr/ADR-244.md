# ADR-244 — Every account owns its display timezone

**Context.** ADR-115 made every stored and transported instant UTC, but fixed every rendered time to
`America/Los_Angeles`. The content calendar later diverged and used the browser timezone because its
`datetime-local` inputs did. In a multi-tenant product, both rules are wrong for somebody: a fixed
Pacific clock belongs to one author, while the browser clock changes when the same author travels or
opens the account on another machine.

**Decision.** `ApplicationUser.TimeZoneId` is the account's IANA timezone. Existing and newly created
accounts default to `America/Los_Angeles`, preserving every date already shown before this decision.
Settings → Profile owns the field. The API validates the identifier before storing it and returns it
from `/api/auth/me` and the profile write response.

The authenticated app formats every instant through that value. The calendar uses it for day
grouping, labels, drag-to-day and `datetime-local` conversion, so Month, Week and scheduling cannot
disagree. A nonexistent local time in a daylight-saving gap is refused; when the clock repeats an
hour, the earlier matching instant wins. Queue slots keep their existing UTC weekly rule from
ADR-228; changing that recurrence model is not hidden inside a display decision.

The public blog uses the owner's timezone, not the reader's browser. A page is the author's
publication, server-rendered HTML must be complete without JavaScript, and the existing zone label
continues to tell remote readers what its clock means. RSS dates stay RFC 1123/GMT.

`DisplayTime` and the Angular formatter retain Pacific as a fallback for old callers and malformed
stored data. The wire contract from ADR-115 does not change: UTC with `Z` remains mandatory.
