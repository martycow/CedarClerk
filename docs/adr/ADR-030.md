# ADR-030 — `/stats` gains a channel-agnostic "Blog" tab: `BlogStatSnapshot` keyed by `OwnerId`, on-demand first snapshot
**Context**: Marty asked to see stats for the blog/site itself on `/stats`, not just per-Telegram-channel. `ChannelStatSnapshot`'s `ViewCount`/`LikeCount`/`CommentCount` (ADR-025) are already an approximation joined through `ChannelPost` — a blog view isn't intrinsically tied to any channel, and a draft never published to Telegram at all (blog-only) had no stats surface anywhere.
**Decision** (19.07.2026): Added `BlogStatSnapshot` (`OwnerId`, `ViewCount`, `LikeCount`, `CommentCount`, `TakenAt` — no `MemberCount` equivalent, a blog has no "subscriber" concept), migration `AddBlogStatSnapshot`. `SnapshotChannelStatsJob` (same daily 4 AM job, unchanged trigger) now also loops over every distinct `OwnerId` with at least one `IsBlogPublished` draft and writes one row summing **all** of that owner's drafts' `ViewCount`/`Reaction`("like")/`Comment` counts — no `ChannelPost` join, since this is deliberately channel-agnostic. New `GET /api/blog/stats?days=` (`BlogEndpoints.cs`, alongside the existing per-draft blog endpoints) mirrors `GET /api/channels/{id}/stats`'s response shape minus the subscriber fields, reusing `ChannelStatsCalculator.DeltaOverDays` unmodified (already generic over any `(DateTime, int)` series, per ADR-025). Unlike a Telegram channel — which gets an immediate first snapshot at connect-time (`ChannelEndpoints.cs`) — there's no equivalent "connect" moment for the blog, so the new endpoint takes an on-demand snapshot for "today" itself if one doesn't already exist for the requesting owner, rather than leaving the user looking at "—" until the next nightly job run. Frontend (`stats.component.ts`): a `selectedView: 'blog' | 'channel'` signal, a "📄 Blog" tab shown first (before channel tabs, always present even with zero connected channels — the old whole-page "connect a channel first" empty state was removed since Blog stats no longer depend on having any channel), and `metricCards()` branches on view to build 3 cards (no Subscribers) from `BlogStats` instead of 4 from `ChannelStats`. `buildChart()` now takes `(ChannelStatSnapshotDto | BlogStatSnapshotDto)[]` and reads the metric key via a `Record<string, number>` cast, since the two DTOs only partially overlap.
**Consequence**: Same no-backfill caveat as ADR-023/025 — history only starts accumulating from this deploy forward (or from the first on-demand snapshot, whichever the user triggers first by opening the tab). A user who opens the Blog tab before the nightly job has run that day, and is then still active when the 4 AM job runs, ends up with two snapshot rows for the same calendar day (same latent behavior already accepted for channel connects immediately followed by the nightly job — not a new problem introduced here, just the same existing trade-off extended to a second call site). Owners with zero blog-published drafts never get a row and the tab shows the existing per-card "not enough history" empty state, same as a freshly-connected channel with < 2 snapshots.
