# ADR-039 — Folders: a real, named entity with one folder per draft, unlike Tags
**Context**: First item picked from the "Cedar Clerk 0.9.0" idea dump (`docs/BACKLOG.md` idea #19, "Folders / drafts grouping"). No grouping concept existed beyond `Draft.Tags` (flat, multi-valued, unmanaged string — no entity, no rename/delete, just usage-count aggregation for a picker). The backlog entry itself flagged the fork: a real `Folder` entity + `Draft.FolderId` vs. reusing the tag mechanism as a second flat-string field. Asked Marty directly — confirmed folders should behave like a filesystem/mailbox: **at most one folder per draft**, with real management (create/rename/delete), not a lightweight tag-shaped workaround.
**Decision** (26.07.2026): New `Folder` entity (`Id`, `OwnerId`, `Name`, `CreatedAt`) + `Draft.FolderId` (`Guid?`, plain scalar, no nav property/FK constraint — same "no strict FK-only model" convention as `Comment.ParentCommentId`/`DraftId`), migration `AddFolders`. New `FolderEndpoints.cs` (`GET/POST/PUT/DELETE /api/folders`, owner-scoped) — full CRUD, since unlike tags, folders are explicitly named/managed. `GET /api/folders` returns a live draft-count per folder (`GroupBy` over `Drafts.FolderId`), not a separate counter column. New `PUT /api/drafts/{id}/folder` (`DraftEndpoints.cs`) validates the target folder belongs to the same owner (since `FolderId` has no DB-level FK to catch a cross-owner reference). **Deleting a folder unassigns its drafts (`FolderId` → `null`) rather than deleting them** — a folder is purely an organizational label, never a reason to lose content; the confirm dialog states how many drafts will become uncategorized. Frontend: `/drafts` gets a folder-filter dropdown (combines via AND with the existing status-tab/search filters, same composition principle already used there) plus a combined filter-and-manage popover (inline rename, delete-with-confirm, add-new) and a per-row folder-assignment popover in both table and grid views; the editor gets a lighter mirror (assign-only, no rename/delete — that stays on `/drafts`) next to the tag row.
**Consequence**: Bulk folder assignment (moving multiple drafts at once) is explicitly out of scope for v1 — one draft at a time, matching how tag/archive actions already work per-row. The New Draft dialog was deliberately not extended with a folder picker at creation time — folders are assigned after the fact, keeping that dialog's scope unchanged. No dedicated tests added — folder CRUD has no branching logic beyond simple ownership checks and name-length validation, consistent with how other simple CRUD endpoints in this codebase (e.g. `ChannelEndpoints`) aren't unit-tested either. Not yet live-verified in a browser as of writing.
