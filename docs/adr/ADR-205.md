# ADR-205 — Telegram reactions and comments are counted from updates; views are not available at all

**Context.** The Stats board shows Views, Likes and Comments per source, and for a Telegram channel
all three are blog numbers: ADR-025 summed the owner's own `Reaction` and `Comment` rows over every
draft ever sent to that channel, and said in its own consequence that real
`message_reaction_count` reactions "remain unbuilt". Read as "likes on this channel", the number is
wrong in both directions — it counts blog readers who never opened Telegram, and misses everyone who
reacted there.

**Decision.** Three different answers, because the Bot API gives three different amounts of help.

**Views: not available, and the metric is withdrawn for a channel.** A channel post's view counter
does not exist in the Bot API — there is no field on `Message` and no method that returns one. It
exists only in the client protocol, under a user account. Rather than keep showing a blog number
under a Telegram source's name, a Telegram source offers Subscribers, Reactions and Comments, and
the strip says why the fourth is missing.

**Reactions: counted from `message_reaction_count`.** Anonymous aggregates for a channel post, which
is exactly the shape a channel needs. Two conditions Telegram imposes and the code did not meet: the
bot must be an administrator of the chat, and it must **explicitly** name the update in
`allowed_updates` — Telegram leaves both reaction updates out of the default set. The library's event
API (`OnMessage`/`OnUpdate`) exposes no such knob, so the service moves to `StartReceiving` with
`ReceiverOptions.AllowedUpdates` and dispatches messages itself. That is the whole reason the events
are gone; nothing about the polling loop or the one-process-per-token rule changes.

**Comments: counted from the linked discussion group.** A channel's comments are messages in the
group Telegram links to it, each a reply to the post's automatic forward. The bot counts them when it
is a member of that group and stays at zero when it is not, which is a state the screen names rather
than a number it invents.

**The count is what the bot has seen, and it is never fetched.** There is no call that asks Telegram
for a post's current reactions, so an update missed while the service was down is missed for good,
and a post that stopped changing before this ships stays at zero. History starts here — the same
caveat ADR-025 made for its own metrics, and for the same reason.

**Storage.** `ChannelPost` already maps channel, draft and Telegram message id, so the per-post
numbers live there. `ChannelStatSnapshot` gains `TelegramReactionCount` and `TelegramCommentCount`
as new columns rather than redefining `LikeCount`/`CommentCount`: those hold ADR-025's blog
attribution, and changing what a stored column means would put a cliff in the middle of an existing
chart at the exact point the meaning changed.

**Consequence.** A channel's reactions and comments are that channel's. The costs are stated on the
screen rather than discovered: no views for Telegram, no history before this deploy, no comments
without the discussion group, and a number that is a floor rather than a total whenever the service
has been down.
