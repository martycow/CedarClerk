# ADR-241 — X carries pictures, and the matrix says what goes where (02.09.2026)

**Context.** The X target went out as text and a link since T-110 (ADR-093): API v2 had no media
upload under OAuth 2.0 when it was written, so `MaxMediaItems` said 0 and a devlog with four
screenshots arrived on X as a sentence. Bluesky attached its four pictures since 10.08.2026. The
maintainer named it on 02.09.2026 — «твиттер не умеет постить картинки» — and asked for something
the editor never had: one place that says, per destination, what of the document goes out, what is
cut down and what is dropped, before the publish.

**Decision.**

1. **X attaches up to four of the document's pictures** through `POST /2/media/upload`
   (`media_category=tweet_image`, multipart), the ids riding on the tweet's `media.media_ids`. The
   first four local `/media/` references in reading order, like Bluesky; an image over X's 5 MB
   still cap is recompressed by `ImageCompressor`; an external URL is skipped. A thread carries
   them on its first post only. The upload never fails the publish: a refused picture is logged and
   the post goes out without it.
2. **The connect flow asks for `media.write`.** A connection made before this entry lacks the
   scope and X answers 403 to the upload; the target records that on `PublishTarget.LastError`
   (`ErrorMessages.XMediaScopeMissing`), which the Preview rows and the Publish window already
   surface, and clears it on the first upload that succeeds after a reconnect. Nothing else changes
   for such an account — its posts keep going out as text.
3. **A publish matrix, read off the capabilities.** `app-publish-matrix` draws one row per kind of
   content (text, headings, lists, links, pictures, video, audio, tables, code, formulas, quotes)
   and one column per destination — the blog, then Telegram, X, Bluesky, Discord — with each cell
   the network's own answer from `PublishCapabilities`: goes as is, goes with limits (and the
   limit: «up to 4, first post», «as plain text», «teaser or thread, 280 each»), does not go. The
   rows the open document holds are lit with their counts (`documentKinds`, a walk over the TipTap
   JSON). The matrix reads the same record the pre-flight reads, so it cannot promise what a
   target drops. It lives in the editor's Preview tab under the destinations, and in the Publish
   window's *Where to publish* step — the two places the question is asked.

**Consequences.** `MicroPreviewProjection` now attaches pictures to X previews because it reads
`MaxMediaItems`. The X row of `docs/for_user/integrations-setup.md` names the new scope. A picture
that is only a thumbnail-sized external URL still cannot go — X uploads bytes, and the bytes must be
on this server.
