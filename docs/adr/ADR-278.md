# ADR-278 — Sync edits the one message the last send left, and answers with Telegram's own verdict (05.09.2026)

**Context.** A post edited after its Telegram send could only be re-sent, which puts a second
message in the channel; the blog's Update rewrites the page in place. Telegram.Bot 22.10.3's XML
says `EditMessageText(chatId, messageId, …, richMessage:)` edits "text, rich and game messages",
with `richMessage` required when `text` is absent — so a Blocks post is edited with the same
`InputRichMessage` a send carries. There is no `EditRichMessage`, and the 48-hour limit in the Bot
API text applies to business messages, not to a bot's own channel posts. That last fact is an
assumption until checked live on `@testingandfun` with a post older than 48 h; no token exists
where this was written, so the row stays open on that check.

**Decision.**

1. **One method builds the content for both verbs.** `TelegramPublishTarget.PublishAsync` is
   split: `BuildContentAsync` returns the Blocks with the signature, blog link, hashtags and CTA
   row a fresh send would carry (media by file_id via the ADR-089 pre-upload, since new bytes are
   still not accepted inside blocks), and `PublishAsync` sends what it gets. `EditAsync` calls
   the same builder and `EditMessageText`. It is not an `IPublishTarget` member — ADR-078 says a
   target sends, and nothing else — and its client is a parameter so the mapping can be proved
   against a stubbed Bot API.
2. **Single messages only.** `POST /api/posts/{id}/telegram-sync` edits `LastTelegramChatId` +
   `LastTelegramMessageId`. A draft whose last send was a thread — a `PublishJob` for it with
   `ThreadId` set and `RemoteId` equal to that message id — answers 409
   (`ErrorMessages.TelegramThreadNotSyncable`): editing the last of eight parts is not syncing the
   post, and re-splitting into a different number of parts has no honest edit.
3. **Staleness is a timestamp, not a hash.** `Draft.LastTelegramSentAt` (A1's column) is stamped
   by every send and by every successful sync, including one Telegram calls "not modified"; the
   client shows *stale* when `updatedAt` is later. Autosave makes any edit stale, the same rule the
   blog's Update lives with.
4. **The failure surface is Telegram's, mapped once.** Bot down → 503; no send on record → 404;
   thread → 409; "message is not modified" → 200 with `unchanged: true`; "message can't be
   edited" / "message to edit not found" → 409 carrying Telegram's text (`TelegramPostGone`);
   403 → 403; 429 → 429 with the retry hint; everything else as `PublishAsync` maps it. A refusal
   lands on `PublishTarget.LastError` like a failed send, so a broken connection shows before the
   next attempt.

**Rejected.** *Hashing the wire content to decide staleness* — the list path would render every
draft to Blocks to draw a badge. *Wiring sync into Publish-all* — a new send and an edit are
different verbs, and one button doing either depending on state is how a channel gets a duplicate.
*Syncing threads by editing each part* — the parts are recomputed from the document, and a
document that now splits into seven cannot be written over eight messages.

**Consequence.** `DraftMeta` carries `lastTelegramSentAt`. `PublishAsync` is unchanged in
behaviour; its body is now two methods. The live check on a post older than 48 hours is the one
thing this record cannot settle from the machine it was written on.
