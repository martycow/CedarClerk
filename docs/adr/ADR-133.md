# ADR-133 — Onboarding: starter documents with real skeletons, an example project on demand (18.08.2026)

**Context.** T-160: a new account meets emptiness, and activation is the first BUSINESS §4 metric — an empty screen kills it. The base existed: `ProjectTypes` decides each project's starter document (ADR-103), but that document was created **blank**, and a brand-new `/projects` screen offered nothing but a "New project" button pointing at more emptiness. The reference is Codecks: stage templates → a seeded deck.

**Decision.**
1. **Starter documents get real skeletons** — `StarterTemplates` builds a TipTap body per project type (GDD sections for a full game, scope/schedule/ships-or-cut for a jam, the hypothesis questions for a prototype, a changelog scaffold for a released game). Section headings only, with empty paragraphs under them: the skeleton says what goes here, never pretends to be content.
2. **Skeletons follow the document's language** (ru/en, en otherwise) — same rule and same reasoning as the devlog assembler (ADR-132). `CreateProjectRequest` gains an optional `Language`, which also becomes the starter document's `PrimaryLanguage`; the client passes the interface language.
3. **The example project is a button, not a silent seed** — `POST /api/projects/example` creates "Cedar Quest" (a full-game project with a filled GDD skeleton, a current sprint, six tasks across the board's columns, a released 0.1.0 build and a written devlog draft), and the `/projects` empty state offers it beside "New project". Explicit beats automatic: an account seeded without asking starts its life cleaning up someone else's data, and the description says outright that deleting it is fine.
4. The example's material demonstrates the loop that sells the product: tasks → sprint → build → **devlog assembled from them** — the T-158 bridge, pre-walked.

**Consequence.** "Honest empty states on every screen" (the IndieViral manner) stays open as the wider sweep — the planner, board and asset screens already have them; auditing the rest is incremental polish, not this ADR. The example project is ordinary data: deleting it is the ordinary delete path, nothing special survives.
