# ADR-293 — A project stores its modules; its type is a creation preset

**Status**: DONE
**Date**: 2026-09-07
**Relates to**: Q-1 (the fifth audience category), Phase 13a

## Context

A project's type (`Project.Type`) decides everything at once: the starter documents, which navigation sections are available, how endpoints behave. In practice the types differ only in which documents are created at start. Navigation is hardcoded and identical for everyone.

Three problems follow:

1. Types carry no meaning. Blog and Game differ only in their starter documents, although a blog needs no Builds or Dialogues and a game needs no publishing Calendar.
2. A type cannot be changed. A user who picked Blog cannot add tasks without recreating the project.
3. Adding any new section means editing the hardcoded navigation.

## Decision

**A project stores a set of enabled modules, not a type.**

1. A table `ProjectModule (ProjectId, ModuleKey, Enabled)` is added, with a composite PK and cascade delete from `Project`.
2. `Project.Type` is renamed to `Project.CreatedFromPreset` (`RenameColumn`, not a re-create). The field is kept only for the icon and the vocabulary and **does not affect which functionality is available**.
3. The project type in the UI is a creation preset: it expands into a set of `ProjectModule` rows at creation and has no force afterwards.
4. `ModuleKey` is stored as a string; the list of keys lives as an enum in `CedarClerk.Core`. Adding a module needs no migration.
5. The canonical keys: `documents, assets, site, posts, calendar, metrics, tasks, planner, builds, canvas, dialogues`.
6. The `documents` module is always on and cannot be switched off. Code enforces the invariant, not the schema.
7. **Switching a module off deletes no data.** `Enabled = false` means "hidden from navigation". Switching it back on restores everything. It is not a destructive operation and needs no confirmation.
8. A `ProjectModule` row is created for every key when a project is created, including the disabled ones, so the UI can show the full list of toggles.

Existing projects expand during backfill: `Blog` → the Channel column, `Game` → the Game column.

### Boundaries

- Modules are **not** a plan-gating mechanism. Plan quotas stay a separate mechanism (ADR-012/013/014); module availability and plan limits do not intersect.
- This ADR does not touch document types (a separate decision, 13b).
- This ADR does not touch site addressing (a separate decision, 13c).

## Consequences

**Gains**

- A project type gets a real difference (a set of capabilities), not only a set of starters.
- Navigation is built from data; adding a section needs no hardcode edit.
- A user can grow a project to fit without recreating it.
- Modules are queryable from the admin panel and land in the audit log.

**Costs**

- A state that did not exist before: a project with a non-standard module set. Bug reports need to know that set, so the admin panel and diagnostics must show it.
- An empty project now creates 11 rows instead of none.
- Every reader of `Project.Type` needs an audit before the migration.

**Risks**

- Renaming a column without a migration gives `no such column` at runtime (incident 27.07). `SchemaDriftGuardTests` is mandatory in the same commit.
- If production holds a type outside the preset table, the backfill must stop, not default to Empty.

## Alternatives considered

| Option | Why rejected |
|---|---|
| A JSON column `Project.Modules` | Not queryable from the admin panel, not in the audit log, breaks filtering |
| Keep the type as a class and add override flags | Two sources of truth about a section's availability, a direct breach of the anti-desync rule |
| An enum `ModuleKey` in the DB schema | Every new module needs a migration |
| Delete `Project.Type` entirely | Loses the vocabulary and the icon; breaks rollback |
