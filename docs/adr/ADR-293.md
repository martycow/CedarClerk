**Status:** Accepted
**Date:** 2026-09-07
**Relates to:** Q-1 (пятая категория аудитории), Phase 13a

### Context

Сейчас тип проекта (`Project.Type`) определяет всё сразу: набор стартовых документов,
доступность разделов навигации, поведение эндпоинтов. При этом фактическое различие
между типами сводится к тому, какие документы создаются при старте — навигация
захардкожена и одинакова для всех.

Из этого следует три проблемы:

1. Типы не несут смысла. Blog и Game отличаются только заготовками, хотя блогу
   не нужны Builds и Dialogues, а игре не нужен Calendar публикаций.
2. Тип нельзя изменить. Пользователь, выбравший Blog, не может добавить задачи,
   не пересоздав проект.
3. Добавление любого нового раздела требует правки хардкода навигации.

### Decision

**Проект хранит множество включённых модулей, а не тип.**

1. Вводится таблица `ProjectModule (ProjectId, ModuleKey, Enabled)` с составным PK
   и cascade delete от `Project`.
2. `Project.Type` переименовывается в `Project.CreatedFromPreset` (RenameColumn,
   не пересоздание). Поле сохраняется исключительно для иконки и vocabulary
   и **не влияет на доступность функциональности**.
3. Тип проекта в UI — это creation preset: он разворачивается в набор строк
   `ProjectModule` в момент создания и после этого не имеет силы.
4. `ModuleKey` хранится в БД строкой; перечень ключей живёт enum'ом
   в `CedarClerk.Core`. Добавление модуля не требует миграции.
5. Канонический список ключей:
   `documents, assets, site, posts, calendar, metrics, tasks, planner, builds,
   canvas, dialogues`.
6. Модуль `documents` всегда включён и не может быть выключен. Инвариант
   обеспечивается кодом, не схемой.
7. **Выключение модуля не удаляет данные.** `Enabled = false` означает «скрыт
   из навигации». Повторное включение возвращает всё содержимое. Выключение
   модуля не является destructive-операцией и не требует подтверждения.
8. Строка `ProjectModule` создаётся для каждого ключа при создании проекта,
   включая выключенные — чтобы UI мог показать полный список тумблеров.

### Границы решения

- Модули **не являются** механизмом тарифного гейтинга. Квоты планов остаются
  отдельным механизмом (ADR-012/013/014); доступность модуля и лимиты плана
  не пересекаются.
- ADR не затрагивает типы документов — это отдельное решение (13b).
- ADR не затрагивает адресацию сайтов — это отдельное решение (13c).

### Consequences

**Положительные**

- Тип проекта получает содержательное отличие (набор возможностей), а не только
  набор заготовок.
- Навигация строится из данных; добавление раздела не требует правки хардкода.
- Пользователь может достроить проект под себя, не пересоздавая его.
- Модули запрашиваемы из админки и попадают в audit log.

**Отрицательные**

- Появляется состояние, которого раньше не было: проект с нестандартным набором
  модулей. Баг-репорты требуют знания этого набора — его нужно выводить
  в админке и в диагностике.
- Пустой проект теперь создаёт 11 строк вместо нуля.
- Все читатели `Project.Type` требуют аудита перед миграцией.

**Риски**

- Переименование колонки без миграции даёт `no such column` в рантайме
  (инцидент 27.07). Обязателен `SchemaDriftGuardTests` в том же коммите.
- Если в проде обнаружится тип вне таблицы пресетов — backfill должен
  остановиться, а не подставлять Empty по умолчанию.

### Alternatives considered

| Вариант | Почему отклонён |
|---|---|
| JSON-колонка `Project.Modules` | Не запрашиваемо из админки, не попадает в audit log, ломает фильтрацию |
| Оставить тип классом, добавить override-флаги | Два источника истины о доступности раздела — прямое нарушение anti-desync правила |
| Enum `ModuleKey` в схеме БД | Каждый новый модуль требует миграции |
| Удалить `Project.Type` полностью | Теряется vocabulary и иконка; ломается откат |
