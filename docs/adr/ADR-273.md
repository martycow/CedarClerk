# ADR-273 — X and Bluesky get their own snapshot table and their own nightly job (05.09.2026)

**Context.** ADR-161 rule 4 kept X and Bluesky off the Stats tab because no snapshot entity
existed for them: a `dried` leaf would have promised a line that connecting the account could
never draw. T-241 builds the readings. Two shapes were on the table: more columns on
`ChannelStatSnapshot`, or a new table; and two homes for the reader: a branch inside
`SnapshotChannelStatsJob`, or a job of its own.

**Decision.**

1. **A new table, `PublishTargetStatSnapshot`**, keyed by `PublishTarget.Id` with `Network`
   denormalised, `FollowerCount`/`PostCount` always, and `LikeCount`/`CommentCount`/`RepostCount`
   nullable. `ChannelStatSnapshot` keys off the Telegram detail row, and its `ViewCount`/`LikeCount`
   carry ADR-025's blog attribution — a second meaning under the same column name is exactly the
   cliff ADR-205 refused to put in the middle of a chart. Null is a value here: X's free tier hands
   out no per-tweet metrics, so an X row has nulls and the tab reads them as "not tracked", never as
   zero engagement.

2. **Engagement is summed over Cedar Clerk's own posts only** — the Bluesky author feed filtered to
   the `uri` half of a Succeeded `PublishJob.RemoteId` for that target. The account's hand-written
   posts are the author's, not the app's; a total that included them would flatter every chart.

3. **A separate Quartz job, `SnapshotPublishTargetStatsJob`, at 04:10 UTC** — ten minutes after the
   Telegram job and not inside it. `SnapshotChannelStatsJob` returns before doing anything while the
   bot is down, which is correct for Telegram and would silently stop X and Bluesky readings for a
   reason that has nothing to do with them.

4. **One save per target.** A failing account logs a warning and is skipped; its row is detached so
   the next target's save does not carry the failure forward. A dead X token marks the target with
   `ErrorMessages.XReconnect` the same way a failed publish does.

5. **The reading is a static helper, `PublishTargetStats.TakeAsync`**, so the connect flows can take
   a first row the moment an account is connected — the same courtesy a Telegram channel gets — and
   the tab is not empty until the next morning.

6. **Bluesky is read over the public XRPC host without a session.** A nightly reading must not
   depend on, or spend, the stored app password; the profile and the author feed are public.
   X needs the bearer, so `XPublishTarget.FreshCredentialsAsync` wraps the existing read+refresh
   with ADR-093's save-before-use rule intact.

**Rejected.** *Columns on `ChannelStatSnapshot`* — see 1. *Per-target legacy endpoints* like
`GET /api/channels/{id}/stats` — the tab reaches every source through one aligned series request
(`GET /api/stats/series`, source id `target:{guid}`), and a third single-source endpoint would be a
third DTO for the same picture. *Bluesky via the target's own session* — a reading is not a
publish; the app password stays for writes.

**Consequence.** `available[]` on the series endpoint lists a target the moment it exists and
dries it until its first row, which is what makes ADR-161 rule 4 hold by construction rather than
by omission. The series endpoint itself (T-242/T-243, `StatSeriesEndpoints.cs`) moves ADR-161's
window rule server-side: the axis starts at the youngest selected source's first reading, gaps carry
the last reading forward, and the delta shown is last−first over that window. An id of an unknown
kind is a 400; an unowned or nonexistent guid is dropped without a word, so the endpoint never
confirms another owner's id. Day keys are calendar days in the account's own `TimeZoneId`, which the
response names in `zone`.
