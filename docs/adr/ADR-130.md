# ADR-130 — Image metadata stripped on every write path, losslessly (18.08.2026)

**Context.** T-175 / MED-04: photos reach the public blog with full EXIF, including GPS coordinates — a safety issue for a personal blog, not hygiene. Media enters the media directory on three paths: `/api/assets` upload (which paste/drop and the media library also use), `.cedar` import and Markdown-zip import. Two more places *re-encode* images with ImageSharp — the Telegram derivative (`ImageCompressor`) and the agent's asset-index thumbnails (`AssetMetadata`) — and ImageSharp carries the source EXIF into its output by default.

**Decision.**
1. **Byte-level segment/chunk removal, not re-encoding** — `ImageMetadataStripper` in `CedarClerk.Core` (pure C#, no dependency). Re-encoding a JPEG through ImageSharp would degrade pixels on every upload; dropping metadata segments is lossless and cheap. JPEG: drop APP1 (EXIF/XMP), APP13 (IPTC), COM — keep APP0/APP2/APP14, which decoders need (JFIF, ICC color, Adobe transform). PNG: drop `eXIf`, `tEXt`, `zTXt`, `iTXt` chunks. WebP: drop `EXIF`/`XMP ` RIFF chunks, patch the RIFF size and clear the VP8X presence flags. GIF is passed through — no EXIF standard, and its rare comment blocks carry no coordinates.
2. **Fail open on parse, never corrupt**: any structure the stripper does not understand returns the original bytes unchanged. A stripped file that fails to decode would be worse than a metadata leak.
3. Applied on all three write paths (`AssetEndpoints`, both imports) before the bytes hit disk, and the two ImageSharp re-encode paths null out `ExifProfile`/`XmpProfile`/`IptcProfile` before saving.

**Consequence.** Files uploaded before this ADR keep their metadata on the droplet and on the blog; cleaning them is a one-off pass over `media/` (a server-write operation, Marty's hands) — tracked on the board, not pretended solved. `Asset.SizeBytes` records the stripped size, so quota accounting matches the file on disk.
