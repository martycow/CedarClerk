# ADR-306 — Project-centered workflows and the Framer reference

## Context

The owner's `0.23.6_Review.md` identifies broken media, unclear project ownership,
weak application chrome, and public pages that do not explain the product well.
Framer is the primary reference for interaction and visual hierarchy. Cedar Clerk
keeps its own branding, design tokens, localized copy, and publishing model.

## Decisions

- Use the existing shell, project switcher, command registry, and inspector. Put
  the persistent project switcher in the top bar and selected-document properties
  in the shell inspector. List screens must not duplicate those properties.
  Below 1100px, the open inspector overlays the workspace with its close handle
  visible, preserving access without squeezing the document list.
- Documents belong to projects. Core document creation must resolve an owned
  project; existing unfiled documents need a non-destructive personal-project
  backfill. Core project organization must remain available with IndieDev off;
  game-specific tools remain optional. This supersedes the projectless creation
  path in ADR-101/102 and the independent-Blog organization in ADR-243, without
  changing public blog URLs or Discovery eligibility.
- Media access follows actual public references, including post covers, showcase
  gallery images, and glossary illustrations rendered in a post. Unpublished,
  private-only, excluded, and unrelated media remain protected. Uploads accept an
  explicitly validated project so an upload need not wait for document autosave
  to appear in project assets.
- Use the owner's final Cedar logo. Keep version beneath the sidebar name. Use
  deliberate branded authentication and creation screens without generated art.
- Landing tool details are keyboard/click accessible as well as discoverable on
  hover. Keep an inline waitlist form and add a modal entry point. Make Free/Pro
  differences explicit and retain invite-only registration.
- Discord uses the existing external-login and invitation rules. Account security
  actions require the established Identity mechanisms and explicit destructive
  confirmation in the product.

## Delivery and verification

Implement separate review slices: media and upload correctness; project ownership;
shell and hub; public pages and authentication. Reuse existing backlog IDs where
applicable. Each slice updates UI inventory and records its checks in CHANGELOG.
No deployment is implied by completion of local implementation.

Project presets, community features, and Skill Points remain proposals, outside
this implementation. Provider sign-in requires real configured credentials for
live verification; tests alone do not establish that production sign-in works.
