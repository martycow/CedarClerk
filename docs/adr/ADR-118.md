# ADR-118 — Cedar CLI: an interactive shell over existing scripts, only a human initiates deploy (12.08.2026)

**Context**: Marty's request. Project management had scattered across five PowerShell scripts with twenty flags, plus a dozen `ssh` commands retyped every time. The request: bundle this into one interactive C#/Spectre.Console tool with a menu, prompts and rich terminal graphics. Explicit condition for this stage: **a wrapper, not a logic port.**

**Decision 1: the CLI calls the `.ps1` scripts, it doesn't repeat them.** `deploy.ps1` is 875 lines, every branch of which was written following a real incident: resume-from-byte appeared after `scp -r` twice left production hanging (ADR-113), the order `.exe` → `.blockmap` → `latest.yml` came after working out what `electron-updater` actually reads (ADR-116), and the sha256 on the far side exists because a broken upload silently looks successful.

Porting this to C# would mean rewriting battle-tested code while simultaneously changing the interface used to invoke it. Then the first deploy failure would become the question "is this new logic or a new wrapper," and the only way to answer it is to roll back both. **We change exactly one thing at a time**; the port is stage 2, and only after the wrapper has proven itself live.

**Decision 2: `cedar deploy` doesn't deploy.** It runs preflight (branch, clean working tree, tag, connectivity to the server, live version vs. the version being built), prints a `0.11.0 → 0.11.1` summary, and **a ready-to-run command** that Marty runs himself.

This isn't caution for caution's sake. `deploy.ps1` is monolithic: there's no breakpoint before the swap in it, and getting it to "run up to the restart and stop" would require cutting it apart — that is, violating Decision 1 in its very first scenario. Plus the rule in `.claude/rules/destructive-operations.md` requires a stop before anything irreversible, and a deploy stops production. Hence the honest formulation: the CLI knows everything about the deploy and doesn't run it.

`cedar restart` is the exception and the only destructive command at this stage, because `sudo` on the droplet is granted `NOPASSWD` for exactly `systemctl start|stop|restart cedarclerk` and nothing else: the capability the CLI gets is already bounded by the server, not by us. The confirmation defaults to `false`.

**Decision 3: remote calls shell out to `ssh`, rather than going through SSH.NET.** Keys, the agent, `known_hosts` and `BatchMode` are already set up and already work — a library would require a second, parallel trust configuration that could silently drift from the first. Plus any CLI command can be copied from `--dry-run` and run by hand; with a library there's no reproducibility.

**Decision 4: `--dry-run` is an implementation swap, not an `if` inside the commands.** One interface `ICommandRunner`, three implementations: the real one, a printing one, and a fake one for tests. A condition inside a command would sooner or later end up on the wrong path — and a "dry" deploy that actually ran something is worse than having no flag at all.

**Decision 5: everything drawn is pulled from the machine, and the CLI doesn't invent history.** Verified live on 12.08.2026, before any code was written:
- `journalctl -u cedarclerk` **reads without sudo** — the service runs as `martycow`, and its log lines belong to that owner. The rule in `.claude/rules/production-environment.md` claimed the opposite and **is corrected by this ADR**. A caveat that became an interface constraint: over a day the journal holds **1.49 million lines** (EF logs every query), so `cedar logs` always bounds the query — there is no "show everything" mode.
- **`sysstat`/`sar` is installed and collects data every 10 minutes.** So the CPU/RAM sparkline is a real measurement, not an animated placeholder. The default window is **24 hours (144 points)**, not an hour — an hour's window gives six points, which isn't enough to make a graph.
- `systemctl show`, `df`, `free`, `du`, `sqlite3`, `ps` are available without elevation; `sqlite3` is used read-only (`PRAGMA quick_check`, `SELECT count(*)`).

**Decision 6: `cedar backup verify` shows the absence of a backup, and `cedar backup now` isn't built.** The droplet has neither a crontab nor `~/bin` nor `/mnt/backup` — the nightly copy from the Pi didn't come across (ADR-114). A "verify the latest backup" command has nothing to verify, and the right answer isn't to remove it but to make it say out loud: the only copy is DigitalOcean's weekly image, in the same account, restorable only as a whole.

Creating a backup is `T-071` — that is, new server-side logic, not a wrapper over something existing. Building it inside a session about the interface would mean smuggling a server-side change in under the guise of a button.

**Decision 7: color is never the only carrier of meaning.** Next to every color there's a symbol or a number. Terminals can be monochrome, `--no-unicode` degrades to ASCII, and not everyone distinguishes red and green the same way. Checked against `AnsiConsole.Profile.Capabilities`; the flag only forces it.

**Decision 8: test progress is drawn by parsing the stream, not by waiting for the exit code** (Marty's direct request — to watch hundreds of checkmarks turn green). `dotnet test`, `vitest` and Playwright print a line per completed test; `ICommandRunner` gets a streaming variant with a per-line callback, and the grid of checkmarks fills in as they arrive.

The cost is stated: the format of these lines isn't a contract, it's the output of someone else's tools, and it can change on an update. So **the parser must degrade, not crash**: an unrecognized line isn't counted as a test, and the verdict of the run is taken from the exit code, not from the count of recognized checkmarks. A pretty grid must never become the reason a red run looks green.

**What's out of scope**: any changes to `CedarClerk.Server` and `cedarclerk-web`, new endpoints (including `/api/admin/telemetry`), automatic deploy, CI, cron, and storing any secrets. The CLI's config holds only paths and hostnames; authentication is the existing ssh-agent.

**Decision 9 (12.08.2026): installed as a .NET global tool, not published to a folder on PATH.** `PackAsTool` + `ToolCommandName=cedar` in the `.csproj`, installed via `Scripts/install-cli.ps1`. The reason lies in what this path **doesn't** do: `%USERPROFILE%\.dotnet\tools` is already created and already on PATH by the SDK itself, so no environment variables are edited by hand — meaning nothing needs cleaning up on removal (`install-cli.ps1 -Uninstall`). The version for `pack` is read from `Consts.CurrentVersion`, so `dotnet tool list` doesn't show a number that exists nowhere else.

A side effect that had to be closed separately: `ConfigStore.FindRepoRoot` looks for `CedarClerk.sln`, walking up from the executable, and that worked while the tool lived in `bin/` inside the repo. A global tool lives in the SDK's storage, from which there's nowhere to walk up to — outside the working folder it can't find the repo. So the installer writes `RepoRoot` into `%APPDATA%\cedar\config.json` (an existing config gets appended to, not overwritten); without this, `cedar deploy` from an arbitrary directory would honestly answer "run 'cedar config'" on every single invocation.

**Decision 10 (12.08.2026): the menu draws itself, rather than through `SelectionPrompt`.** Marty's request — that the logo keep shimmering while you sit in the menu, and once every ten seconds the letters bounce one after another. `SelectionPrompt` can't do this in principle: it owns the bottom part of the screen and only redraws its own list, so anything drawn above it freezes forever.

So `Rendering/Chooser.cs` holds the whole screen as a single `Live` frame: logo, header, items. The cost is its own arrow-key handling; in exchange, three things rather than one: the logo stays alive, the header (which machine, which version) doesn't scroll up with the previous command's output, and a submenu **replaces** the screen instead of pasting a second copy of everything underneath the first.

The animation is a **pure function of time** (`Logo.IdleAt`), not a stateful coroutine. The menu asks "how should the logo look right now" and redraws the frame only if the answer changed. This isn't a micro-optimization: at rest (and rest is more than half of the cycle — this is checked by a test), the loop sleeps, and a menu open in an ssh session doesn't push 25 frames a second down the channel.

The bounce is implemented as **an extra blank line on top**: the frame is one row taller than the art, and "a letter jumped" is "read its columns one row lower." The same lookup serves both the airborne letter and the resting one, instead of a second layout for the special case. Without this blank line the top row of `CEDAR` would be clipped by the block's edge, and the jump would read as the cap being lost.

Degradation is mandatory, because the tool owns the keyboard: redirected output, no ANSI, a non-interactive console, **or a window that's simply too short** — and `Chooser` falls back to the old `SelectionPrompt`. A menu that drew half a logo and ate the keyboard is worse than a plain list.

**Decision 11 (12.08.2026): `cedar claude` opens a second window, not a subprocess.** A menu item and a command that launch a terminal in the repo folder with `claude /remote-control` already running (Marty's request). Specifically **a second window**: both programs read the keyboard, and a shared console would mean two readers fighting over every keystroke. The session is launched and forgotten — no pipes, no exit code worth waiting for.

For this, `LaunchDetachedAsync` was added to `ICommandRunner` — a separate method, not a flag on `RunLocalAsync`, because that one captures stdout and blocks until exit, which are exactly the two things an interactive session must not do. It still goes through the interface, so that `--dry-run` keeps meaning "we touch nothing," including "we don't open any windows."

Windows Terminal if present, otherwise plain pwsh: `wt` splits its own arguments on `;`, so in its variant there's no `Set-Location` at all — `-d` already sets the tab's starting directory, and no semicolons remain in what's left of the command. On non-Windows, the command is printed rather than guessed: a portable "open a terminal" doesn't exist.

**Decision 12 (12.08.2026): the `LIVE` tag is set after the health check, locally, and knows how to be wrong out loud.** Marty's request: tag with `LIVE` the commit currently in production, and make sure there's exactly one such commit.

The second part is free and needs no enforcement: a tag name by definition resolves to exactly one object, so `git tag -f` doesn't add a second label — it **moves** the one that exists. There is no state where `LIVE` hangs on two commits.

The first part needs enforcement — a tag that lies. It can drift from reality via a deploy from a different machine, a manual edit on the server, or a rollback git never learned about. Hence two measures. First: the tag moves **only after the health check received that exact version back from production** — before that it's an intention, not a fact, and a `LIVE` on a commit that never made it is worse than no tag at all (you act on a wrong answer; you investigate a missing one). Second: `Test-LiveTag` in preflight reads `CurrentVersion` at the tag's commit (`git show LIVE:…/Consts.cs`) and compares it against what the live server answers; a mismatch is a warning, not a stop, because the deploy that stop would block is exactly the one fixing the tag.

`LIVE-PREV` mirrors the server's `app.prev` **exactly one level**. The server keeps one previous release, so a chain of two tags would promise a rollback the server can't perform. From this follow three consequences: the outgoing `LIVE` becomes `LIVE-PREV` even when it's the same commit (redeploying the same commit makes `app.prev` that same commit); on the very first deploy ever, `LIVE-PREV` is **deleted** rather than left over from a previous life; and `-Rollback` moves `LIVE` onto `LIVE-PREV` and deletes `LIVE-PREV` — just like a server that leaves nothing behind after a rollback. If there's nowhere to roll back to, `LIVE` is removed entirely: after such a rollback, the running commit is honestly unknown here, and having no tag is the only way to say so.

**The tag is not pushed to origin** (Marty's decision). The cost is stated: from a different machine, and from GitHub, you can't see what's in production. In exchange, `deploy.ps1` stays fully offline with respect to git — no network dependency in the script that already performs the riskiest operation in the project, and no force-push as part of it.

None of these operations can fail the deploy: by the time they run, the site is already live, and letting a finished release fail over bookkeeping would be the tail wagging the dog.

**Decision 13 (12.08.2026): the glossary is grouped by tile, not alphabetically.** Marty's request: "sometimes I don't understand what the abbreviations in the stats mean." `cedar legend`, a menu item, and `cedar status --legend`, which puts the panel right under the dashboard; without the flag, `status` leaves one gray line with a pointer — otherwise the glossary is a command you'd have to already know about in order to find it.

The order is by the tile the word appears in. An alphabetical list is simpler to build and requires that you already know which word confused you; by tile, you read the screen the same way you look at it: find the box, then the word inside it.

Definitions are about **this machine**, not about the abbreviation in general. "rss — resident set size" is a translation, not an explanation; the line is justified by what follows: on a droplet with 2 GB and no swap, this exact number is what causes the service to get killed. Same for `wal` (growing means checkpointing isn't keeping up), `avail` (there's no swap, so this is all there is), and `no autostart` (the unit is disabled, a DigitalOcean reboot will leave the site down).

**Decision 14 (12.08.2026): the test grid is a field of squares, not checkmarks.** Marty's request: "didn't like the purple checkmarks, cooler would be a ton of little squares, filled in green, but with the border visible."

They weren't purple because of the palette. `✔` (U+2714) is part of the emoji set, so Windows hands it to Segoe UI Emoji, which draws its own colored glyph and **ignores the ANSI color entirely**. One checkmark in a line hides this; a wall of eight hundred doesn't. Geometric Shapes characters have no emoji presentation and stay whatever color they're given, so changing the symbol fixes the cause, not the symptom.

Three requirements for the cell glyph, and all three are consequences, not taste: **exactly one column width in both modes** (in ASCII, `Ok`/`Bad` were two characters — `OK`/`XX` — and a grid that wraps by result count rather than character count would silently render twice as wide); **not an emoji** (above); **distinguishable by shape, not only by color** (Decision 7) — filled, crossed-out and dotted read fine in monochrome, three shades of the same square don't. Hence `□ ▣ ⊠ ⊡`. The filled one keeps its border, so a finished grid stays a grid of cells rather than one solid green slab.

**The field is drawn ahead of time from memory of the previous run** (`%APPDATA%\cedar\last-run.json`, keyed by the flag set, because `-Backend` and `-Smoke` are different sets). Otherwise the "filling in" effect doesn't exist: a grid that appears as results come in has nothing to fill. The count is a guess, and it's treated as a guess: the field is drawn to the larger of the remembered and the actual counts, the final frame is redrawn from the actual count only, and no decision follows from that count. A stale count makes the animation slightly wrong once and is immediately overwritten; it cannot turn a red run green — the verdict is still the exit code (Decision 8).

**Fixed as a side effect**: `Live` hides the cursor, and on Windows, with redirected output, that throws `IOException: The handle is invalid` — meaning `cedar test` run from a script crashed without running a single test. Now non-interactive output bypasses `Live` and prints the finished frame once.
