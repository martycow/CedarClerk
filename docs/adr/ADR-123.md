# ADR-123 — Front-matter метаданных на живых доках (18.08.2026)

**Context.** Главный failure mode документации этого проекта — дрейф: файл заявляет статус, который код давно опроверг (PRD чинился дважды за восемь дней; integrations-setup нёс выдуманные ключи). У файлов не было машиночитаемой метки «когда это в последний раз сверяли» — свежесть приходилось восстанавливать по git log и памяти сессий. Предложение пришло из внешнего анализа DOCS-FLOW (18.08.2026), разобранного против репо.

**Decision.** Каждый **живой** док (`docs/` и его подкатегории) начинается с YAML front-matter из четырёх полей:

```yaml
---
owner: marty
last_verified: 2026-08-18
source_of_truth_for: <одна строка — чему этот файл источник истины>
guard: <автоматический страж файла: имя теста/хука, или none>
---
```

- `last_verified` — дата последней **сверки с кодом**, не последней правки. Правишь док по итогам сверки — поднимаешь дату; правишь косметику — не трогаешь.
- `guard` — только реально существующая автоматика (`DocsFlowGraphTests`, `UiInventoryDriftTests` + PreToolUse-хук). Желаемое, но не построенное — `none`, не имя мечты.
- `owner` — пока один: marty. Поле существует ради будущего, где владельцев больше одного.

**Scope.** Только живые доки. **Не** получают front-matter: `docs/adr/*` и `docs/archive/*` (append-only записи момента — «когда сверено» к ним неприменимо), `docs/INPUT_PROMPT.md` (нетрекаемый файл Марти, его формат — его дело).

**Consequence.** Свежесть каждого дока читается без git log — и человеком, и агентом будущего docs-auditor'а. Цена: ещё одно поле, способное врать; смягчение — `last_verified` обязана поднимать только сверка, и большие разборы (аудит, Input sweep) поднимают её пачкой.
