# ADR-123 — Front-matter metadata on live docs (18.08.2026)

**Context.** The main failure mode of this project's documentation is drift: a file claims a status the code has long since disproven (PRD was fixed twice in eight days; integrations-setup carried invented keys). Files had no machine-readable mark of "when this was last checked against the code" — freshness had to be reconstructed from git log and session memory. The proposal came from an external DOCS-FLOW analysis (18.08.2026), worked through against the repo.

**Decision.** Every **live** doc (`docs/` and its subcategories) starts with YAML front-matter of four fields:

```yaml
---
owner: marty
last_verified: 2026-08-18
source_of_truth_for: <one line — what this file is the source of truth for>
guard: <the file's automatic guard: a test/hook name, or none>
---
```

- `last_verified` — the date of the last **check against the code**, not the last edit. Editing the doc as a result of a check — bump the date; editing cosmetics — leave it alone.
- `guard` — only automation that actually exists (`DocsFlowGraphTests`, `UiInventoryDriftTests` + the PreToolUse hook). Something wanted but not built — `none`, not the name of a wish.
- `owner` — for now just one: marty. The field exists for a future where there is more than one owner.

**Scope.** Live docs only. **Not** given front-matter: `docs/adr/*` and `docs/archive/*` (append-only records of a moment — "when checked" does not apply to them), `docs/INPUT_PROMPT.md` (Marty's untracked file, its format is his business).

**Consequence.** The freshness of every doc can be read without git log — by a human and by a future docs-auditor agent alike. The cost: one more field that can lie; the mitigation is that `last_verified` may only be bumped by an actual check, and large reviews (an audit, an Input sweep) bump it in bulk.
