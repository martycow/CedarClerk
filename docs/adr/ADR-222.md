# ADR-222 — The landing stays reachable at /welcome, and the desktop build gets a public page (29.08.2026)

**Context.** ADR-215's landing is served at `/` only to visitors without the auth cookie — an author who types the address wants their drafts. That left a signed-in author with no way to see the front door at all short of a private window. Separately, the desktop build had a download *redirect* (`GET /downloads/latest`) and nowhere that a stranger — or the landing — could point at it as a page.

**Decision.**

1. **`/welcome` is the landing for everyone, cookie or not.** The same middleware answers it; only the cookie check is skipped, and only for that path — `/` behaves exactly as before, and tenant hosts are unaffected. The chrome links to it from beside the version label with a plain `href`, deliberately not a `routerLink`: the page is server-rendered, and the SPA router must not swallow the navigation. No Angular route named `welcome` exists.
2. **`/download` is a public Angular page outside the shell** — a sibling of `/terms`, no guard: title, short copy, a primary button to `/downloads/latest`, and the one sentence that matters — the data lives in the account on the server, the app is another door to it. `app-button` gained an `href` input to render that primary action as a real link.
3. **The landing gains a `#download` section behind `LandingSettings.ShowDownload`, default false** — off like `ShowRoadmap` and `ShowStory` before it, and for the same reason: a download section is a promise the build has to keep first, and the installer has never run on a clean machine (T-121). The flag is a column (migration `AddLandingShowDownload`, in the same change as the entity per `SchemaDriftGuardTests`) toggled from the admin Landing tab.

**Consequence.** Both marketing surfaces render signed-in and signed-out, and neither disturbs `/`'s claim by the app. Nothing is advertised on the landing until the flag is flipped by hand — which is the intended order: verify the installer, then turn the section on.
