# ADR-047 — Forms tab: multi-choice questions, answer distribution, and copied (not linked) presets
**Context**: Brainstorm v2 items N10 (the Forms tab for real — edit/delete a form, see who answered what and when, a multiple-choice field type, and a pie chart of the answer distribution) and N12 (form presets: build a question set once, choose it before publishing). Both land on the tab N7 left read-only.
**Decision** (26.07.2026):
- **Multi-choice is a new question type (`multi`), and its answer is a JSON array inside the existing string map.** `PostRegistration.AnswersJson` is a `Dictionary<string,string>` (ADR-042); widening it to a union type would invalidate every row already stored. A multi answer is therefore the string `["A","B"]`, decoded by `MultiAnswer.Split` (Core, unit-tested): self-describing, no delimiter that can collide with option text, and a plain text answer that happens to start with `[` still round-trips as a single value. Rendered as checkboxes, not a multi-`<select>` — the latter needs ctrl-click to pick more than one, which nobody discovers on a public page. Server-side required-validation treats an empty array as unanswered, since a replayed POST can send `[]` where the browser sends `""`.
- **The form editor moved out of the export modal** into the Forms tab, and the submissions list with it. What stays in the modal is the one form decision that genuinely belongs to publish time: applying a preset. Two editors for one blob would have been two places to fix every future change.
- **A preset is copied onto the post, never linked** (`FormPreset` entity: `OwnerId`, `Name`, `FormJson`; migration `AddFormPresets`; `FormPresetEndpoints` CRUD). Editing a preset later must not silently rewrite the form of a post that already went live with it — the alternative (a foreign key) makes every preset edit a retroactive change to published posts.
- **Answers now resolve to question labels** instead of raw keys (the gap ADR-046 flagged): the tab has the form definition in hand, so it maps id→label, falling back to the raw key for questions deleted after someone answered them.
- **Charts**: distribution is drawn only for closed questions (`choice`/`multi`) — free text would produce as many slices as submissions. Six is the ceiling on distinguishable series, so a seventh option folds into one "Other" slice rather than inventing a colour. **A question with a single distinct answer renders as a line of text, not a pie** — a full-circle "chart" carries no comparison. Every slice is accompanied by a legend row with label, count and percent, so identity never rests on colour alone, and slices are separated by a 2px surface-coloured stroke.
- **New `--series-1..6` design tokens** (`styles.scss`, both themes) rather than per-chart colours. The dark steps are chosen against the dark chart surface, not lightened from the light ones — a mechanical flip lands outside the lightness band dark needs. Both sets were checked with a palette validator (lightness band, chroma floor, colourblind separation for adjacent pairs, contrast vs the surface) and pass in both modes; re-run that check before changing a value rather than eyeballing it. `--danger`/`--ok` are deliberately excluded: they mean a state, not an identity.
**Consequence**: `.reg-multi` styling had to go into the blog page shell (`BlogEndpoints.PageShell`), which is where all public-page CSS lives — the form is rendered server-side, so it can't reuse the app's stylesheet. Old submissions predating this change still show a single value for what is now a multi question; `MultiAnswer.Split` treats them as one answer rather than trying to re-parse history. The Forms tab still has no per-question free-text summary (a list of distinct text answers) — out of scope here, and the submissions list already shows them per person.
