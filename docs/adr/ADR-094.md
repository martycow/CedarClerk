# ADR-094 — Microblog threads: the whole document to X and Bluesky as a reply chain (05.08.2026)

**Context**: Marty's request after the first live X post. ADR-077 gave short networks a teaser/override — an announcement with a link. A thread is a second, explicitly opt-in mode: the whole document goes out to the network, in parts ≤ the limit, each part a reply to the previous one. Telegram already has thread infrastructure (T-106: one job per part, ordering via the queue, `ReplyToRemoteId`) — reused as-is.

**Decisions**:
- **A thread splits the document's text, not the override.** The point of a thread is the whole post; the override stays the text of a single teaser. Splitting is by paragraph (`CedarPlainText.Paragraphs`), an overflowing paragraph is split by sentence, then by word; the count is native to the network (`XPostBuilder.WeightedLength` / Bluesky graphemes). A shared `MicroThreadSplitter` lives in Core, the network is a parameter.
- **"N/M" numbering at the end of each part** (budget reserved for it), **the blog link goes in the last part**. A single-part "thread" is not a thread — no numbering or chain appears.
- **The queue and the target use the same plan**: `/jobs` counts the number of parts with the same `MicroThreadSplitter`; the target recomputes the same thing from the document (the T-106 principle — the same input and rules produce the same parts, nothing to synchronize).
- **Bluesky reply requires the parent's and root's uri+cid** — a bluesky job's `RemoteId` becomes `uri|cid` (the public URL is still built from the uri); `ThreadPartRef` gets a `RootRemoteId`, which the runner fills in. X reply is just `in_reply_to_tweet_id`.
- **A thread on X costs N credits** — one credit per part actually created (a direct consequence of ADR-092/093: the debit anchor is the post id). The balance is checked at the start of part i as "is there enough for the remaining Count−i", so a thread doesn't break off mid-way for lack of money; the cost is shown in the modal before sending.
