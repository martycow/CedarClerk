# ADR-247 — Table-shaped collections can be sorted and filtered (02.09.2026)

**Context.** The application has several table-shaped collections, but their controls differ.
Drafts have useful facets and sorting. Posts Manager has only title or tag search. Media Library and
Project Assets expose named columns, yet the column labels do not sort. A long collection therefore
answers neither "show only this kind" nor "put the newest or largest first" consistently. Adding a
DOM-owning data-grid package would solve the interaction by replacing the Cedar Bench surface, which
is the wrong trade.

**Decision.**

1. Every user-facing data table provides a visible query filter, the facets that matter to that
   entity, and an explicit sort. High-volume manager lists named in the consequence follow the same
   contract. A labelled column header may be the sort control. The current key and direction are
   conveyed by text or icon plus `aria-sort`; colour is not the only signal.
2. Sorting and filtering happen before pagination. Server-paged collections accept and validate the
   sort key, direction and facets on the server. A client must not sort one fetched page and present
   it as the order of the full collection.
3. The default order is stable and includes an ID tie-breaker. A collection manager that already
   persists its view in route query parameters represents new criteria there too, so reload and Back
   keep the user's view. An item-selection query alone does not make working filters persistent.
4. On every surface covered by this contract, a filtered empty state says that no rows match and
   offers one *Clear filters* action. It does not reuse the collection's first-use empty state.
5. Cedar owns a small headless table contract: toolbar layout, sortable-header semantics, filter
   chips, empty state and row anatomy. Screens keep their own row markup and design tokens. Angular
   CDK remains the first escalation for templating or virtualisation; a DOM- or theme-owning grid is
   not introduced. This supersedes ADR-229 only where it said that current tables need no change.
6. Fixed comparison matrices, tiny key/value summaries, layout tables in generated email, and an
   off-screen accessibility mirror of a chart are not browsable collections. They do not gain false
   sort or filter controls.
7. Developer-only diagnostic collections, including `/dev/icons`, are exempt. Their generated order
   is diagnostic output, not a user sorting contract. The existing search remains for inspection.

**Rejected.** *AG Grid, Material Table or another themed grid* — each would create a second visual
system. *Client-side sorting of one API page* — it gives a convincing but false result. *A single
generic row component* — the entities do not share enough content, and forced slots would weaken
their hierarchy.

**Consequence.** Posts Manager gains a real collection toolbar and a legible row. Existing Drafts
controls are aligned to the same vocabulary. Media Library, Project Assets, Project Tasks, Teams,
Forms, statistics series and the table-shaped admin reports gain the relevant sort and filters;
server-paged endpoints own their ordering. Tests cover valid and invalid server sort keys, stable
ordering, filter combinations, empty results and keyboard-accessible headers.
