# ADR-128 — Document tree and wiki-links: GDD structure (18.08.2026)

**Context.** T-181 (Phase 13): the GDD {game design document} is not a flat list but a tree ("Gameplay → Combat → Weapons") with cross-references between documents. Today a Draft has only a folder (a flat filter) and a project; there is neither hierarchy nor "this document mentions that one" links. Marty's decision — both halves at once: the tree AND wiki-links with backlinks.

**Decision — tree.**
1. **`Draft.ParentDraftId (Guid?)` + `Draft.SiblingOrder (int, default 0)`** — directly on Draft, with no separate table: the tree node *is* the document. Root = `ParentDraftId is null`. **Folder ≠ tree**: the folder remains a flat list filter, the tree is a structure; in tree-view the folder filter is disabled, because there is no honest way to show "a subtree filtered by folder" — a parent might not pass the filter.
2. **`PUT /api/drafts/{id}/parent {parentId, beforeId?}`**: an owner check on both ends, a **cycle guard** by walking up through ancestors (moving under one's own descendant → 400), **depth ≤ 10** (enough for a GDD's structure, and the UI doesn't degrade), renumbering of the new sibling set 0..n (splice before `beforeId`, otherwise append to the end).
3. **Deleting a node raises its children to the grandparent** in one UPDATE (`ParentDraftId = the deleted node's ParentDraftId`) — the subtree is neither cascade-deleted nor orphaned: documents matter more than structure.
4. **Tree-view — a third `/drafts` view** alongside the table and the cards; expansion is a client-side Set. v1 controls: a row menu "Move…" (a parent picker) and up/down buttons; drag&drop — only if time remains (cdk has no tree drop-list, and hand-rolled math is the session's main risk on the last task). **Breadcrumbs** in the editor are built from ancestors out of the already-loaded list; a click opens the document directly.

**Decision — wiki-links.**
5. **A `wikilink` node — an inline atom `{draftId, label}`** (modeled on the footnote-node + stopEvent pattern from the image node): a link by id, not by name — renaming the target doesn't break the link; label is a snapshot of the name at insertion time. Triggered by `[[` via `@tiptap/suggestion@^3.27.2` (the TipTap 3.27 family, like the other extensions); the popover is hand-built from clientRect; its source is a client-side filter over the loaded draft list (there is no server-side search yet — T-176 upgrades this via FTS).
6. **`DocumentLink {Id, OwnerId, FromDraftId, ToDraftId, CreatedAt}`, unique(From, To) — separate from the module's `EntityLink`**: EntityLink is a *declared* relationship with a mandatory `ProjectId`, DocumentLink is *derived from the text* and lives outside projects too. Sync happens by diffing on save of the **primary language** (translations inherit the links, they don't generate their own); deleting a draft cleans up both sides. `GET /api/drafts/{id}/backlinks` → `[{id, title}]`; in the editor a "← N" chip opens the list.
7. **Renders** (per the renderers.md rule — escaping + a test for the node): the blog links to the target if it's visible per the index (`IsBlogPublished && (!IsPrivate || IsListedWhilePrivate)`), otherwise an escaped `<span>` with the label; the visibility map is built with one query. Blocks/legacy HTML/MD — an escaped plain label (in Telegram there's nowhere for internal links to lead). **`wikilink` is added to `PublishValidator`'s whitelist and to the `TipTapTextNodes`/`CedarPlainText` emission** — otherwise the validator would reject the post, and teasers/og:description would silently lose the word.

**Consequence.** Sibling order in lists is `(SiblingOrder, UpdatedAt)`; flat views ignore the tree. A broken link (target deleted) renders as a plain label — the document doesn't break. Drag-and-drop reordering, server-side search for the suggestion, and cross-project links are deferred to the board.
