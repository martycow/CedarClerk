# ADR-312 — Build the desktop shell on each supported host

**Status**: DONE

## Decision

Keep one Electron shell and one cloud account across Windows, macOS and Linux. Build the local .NET filesystem agent for the target machine's runtime identifier, then package it with Electron on that operating system. The Angular application remains hosted by production and is not copied into the desktop bundle.

Use `https://cedarclerk.app` as the window, preload bridge and update origin. The earlier domain redirects there, and an origin-gated filesystem bridge cannot follow that redirect while retaining its old allowlist.

Use one Node build entry point in `CedarClerk.Desktop` to select the runtime identifier and package target, and to keep the shell version equal to `Consts.CurrentVersion`. Produce NSIS on Windows, DMG and ZIP on macOS, and AppImage on Linux. The ZIP exists because macOS auto-update requires it. Build on the target operating system so the result can be run and inspected there.

Closing the last macOS window leaves the application and its local agent running, as macOS users expect; quitting the app stops the agent. The window can then reopen from the Dock without losing folder indexing.

Compare granted paths using the host filesystem's case rules. Do not follow a link below a granted root into another location when scanning or serving an explicit file request. The Windows-only case-insensitive comparison would widen a grant on a case-sensitive Linux or macOS volume.

An unsigned local build may be used for development. A public macOS release requires Developer ID signing and notarization. A build artifact alone does not publish an update or change production.

## Consequences

The existing Windows installer and cloud-only data model remain. Each target needs a build host and a clean-machine check. The desktop build guide names the prerequisites and verification steps for all three systems. Distribution and signing credentials stay outside the repository.
