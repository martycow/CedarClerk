# ADR-113 — Deploy travels as a single archive with resume, and the service stops only for a directory rename (11.08.2026)

**Context**: `scp -r publish/* host:app/` kept breaking near the finish line, over and over — `client_loop: send disconnect: Connection reset` — and every time this happened **after** the service had already been stopped. So every connection failure left production hanging: half the files new, `wwwroot` missing entirely, `/api/health` answering 502. This is exactly the state this ADR was written in: 50 files out of 174 in `app/`, service `inactive`. Re-running the script started the same 50 MB from scratch, because `scp` can't resume.

**Decision 1: everything slow happens while the old version is still serving users.** Build, packaging, transfer, checksum verification and unpacking all run while the service is up — into a separate `app.new` directory that nobody reads. Stopping is needed only for two `mv`s. Downtime dropped from "however long the copy takes" (minutes, and up to the next successful run if the connection drops) to about a second — and that second is measured on the server itself and printed in the report.

**Decision 2: one tar.gz is transferred, not 174 files.** It's not only about speed (50 MB compresses to roughly half, and one sequential transfer doesn't spend a round-trip per file). It's that a single byte stream has a **position**, and a file tree doesn't: a broken `scp -r` can't say how far it got, but a broken file transfer can.

**Decision 3: resume is homegrown, streamed via `cat >>`, not `scp`.** `scp` only knows "start from the beginning." The script asks the server file for `stat -c %s` and sends the local file's tail starting at that byte. Verified on the live server: a transfer interrupted at 2 MB out of 5 resumed and produced a matching sha256. This is also where the requirement not to repack the archive between attempts comes from — gzip stamps a timestamp into its header, and repacking the same input produces different bytes, so the appended tail would end up glued onto someone else's beginning. So the artifact is cached in `%TEMP%` together with a signature of the `publish/` directory (file count, total size, most recent date), and `-SkipBuild` resumes **that exact same** file.

**Integrity is verified before anything is touched**: sha256 on both sides, presence of `CedarClerk.Server.dll` and `wwwroot/index.html` in the unpacked directory, matching file count. If any of these checks fails, the deploy stops, and production never even knew anything was happening. This is a direct answer to how the previous failure ended: a working half-build is worse than a deploy that never happened, because it looks like it succeeded.

**The previous release stays as `app.prev`**, so rollback is the same two renames rather than a rebuild and re-transfer: `.\Scripts\deploy.ps1 -Rollback`. It keeps the bad version as `app.broken`, so there's something to inspect.

**What the script deletes on the server**: `app.prev` (the release before last) and other people's archives in `staging/`. It never touches `data/`: the database and media live there, and no deploy operation goes above `app*`.

**Lesson**: the order of deploy steps is exactly what makes it reliable. The old script stopped the service as the first of three risky actions, and any error after that turned into an outage. The new one is arranged so that everything that can fail happens before the stop, and only operations that can't run long remain after it.
