# ADR-163 — A bench control that navigates is an anchor, and the control carries the route

**Context.** Three hub destinations were anchors before the port: the assets and builds actions and
the planner card link were `<a [routerLink]>`, and the "up next" row was
`<a [routerLink] [queryParams]>`. The port replaced them with `app-module-tile` and `app-task-tag`,
whose hosts are `role="button" tabindex="0"` with a click handler calling `router.navigate`.
Keyboard access survived. What did not: middle-click and Ctrl-click to open in a tab, the context
menu's copy-link-address, and the status-bar URL preview on hover. `router.navigate` is a function
call; a browser cannot offer any of that over a function call, because there is no URL to offer.

The same question already had an answer one component away. `app-hook-rail` renders each hook as a
real `<a [routerLink]>` and says why in a comment on its own API: *"A hook is a link, so a middle
click opens it in a tab."* So the app shipped both answers at once — the rail opening in tabs and
the wall of plates on the same screen refusing to — and neither was written down.

The pressure to make a plate a button is the kit, not the platform. `ModuleTile.jsx` in the mirror
is `React.createElement('button', { onClick })`, and `TaskTag` is drawn the same way; the kit draws
these as plates, and a plate looks like a thing you press. The kit is a drawing of a surface. It has
no router, no history and no tab strip, so it cannot have an opinion on this.

**Decision.** A bench control whose activation is a navigation renders a native `<a>` and carries
the route itself. A bench control whose activation is anything else — a filter, a mode, a dialog,
a language — stays a native `<button>`. Which one a given instance is, is decided by the consumer
handing it a route, not by a variant flag.

**Attribution.** *This is the implementer's choice under a verified regression report. It was not
put to Marty as a question.* What it reverts to is the shipped port, and the cost of reverting is
the three affordances named above.

1. **One input, and it is the route.** `link` takes what `routerLink` takes, the same wording
   `HookRailItem.link` already uses. Set, the control renders `<a [routerLink]="link()">`; unset, it
   renders `<button type="button">` and its `activated` output is the only way it says anything.
   `app-task-tag` takes `queryParams` beside it because its one commissioned destination is a task
   inside a board, which is a query and not a path segment. `app-module-tile` does not take it,
   because none of the four doors on the wall needs one, and an input added against a future call
   site is an input nobody can delete.

2. **The API stays closed where it was closed.** `ModuleTile.prompt.md` rules that a tile carries
   ONE number and the second belongs on the screen the tile opens. Today that is enforced by shape
   rather than by prose: the component has no `ng-content`, so a consumer's attempt to project a
   second readout reaches nothing. An anchor form does not need a content slot, and does not get
   one. The unit test that hangs a second readout on a tile and finds it gone is the guard, and it
   guards the anchor form too.

3. **The control is inside the host, not the host itself.** An Angular host element is
   `<app-module-tile>` whatever else it is told to be; a tag name cannot be switched at runtime. So
   the interactive element moves inside the template and the host becomes the wrapper that carries
   `data-surface` and the tilt — the shape `app-button` already uses. Two consequences are load-
   bearing and both are checked: the paper block keeps `min-height: var(--hit-target)`
   unconditionally, because the global coarse-pointer rule matches `[data-surface] button` and not
   a bare `<a>` (ADR-074 exempts inline links, and a plate is not one); and `data-surface` stays on
   the host, so `--hit-surface` still reaches the control by inheritance and is never pinned by a
   selector (ADR-156).

4. **`role="button"` and `tabindex="0"` are deleted rather than moved.** Both existed to give a
   non-control host the behaviour of a control. A native `<button>` and a native `<a href>` are
   focusable and Enter-activated by the platform, and a `<button>` takes Space as well — so the
   hand-written `keydown` handler goes with them. Its unit test is replaced by one that reads the
   tag name and, for the link form, the resolved `href`: the platform's guarantee is the assertion,
   and an `href` that never rendered is what a role attribute would have hidden.

5. **In link form the control does not also emit.** The anchor navigates; `activated` stays silent.
   A consumer wiring both would navigate twice to the same URL, and the second navigation is the
   one that would look like a bug months later.

**Rejected.** *A `variant="link"` flag beside a click handler.* Two inputs for one fact, and
nothing stops a link-variant tile with no route. The route's presence is the fact. *Letting the
call site write `<a app-module-tile [routerLink]>` through a second selector.* The component then
cannot tell whether it is a link, its own stylesheet has to cover a tag it does not control, and
every consumer has to remember both halves. *Stretching an invisible anchor over the plate,
Bootstrap-style.* The plate's accessible name would come from the overlay rather than from the
content that is actually on it, and a text selection inside the plate stops working. *Leaving it as
it was and calling the keyboard path sufficient.* Keyboard access was never the thing that broke.

**Consequence.** Every bench control that gains a destination from here on is governed by this, and
the cost lands on the ones that have not been written yet: a control that is sometimes a door and
sometimes a switch has to render two elements, and its stylesheet has to reset an anchor's
underline and a button's font in the same rule. That is the price of the address bar.

The debt this leaves is named rather than absorbed, and it is all one debt: opening a document.
The hub's "Continue" action, the hub's document rows and the posts manager's "Open in editor" all
reached `/editor?draft=…` from a `<button>`. None was a port regression — every one of them was a
button on `master` — and what stood between them and the rule above was one decision nobody had
made: what a pine button looks like when it is a link.

**ADR-169 makes it, and the three are anchors.** The answer is that a pine link is a pine button:
the face belongs to the variant and the tag to the consumer, so `app-button` gained a link form that
adds `text-decoration: none` to the stylesheet and nothing else. The hub's Continue is that form;
the hub's document rows and the posts manager's action are page markup rather than bench controls
and take `<a routerLink>` directly. `openDocument` and `openInEditor` are gone with them.

What is left is one site this entry did not name and one class of action it does not reach. The
site is `/drafts`, where all three views open a draft from a `<div>` carrying a click — a defect
older and larger than this rule, since a `<div>` is not even keyboard-reachable, and one an anchor
cannot fix in place: each row holds a folder picker and three mini buttons, which an `<a>` may not
contain. Making only the title a link while the row keeps its handler would navigate twice from one
click, which is what clause 5 exists to stop, so the row's shape is the decision and it is on the
board (`T-261`). The class is create-then-navigate — a new document, a devlog, a changelog — which
stays a button, because the id it would link to does not exist until the server answers.
