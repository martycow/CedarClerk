# ADR-119 — Stage 2: the logic moves into C#, the scripts become thin wrappers (12.08.2026)

ADR-118 ended with the phrase "stage 2 is a separate decision." Here it is. Marty: "go ahead with stage 2; the main thing is that everything still builds, tests and deploys the way it did before."

**Decision 1 (rewritten the same day per Marty's remark): `deploy.ps1`, `build.ps1` and `test.ps1` are deleted, not kept as wrappers.** There is now exactly one entry point for the logic — `cedar`.

The first draft of this decision left the three scripts as thin wrappers calling `cedar`, so that `.\Scripts\deploy.ps1` kept working under its old name. Marty asked: "do we actually need them? there's basically no code in them." A check answered on my behalf — **not a single automated call uses them**: not CI (there isn't any), not `e2e.ps1`, not the npm scripts, not electron-builder. All 30 matches across the repo were mentions in comments and documentation — that is, text that gets fixed by the same motion as everything else.

So the argument "the name is written into CLAUDE.md and into muscle memory" was resting on nothing: I was rewriting the documentation in that same session, and there is exactly one set of hands, and they asked for it to be removed. What would have remained, and all of it a cost rather than a benefit:

- **a second surface of flags** to keep in sync: `-SkipBuild` ↔ `--skip-build`, `-Ascii` ↔ `--no-unicode`, `-CloudHost` ↔ `--host`. A new flag tomorrow means two edits instead of one, and a forgotten second one shows up as "why doesn't it work from the script";
- **a risk of recursion** that doesn't exist without the wrappers: an installed `cedar` older than the scripts calling them back. A guard with an environment variable had to be put in place — protection against a problem created entirely by the wrappers themselves;
- **two names for one thing** in every sentence of documentation.

The one thing the wrappers honestly provided was running on a machine where `cedar` isn't installed yet, via a fallback `dotnet run`. That hasn't gone anywhere — it just moved to where it belongs: **`install-cli.ps1` is the entry point on a fresh clone**, and after it everything else is `cedar`. The circle "the script only works after the tool that the script installs" isn't broken by a fallback path in three places, it's broken by there being exactly one install, and it coming first. The emergency path, if `cedar` itself is broken, is also just one, and it's documented: `dotnet run --project CedarClerk.Cli -- deploy`.

What remains in `Scripts/`: `e2e.ps1` and `install-cli.ps1` (Decision 3). Both are genuine scripts, not redirection.

**Lesson worth recording**: "but it's written in the documentation" is not an argument for keeping an interface when you're the one writing that documentation, in this same session. The real argument is an existing caller that can't be fixed. There wasn't one here, and checking that cost one `grep` — which only got run after the question was asked.

**Decision 2: `cedar deploy` now actually deploys.** This reverses Decision 2 from ADR-118, and it's reversed along with its own reason, not against it.

The reason went like this: `deploy.ps1` has no safe stopping point before the directory swap, so "run to the last step and halt" would mean cutting the script apart — in the very same session that was changing the interface calling it. Then the first failed deploy would be inexplicable: new logic, or a new wrapper? At stage 2 there's nothing left to cut apart. The logic is rewritten wholesale, together with its interface, meaning exactly one thing changes — the deploy implementation — and it changes completely.

What survives from the old decision and must not disappear: **a human presses the button.** `cedar deploy` shows the preflight, prints the version pair, and **asks, defaulting to "no"** (`.claude/rules/destructive-operations.md`). `--preflight` keeps the previous behavior — checks and stop; `--yes` is needed by the wrapper so that `.\Scripts\deploy.ps1` behaves as before, i.e. asks only once, not twice.

**Decision 3: not everything moves, and the boundary isn't set by file size.** `_git-guard.ps1`, `build.ps1`, `test.ps1`, `deploy.ps1` — these move: it's orchestration, branching and reporting, exactly what C# does better and PowerShell does more verbosely.

These stay as scripts:
- **`e2e.ps1`** — it's not an orchestrator but a rig: it wipes `CEDAR_DATA_DIR`, brings up the server with no bot token, registers an account, restarts the server for admin bootstrap, runs Playwright, and shuts the server down no matter what happens. This is process lifecycle and environment variable management — exactly what a scripting language exists for. `cedar test --smoke` calls it as one phase.
- **`install-cli.ps1`** — bootstrap. Installing `cedar` by means of `cedar` is impossible by definition, and attempting it would be exactly the circle from Decision 1.

**Decision 4: `tar` stays external.** .NET 8 has `System.Formats.Tar`, and there was a temptation to drop the dependency on `tar.exe`. Rejected for two reasons, the second more important than the first. First: on Windows a file has no unix mode, `TarWriter` writes zero there, and files would unpack on the server with `000` permissions — that is, a deploy that passes every check and doesn't start. This is workaroundable, but only verifiable on the server. Second: changing the packer in the same session that changes the orchestrator is exactly the mistake ADR-118 guarded against at stage 1. The bytes on the wire remain the same as yesterday's.

By the same logic, kept unchanged: the detection of GNU tar for `--force-local` (GNU reads `C:\...` as host `C`), archive reuse keyed by the `files|bytes|mtime` signature (gzip stamps the time, so repacking the same input produces different bytes and kills the resume), resume via `cat >>` instead of `scp` (scp starts from zero), sha256 on the far side, unpacking into `app.new` before stopping the service, the swap done in a single ssh call, `app.prev` for rollback, and the `.exe` → `.blockmap` → `latest.yml` order for desktop (ADR-116).

**Decision 5: deploy steps are data, not a sequence of calls.** Each step is an object with a name, a detail and a body; the executor keeps a timer, draws a live screen, and assembles the report. This is what made possible the interface Marty asked for ("the cooler, the better"): a progress bar with speed and ETA, a **live braille throughput graph** (the same `BrailleChart` as on the dashboard), a downtime counter in milliseconds, and a final summary with proportional time bars. None of these elements knows what it's actually measuring, so adding a step doesn't require touching the rendering.

ADR-118's rule about color applies here too: every bar has a number, every status has a word, and `--no-unicode` still strips all the graphics down to ASCII.

**Decision 6: `_git-guard.ps1` is deleted.** Its only consumers were the three scripts that moved, and `GitGuard.cs` is it, verbatim, along with the `LIVE`/`LIVE-PREV` tag logic (ADR-118, Decision 12). A file left behind "just in case" is a second implementation that will silently drift from the first.

**What this costs, honestly.** The riskiest script in the project no longer has a parallel copy to fall back to with a single run. Rollback is now git (`git show <commit>:Scripts/deploy.ps1`), and the first real deploy with the new code has to be done with a witness present. This is mitigated by the failure modes staying the same by construction: the service doesn't stop until the archive is checksum-verified and unpacked, `app.prev` is in place, `-Rollback` works, and an interrupted upload resumes from the same byte.
