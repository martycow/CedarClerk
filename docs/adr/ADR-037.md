# ADR-037 — Phase 8 Step 7: comment replies (one level), owner highlight, name reservation, dual timestamp
**Context**: `docs/ROADMAP.md` Step 7 listed four sub-items with zero prior implementation: replies, highlighting the channel owner's own comments, reserving the owner's display name, and showing both the post's publish time and each comment's write time. The comment system (`Comment` entity, `BlogEndpoints.cs`) has no account/identity concept at all — comments are anonymous, free-text `AuthorName`, no `VisitorHash`-equivalent tracking (unlike `Reaction`). Rendering is vanilla JS embedded in `BlogEndpoints.cs`'s `ShellTemplate` (not an Angular component), which shaped every decision below toward minimal, dependency-free client code.
**Decision** (26.07.2026):
- **Replies**: `Comment.ParentCommentId` (`Guid?`, plain scalar, no nav property or FK constraint — matches `Comment.DraftId`'s existing shape, consistent with `docs/ARCHITECTURE.md`'s "no strict FK-only model"), migration `AddCommentParentId`. **Scoped to one level of nesting** — `PostCommentAsync` rejects (silently falls back to top-level) a `ParentCommentId` that itself already has a parent, and the client UI only ever offers a "Reply" button on top-level comments. A full comment tree was judged unnecessary complexity for a personal blog's comment volume.
- **Owner highlight**: `owner.AuthorDisplayName` (already loaded in `RenderPostAsync` for header slots, ADR-034) is passed into `AnnotationControlsHtml` as a new optional parameter and rendered as an HTML-encoded `data-owner-name` attribute on the whole-article `.comment-box`. **Scoped to the whole-article comment box only** — per-fragment inline annotations don't receive it, since threading the value through `RenderContext`/`Render()` for every inline annotation instance would add real plumbing for a cosmetic detail; the highlight simply doesn't apply there (graceful degradation, not an error).
- **Name reservation**: no reservation table — `PostCommentAsync` compares the submitted `AuthorName` (case-insensitive, trimmed) against the live `owner.AuthorDisplayName` at submit time and rejects with 409 if they match. Skipped entirely when the owner hasn't set a display name. **Known accepted edge case**: the real owner commenting through the anonymous public form (not the authenticated `/comments` management page) would also be rejected — there's no identity verification on the public form to distinguish "the real owner" from an impersonator, so this is the same check either way.
- **Dual timestamp**: `draft.BlogPublishedAt` is passed into the same `AnnotationControlsHtml` call as `publishedAt`, rendered as one "Post published: {date}" line above the comment list (whole-article box only, same reasoning as the highlight scoping) — each comment already showed its own `createdAt`.
- Error surfacing in the vanilla-JS comment form uses a plain `alert()` for the reservation rejection — every other fetch on this page silently swallows errors (`.catch(function(){})`), but silently dropping a rejected comment with no explanation would be worse UX than a blocking `alert()`. No styled-modal infrastructure exists on this vanilla-JS blog page (unlike the Angular app's `ModalComponent`, ADR-028) to do better without adding one.
**Consequence**: `GetAnnotationsAsync`'s per-comment projection and the create-comment response both gained `parentCommentId`; the owner's private `/comments` management page (`comments.component.ts`, `GET /api/comments/`) was deliberately **not** updated to show reply threading — out of scope, Step 7 is about the public reading experience. Not yet verified live in a browser as of writing (deferred by Marty's choice this session).
