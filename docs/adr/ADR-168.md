# ADR-168 — The project index is not the hub's shelf: what the switcher refused stays a screen

**Context.** `docs/design/UI-V2-PLAN.md` §Stage 5 files three screens under one pattern — a
`Worktop` carrying the content and a `ShelfPanel` for what is contextual to it — and adds a
parenthesis against the first of them: *`projects` (absorbed as the hub's left shelf)*. Stage 4 then
built half of that. ADR-160 rule 5 put the projects list into the hub's left dock as a **switcher**,
kept search, the filter chips, the counts and project creation on `ProjectsComponent`, and said in
its own consequence paragraph that the route tree is `T-226`'s to change rather than that task's.

So the open question this entry answers is not how to draw three screens. It is whether `/projects`
still exists after the absorption, and, if it does, what each of the two lists is for.

The three screens also share three defects the port has already named elsewhere and not yet reached
here. Every row that opens something is a `<div>` or a `<button>` with a click handler — five of
them across the three files — which ADR-163 settled: a control that navigates is an anchor. Two of
those handlers navigate to `/editor` with an `id` query parameter, and `editor.component` reads only
`draft` (the `queryParamMap.get('draft')` call in `openInitial`), so a devlog draft and a changelog
document have been opening *the most recently edited draft* rather than themselves, silently,
whenever the new document was not also the newest. And `project-planner` and `project-builds` draw
the same object — a `GameTask` — as two different rows with two different sets of fields, while
`bench/display/task-tag.component.ts` was cut for exactly that object and names both screens in its
own comment.

**Decision.**

1. **`/projects` stays a route and stays a screen.** Three things stand on it that a 300px dock
   cannot hold and that ADR-160 rule 5 already refused to move: the create-project modal (a type
   list, a name field), the empty state with the example project (ADR-133), and search with three
   state filters over a list that has no upper bound. Two more stand on it structurally — the hook
   rail's Hub tool and the rail header's project tile both point at `/projects` whenever no project
   is in the URL (`bench/chrome/bench-shell.component.ts`), and an account with no projects has no
   hub to land on at all.

2. **What was absorbed is the switch, not the list.** The two are one dataset doing two jobs and
   each names the other: the hub's dock switches between projects while you are inside one, and its
   header action links here; the index is where a project is found, made and compared, and every row
   links to that project's hub. Neither grows the other's controls — the dock takes no search and no
   create, and the index does not become a second switcher. That is the "consistently" half of
   `T-226`: the duplicate ADR-160 accepted for one stage is resolved by giving the two lists
   different jobs, not by deleting one of them.

3. **Every row that navigates is an anchor, and the editor is addressed the way the editor reads.**
   The five click-handler rows become `routerLink` anchors — index rows, planner task rows, build
   task rows, build document chips — and `openDocument`/`createDevlog` send `draft`, not `id`. The
   second half is a bug fix carried by the port rather than caused by it, and it is recorded here
   because a reader of the diff would otherwise take it for a rename.

4. **A task is a task tag on both screens, and its status is the projected stamp.** `app-task-tag`
   takes the title, the priority chip, the due date with its overdue ink and the done fade, and
   `app-stamp-badge` goes into its `stamp` slot for the status. `project-builds` gains the priority
   and the due date it was not drawing, because the alternative is one object drawn two ways on two
   screens one click apart.

5. **One worktop per screen; the shelf carries the standing summary.** This is ADR-164 rule 4's
   shape applied to three more screens: the right column is never empty, and it carries only sums
   over rows already fetched — active and archived projects, documents, open tasks and assets on the
   index; sprint states, the pile of unplanned tasks and the current sprint's progress on the
   planner; released and unreleased versions, their tasks and their documents on the builds screen.
   Nothing is fetched to fill it and nothing is estimated.

6. **The screen's commands stay on the screen.** `core/rail-actions.service.ts` carries one action
   by type (ADR-159 clause 2) and each of these screens has two — a create, and a link to a sibling
   screen. The hub settled this shape already by keeping both of its commands in the worktop; the
   link half additionally cannot be an `app-button`, which has no anchor form (ADR-163's recorded
   debt), so it stands in the shelf as a text link beside the summary it belongs to.

7. **The index keeps `data-density="compact"`; the planner and the builds screen drop it.** ADR-164
   rule 6 draws the line where ADR-071 principle 3 does — a table you scan against a screen you
   read — and these three fall on opposite sides of it: the index is a seven-column list, the other
   two are stacked cards, which is what the hub is and why the hub carries no density attribute.

8. **Nothing is drawn that the API cannot answer.** The kit's project card carries a cover image;
   `ProjectSummary.coverUrl` is real and `PUT /api/projects/:id` accepts it, but no screen in the
   app ever sets one, so the thumbnail stays the wood-and-initials plate the hub's switcher already
   uses and shows an image only if one ever arrives. A sprint burndown, a velocity, a build size and
   a per-version download count are all absent from the schema, and none of them is drawn as an
   empty row.

**Rejected.** *Retiring `/projects` and moving creation into the dock's header*, which would put a
modal behind a 28px action in a switcher, leave a fresh account with nowhere to land, and strand the
example project. *A redirect from `/projects` to the last-opened hub*, which needs a stored
last-opened project the app does not have and makes the Hub tool's destination depend on history.
*Drawing planner tasks as compact ruled rows and hub tasks as tags*, which is the same object in two
vocabularies and the reason item 4 exists. *Putting each screen's create on the rail*, which spends
the one primary action the rail can hold on the screen that needs it least.

**Consequence.** The index and the dock will drift apart if someone adds a control to one and not
the other; what guards it is the pair of assertions that the dock carries no search field and the
index carries no `aria-current` row. Item 3 changes what two buttons do rather than how they look,
so a reader comparing screenshots will not see it — the specs name it instead. Item 4 makes the
planner taller: a sprint of twenty tasks is twenty tags on a grid rather than twenty 32px rows,
which is the kit's density and not this port's invention, and the collapse behaviour on finished
sprints is what keeps a long history out of the way.
