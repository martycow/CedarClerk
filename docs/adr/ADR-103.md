# ADR-103 — "At least one document per project" is a UI rule, not a DB constraint (10.08.2026)

**Context**: the brief requires that a `Project` must always include at least one document.

**Decision: the rule lives in project creation, not in the schema.** Creating a project, in one transaction, also creates a starting document from the template of the chosen project type; deleting a project's last document is forbidden at the endpoint with a clear error.

**Why not a constraint**: a schema-level requirement breaks on the very first `INSERT` — a project can't reference a document that doesn't exist yet, and a document can't reference a project that doesn't exist yet. This gets resolved either by deferred constraints (SQLite can't do those) or by a nullable "first document" field, which guarantees nothing. That is, the constraint would end up decorative anyway — better to keep the rule right where it's actually enforced.

**Consequence for the UI**: creating a project is a selection dialog, not a "name" field. An empty project doesn't exist in the system, not even for a second.

**Narrowed, then restored — within one day.** On the morning of 10.08, the project-type taxonomy was removed as invented: neither the brief nor Marty had such categories, and a classification with nothing to say for itself is a spare concept in place of a decision. That evening Marty brought a design handoff (`docs/design_handoff_indiedev_core_loop/`) in which the creation dialog is exactly a **project type** choice, with four concrete types and a starting document for each:

| Type | What it is | Starting document |
|---|---|---|
| `fullgame` | The whole toolkit: documents, sprints, asset index, press kit | GDD (master) → `design` |
| `jam` | Deadline first: one sprint, a plan, a submission checklist | Jam plan → `design` |
| `prototype` | A question that needs an answer. Notes and tasks, no ceremony | Hypothesis note → `note` |
| `released` | Post-release: patches, changelogs, press | Changelog → `changelog` |

**This isn't a reversal of the narrowing, it's the reason for it.** The narrowing removed a concept that had no product decision behind it; the handoff brought that decision. `ProjectTypes` lives in Core next to `DocumentTypes` and answers exactly one question — which document a project starts with. Beyond that, the project type constrains nothing: a `prototype` project is free to hold documents of any type.

**The server doesn't invent the starting document's title.** "GDD (master)" and "Jam plan" are user-facing text, and the server has no second language (`ErrorMessages` is translated, content isn't). The type is derived on the server as a rule; the title is sent by the client, which already has both locales; without a title, the project's name is used.

**What this looks like in code**: `POST /api/projects` accepts `{ name, description, documentType, documentTitle }` and writes `Project` and `Draft` with `ProjectId` set in a single `SaveChangesAsync`. The other side is deletion: `DELETE /api/projects/{id}` **detaches** documents (`ProjectId = null`) rather than deleting them, unlike what `FolderEndpoints` does with folders, and for a stronger reason — a project holds what was actually written, and deleting the container must not be a way to accidentally lose that. The "can't delete the last document" refusal sits in two places: on the module's path and in the ordinary `DELETE /api/drafts/{id}`, because a rule kept by only one of two doors isn't a rule.
