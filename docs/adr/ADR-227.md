# ADR-227 — Invite-link analytics keeps daily tallies, never member identities (29.08.2026)

**Context.** Wave 2 item 15 answers "which link brings channel members": named Telegram invite links per channel, with joins and leaves read from `chat_member` updates (the bot receives them wherever it is admin, which posting channels are). Every such update carries the full user object of the person who moved — id, name, username — so the tempting build is a member log: who joined, when, through what, who left. The app already refused that shape twice: reader geography is a daily aggregate, not a visit log (`BlogViewGeoDaily`, ADR-097), and reader identity on the blog is a salted hash, never an IP (ADR-016).

**Decision.** The same stance, third surface:

1. `ChannelInviteLink` stores the link itself — name, the `t.me/+…` URL exactly as Telegram returned it (the join update's match key), created/revoked stamps. A revoked link keeps its row: the tallies that attributed to it still point here.
2. `ChannelMemberDaily` is the **only** thing ingestion writes: joins and leaves per (owner, channel, UTC day, invite link). Nothing about the person survives the handler. Null `InviteLinkId` is the organic/unattributed row — and every leave lands there, because Telegram attaches no invite link to a leave; the UI note says so rather than implying leave attribution exists.
3. Membership is a line, and a mute does not cross it: `ChatMemberRestricted` defers to its own `IsMember` flag, so a restriction applied to someone still in the chat counts as neither join nor leave (a tester finding — the first cut read every mute as churn). Admin promotions of existing members likewise move nobody.
4. The bot is shared, so two accounts may have connected the same channel: every `Channel` row with that chat id gets its own tally — each owner's analytics are their own.

**Consequence.** The stats shelf can answer "how many, when, via which link" and can never answer "who" — there is nothing to leak, nothing to export, nothing for a deletion request to find. The price is real and accepted: no per-member retention or cohort analysis, ever, on this data. `GET /api/channels/{id}/member-flow` serves the daily series; the Wave 2 UI ships lifetime totals per link and leaves the per-day bars on the board.
