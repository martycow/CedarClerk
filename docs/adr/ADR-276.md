# ADR-276 — Engine and platforms cross the wire as keys, and the API refuses what the column would forgive (05.09.2026)

**Context.** ADR-160 §7 left the hub's chalk edge empty because the app stored no engine and no
target platforms. A1's schema (T-247) adds `Project.Engine` — one key from `ProjectEngines` — and
`Project.TargetPlatforms`, a comma-joined subset of `ProjectPlatforms` in list order.
`ProjectPlatforms.Parse` drops anything it does not know, which is the right reading of a stored
column and the wrong reading of a request.

**Decision.**

1. **On the wire the engine is a string (`""` = unset) and the platforms are a `string[]`**, parsed
   from the column on every projection that carries the project — list, detail and the PUT
   response — so no client ever sees the delimiter.
2. **`UpdateProjectRequest` takes both as nullable, and null means "leave it".** A client written
   before the fields existed sends neither and changes nothing; `""` and `[]` clear. The name and
   description keep their existing semantics.
3. **An unknown key is a 400 naming the key, never a silent drop.** `Parse` forgives what is
   already in the column because a list can shrink; a request naming `amiga` is a client bug, and
   swallowing it would store an empty field with no complaint. Known keys are stored through
   `ProjectPlatforms.Join`, so order and duplicates never reach the column.

**Rejected.** *Free text for the engine* — `PressEngine` already is that, for the press page; the
hub wants a key it can label in two languages. *A PATCH endpoint for the two fields* — the settings
modal already PUTs the project, and a second door for two fields is the ADR-095 mistake in small.

**Consequence.** `engine` and `targetPlatforms` appear on `ProjectSummary` and `ProjectDetail`;
B2's pickers write them through the existing update. Adding a key means a Core constant plus
labels in both dictionaries, and nothing else.
