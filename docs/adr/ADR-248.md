# ADR-248 — Navigation gives each destination one door (02.09.2026)

**Context.** The sidebar repeats *All projects* in the project switcher and its foot, repeats
Settings between the foot and account menu, and presents the sidebar mode as another navigation
row. Teams was placed in Library even though a Team manages project access. The account popover has
grown into a second settings surface and opens over the sidebar because the generic popover has no
side placement. Settings then gives an entire Account tab to one language control while Appearance
remains a modal outside Settings.

**Decision.**

1. The project switcher is the only project-level switch: current and recent projects, *All
   projects*, and *Manage teams*. The last two remain available when the account has no project.
   Teams leaves Library. Library contains Glossary and Presets only. This supersedes ADR-240's
   placement of Teams.
2. The sidebar foot contains identity and notifications, not a second navigation list. *Settings*
   exists once, in the account menu. The sidebar mode becomes a compact named control in the sidebar
   header, outside the navigation groups. Its stored state and full/rail parity from ADR-246 remain.
3. The account menu contains identity and plan context, Settings, Feedback, Help or About, developer
   tools when allowed, and Log out. It does not duplicate Profile, Account, Appearance or theme.
   Fullscreen is a transient shell action, not an appearance preference.
4. An account popover uses an explicit side placement, stays inside the viewport, has one scroll
   owner and exposes `aria-haspopup`, `aria-expanded` and `aria-controls`. Escape and outside press
   close it and return focus to its trigger. ADR-246's one-transient-layer rule still applies.
5. Settings has Profile, Preferences, Integrations and Billing. Preferences contains Interface
   language and Appearance. Legacy `?tab=account` and `?tab=appearance` links resolve to Preferences.
6. Appearance is the only authenticated surface for persistent visual preferences. It owns theme,
   accent, sidebar mode, editor sheet measure, typeface, type scale, line spacing, editor aids and
   insert-table defaults. Theme and sidebar mode join the account's existing appearance preference
   payload; local storage remains the immediate bootstrap and signed-out fallback.
7. Reader controls on a public blog belong to that reader. Grid/list choice, open panels and column
   widths are working-view state. Design-system density remains a product invariant. None of these
   are author appearance settings.

**Rejected.** *Keep the links and merely restyle them* — duplicate destinations remain duplicate.
*Put Teams in Plan* — it still makes an account/workspace object look project-local. *Add a separate
Appearance page beside the one-control Account tab* — it preserves the weak tab. *Turn Appearance
into skins* — ADR-136's one Cedar Bench look remains.

**Consequence.** ADR-151's modal placement, ADR-239's footer composition and ADR-240's Library and
Display composition are superseded. Existing appearance JSON remains backward-compatible: missing
new fields use current defaults. Shell, popover and settings tests cover zero/one/many projects,
full and rail modes, legacy URLs, keyboard behaviour and preference reload.
