# ADR-026 — Markdown (.zip) import: hand-rolled scoped parser, matched by basename, Notion's native export format accepted as-is
**Context**: Marty exported a large Notion page as Markdown to test whether Cedar Clerk could import it — Notion's export is a single `.zip` containing the `.md` file plus its referenced images (confirmed with Marty; not two separate loose items as first assumed). No Markdown → Cedar (TipTap JSON) parser existed anywhere — only the reverse direction (`CedarToTelegramMarkdownRenderer` etc.). Marty's own content is "mostly text, images, and lists," not tables/embeds/toggles.
**Decision** (17.07.2026): Added `CedarClerk.Core.MarkdownToCedarConverter` — a **hand-rolled, deliberately scoped** line-based Markdown parser, not a full CommonMark implementation and not a new dependency (`CedarClerk.Core` is explicitly zero-external-dependency, `docs/ARCHITECTURE.md`). Supports headings, paragraphs, bullet/ordered/checkbox lists (checkbox lists map to the editor's real `TaskList`/`TaskItem` nodes, with indent-based nesting for sub-lists), block-level images, blockquotes, fenced code blocks, horizontal rules, and inline bold/italic/strikethrough/code/links — built with `System.Text.Json.Nodes` (`JsonObject`/`JsonArray`), matching the idiom every other Core file (`CedarPackage.cs`, the renderers) already uses. Anything outside this scope (tables, toggles, callouts, embeds) degrades to a plain paragraph of the raw line — never thrown away, never a crash. New endpoint `POST /api/drafts/import-markdown` (`DraftEndpoints.cs`) mirrors the existing `.cedar` import block almost line-for-line: same size caps (`CedarZipMaxBytes`, `CedarMaxAssetCount`), same `ImageContentSniffer`/`Consts.FileSizes.ImageMaxBytes`/`PlanLimitations.HasStorageRoom` checks, and reuses `CedarPackage.RewriteMediaPaths` unmodified — the converter just emits image `src` as a `/media/{basename}` placeholder (the exact convention `RewriteMediaPaths` already expects), so no new media-rewrite logic was needed. Images are matched to zip entries **by basename only** (Notion's exact subfolder path isn't preserved); any unmatched reference is reported back to the caller (`unmatchedImages` in the response) instead of silently leaving a broken image or failing the whole import.
**Consequence**: A same-named image appearing under two different subfolders in one zip (possible in a large multi-page export) resolves to whichever one is encountered first — a known, accepted limitation given the explicitly scoped basename-matching approach. Complex Notion-specific blocks (tables, toggles, callouts, database embeds) are not faithfully reproduced — they degrade to plain text — which was an explicit trade-off given Marty's stated content shape, not an oversight.
