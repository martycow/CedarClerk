# ADR-150 — The toolbar fits itself: adaptive rows, captions when there is room, no customization

**Context.** The editor's toolbar is the app's densest control surface and the port's biggest density delta. It ships as two rows of ~58px inside 187px of vertical chrome; the bench shell budgets 56 + 32 + 30 = 118px of global chrome plus one in-content tool strip, and the kit draws that strip 36px tall (`ui_kits/writer.html:48`).

What has to fit in it: `ALL_BUTTON_IDS` is 34 buttons across eight groups (`core/toolbar-layout.ts`), plus a block-type dropdown and undo/redo pinned outside the group system, plus the AI popover pinned to row 1. The kit's strip carries nine buttons, one block-type chip and two dividers. At the kit's own box — `.tb` is 26px with a 4px gap — 34 buttons alone are ~1020px, and the writer kit's middle column measures 1440 − 52 (`--bench-tool-w`) − 24 (content padding) − 20 (two gaps) − 224 (structure shelf) − 330 (inspector shelf) = 790px, leaving ~774px inside the strip's padding. One row does not fit the default layout, and it is not close.

The rows are also *user property*. ADR-035 built `ApplicationUser.ToolbarLayoutJson` — `{ preset, row1Groups, row2Groups, hiddenButtons }` — with four presets, group-level placement between the two rows via `@angular/cdk` drag-drop, and a per-button visibility catalogue; `ToolbarLayoutService` loads it on every `authGuard` pass and the editor renders `row1Ordered()` and `row2Ordered()` through one `<ng-template>` per group.

One premise in the plan's Q-21 is wrong and the code wins: **group captions already ship**. `.tb-caption` appears ten times in `editor.component.html`, one per group plus the block-type chip and the accented `AI · Pro Plus`. They are unconditional today.

**Decision.** This is Marty's answer to Q-21, verbatim: «Адаптивно либо 1, либо 2 строки с кнопками. Если хватает место - добавляй подписи групп. Но кастомизацию убирай - она лишняя.»

1. **The strip is adaptive: one row when the controls fit, two when they do not.** The count of rows is measured from available width, not stored, not chosen. At the kit's own writer dress it will be two; on a wide window with both shelves collapsed it can be one.

2. **Group captions appear only when there is room.** They are not added — they exist — they stop being unconditional and become the first thing the strip gives up, before wrapping to a second row.

3. **Customization goes entirely.** `core/toolbar-layout.service.ts` is deleted and its injection in `core/auth.guard.ts:11` with it; the Appearance panel's whole toolbar section (`appearance-panel.component.html:89-141`) goes, along with the `settings.toolbar` string block in `core/i18n/en.ts` and `ru.ts` and the four inventory rows that describe those controls. `core/toolbar-layout.ts` keeps the part that is a *catalogue* — `TOOLBAR_GROUPS`, the ids and their canonical order, which the strip still renders from — and loses `ToolbarLayout`, the four presets, `hiddenButtons`, `normalizeRows` and `parseToolbarLayout`.

4. **The mechanism ADR-035 built for two rows survives, because there are still two rows.** Each group's markup exists once as an `<ng-template>` instantiated into whichever row it lands in; the row assignment simply comes from measurement rather than from storage.

**Which ADR-035 clauses this voids.** Its first decision bullet, in full: `ApplicationUser.ToolbarLayoutJson`, the JSON-blob-not-columns argument for it, group-level row placement, and the per-button visibility catalogue. With it goes that entry's justification for `@angular/cdk` — "the first new frontend runtime dependency added in this project", added for these drag lists — which is the package's **only** consumer in `src` today. The other three preference fields are untouched: `AppearancePrefsJson` (whose `focusModeHideToolbar` is about hiding the toolbar, not composing it), `NewDraftDefaultsJson`, and `Draft.IsArchived`. So is everything in ADR-035's consequence paragraph about status badges and the tag cloud.

**What was rejected.** *One 36px strip at any cost*, as the kit draws it, would have to hide roughly two thirds of the buttons behind an overflow menu, which is per-button visibility again with the user's say taken away. *Keeping customization and making it adaptive too* — a stored row assignment and a measured one are two authorities over one layout, and the stored one silently loses every time the window is narrow, which is worse than not having it. *Keeping the storage while dropping the UI*, so a future panel could return: an unreachable preference that still steers rendering is a setting nobody can see and nobody can fix.

**Consequence, and the cost taken with eyes open.** Anyone who had hidden buttons gets them back, and anyone on the Minimal preset gets all 34. Nothing migrates that away — the stored blobs simply stop being read.

The column disposal is left open rather than decided: `ApplicationUser.ToolbarLayoutJson` (`CedarClerk.Server/Data/Entities.cs:134`) stops being projected at `AuthEndpoints.cs:233` and its save endpoint retires, but the column itself stays. An unread nullable column costs nothing, every saved layout stays recoverable if this is ever reversed, and dropping it on SQLite is a table rebuild for no benefit. *That disposition and the fate of the now-unused `@angular/cdk` dependency are the implementer's, under Marty's instruction to remove the feature — he was asked about the toolbar, not about a column or a package.* `T-229`'s task board is the one plausible future consumer of the package, which is a reason to leave the decision to whoever writes it.

Two stale artefacts fall out of the same area and should go with it rather than be rediscovered: `t().editor.tb.customize` ("Customize toolbar") is an orphan string with no trigger anywhere in the template — the only trace left is a row-1 comment that still names it — and `docs/design/UI-INVENTORY.md` describes six toolbar groups as "movable via Settings → Toolbar", which stops being true with the panel.

Implementation is `T-224`. This entry is the decision, and it lands before the code as the anti-desync rule requires.
