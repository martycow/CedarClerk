# ADR-108 — Desktop asks the Pi "who are you" but keeps the data local (10.08.2026)

**Context**: Marty's request after the desktop's first launch. He created a local account under the same email as on the Pi, and saw where this was headed: two accounts with the same address are different accounts, and nothing about it says so.

**Decision: identity's source of truth is the Pi; data stays local.** With `Cedar:Auth:Upstream` configured, desktop login is verified against `cedarclerk.mooexe.dev`, and the local user row is created (or picked up) under the remote identity. Registration on desktop is **disabled** as a result: the account is created on the server, and creating a second one locally is not possible — that's exactly what was producing the confusion.

**Why not full cloud mode** (the second mode from ADR-105, where desktop simply opens the website): then there would be one set of data, but **the asset index would stop working** — the server on the Pi can't see Marty's disk, and `Cedar:AssetIndex:Enabled` is off there by design (ADR-107). That would disable exactly the capability desktop exists for. Cloud mode remains a separate, not-yet-built option; this is not it.

**Identity is bound to an id, not to an email.** `ApplicationUser.RemoteUserId` stores the Pi's id; an email can change, an id doesn't. While the Pi's `/api/auth/me` still returns no `id` (builds before this one), email is used as a fallback key — it works today already and will self-correct once the Pi is updated.

**An existing local account is picked up, not duplicated.** On the first remote login, if a local row with the same email and no `RemoteUserId` already exists, the remote identity is attached to it along with everything already linked to it. Otherwise the very first login after this change would create a second account and do exactly what Marty asked to avoid. Picking up by email is safe here specifically because upstream authentication is only enabled on a single-user machine; on a shared server it's off.

**The honest cost, which needs to be said out loud: one identity is not one dataset.** Drafts on the Pi and documents on desktop remain different sets. With a shared account the expectation that they're the same thing gets **stronger**, not weaker — so the UI has to keep saying, continuously, that the data is local. Without that label, the decision makes the confusion worse, not better.

**Offline**: an already-issued session lives for 30 days (`Consts.AuthCookieLifetime`), so working without network is possible. **A new login requires the Pi** — and says so with a message distinct from "wrong password": "server unreachable" and "wrong password" are different things, and confusing them is the worst kind of login error.
