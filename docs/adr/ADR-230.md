# ADR-230 — A dialogue is a Yarn graph: the text is the graph, and the sheet keys on stamped line ids (30.08.2026)

**Context.** The maintainer's Unity game (Yarn Spinner for dialogue, Unity Localization for
strings) needs a place to write branching dialogue: a node editor, a `.yarn` file the engine can
load, and a spreadsheet translators can work in and hand back. Cedar Clerk already owns the
"one source, many outputs" shape and the gamedev module, so the tool lands there —
`/projects/:id/dialogues`, behind `Cedar:Modules:IndieDev`.

**Decision.** Four commitments:

1. **The stored unit is the graph, and the body is Yarn syntax.** `DialogueScript.GraphJson` holds
   the whole node list (`{id, title, x, y, body}`); the editor loads and saves it whole, so nodes
   are not rows. Edges are **never stored**: they are derived, on every keystroke and on export,
   from the jumps the bodies themselves name (`<<jump>>`, `<<detour>>`, `[[text|target]]`). A
   stored edge list would be a second copy of the text's own facts, wrong within one edit.
2. **`#line:` ids are stamped at save, not at export** (`YarnDialogue.EnsureLineIds`, in Core,
   dependency-free and unit-tested). The xlsx sheet keys on those ids, so they must exist in the
   stored body before the first export and survive every edit after — stamping at export would
   re-key the sheet each time. Existing tags are never rewritten.
3. **The sheet is a round trip, and the base text always re-reads from the body.** Export writes
   `Id | Node | Character | Text` plus one column per language (stored translations filled in);
   import upserts `DialogueLineTranslation` by (script, line id, language). An empty cell means
   "not yet", never "delete"; an unknown line id is imported, not refused — a line deleted in the
   editor and restored by undo gets its translations back, and losing a translator's work to a
   race with editing is the worse failure. The xlsx itself is `ClosedXML` (server-only; Core stays
   package-free).
4. **The `.yarn` export carries `position: x,y` headers**, so the canvas layout survives into Yarn
   Spinner's own VS Code graph view. Node titles are sanitized to Yarn identifiers at export
   (`SafeTitle`); two nodes collapsing onto one sanitized name are refused at save, because Yarn
   addresses nodes by title and the collision would silently rewire their jumps.

**Consequence.** One new dependency (ClosedXML), two tables (`DialogueScript`,
`DialogueLineTranslation`), and no engine integration to maintain: like the Steam/itch renderers
(ADR-223), the tool ends at files the engine's own pipeline accepts. The price of deriving edges
is that a typo'd jump simply draws no arrow — accepted, since the same typo would fail the same
way in the engine, and the graph shows it earlier.
