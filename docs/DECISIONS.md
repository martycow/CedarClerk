# Decisions (ADR log)

Consequential technical/product decisions already made and visible in the codebase or prior planning docs, recorded here per `CLAUDE.md`'s anti-desync rule: **any time a decision here changes, update this file first, then write code.** Entries are append-only; a superseded decision gets a new entry that references the old one rather than an edit-in-place.

### ADR-001 — Backend: C#/.NET 8 LTS, Rust excluded
**Context**: Choosing a backend language/runtime for a personal project that must run on a Raspberry Pi 4 (armhf).
**Decision**: C# on .NET 8 LTS. Rust was considered and excluded.
**Consequence**: .NET 8 is the only runtime version supported on Bullseye/armhf without extra work; support runs to ~November 2026, tying the runtime upgrade to the planned OS migration (`.claude/rules/production-environment.md`). Rust offered no advantage in this stack and was dropped without further evaluation.

### ADR-002 — Frontend: Angular + TipTap, standalone components
**Decision**: Angular (standalone components, signals) with TipTap as a headless rich-text editor operating on a JSON document model, used directly (not via the `ngx-tiptap` wrapper originally scoped).
**Consequence**: The TipTap JSON *is* the document format (`Draft.CedarJson`) — see ADR-006. Frontend conventions (signals, `inject()`, thin RxJS→Promise services) follow from this choice; see `docs/ARCHITECTURE.md`.

### ADR-003 — Database: SQLite + EF Core
**Decision**: SQLite via EF Core, single file, WAL mode enabled at startup.
**Consequence**: Trivial backup story (file copy), no separate DB server to run on the Pi. Ties migration discipline directly to `Entities.cs` — see `.claude/rules/ef-migrations.md`.

### ADR-004 — Hosting: Raspberry Pi 4 + Cloudflare Tunnel, no reverse proxy
**Context**: Home internet has NAT/dynamic IP (Xfinity).
**Decision**: Self-host on a Pi 4, exposed via Cloudflare Tunnel rather than port-forwarding. No separate reverse proxy (nginx/Caddy) — Tunnel routes straight to Kestrel on :8080.
**Consequence**: Zero open inbound ports, HTTPS handled entirely at Cloudflare's edge, Kestrel only ever serves plain HTTP. Port 8080 is effectively fixed infrastructure, not a free choice — see `.claude/rules/production-environment.md`. Planned migration off the Pi: once there's a first paying user, move to a VPS and demote the Pi to staging (not yet done).

### ADR-005 — Telegram transport: long polling (not webhook)
**Context**: Early planning (`docs/ROADMAP.md` §1) favored a webhook through the tunnel, with long-polling as a fallback.
**Decision (supersedes the above, as actually implemented in Phase 2)**: `TelegramBotService : BackgroundService` uses **long polling** as the primary and only mechanism; webhook mode was left optional/deferred and was never built.
**Consequence**: Exactly one process may poll a given bot token at a time — this is the source of the 409 Conflict hard rule (`.claude/rules/telegram-bot.md`). If webhook mode is ever revisited, that constraint changes and the rule needs updating.

### ADR-006 — Document format: `.cedar` as a zip container
**Context**: Needed a portable export/import file format for drafts, including embedded media.
**Decision** (08.07.2026): `.cedar` is a zip container — `document.json` (`{ formatVersion, meta, doc: <TipTap JSON> }`) plus an `assets/` folder — modeled on `.docx`/`.epub`. Base64-encoding assets inline in the JSON was evaluated and rejected (+33% size cost).
**Consequence**: `CedarPackage` (Core) owns roundtrip/corruption/version handling, unit-tested. Translations are deliberately **not** included in `.cedar` yet (RU/EN both live in the DB via `DraftTranslation`, not surfaced in export).

### ADR-007 — Telegram renderer: HTML-only, Markdown/HTML hybrid dropped
**Context**: Early Phase 3 renderer work considered a hybrid Markdown+HTML approach after an initial (mistaken) belief that Telegram's HTML mode didn't support block tags.
**Decision**: That belief was a verification error (wrong test channel). `CedarToTelegramHtmlRenderer` (HTML-only) is canonical; the Markdown hybrid was dropped. A separate `CedarToTelegramMarkdownRenderer` exists as an export *format option*, not as part of the send pipeline's HTML/Markdown alternative.
**Consequence**: All the Telegram HTML-mode quirks (non-void tag closing, block tag support) in `.claude/rules/telegram-bot.md` apply directly to the canonical renderer.

### ADR-008 — Multi-tenancy: shared bot, not BYO
**Context** (decided with Marty, 09.07.2026, Phase 6): needed an onboarding path for multiple users to connect Telegram channels.
**Decision**: One shared, official Cedar Clerk bot. Users add it as an admin to their channel; the server verifies via `getChatMember`. Bring-your-own-bot is deferred as a possible future Premium feature (would need per-user webhooks).
**Consequence**: All bot-membership discovery (`BotKnownChat`/`BotKnownChatAdmin`) must be scoped per-user via `TelegramUserId`, since the bot itself is shared across every account — see `.claude/rules/telegram-bot.md`.
> TODO (Marty): the shared bot's public username/name is still unset — see `docs/ROADMAP.md` open questions.

### ADR-009 — Telegram account linking is additive, not a login replacement
**Context**: Original Phase 6 brief proposed "login via Telegram" replacing/supplementing email auth, plus public registration via Telegram.
**Decision** (corrected with Marty during Phase 6, 09–10.07.2026): Email/password login and registration stay as the only entry point. Telegram Login Widget is used solely to *link* an already-authenticated account to a Telegram identity (HMAC-verified via `TelegramLoginVerifier`), from a button in the Account popover. No public Telegram-based registration.
**Consequence**: `ApplicationUser.TelegramUserId` is nullable — most accounts never link Telegram at all. The Login Widget only works on the exact domain registered with BotFather (`/setdomain`), so it cannot be tested on `localhost`.

### ADR-012 — Billing: three tiers (Pro / Pro Plus / Trial), all three payment providers built fully
**Context**: Original Phase 6 planning sketched a simple two-tier Free/Pro freemium model with Telegram Stars first and Paddle/Lemon Squeezy considered later for cards.
**Decision** (evolved 10–11.07.2026, refactored `788d421`): Ended up as **Pro** $3/mo, **Pro Plus** $6/mo (+ AI features via `PlanLimitations.HasAiFeatures`), **Trial** $1 one-time → 7 days of Pro Plus (once per account, `TrialUsedAt`). Paddle/Lemon Squeezy were never built; Stripe filled that role instead.
**Consequence**: Tier/quota/pricing logic centralizes in `PlanLimitations`/`SubscriptionPlanHelper` (Core) and `SubscriptionPlan` (Server), not scattered per-provider. `docs/integrations-setup.md` has the exact provider setup steps. All three providers are code-complete but **not yet live** — waiting on Marty to push real provider keys to the Pi's `data.conf` (see `docs/TASKS.md`... i.e. `TASKS.md`).

### ADR-013 — PayPal recurring explicitly rejected
**Context**: PayPal supports a Subscriptions API for recurring billing.
**Decision** (with Marty, 11.07.2026): Not implemented. Stripe (auto-renewing subscriptions) and Telegram Stars (native recurring) already cover the recurring-payment need; a third recurring provider was judged unnecessary complexity. PayPal stays a one-time 30-day payment, renewed by the user paying again manually.
**Consequence**: This is a **final state, not tech debt** — don't propose PayPal Subscriptions as a "missing feature" without re-raising it as a deliberate scope change first.

### ADR-014 — Default AI/translation provider: Anthropic
**Decision**: `Cedar:Translate:Provider` and the AI-edit provider factory default to `anthropic`, model `claude-opus-4-8`, with OpenAI and DeepL as configurable alternatives (`ITranslationProvider`/`IAiEditProvider` implementations for each).
**Consequence**: DeepL translates text-node-by-text-node (`TipTapTextNodes` in Core extracts/reinserts), preserving document structure perfectly but losing cross-paragraph context; the LLM providers translate the whole document in one prompt instead, trading structural safety for better context. Both approaches coexist by design, provider-selectable.

### ADR-015 — Migration history collapsed to a single `InitialCreate`
**Context**: Migration history had grown incrementally through early development.
**Decision** (11.07.2026): Collapsed to one `InitialCreate` migration. Applied to the dev DB only at the time; prod's `__EFMigrationsHistory` was separately verified in sync via direct SSH (15.07.2026) — no manual prod fix was needed, prod already matched.
**Consequence**: Any future migration builds on top of this single baseline — don't expect to find the original incremental migration history.

### ADR-016 — Comment moderation: delete-after-the-fact, not an approval queue
**Decision**: Blog comments are simple and unmoderated at post time; the channel owner can delete any comment after publication from a right-side panel in the editor. No pending/approval queue exists.
**Consequence**: Comments appear on the blog immediately on submission. Anti-abuse for reactions relies on `VisitorHash` (derived from `CF-Connecting-IP` + salt, no raw IP stored) rather than moderation gating.

### ADR-018 — Telegram send path switched to `InputRichMessage.Blocks` (Bot API 10.2)
**Context**: Marty reported markdown formatting "completely came apart" after posting — a raw `![](url "caption")` string was showing up as literal text in the channel instead of an embedded photo. Investigation (16.07.2026) found Telegram Bot API bumped to **10.2 on 14.07.2026**, introducing a structured `Blocks` model (`InputRichBlock*`/`RichText*` types) alongside the existing free-form `Markdown`/`Html` text fields, plus an `InputRichMessageMedia`/`Media` field with a documented `tg://{kind}?id=` reference convention for embedding media inside that free-form text. `Telegram.Bot` NuGet was one version behind (`22.10.1`, predating the library's own 10.2-aware `22.10.2` release, itself preceded by an interim dev build already patching related bugs).
**What was tried and empirically ruled out** (live-tested against `@testingandfun`, not just reasoned about):
1. Upgrading `Telegram.Bot` to `22.10.2` alone — necessary (new types don't exist below it) but not sufficient.
2. `InputRichMessage.Markdown`/`.Html` + `Media` + a `tg://{kind}?id=` reference in the text (matching the `InputRichMessageMedia.Id` XML doc literally) — **accepted by Telegram with no error, but the media is silently dropped**, not rendered at all.
3. `<photo src="...">` as the Html-mode media tag (introduced by an earlier commit reacting to the same 10.2 change) — **not a recognized tag**; also silently drops the media. Plain `<img>` is correct.
4. Caption via `InputMediaPhoto.Caption` when the photo is referenced inline from Markdown/Html text — **ignored**; renders as nothing. Only visible when the caption text is placed as an ordinary paragraph in the flowing text, and even then it displays as plain body text (no native muted/caption styling), not a real caption.
**Decision**: `PostEndpoints.PublishAsync` now always builds `InputRichMessage.Blocks` via a new `CedarToTelegramBlocksRenderer` (Core) + a mapping layer in `PostEndpoints` (`ToInputRichBlock`/`ToRichText`) — this is the only combination verified to reliably embed media **and** give it a real, natively-styled caption (`InputRichBlockPhoto.Caption` via `RichBlockCaption`). `CedarToTelegramMarkdownRenderer`/`CedarToTelegramHtmlRenderer` are kept (not deleted, still unit-tested) but are **no longer used for sending** — see the "NOT USED" note at the top of each file.
**Consequence**: `CedarClerk.Core` stays free of a `Telegram.Bot` dependency by design — `RichBlockModel.cs` defines a framework-agnostic `CedarRichBlock`/`RichRun` tree, and only `CedarClerk.Server` (which already depends on `Telegram.Bot`) maps it onto the real wire types. `ExportRequest.Format`/`ScheduledPost.Format` (Markdown vs Html) are still accepted for API/DB compatibility but no longer influence what's actually sent — the frontend's format selector is now vestigial; removing it is a follow-up cleanup, not done in this pass. See `.claude/rules/telegram-bot.md` for the operational summary.

### ADR-019 — Empty carousel/collage blocks are dropped, not sent
**Context**: First real production post after ADR-018's Blocks migration (16.07.2026) failed with a Cloudflare-origin 502. Root-caused against a real draft ("My plan") pulled read-only from the prod DB and replayed locally: the document had **three empty carousel nodes** (`{"type":"carousel","attrs":{"images":[]}}`, an editor artifact from repeated insert/delete) nested inside one list item. Sending an `InputRichBlockSlideshow`/`InputRichBlockCollage` with zero child blocks gets rejected by Telegram with `RICH_MESSAGE_CONTENT_REQUIRED`.
**Separately found, NOT a code bug**: one specific image asset in that same draft consistently failed with `Bad Request: wrong type of the web page content` even though the URL was confirmed live and reachable (`curl` returned 200/valid `image/png`) — appending a cache-busting query string to the exact same URL made it succeed immediately. This points to Telegram caching an earlier failed fetch of that exact URL (from earlier in the same debugging session, when the origin was briefly stopped for an unrelated test) rather than any defect in the renderer or mapping — expected to self-resolve as Telegram's cache for that URL expires. Also clarified: a one-off `SendRichMessage` API call does **not** need the Pi's bot service stopped first — the 409/single-poller rule (`.claude/rules/telegram-bot.md`) only applies to concurrent `getUpdates` long-polling, not to ordinary send calls.
**Decision**: `CedarToTelegramBlocksRenderer` now returns `null` (dropped, matching the existing null-filtering pattern used for unknown node types) for a `carousel`/`collage` node with zero resolved image URLs, instead of emitting an empty `RichSlideshowBlock`/`RichCollageBlock`.
**Consequence**: A draft with leftover empty carousel/collage nodes now exports cleanly instead of failing outright. Verified against the real "My plan" draft end-to-end (list item with the fix applied sent successfully; full document sent successfully once combined with a diagnostic-only cache-bust of the one Telegram-side-cached asset).

### ADR-021 — Positioning: multichannel / write-once-publish-everywhere
**Context**: The product's framing had drifted toward "Telegram tool with a blog mirror" in its own docs, without a deliberate decision behind that framing — `docs/PRODUCT.md` even carried an open TODO asking whether the audience was Telegram-first or broader.
**Decision** (16.07.2026): Cedar Clerk is a write-once, publish-to-many tool for creators who maintain a presence across multiple channels. The editor is the spine; every output (Telegram channel, hosted blog, later Twitter/Bluesky cross-posting) is a co-equal destination. Telegram is currently the most-developed output — not the product identity. The blog is **not** a "Telegram mirror"; it's a first-class destination in its own right.
**Consequence**: `docs/PRODUCT.md`'s "What it is" and "Who it's for" sections are rewritten to match (mirror framing dropped, Telegram-first-vs-broader TODO resolved in favor of channel-agnostic). Cross-posting to Twitter/Bluesky (`docs/ROADMAP.md` Backlog ideas #1) is now understood as a core axis of the product, not a peripheral nice-to-have — its standing in the roadmap note is raised accordingly, without inventing a new phase for it. An artist/furry-creator vertical was raised as a possible future niche direction in this same conversation — it stays a **backlog niche direction, not a positioning decision**, and NSFW content handling stays deferred/gated; no such content currently exists anywhere in the docs to preserve, and none is invented here.
**Consequence (secondary)**: The Telegram-specific renderer investment already done (Bot API 10.2 Blocks migration, ADR-018/019) remains valid and valuable precisely because Telegram is the most-developed output today — this decision doesn't deprecate that work, it just clarifies it isn't the whole product.

### ADR-022 — Founder lifetime plan via a designated invite code
**Context**: Wanted a way to reward early supporters with a permanent plan without building a separate payment/grant flow, given registration is already invite-code gated (`Cedar:InviteCode`, `AuthEndpoints`).
**Decision** (16.07.2026): A designated founder invite code (distinct from the normal invite code) grants a **permanent Pro tier** on registration — multichannel (`PlanLimitations.MaxChannels(Pro)` = 3 today), no "Powered by Cedar Clerk" badge, full history subject to the same 30-snapshot cap as everyone else (see the pricing-table correction below). **Not** Pro Plus, and **not** a reuse of the existing `PlanTiers.Forever` enum value (see the note below) — this is a deliberately smaller-scoped grant. AI features are explicitly **not** included: `PlanLimitations.HasAiFeatures` only returns true at Pro Plus and above, so a lifetime-Pro grant simply never reaches AI at all — this satisfies the "don't hand out unbounded-cost AI for life" concern without needing any new quota logic.
**Related but distinct — found during this session, not being reused**: `CedarClerk.Core/PlanTiers.cs` already defines a `Forever` tier (enum value 3), and `PlanLimitations`'s catch-all cases (`MaxChannels`, `StorageLimitBytes`) currently treat it identically to Pro Plus (10 channels, 5GB, custom signature, AI features — since `Forever >= ProPlus` numerically). It's referenced in `settings.component.html` (shown as "current plan" alongside Pro Plus) but **nothing anywhere grants it** — no invite-code path, no billing path, no admin toggle sets `PlanTier = Forever` today. It was confirmed with Marty (16.07.2026) that the founder plan should NOT reuse this dormant tier; `Forever` stays as an unrelated, already-existing-but-unwired enum value for potential future use.
**Consequence**: No new schema concept is needed for "permanent" — `ApplicationUser.PlanExpiresAt = null` on a paid tier already means "manual grant, never expires" per its own existing doc comment in `Entities.cs`. Implementing this later is expected to be a small registration-time branch (does the submitted invite code match the founder code? if so, set `PlanTier = Pro` and leave `PlanExpiresAt = null` instead of defaulting to Free) rather than a new mechanism.

### ADR-023 — Public blog view counter: a simple always-on counter, not the blocked Channel Analysis infra
**Context**: `docs/PRD.md`'s "Blocked" section flags Channel Analysis UI (views/subscribers/engagement rate/poll percentages) as blocked on a data-collection layer (`PostStatSnapshot`, `ReactionEvent`, a site view beacon) that doesn't exist yet — "historical data cannot be backfilled... blocks on a dedicated future phase." Marty asked for a public view counter shown on both the blog post page and its card in the post list. These are different-sized asks: a live running total needs none of the historical-snapshot machinery the PRD note is about.
**Decision** (16.07.2026): Add a minimal, always-on raw counter — `Draft.ViewCount` (int, new column) — incremented atomically on every blog post-page request (`BlogEndpoints.RenderPostAsync`), shared across a post's RU/EN language versions (matches the existing precedent that comments/reactions are shared per-post, not per-language). Not deduped by visitor (unlike `Reaction`, which uses `VisitorHash`) — a raw hit count, matching how Telegram's own native view count behaves on channel posts. Displayed on the post page and on its card in the blog homepage list; **not** incremented by appearing in the list, only by opening the post itself.
**Consequence**: This is deliberately **not** the blocked Channel Analysis work — no historical snapshots, no per-day breakdown, no engagement-rate math, no bot/crawler filtering, no rate limiting per visitor (a refresh inflates the count, same as most simple blog counters). It's one small, low-risk piece of the eventually-needed "site view beacon" building block referenced in `docs/PRD.md`, not a reversal of that blocked status — real analytics (unique visitors, trends over time) still requires the separately-planned dedicated phase.

### ADR-024 — Table of Contents: auto-generated from headings, works on both the blog and Telegram
**Context**: Marty asked for a Table of Contents feature, ideally working both on the blog and in Telegram (channel export doesn't have a concept of a "post list," so cross-posting targets like Twitter/Bluesky are naturally out of scope — there's no renderer for them yet anyway). This landed alongside Phase 8 Step 1 (blog polish) rather than as its own roadmap line.
**Decision** (16.07.2026): A new `tableOfContents` TipTap node (inserted explicitly via the toolbar, like `toggle`/`footnote`) whose content is **not authored** — it's computed at render time from whatever headings exist in the document, via a new shared `CedarClerk.Core.HeadingOutline.Extract()` pass that both `CedarToBlogHtmlRenderer` and `CedarToTelegramBlocksRenderer` call once at the start of `Render()`. Headings get a slug (reusing `SlugGenerator.Slugify`, already used for blog post slugs — handles Cyrillic transliteration), disambiguated on collision (`slug`, `slug-2`, ...). Blog: each `<hN>` gets `id="{slug}"`, the TOC node renders `<nav class="toc"><ul>...</ul></nav>` linking to `#{slug}`. Telegram (Bot API 10.2 Blocks): each heading is preceded by an `InputRichBlockAnchor{Name=slug}` marker; the TOC node becomes an `InputRichBlockList` of `RichTextAnchorLink` entries — **verified live against `@testingandfun` (16.07.2026): tapping a TOC entry actually jumps to the corresponding section within the same message.** This is the first real use of Bot API 10.2's anchor primitives in this codebase.
**Consequence**: `CedarToTelegramBlocksRenderer.RenderBlock` was refactored from returning `CedarRichBlock?` (0 or 1 block) to `IEnumerable<CedarRichBlock>`, since a heading now always produces two blocks (anchor + heading) — this also let the `default:` fallback case drop its old "wrap multiple children in a `RichQuoteBlock`" hack in favor of just yielding them directly. Substantially satisfies the older, vaguer "Anchors (in-page links)" line in Phase 8 Step 1 (`docs/ROADMAP.md`) — heading anchors now exist as a side effect, not a separate feature. `CedarToTelegramMarkdownRenderer`/`CedarToTelegramHtmlRenderer` (already unused for sending, see ADR-018) were not touched — a `tableOfContents` node falls through to their existing "unknown type" default there.

### ADR-025 — `/stats` per-channel growth dashboard: `ChannelPost` log + extended `ChannelStatSnapshot`, partially unblocking the Channel Analysis UI
**Context**: Marty asked for a `/stats` page graphing subscriber/view/like/comment growth per connected channel. Per ADR-023 and the PRD's "Blocked" note, views/likes/comments had no channel attribution at all: `Reaction`/`Comment` are keyed only by `DraftId`, `Draft.ViewCount` (ADR-023) is a single running total with no daily history, and `Draft.LastTelegramChatId` records only the *most recent* send target, not a full publish history. Subscriber counts already had real per-channel daily history via `ChannelStatSnapshot`/`SnapshotChannelStatsJob`. Asked Marty whether to ship subscriber-only stats now or build the missing collection layer first; chose the latter.
**Decision** (17.07.2026): Added `ChannelPost` (`ChannelId`, `DraftId`, `TelegramMessageId`, `PublishedAt`) as an append-only publish log, written once in `PostEndpoints.PublishAsync` right after a successful `SendRichMessage` — this single insertion point covers both immediate publish and scheduled publish (`PublishDueScheduledPostsJob`), since both funnel through `PublishAsync`. `ChannelStatSnapshot` gained `ViewCount`/`LikeCount`/`CommentCount`, computed daily by `SnapshotChannelStatsJob` alongside the existing member-count fetch: sum of `Draft.ViewCount` / count of `Reaction` (`Kind == "like"`) / count of `Comment`, across every distinct `DraftId` ever logged to that channel via `ChannelPost`. `GET /api/channels/{id}/stats` (already used by the editor's channel-popover sparkline) gained the 3 new metrics' `current`/`deltaWeek` (reusing `ChannelStatsCalculator.DeltaOverDays`, which is structurally generic over any `(DateTime, int)` series) plus per-snapshot values, and an optional `?days=` param (popover keeps its default of 30; the new `/stats` page requests more) — the existing `current`/`deltaWeek`/`snapshots[].memberCount` shape was left untouched so the popover needed no changes.
**Consequence**: Attribution is an approximation, not a true per-channel split — a draft published to multiple channels contributes its **full** view/like/comment totals to each channel's snapshot, since blog views aren't intrinsically channel-scoped (they're hits on the shared blog page, unrelated to which Telegram channel a post was sent to). No historical backfill is possible for the 3 new metrics — daily snapshots only start accumulating from this deploy forward, exactly the caveat the PRD's "Blocked" note already anticipated. This substantially unblocks the PRD's "Channel Analysis UI" item (moved to Shipped) at the channel-growth-chart scope Marty asked for; it does **not** cover the fuller original scope (`PostStatSnapshot` per-post granularity, real Telegram `message_reaction_count` reactions, poll percentages) — those remain unbuilt.

### ADR-026 — Markdown (.zip) import: hand-rolled scoped parser, matched by basename, Notion's native export format accepted as-is
**Context**: Marty exported a large Notion page as Markdown to test whether Cedar Clerk could import it — Notion's export is a single `.zip` containing the `.md` file plus its referenced images (confirmed with Marty; not two separate loose items as first assumed). No Markdown → Cedar (TipTap JSON) parser existed anywhere — only the reverse direction (`CedarToTelegramMarkdownRenderer` etc.). Marty's own content is "mostly text, images, and lists," not tables/embeds/toggles.
**Decision** (17.07.2026): Added `CedarClerk.Core.MarkdownToCedarConverter` — a **hand-rolled, deliberately scoped** line-based Markdown parser, not a full CommonMark implementation and not a new dependency (`CedarClerk.Core` is explicitly zero-external-dependency, `docs/ARCHITECTURE.md`). Supports headings, paragraphs, bullet/ordered/checkbox lists (checkbox lists map to the editor's real `TaskList`/`TaskItem` nodes, with indent-based nesting for sub-lists), block-level images, blockquotes, fenced code blocks, horizontal rules, and inline bold/italic/strikethrough/code/links — built with `System.Text.Json.Nodes` (`JsonObject`/`JsonArray`), matching the idiom every other Core file (`CedarPackage.cs`, the renderers) already uses. Anything outside this scope (tables, toggles, callouts, embeds) degrades to a plain paragraph of the raw line — never thrown away, never a crash. New endpoint `POST /api/drafts/import-markdown` (`DraftEndpoints.cs`) mirrors the existing `.cedar` import block almost line-for-line: same size caps (`CedarZipMaxBytes`, `CedarMaxAssetCount`), same `ImageContentSniffer`/`Consts.FileSizes.ImageMaxBytes`/`PlanLimitations.HasStorageRoom` checks, and reuses `CedarPackage.RewriteMediaPaths` unmodified — the converter just emits image `src` as a `/media/{basename}` placeholder (the exact convention `RewriteMediaPaths` already expects), so no new media-rewrite logic was needed. Images are matched to zip entries **by basename only** (Notion's exact subfolder path isn't preserved); any unmatched reference is reported back to the caller (`unmatchedImages` in the response) instead of silently leaving a broken image or failing the whole import.
**Consequence**: A same-named image appearing under two different subfolders in one zip (possible in a large multi-page export) resolves to whichever one is encountered first — a known, accepted limitation given the explicitly scoped basename-matching approach. Complex Notion-specific blocks (tables, toggles, callouts, database embeds) are not faithfully reproduced — they degrade to plain text — which was an explicit trade-off given Marty's stated content shape, not an oversight.

### ADR-027 — Every endpoint returns a readable `{error}` body; empty-container guard extended past carousel/collage
**Context**: Marty couldn't tell whether a stuck "Publish" button meant a hung request or a real failure, and — separately — reported Telegram publish failures with no way to see the actual reason without SSH-ing into the Pi. Investigation found: (1) `PostEndpoints.PublishAsync` only caught `Telegram.Bot.Exceptions.ApiRequestException`; anything else (a `NotSupportedException` from `ToInputRichBlock`/`ToRichText`'s unmapped-type fallback, a malformed-JSON `JsonException` from the renderer, a plain network failure) fell through as a bodyless 500, which the frontend's `httpErrorMessage()` helper (`core/http-error.util.ts`) can't do anything with beyond a generic fallback string. (2) No middleware anywhere caught unhandled exceptions globally — the same bodyless-500 problem existed on every other endpoint, not just publish. (3) `ApiRequestException.ErrorCode`/`.Parameters.RetryAfter` were available on the exception but never read or surfaced. (4) ADR-019 dropped empty `carousel`/`collage` nodes to avoid Telegram's `RICH_MESSAGE_CONTENT_REQUIRED`, but `blockquote`, `toggle`, `bulletList`/`orderedList`/`taskList`, and `table` had the exact same latent shape (an `InputRichBlock*` with an empty `Blocks`/`Items`/`Rows` collection) with no equivalent guard — a plausible second source of the carousel-shaped failures Marty suspected.
**Decision** (19.07.2026): Added `app.UseExceptionHandler(...)` in `Program.cs` — logs the full exception (stack trace included) via `ILogger` and returns `{ error: "<ExceptionType>: <Message>" }` with 500 on **any** unhandled exception, on every endpoint. `PostEndpoints.PublishAsync` now takes an optional `ILogger`, logs every publish failure server-side (both the interactive `/api/posts/export` path and the `PublishDueScheduledPostsJob` path — previously only the latter logged anything), and its `ApiRequestException` catch appends `ex.ErrorCode` and, when present, `ex.Parameters.RetryAfter` to the returned message; a second `catch (Exception ex)` covers everything else with the same readable-message treatment instead of an opaque crash. `CedarToTelegramBlocksRenderer` now applies ADR-019's "drop rather than send an empty container" rule to `blockquote`/`toggle`/lists/`table` too (guarded by `Count > 0` before `yield return`, mirroring the existing `tableOfContents`/carousel/collage checks) — covered by a new test, `Drops_empty_list_blockquote_toggle_and_table_blocks_entirely` (`CedarClerk.Tests/BlocksRendererTests.cs`).
**Consequence**: Every error the server can produce is now inspectable from the client without SSH — this is deliberately verbose (full exception type + message returned to the caller) rather than a sanitized generic message, an accepted trade-off for a small self-hosted tool where Marty is the one reading these; worth revisiting if/when Phase 6's multi-tenant SaaS exposes this to end users who shouldn't see internal exception detail. The extended empty-container guards are unverified against a live Telegram failure the way ADR-019's carousel fix was (that one was root-caused against a real failing prod post) — they're a preventive generalization of the same known bug shape, not a confirmed fix for a specific reproduced case.

**Context**: Same session as ADR-027. ### ADR-029 — RU/EN structural diff gutter: block-level LCS against a snapshot taken at last translation sync
**Context**: Same session as ADR-027/028. Marty wanted a visual indicator, beside the editor, of where the RU and EN versions differ — "like a git diff." The existing `enStale()` mechanism (`editor.component.ts`) already answers *whether* RU changed since the EN translation was last touched, by comparing `ruUpdatedAt` against the translation's `updatedAt` timestamp, but not *where*. A literal word-level RU-vs-EN text diff doesn't make sense across two different languages (a faithful translation looks nothing like its source at the word level) — clarified with Marty that the useful comparison is **RU against its own earlier state**, i.e. what changed structurally in the Russian draft since the English version was last synced, so a translator knows what needs re-translating without re-reading the whole piece.
**Decision** (19.07.2026): Added `DraftTranslation.SourceSnapshotJson` (nullable `TEXT`, migration `AddDraftTranslationSourceSnapshot`) — a copy of the RU draft's `CedarJson` captured at the exact moment a translation is created, manually saved, or auto-translated (`DraftEndpoints.cs`'s three translation-write endpoints all now set `translation.SourceSnapshotJson = draft.CedarJson` alongside `UpdatedAt`). The frontend (`editor.component.ts`) diffs the **current** RU `Editor.getJSON().content` array against this snapshot's `content` array at the **top-level block** granularity (paragraphs, headings, images, lists, etc. as atomic units — not word-level), via a classic LCS diff (`diffTopLevelBlocks`) keyed on exact JSON equality per block. Consecutive delete+insert runs are paired as "changed" blocks (matching how a line-level text diff usually reads a modification); unpaired leftover deletions become a thin "removed here" marker at the boundary position since there's no surviving block to attach a delete marker to. Results are rendered as colored bars (green/added, amber/changed, red/removed marker) in a new `.ru-diff-gutter` positioned via live DOM measurement of `.ProseMirror`'s direct children (which correspond 1:1 to top-level doc nodes) against a `.sheet-wrap` wrapper added around the editor's mount element — recomputed on a 200ms debounce off the editor's existing `onTransaction` hook, only while `lang() === 'ru'` and only when a snapshot exists.
**Consequence**: Only visible above a ~1200px viewport width (gutter needs room beside the 680px-max-width `.sheet`; hidden below that breakpoint rather than attempting to squeeze it in or overlay it). Translations created before this migration, or not resynced since, have `SourceSnapshotJson = null` and silently fall back to no gutter (just the pre-existing `enStale()` dot) until the next save/auto-translate populates it — no backfill was attempted, matching the precedent set by ADR-023/025 for other "starts accumulating from this deploy forward" additions. The diff is **not** persisted or computed server-side; it's a client-only, ephemeral recomputation each time the RU tab is viewed, so it carries no migration risk beyond the one new nullable column.

### ADR-030 — `/stats` gains a channel-agnostic "Blog" tab: `BlogStatSnapshot` keyed by `OwnerId`, on-demand first snapshot
**Context**: Marty asked to see stats for the blog/site itself on `/stats`, not just per-Telegram-channel. `ChannelStatSnapshot`'s `ViewCount`/`LikeCount`/`CommentCount` (ADR-025) are already an approximation joined through `ChannelPost` — a blog view isn't intrinsically tied to any channel, and a draft never published to Telegram at all (blog-only) had no stats surface anywhere.
**Decision** (19.07.2026): Added `BlogStatSnapshot` (`OwnerId`, `ViewCount`, `LikeCount`, `CommentCount`, `TakenAt` — no `MemberCount` equivalent, a blog has no "subscriber" concept), migration `AddBlogStatSnapshot`. `SnapshotChannelStatsJob` (same daily 4 AM job, unchanged trigger) now also loops over every distinct `OwnerId` with at least one `IsBlogPublished` draft and writes one row summing **all** of that owner's drafts' `ViewCount`/`Reaction`("like")/`Comment` counts — no `ChannelPost` join, since this is deliberately channel-agnostic. New `GET /api/blog/stats?days=` (`BlogEndpoints.cs`, alongside the existing per-draft blog endpoints) mirrors `GET /api/channels/{id}/stats`'s response shape minus the subscriber fields, reusing `ChannelStatsCalculator.DeltaOverDays` unmodified (already generic over any `(DateTime, int)` series, per ADR-025). Unlike a Telegram channel — which gets an immediate first snapshot at connect-time (`ChannelEndpoints.cs`) — there's no equivalent "connect" moment for the blog, so the new endpoint takes an on-demand snapshot for "today" itself if one doesn't already exist for the requesting owner, rather than leaving the user looking at "—" until the next nightly job run. Frontend (`stats.component.ts`): a `selectedView: 'blog' | 'channel'` signal, a "📄 Blog" tab shown first (before channel tabs, always present even with zero connected channels — the old whole-page "connect a channel first" empty state was removed since Blog stats no longer depend on having any channel), and `metricCards()` branches on view to build 3 cards (no Subscribers) from `BlogStats` instead of 4 from `ChannelStats`. `buildChart()` now takes `(ChannelStatSnapshotDto | BlogStatSnapshotDto)[]` and reads the metric key via a `Record<string, number>` cast, since the two DTOs only partially overlap.
**Consequence**: Same no-backfill caveat as ADR-023/025 — history only starts accumulating from this deploy forward (or from the first on-demand snapshot, whichever the user triggers first by opening the tab). A user who opens the Blog tab before the nightly job has run that day, and is then still active when the 4 AM job runs, ends up with two snapshot rows for the same calendar day (same latent behavior already accepted for channel connects immediately followed by the nightly job — not a new problem introduced here, just the same existing trade-off extended to a second call site). Owners with zero blog-published drafts never get a row and the tab shows the existing per-card "not enough history" empty state, same as a freshly-connected channel with < 2 snapshots.

### ADR-031 — Large camera photos auto-compressed for Telegram sends: root-caused a live prod 502, not a repeat of ADR-019's caching theory
**Context**: Marty reported a real production 502 publishing a post. Prod logs (`journalctl`) showed `Telegram Bot API error 400: Bad Request: wrong type of the web page content` — the exact same message ADR-019 previously attributed to Telegram caching an earlier failed fetch. This time it was root-caused differently: a direct one-off `sendPhoto` test against `@testingandfun` (per `.claude/rules/telegram-bot.md`, safe without stopping the Pi's bot service) with three of the draft's real images — 0.94MB (succeeded), 9.88MB (failed), 14MB (failed) — proved Telegram flatly rejects a photo fetched by URL above some threshold well under 10MB, full stop, independent of any caching. The draft's photos (Sony ZV-E10 / iPhone camera originals, 6000×3376 and similar) were exactly the large files `Consts.FileSizes.ImageMaxBytes` was raised from 5MB to 50MB to accommodate (see the uncommitted-at-start-of-session change referenced earlier this session) — that upload-limit increase enabled storing images Telegram itself can't embed as inline photos.
**Decision** (19.07.2026): Added `SixLabors.ImageSharp` (3.1.12, patched past the known 3.1.7 moderate-severity advisory) to `CedarClerk.Server` only — `CedarClerk.Core` stays zero-dependency per `docs/ARCHITECTURE.md`. New `Consts.FileSizes.TelegramSafeImageBytes` (4MB, safety margin under the empirically-confirmed failure point). New `ImageCompressor.TryCompressJpeg` (`CedarClerk.Server`): resizes to a 2560px long edge (camera-native resolution is far more than any chat app displays usefully) then steps JPEG quality down (85→75→65→50) until under budget, returning its best effort even if still over. New `Asset.TelegramLocalPath` (nullable, migration `AddAssetTelegramLocalPath`) points at this derivative's filename, sitting alongside the untouched original in the same flat `MediaPaths.Dir`. `AssetEndpoints.EnsureTelegramSafeAsync` (JPEG-only — camera photos are the actual reported case, and re-encoding PNG/GIF/WebP as JPEG would lose transparency/animation) generates the derivative both **eagerly at upload time** (new photos) and **lazily from `PostEndpoints.PublishAsync`** for any referenced asset that doesn't have one yet (old photos uploaded before this feature existed, or where compression didn't run for any reason) — `PublishAsync` gained a `MediaPaths media` parameter (threaded through both the `/api/posts/export` endpoint and `PublishDueScheduledPostsJob`) to support this. The substitution itself reuses `CedarPackage.FindReferencedMediaPaths`/`RewriteMediaPaths` (already used for `.cedar`/Markdown import) to build an old-name→derivative-name map and rewrite a **copy** of the `cedarJson` right before `CedarToTelegramBlocksRenderer.Render` — the stored `Draft.CedarJson`, blog rendering, and `.cedar` export are never touched, so no quality loss anywhere except the Telegram copy. Verified against a real 21MB production asset (downloaded from prod, compressed locally): came in under the 4MB target. Covered by `CedarClerk.Tests/ImageCompressorTests.cs` (a synthetic noise image, which compresses far worse than a real photo at any quality — a harder case than production images).
**Consequence**: The derivative's size is **not** counted toward the owner's storage quota (`PlanLimitations.HasStorageRoom` still sums only `Asset.SizeBytes`, the original) — it's an internal, regeneratable implementation detail, not user-owned content. `Asset.TelegramFileId` (an existing, previously-unused column) was considered as a reuse target for this but left alone — it's specifically for caching Telegram's own returned `file_id` after a successful send (a different, still-unbuilt optimization), not a general "alternate file" slot. This also retroactively clarifies ADR-019: that entry's "Telegram cached an earlier failed fetch" theory for the *first* time this exact error message was seen may itself have been this same file-size issue rather than a caching artifact — no way to confirm after the fact, but worth remembering that "wrong type of the web page content" has (at least) two distinct real causes now, and size should be suspected first.

**Context**: Follow-up feedback after ADR-031's auto-compression fix: Marty wanted to (1) control the compression degree instead of it being fully automatic, (2) see which media files a draft actually references (name/size/location) so they're manageable, and (3) store links to other social profiles in Settings — plus assorted UI polish (mobile topbar overflow, bigger/clearer toolbar icons, blog comment form always stacked, Facebook added to the export mockup row).

### ADR-034 — Signature monetization (Phase 8 Step 5): Free gets a fixed, non-removable attribution; Pro can customize or clear it, optionally as a clickable link
**Context**: `docs/ROADMAP.md` Phase 8 Step 5 called for "Free: fixed Cedar Clerk attribution, Pro: custom signature text, links must be clickable." Reading the existing code first (per the recurring backlog-drift lesson) found this was already partially built: `ApplicationUser.PostSignature` + a Pro-only gate on `POST /api/auth/signature` (403 if a non-Pro account tries to set one) already existed from an earlier session, appended as plain text to both the Telegram export (`PostEndpoints.PublishAsync`) and the blog page (`BlogEndpoints.RenderPostAsync`) — but a Free-tier account with no signature got **nothing** appended (no fixed attribution existed anywhere), and there was no way to make a signature clickable at all.
**Decision** (23.07.2026): New `ApplicationUser.PostSignatureUrl` (nullable, migration `AddPostSignatureUrl`) — when set alongside `PostSignature`, the whole signature text becomes a link; this is a single text+URL pair, not per-line/rich-text formatting (that richer version stays the deliberately-deferred "Pro Plus signature tier" per `docs/PRD.md`'s non-requirements). New `Consts.Signatures.FreeAttributionText` = "Published with Cedar Clerk", linked to `Consts.URLs.MainHost`. Centralized the actual Free-vs-Pro decision in one place — `PlanLimitations.ResolveSignature(tier, postSignature, postSignatureUrl) : ResolvedSignature?` (Core, unit-tested) — rather than re-deriving the gate at each of the three render sites (Telegram Blocks, live blog page, static single-file HTML export added in ADR-028) that each format the result differently:

- Pro+ with a blank `PostSignature`: `null` — **no signature at all**, the actual point of paying (removing the Free-tier ad), not a fallback to the fixed attribution.
- Free (or any tier failing `HasCustomSignature`): always `ResolvedSignature(FreeAttributionText, MainHost)`, regardless of whatever stale value might be sitting in the (write-gated, so normally never populated for Free) `PostSignature` column.
`BlogEndpoints.SignatureHtml(ResolvedSignature?, tag)` is the one HTML-formatting helper shared between the live blog page (`<span>`) and the static HTML export (`<div>`) — same wrapping rule (anchor if `Href` set, encoded plain text otherwise), different tag per existing markup convention at each call site. Settings UI: signature textarea gets a PRO badge + disabled state (matching the existing header-slot-3 pattern) for Free accounts, with a hint naming the fixed attribution they'll get instead; Pro accounts additionally see an optional "link" input beneath the text.
**Consequence**: This is a real behavior change for every existing Free-tier account — posts that previously carried no signature now get "Published with Cedar Clerk" appended, by design (that's the monetization mechanism). Not yet verified live against `@testingandfun` or on a real blog post as of writing.

### ADR-035 — Editor redesign (Claude Design import): toolbar customization, appearance prefs, new-draft dialog, /drafts screen, unified Insert modal — new preference storage
**Context**: Marty shared a Claude Design project ("Editor Redesign") importing a 12-variant mockup (`Editor Redesign.dc.html`, project `b4ac21d3-…`) covering: a two-row toolbar with an AI button group and full drag-and-drop customization (presets → per-button checkboxes → Row 1/Row 2/More zones, right-click-to-remove), a full-screen `/drafts` table replacing the sidebar list, a New Draft dialog (minimal title+Enter, expandable to languages/tags/template/schedule), a tag "cloud" picker, a unified Insert modal (paste-a-link with clipboard type auto-detection — link vs YouTube — superseding the separate Link and YouTube toolbar popovers), and Settings → Appearance (5 accent presets — Cedar/Bark/Slate/Ink/Rust, configured separately per light/dark theme — plus writing-sheet width/typeface/ruler/paragraph-numbers/focus-mode toggles). Confirmed with Marty this is being built in full, not staged.
**Decision** (24.07.2026): Four new nullable preference fields, `null` always meaning "use the built-in default" (so existing accounts are unaffected until they opt in):
- `ApplicationUser.ToolbarLayoutJson` — `{ preset: "minimal"|"standard"|"everything"|"custom", row2Groups: string[], hiddenButtons: string[] }` (`cedarclerk-web/src/app/core/toolbar-layout.ts`). Row 1 is implicit (every group not named in `row2Groups`); button ids are scoped within their group, not globally ordered. A JSON blob rather than flat columns (unlike e.g. the social-links columns in ADR-032) because this is a variable-length structure, not a fixed set of named scalar values — the same reasoning that already justifies `Draft.CedarJson` itself being JSON rather than relational. **Scoped down from the mockup's per-button drag-and-drop**: row placement (Row 1 vs Row 2) happens at the *group* level, not per individual button — dragging 30+ buttons between two zones is a lot of engineering surface for a personal-blog tool with one active user, while group-level placement (implemented with `@angular/cdk` drag-drop) still delivers the core "customizable toolbar" value. Per-button visibility (the checkbox catalog) IS per-button, independent of which row its group sits in.
- `ApplicationUser.AppearancePrefsJson` — `{ accentLight, accentDark, sheetWidth, typeface, fontSize, lineHeight, showRuler, showParagraphNumbers, showWordCount, focusModeHideToolbar, sheetFlush }` (`core/appearance.service.ts`). Same JSON-blob reasoning: a growable bag of independent, mostly-boolean display toggles, not a fixed profile-field set. Accent presets are a fixed hex per name (Cedar `#5B6E46` — unchanged existing default, Bark `#8A6A3E`, Slate `#4A5A6B`, Ink `#3A3730`, Rust `#A0522D`); the dark-theme variant of any preset reuses the **exact ratio already shipped for Cedar** in `styles.scss` (`color-mix(in srgb, <hex> 55%, #E8F0E8 45%)` — not the mockup's own slightly different 62/38 mix, since consistency with the one formula already live in this codebase matters more than matching the mockup's specific number), applied via a `<style>` override on `:root`/`:root[data-theme="dark"]` rather than duplicating every derived token (`--asoft`/`--abord`/etc. already reference `var(--accent)` via `color-mix`, so overriding just `--accent` recomputes the rest for free). Ruler/paragraph-numbers/sheet-flush are read directly by `EditorComponent` (CSS class/var bindings + a CSS-counter gutter on the ProseMirror content's direct children) rather than mutated globally on `<html>`, since they only ever affect that one component's own template.
- `ApplicationUser.NewDraftDefaultsJson` — `{ languages: "ru"|"en"|"both", tags: string[], template: "blank"|"devlog"|"photodump" }`. **Scoped down from the mockup**: it also showed per-draft channel checkboxes and an inline schedule picker at creation time, but Cedar Clerk has no draft-to-channel relationship at creation (channels/scheduling are chosen at export/publish time, on an existing draft) — inventing one would be a real data-model change beyond "remember my last choices," so the New Draft dialog covers title/languages/tags/template only; schedule-at-creation was dropped rather than faked.
- `Draft.IsArchived` (bool, default false, migration `AddArchiveAndPreferenceFields`) — the only genuinely new piece of *content* state (vs. preference); needed because the mockup's `/drafts` "Archived" filter has no existing equivalent.
**Consequence — status badges scoped to what's honestly derivable**: the mockup's per-draft status list (Draft/Unsaved/Scheduled/Publishing/Published/Failed/Translation incomplete/Archived) includes two states with no persisted backing for an arbitrary row in a list: "Unsaved" and "Publishing" only mean anything for whichever draft is *currently open in this browser tab* (autosave means every other row is by definition saved; publishing is a synchronous in-request action outside the scheduled-post path, never a stored state) — showing either for a row you're not actively editing would be fabricated, so `/drafts` never shows either one, for any row, full stop (not even the currently-open draft — keeping the rule uniform was simpler and more honest than a one-row special case). "Failed" is real and shown, but **only** for `ScheduledPost.Status == "Failed"` — an immediate (non-scheduled) `/api/posts/export` failure was never persisted anywhere before this and still isn't, so a failed immediate publish shows no badge; this is a pre-existing gap this redesign does not attempt to close (would need a new "last publish attempt" column on `Draft`, out of scope here). Tag UI: built as the "cloud" variant (1h in the mockup) over the popover-search variant (1g) — matches Marty's actual tag vocabulary (~10-12 tags total across sample content), needs no incremental search endpoint, and was picked without a further round-trip given the scope already confirmed in full. Toolbar drag-and-drop uses `@angular/cdk` (official Angular package, `^21.2.0` to match the installed `@angular/core`) — the first new frontend runtime dependency added in this project; justified over hand-rolled HTML5 drag-and-drop for accessibility/keyboard support and because it's framework-maintained, not a random third-party library. The toolbar's per-group markup (each with its own popovers/state) is rendered once per group via `<ng-template>` + `NgTemplateOutlet`, instantiated into whichever row `ToolbarLayoutService` currently assigns it to — avoids duplicating ~30 buttons' worth of markup across two static row containers.

### ADR-037 — Phase 8 Step 7: comment replies (one level), owner highlight, name reservation, dual timestamp
**Context**: `docs/ROADMAP.md` Step 7 listed four sub-items with zero prior implementation: replies, highlighting the channel owner's own comments, reserving the owner's display name, and showing both the post's publish time and each comment's write time. The comment system (`Comment` entity, `BlogEndpoints.cs`) has no account/identity concept at all — comments are anonymous, free-text `AuthorName`, no `VisitorHash`-equivalent tracking (unlike `Reaction`). Rendering is vanilla JS embedded in `BlogEndpoints.cs`'s `ShellTemplate` (not an Angular component), which shaped every decision below toward minimal, dependency-free client code.
**Decision** (26.07.2026):
- **Replies**: `Comment.ParentCommentId` (`Guid?`, plain scalar, no nav property or FK constraint — matches `Comment.DraftId`'s existing shape, consistent with `docs/ARCHITECTURE.md`'s "no strict FK-only model"), migration `AddCommentParentId`. **Scoped to one level of nesting** — `PostCommentAsync` rejects (silently falls back to top-level) a `ParentCommentId` that itself already has a parent, and the client UI only ever offers a "Reply" button on top-level comments. A full comment tree was judged unnecessary complexity for a personal blog's comment volume.
- **Owner highlight**: `owner.AuthorDisplayName` (already loaded in `RenderPostAsync` for header slots, ADR-034) is passed into `AnnotationControlsHtml` as a new optional parameter and rendered as an HTML-encoded `data-owner-name` attribute on the whole-article `.comment-box`. **Scoped to the whole-article comment box only** — per-fragment inline annotations don't receive it, since threading the value through `RenderContext`/`Render()` for every inline annotation instance would add real plumbing for a cosmetic detail; the highlight simply doesn't apply there (graceful degradation, not an error).
- **Name reservation**: no reservation table — `PostCommentAsync` compares the submitted `AuthorName` (case-insensitive, trimmed) against the live `owner.AuthorDisplayName` at submit time and rejects with 409 if they match. Skipped entirely when the owner hasn't set a display name. **Known accepted edge case**: the real owner commenting through the anonymous public form (not the authenticated `/comments` management page) would also be rejected — there's no identity verification on the public form to distinguish "the real owner" from an impersonator, so this is the same check either way.
- **Dual timestamp**: `draft.BlogPublishedAt` is passed into the same `AnnotationControlsHtml` call as `publishedAt`, rendered as one "Post published: {date}" line above the comment list (whole-article box only, same reasoning as the highlight scoping) — each comment already showed its own `createdAt`.
- Error surfacing in the vanilla-JS comment form uses a plain `alert()` for the reservation rejection — every other fetch on this page silently swallows errors (`.catch(function(){})`), but silently dropping a rejected comment with no explanation would be worse UX than a blocking `alert()`. No styled-modal infrastructure exists on this vanilla-JS blog page (unlike the Angular app's `ModalComponent`, ADR-028) to do better without adding one.
**Consequence**: `GetAnnotationsAsync`'s per-comment projection and the create-comment response both gained `parentCommentId`; the owner's private `/comments` management page (`comments.component.ts`, `GET /api/comments/`) was deliberately **not** updated to show reply threading — out of scope, Step 7 is about the public reading experience. Not yet verified live in a browser as of writing (deferred by Marty's choice this session).

### ADR-038 — Phase 8 Step 8: AI progress bar as a client-only pseudo-progress estimate, not real streaming
**Context**: `docs/ROADMAP.md` Step 8 asked for "a real progress indicator for in-editor AI operations (currently just an elapsed-time counter)". Investigated whether real streaming was feasible: neither AI-edit provider (`AnthropicAiEditProvider` via the Anthropic .NET SDK, `OpenAiAiEditProvider` via raw `HttpClient`) nor the auto-translate providers stream today: single `await`-to-completion calls throughout, no SSE/chunked-response infrastructure anywhere in the app (backend or frontend). The Anthropic SDK likely supports streaming, but building it out for both providers plus new backend SSE plumbing plus frontend consumption would be substantial new infrastructure — and even then, an LLM call has no known-upfront total (token count, work remaining), so a "real" streamed progress would still be a proxy (tokens-so-far), not a true percentage. Discussed with Marty; chose the smaller-scope option.
**Decision** (26.07.2026): Frontend-only change, no backend/provider modifications. `pseudoProgress(elapsedSeconds, tau=20)` (`cedarclerk-web/src/app/core/pseudo-progress.util.ts`, unit-tested) — an asymptotic curve, `90 * (1 - e^(-t/tau))`, capped at 90% so it never falsely claims completion; the caller jumps the displayed value to 100% only once the real HTTP response actually arrives. Applied to AI-edit and auto-translate only (`aiEditProgress`/`autoTranslateProgress` signals in `editor.component.ts`) — **not** to export/blog-publish (`exportElapsed`/`blogElapsed`), which already have cycling status messages plus an indeterminate bar and aren't AI operations. Per Marty's explicit ask on top of the pseudo-progress approach: elapsed seconds are still shown alongside the percentage (`"67% · 14s"`), a 3-minute client-side timeout (`DraftsService.AI_OPERATION_TIMEOUT_MS`, RxJS `timeout()` piped onto the request) independent of the tighter existing server-side `Consts.Anthropic.RequestTimeout` (60s), and a Cancel button. Cancellation required converting `DraftsService.autoTranslate`/`aiEdit` from `firstValueFrom`-wrapped Promises to raw Observables (`autoTranslate$`/`aiEdit$`) so `editor.component.ts` can keep a `Subscription` reference and call `.unsubscribe()` on cancel — `firstValueFrom` doesn't expose the underlying subscription, so this was a required refactor, not a style choice. Unsubscribing genuinely aborts the in-flight HTTP request client-side.
**Consequence**: `runAutoTranslate()`/`aiEdit()` changed from `async`/`await` methods to synchronous methods driving `.subscribe({next, error, complete})` callbacks — the two call sites (`confirmTranslate()`, `confirmAiEdit()`) dropped their now-meaningless `await`. A user-initiated cancel shows no error message (silent reset) since it's not a failure. A genuine timeout shows a distinct message ("... timed out after 3 minutes") rather than the generic failure fallback. Real token-level streaming remains future work if ever revisited — this ADR's scope is explicitly the pragmatic, no-backend-change option.

### ADR-039 — Folders: a real, named entity with one folder per draft, unlike Tags
**Context**: First item picked from the "Cedar Clerk 0.9.0" idea dump (`docs/BACKLOG.md` idea #19, "Folders / drafts grouping"). No grouping concept existed beyond `Draft.Tags` (flat, multi-valued, unmanaged string — no entity, no rename/delete, just usage-count aggregation for a picker). The backlog entry itself flagged the fork: a real `Folder` entity + `Draft.FolderId` vs. reusing the tag mechanism as a second flat-string field. Asked Marty directly — confirmed folders should behave like a filesystem/mailbox: **at most one folder per draft**, with real management (create/rename/delete), not a lightweight tag-shaped workaround.
**Decision** (26.07.2026): New `Folder` entity (`Id`, `OwnerId`, `Name`, `CreatedAt`) + `Draft.FolderId` (`Guid?`, plain scalar, no nav property/FK constraint — same "no strict FK-only model" convention as `Comment.ParentCommentId`/`DraftId`), migration `AddFolders`. New `FolderEndpoints.cs` (`GET/POST/PUT/DELETE /api/folders`, owner-scoped) — full CRUD, since unlike tags, folders are explicitly named/managed. `GET /api/folders` returns a live draft-count per folder (`GroupBy` over `Drafts.FolderId`), not a separate counter column. New `PUT /api/drafts/{id}/folder` (`DraftEndpoints.cs`) validates the target folder belongs to the same owner (since `FolderId` has no DB-level FK to catch a cross-owner reference). **Deleting a folder unassigns its drafts (`FolderId` → `null`) rather than deleting them** — a folder is purely an organizational label, never a reason to lose content; the confirm dialog states how many drafts will become uncategorized. Frontend: `/drafts` gets a folder-filter dropdown (combines via AND with the existing status-tab/search filters, same composition principle already used there) plus a combined filter-and-manage popover (inline rename, delete-with-confirm, add-new) and a per-row folder-assignment popover in both table and grid views; the editor gets a lighter mirror (assign-only, no rename/delete — that stays on `/drafts`) next to the tag row.
**Consequence**: Bulk folder assignment (moving multiple drafts at once) is explicitly out of scope for v1 — one draft at a time, matching how tag/archive actions already work per-row. The New Draft dialog was deliberately not extended with a folder picker at creation time — folders are assigned after the fact, keeping that dialog's scope unchanged. No dedicated tests added — folder CRUD has no branching logic beyond simple ownership checks and name-length validation, consistent with how other simple CRUD endpoints in this codebase (e.g. `ChannelEndpoints`) aren't unit-tested either. Not yet live-verified in a browser as of writing.

### ADR-040 — Engagement DM notifications: plain-text via the existing bot client, opt-in, like/comment only
**Context**: Third item from the "Cedar Clerk 0.9.0" dump (`docs/BACKLOG.md` idea #18) — DM the post owner via the bot on new comments/likes, gated behind an opt-in so it doesn't spam on every anonymous reaction. `BillingEndpoints.cs` already sends a plain-text DM (Telegram Stars invoice notice) via `bot.Client.SendMessage(user.TelegramUserId.Value, "...")` — the exact mechanism needed here, no new bot infrastructure required.
**Decision** (26.07.2026): New `ApplicationUser.NotifyOnEngagement` (`bool`, default `false` — a real opt-in, not opt-out; linking Telegram alone does not start sending DMs), migration `AddNotifyOnEngagement`. New dedicated `POST /api/auth/notifications` (`AuthEndpoints.cs`), mirroring the existing narrow single-concern endpoints (`/toolbar-layout`, `/appearance`, `/new-draft-defaults`) rather than folding into the shared `/profile` endpoint — that endpoint unconditionally overwrites every field it accepts, so a partial toggle-only call through it would have silently blanked the rest of the profile. New `BlogEndpoints.NotifyOwnerAsync(ctx, db, ownerId, slug, message)` — resolves `TelegramBotService`/`IConfiguration`/`ILogger` from `ctx.RequestServices` (matching this dispatcher's existing `GetRequiredService<CedarDbContext>()` pattern, since `PostCommentAsync`/`PostReactionAsync` are invoked from a manual path-based dispatcher, not a `MapPost` DI-bound delegate), checks `bot.IsRunning` + the owner's `NotifyOnEngagement`/`TelegramUserId`, and wraps the actual send in try/catch that only logs — a failed/unreachable DM (owner never `/start`ed the bot, etc.) never surfaces as an error to the anonymous visitor whose comment/like triggered it. Wired into `PostCommentAsync` (fires for both top-level comments and replies — same code path, no special-casing) and `PostReactionAsync` (fires **only** on a genuinely new `"like"` reaction — excluded: un-liking/removing an existing reaction, switching to `"dislike"`, and dislikes generally, matching the backlog wording "comments/likes" literally).
**Consequence**: The DM is sent synchronously within the request (awaited before the response), adding one Telegram API round-trip to comment/like latency when notifications are enabled — accepted rather than building a background queue, consistent with this codebase's general preference for simplicity at its current scale. No dedicated tests — same reasoning as ADR-039 (simple conditional CRUD/wiring, no branching logic worth isolating). Not yet live-verified against a real Telegram DM as of writing.

### ADR-041 — Private posts: email invite list, first real email infrastructure (Resend), link-based access
**Context**: Fourth item from the "Cedar Clerk 0.9.0" dump — idea #20.1/20.2 (`docs/BACKLOG.md`), 20.3 (polls inside private posts) deliberately deferred since it depends on idea #22 (polls), which doesn't exist yet. Marty chose the access model directly: an email invite list per post. Investigated first: the project has **zero email-sending infrastructure** — no SMTP client, no transactional-email package, nothing (confirmed by grep across `CedarClerk.Server`/`CedarClerk.Core` and by `docs/BACKLOG.md` idea #2, which already flagged this as unbuilt). A magic-link-by-email flow is not possible without building that first. Presented three options (manual link-sharing/no email infra, honor-system email check with no verification, or build real email sending first); Marty chose to build email sending first.
**Decision** (26.07.2026):
- **Email provider — Resend** (`CedarClerk.Server/Email/ResendEmailProvider.cs`), chosen over SMTP for its plain HTTP JSON API (no SMTP protocol handling needed) and generous free tier. **No `IEmailProvider` interface** — unlike `ITranslationProvider`/`IAiEditProvider`, which genuinely have multiple interchangeable implementations already built, there is exactly one email provider today; adding an abstraction for a hypothetical future swap would be premature. Same "not configured → log a warning and return `false`, never throw" shape as `TelegramBotService.IsRunning` — a missing/invalid API key degrades gracefully rather than crashing the request that triggered a send. Config: `Cedar:Email:ResendApiKey`, `Cedar:Email:FromAddress` (`docs/integrations-setup.md` §3) — **manual setup on Marty's side** (Resend account, domain verification via Cloudflare DNS, API key), same pattern as the existing Stripe/PayPal/DeepL provider keys.
- **Access model — per-post `PostInvite` rows** (`Id`, `DraftId`, `Email`, `Token`, `CreatedAt`), no nav property/FK, matching `Draft.FolderId`'s established shape. `Token` is 32 random bytes (`RandomNumberGenerator`), reusable/durable (not single-use) — revoking access means deleting the row, not expiring the token. `Draft.IsPrivate` gates whether the check applies at all; only meaningful alongside `IsBlogPublished`.
- **Delivery is link-based, not truly magic-link-verified**: the invite link (`{postUrl}?invite={token}`) is always generated and shown to the owner (with a copy button) regardless of whether the email actually sends — email is a convenience layer on top of a link the owner can always share manually through any channel. This sidesteps needing delivery guarantees from a brand-new, not-yet-verified provider integration.
- **Gating is centralized**: `BlogEndpoints.HasPrivateAccess(ctx, draft)` — checks a long-lived (90-day) `cedar_access_{draftId}` cookie, set once a valid token has been presented via `RenderPostAsync`. Applied at all **four** places a private draft could otherwise be reached by slug alone: `RenderPostAsync` (sets the cookie), `GetAnnotationsAsync`, `PostReactionAsync`, `PostCommentAsync` (all three would otherwise let someone bypass the HTML page entirely and hit the JSON API directly with a guessed/known slug). An unauthorized visitor gets the **exact same** "Post not found" 404 as a nonexistent slug — a private post's existence is not distinguishable from one that was never created. `RenderIndexAsync` and `RenderRssAsync` additionally exclude `IsPrivate` drafts outright, so a private post never appears in the public list/feed even though clicking it would 404 anyway.
- **Privacy is settable before publishing** (corrected 26.07.2026 after Marty's first real use): the toggle originally lived inside the "already published" branch of the Export modal, which meant a post could only be marked private *after* it was already publicly live — a window where anyone could read it. The toggle now sits outside that branch and applies at any time; the invite list still requires a blog slug (the invite URL needs a post URL), so before the first publish it shows an explanatory hint instead of the email input.
**Consequence**: No real identity verification — anyone who obtains the link (forwarded email, shared screenshot, etc.) gets access; this is an invite-list convenience mechanism for a personal blog, not a security-critical access-control system. No expiry on invites or the access cookie beyond its 90-day `MaxAge`; no per-invite usage tracking (last-accessed, click count). No dedicated tests, consistent with ADR-039/040's reasoning. Not yet live-verified — needs Marty to complete the Resend setup (`docs/integrations-setup.md` §3) before an end-to-end email test is possible; the link-copy fallback can be verified without it.

### ADR-042 — Registration form for private posts: locked, not hidden (supersedes part of ADR-041)
**Context**: Brainstorm item B3 (High) — an uninvited visitor of a private post should get a customizable registration form (name, nickname, email, a social link) with optional Google-Forms-style questions, instead of the current 404. That directly contradicts ADR-041's deliberate choice to make a private post indistinguishable from a nonexistent one. Confirmed the trade-off with Marty before building: filling the form **grants access immediately** (it collects an audience, it is not a verification step), the form is configured **per post** (different posts want different questions), and it **replaces the 404** rather than being an optional per-post mode.
**Decision** (26.07.2026):
- `Draft.RegistrationFormJson` (`string?`, migration `AddRegistrationForm`) holds the form definition as a client-authored JSON blob — variable shape (a question list), so the same treatment as `ApplicationUser`'s preference blobs: the server length-checks it (`Consts.RegistrationForm.FormJsonMaxChars`) and never dictates the schema. **Null keeps ADR-041's original behaviour** — no form configured means an uninvited visitor still gets the indistinguishable 404, so the old guarantee is still available, just no longer the only option.
- `RegistrationFormDefinition` (Core, unit-tested) is the single parser both the renderer and the submit-validation read, so the form shown and the rules enforced can't drift. It **degrades rather than throws** on malformed input (corrupt blob → name+email default; unlabelled question → dropped; `choice` with no options → rendered as text), because a hand-edited blob must never take a published post down.
- `CedarToBlogHtmlRenderer.RegistrationFormHtml` (Core, unit-tested) builds the markup, escaping every author-authored string (intro, question labels, choice options) — that's the one new injection surface this feature introduces, and the tests assert it explicitly.
- New `PostRegistration` entity rather than reusing `PostInvite`: the field sets barely overlap (nickname, social link, answers JSON, visitor hash), and folding them together would push half-empty rows of a different kind through the existing invites UI.
- Submission (`POST /api/posts/{slug}/register`) sets **the same** `cedar_access_{draftId}` cookie a valid invite token sets, so everything downstream (`HasPrivateAccess` and its four call sites) is untouched. Required-field and required-question checks are re-run server-side — a form POST is trivially replayable outside the browser.
- **First rate limit in the blog endpoints**: max 3 submissions per `VisitorHash` per post per 24h (429 otherwise). Nothing else on the public blog is throttled, but a public form that hands out access and writes rows is an obvious flood target.
**Consequence**: A private post's existence is now discoverable to anyone with the URL whenever a form is configured — accepted deliberately, that's the point of the feature. The form performs **no email verification**, so a submitter can enter any address; combined with instant access this makes the form an audience-collection tool, not an access-control boundary. Revoking an already-granted access is still impossible (the cookie isn't checked against a live row) — the same limitation invite links already had, but more visible now that anyone can self-serve. Owner-side UI (form editor + submissions list) lives in the Export modal next to the invite list. Not yet live-verified in a browser as of writing.

### ADR-043 — /drafts activity column: a per-draft baseline row, not a stats history
**Context**: Brainstorm item B23 (High) — the drafts list should show view/reaction counts plus "what changed since the previous session", with a possible sparkline. Two things were missing: an aggregate of `Reaction` rows in the drafts-list DTO (the list only ever carried `Draft` columns), and any notion of "since when". Checked what history exists first: `ChannelStatSnapshot`/`BlogStatSnapshot` are per-channel and per-owner daily totals — **nothing is snapshotted per draft**, and the `Draft.ViewCount` counter (ADR-023) is a bare running total with no history behind it. A sparkline would therefore have nothing to draw and nothing to backfill from, so it was dropped from scope and stays blocked on the same data-collection layer already recorded in `docs/PRD.md`.
**Decision** (26.07.2026):
- New `DraftStatSeen` entity (`OwnerId`, `DraftId`, `BaselineViewCount`/`BaselineReactionCount`, `LastViewCount`/`LastReactionCount`, `SeenAt`), migration `AddDraftStatSeen`. One row per (owner, draft), overwritten in place — deliberately not a time series, so it can't be mistaken for the missing history layer.
- **Two pairs of counters, because "since the previous session" and "since the last page load" are different questions.** A single stored snapshot would make the delta collapse to zero on the first F5 (roll it forward every load) or never move at all (never roll it). Instead `Last*` records the counters at each load, and `Baseline*` — what the shown delta is measured against — takes on `Last*` only when a load arrives more than `Consts.DraftActivity.SessionGap` (30 min) after the previous one. Coming back in the morning shows everything that accumulated while the screen was closed, and that number survives reloads for the rest of the working session.
- **Server-side, not `localStorage`** — chosen with Marty over the cheaper client-side option so the delta is the same on the laptop and the iPad and survives a cache clear.
- Baselines are written from the `GET /api/drafts` list query itself (one `SaveChangesAsync` per load), rather than from a separate "mark seen" endpoint the client could forget to call.
- Reactions are counted **across both kinds** (like + dislike) — the column answers "did anything happen here"; the like/dislike split stays on the blog post page where it can be acted on. The delta is clamped at `Max(0, …)` since a deleted reaction can drop the total below the baseline.
- The cell renders `—` rather than "0 · 0" for drafts that were never blog-published, so the column is quiet for the majority of rows.
**Consequence**: The first time a draft appears in the list its delta is 0 by construction — there is no earlier session to compare against, and pretending otherwise would mean inventing history. Deltas are per owner, not per device or per browser session, so opening `/drafts` on the phone and then on the laptop within the same 30-minute window shows the same numbers on both and consumes the delta once. Telegram views are not included — the Bot API exposes no per-post view count to this bot, so "views" here means blog views only. `Draft` deletion now also deletes its `DraftStatSeen` row; orphaned `Reaction`/`Comment` rows are still left behind, unchanged from before. No dedicated tests — the delta logic is a handful of arithmetic branches inside an endpoint, consistent with ADR-039/040/041's reasoning. Live-verified in a browser 26.07.2026.

### ADR-044 — UI language: a hand-rolled signal service with typed dictionaries, stored on the profile
**Context**: Brainstorm item B26 (High) — a language picker (RU/EN) for the app interface, laid out so a long-word language like German doesn't break it. Two facts shaped the decision. First, **the app UI is English-only today** — there is no RU anywhere, so this is a full translation pass (~450–500 strings: ~280 template text nodes, ~120 `title`/`placeholder` attributes, ~135 in `.ts` — status labels, modal copy, error fallbacks), concentrated in `editor.component.html` (113) and `settings.component.html` (97). Second, `CedarClerk.Localization` is **not** a UI-localization layer despite the name: `Languages.cs` holds the *content* language codes (the RU/EN post translation feature) and `ErrorMessages.cs` is six English server strings. The blog's own page chrome is already localized separately inside `CedarToBlogHtmlRenderer` (a plain `lang` param, Phase 8 Step 1) and is untouched by this.
**Decision** (26.07.2026):
- **Mechanism — a hand-rolled `LocaleService` (signals) over typed dictionary modules**, not Angular's built-in i18n and not `ngx-translate`. Angular's official i18n emits **one bundle per locale** served under separate paths, making a language switch a reload onto a different bundle and dragging `Scripts/deploy.ps1` and the Pi's static-file hosting into the change — infrastructure cost this project deliberately avoids. `ngx-translate` switches at runtime but adds a dependency and reduces every key to a string literal whose typo only shows up in the browser. The hand-rolled version matches this codebase's established preference (thin services + signals, hand-written `MarkdownToCedarConverter` rather than a parser dependency): `en.ts` **is** the canonical shape, `ru.ts` is typed as `typeof en`, so a missing or misspelled key is a build error. Cost accepted: no `ng extract-i18n` tooling — a new string means editing two files — and interpolation/pluralization are hand-written (this UI has only a handful).
- **Naming, to prevent a genuine collision**: the editor already has a `lang()` signal meaning the **content** language (the RU/EN tabs on a post). The interface language is a different axis and is never called `lang` — `LocaleService.uiLang()` throughout.
- **Stored server-side** on `ApplicationUser.UiLanguage` (`string?`, migration `AddUiLanguage`) via a new narrow `POST /api/auth/ui-language`, following ADR-040's reasoning: the shared `/profile` endpoint overwrites every field it accepts, so a picker routed through it would blank the rest of the profile. Chosen over the cheaper `localStorage`-only approach (which is what `ThemeService` does) so the language is the same on laptop and phone. **`localStorage` is still written as a cache**, purely to pick the right language on the very first paint — otherwise every load would flash English until `/me` resolves. The server value wins whenever the two disagree.
- **`null` means "not chosen"** and falls back to the browser's `navigator.language`, so existing accounts and the pre-auth screens (`/login`, `/register`, where no profile exists yet) get a sensible language without anyone having to visit Settings first.
**Consequence**: **Server-side messages stay English** — `ErrorMessages` plus every `{ error }` body surfaces in toasts and inline banners, so a Russian UI will still show English failure text until a separate pass adds RU there (would mean reading `Accept-Language` in the endpoints). Flagged deliberately, not an oversight. **`/terms` and `/privacy` are excluded**: they're long-form legal prose still carrying unfilled `[BRACKETED]` placeholders in English (Phase 8 Step 3), so translating them now would be translating a draft. German is not shipped as a language — the requirement is handled as a layout constraint (no fixed-width buttons, wrapping/ellipsis in the topbar and tab strips) rather than a third dictionary.

### ADR-045 — Export window: click-only channels with a fallback, folded destinations, full-width layout
**Context**: Brainstorm v2 items N4, N5 and N13 all rewrite the same modal, so they were done as one pass. N4: "channels are chosen ONLY by clicking — there must be no input fields in that part". N5: an unticked destination should shrink or disable so it stops drawing attention. N13: the window is narrow; it's the most important surface after the writing area and should use nearly the whole viewport.
**Decision** (26.07.2026):
- **Two text inputs existed, and they are not equivalent.** The export-target field (`chatId`, "@channel or chat id") was pure duplication of the connected-channel list and is **gone** — the only way to set a target now is clicking one of the connected channels, rendered as avatar+title pick buttons. If no channel is connected the section says so and points at the Каналы section instead of offering a text box.
- **The connect-a-channel field is kept, but behind a disclosure link** ("Добавить по @имени или id"), not visible by default. Removing it outright would strand a real case: the "Available" list is built purely from `my_chat_member` updates filtered by the user's linked `TelegramUserId` (see `.claude/rules/telegram-bot.md`), so an account that hasn't linked Telegram sees an empty list and would have **no way at all** to connect a channel. This is a deliberate deviation from N4's literal "no input fields" — the visible flow is click-only, the escape hatch survives one click away. Flagged to Marty; trivially removable if he wants it gone entirely.
- **N5 folds rather than disables**: an unticked destination collapses to its header row (`.dest-off` — muted background, reduced opacity) instead of rendering greyed-out controls, because "disabled but present" still occupies the same space, which is what N5 is complaining about. **The LIVE chip stays visible while folded** — that's state, not a setting. Consequence to know: folding the blog destination also hides the private-post/invite/registration-form controls that live inside it; they're one tick away, and the alternative (a second visibility rule independent of the checkbox) would make the checkbox mean two different things.
- **N13 — the modal goes to 1180px** with a `repeat(auto-fit, minmax(330px, 1fr))` grid over the sections, so the extra width becomes columns instead of one long scroll. No media query needed: the grid collapses to one column by itself, and `app-modal` already clamps to `calc(100vw - 32px)`.
**Consequence**: `anyComponentStyle` **error** budget raised 25kB→32kB in `angular.json` (warning left at 20kB) — `editor.component.css` was already at 24.3kB and this pass pushed it over the error threshold. That file's size is real tech debt (it's the single biggest stylesheet in the app, covering the whole editor plus every modal in it), but splitting it is its own task, not something to smuggle into an export-window change. Nothing here touches `PostEndpoints`/`PublishAsync` — the publish path, formats and scheduling are unchanged; this is layout and input-affordance only. The export modal's strings are still hardcoded (mixed RU/EN, as they were) and were **not** moved onto `t()` — the editor screen's localization is a separate open item (B26), and doing half of it here would have hidden a real change behind a mechanical diff.

**Context**: Brainstorm v2 item N7 — comments, likes, statistics and private-post form management move onto a new "Posts Manager" page with four sections: post management (pick a post, make minimal edits), reactions & comments, statistics, forms. Two of those sections already existed as full top-level pages (`/comments`, `/stats`), each with its own header, theme toggle and back link.

- **"Minimal edits" is deliberately metadata-only**: title, tags, folder, private toggle, archive/unarchive, delete, plus links out to the blog post, the Telegram post and the editor. Editing the form, per-question breakdowns and the answer-distribution pie chart are N10; presets are N12. Submissions can only honestly render "answer key → value" today, since `AnswersJson` is keyed by question id and the labels live in the form definition (ADR-042) — resolving them properly is part of N10.

It joins the pending localization pass as one more screen instead of becoming a third state.
**Consequence**: `/posts` duplicates the base page-chrome CSS (header, avatar, buttons) the same way every other page in this app does — component styles aren't shared here, `drafts.component.css` carries the identical block. Extracting a shared chrome component would be a real improvement and is not part of this change. No backend work was needed: every action on the page uses endpoints that already existed. Not yet live-verified in a browser as of writing.

### ADR-047 — Forms tab: multi-choice questions, answer distribution, and copied (not linked) presets
**Context**: Brainstorm v2 items N10 (the Forms tab for real — edit/delete a form, see who answered what and when, a multiple-choice field type, and a pie chart of the answer distribution) and N12 (form presets: build a question set once, choose it before publishing). Both land on the tab N7 left read-only.
**Decision** (26.07.2026):
- **Multi-choice is a new question type (`multi`), and its answer is a JSON array inside the existing string map.** `PostRegistration.AnswersJson` is a `Dictionary<string,string>` (ADR-042); widening it to a union type would invalidate every row already stored. A multi answer is therefore the string `["A","B"]`, decoded by `MultiAnswer.Split` (Core, unit-tested): self-describing, no delimiter that can collide with option text, and a plain text answer that happens to start with `[` still round-trips as a single value. Rendered as checkboxes, not a multi-`<select>` — the latter needs ctrl-click to pick more than one, which nobody discovers on a public page. Server-side required-validation treats an empty array as unanswered, since a replayed POST can send `[]` where the browser sends `""`.
- **The form editor moved out of the export modal** into the Forms tab, and the submissions list with it. What stays in the modal is the one form decision that genuinely belongs to publish time: applying a preset. Two editors for one blob would have been two places to fix every future change.
- **A preset is copied onto the post, never linked** (`FormPreset` entity: `OwnerId`, `Name`, `FormJson`; migration `AddFormPresets`; `FormPresetEndpoints` CRUD). Editing a preset later must not silently rewrite the form of a post that already went live with it — the alternative (a foreign key) makes every preset edit a retroactive change to published posts.
- **Answers now resolve to question labels** instead of raw keys (the gap ADR-046 flagged): the tab has the form definition in hand, so it maps id→label, falling back to the raw key for questions deleted after someone answered them.
- **Charts**: distribution is drawn only for closed questions (`choice`/`multi`) — free text would produce as many slices as submissions. Six is the ceiling on distinguishable series, so a seventh option folds into one "Other" slice rather than inventing a colour. **A question with a single distinct answer renders as a line of text, not a pie** — a full-circle "chart" carries no comparison. Every slice is accompanied by a legend row with label, count and percent, so identity never rests on colour alone, and slices are separated by a 2px surface-coloured stroke.
- **New `--series-1..6` design tokens** (`styles.scss`, both themes) rather than per-chart colours. The dark steps are chosen against the dark chart surface, not lightened from the light ones — a mechanical flip lands outside the lightness band dark needs. Both sets were checked with a palette validator (lightness band, chroma floor, colourblind separation for adjacent pairs, contrast vs the surface) and pass in both modes; re-run that check before changing a value rather than eyeballing it. `--danger`/`--ok` are deliberately excluded: they mean a state, not an identity.
**Consequence**: `.reg-multi` styling had to go into the blog page shell (`BlogEndpoints.PageShell`), which is where all public-page CSS lives — the form is rendered server-side, so it can't reuse the app's stylesheet. Old submissions predating this change still show a single value for what is now a multi question; `MultiAnswer.Split` treats them as one answer rather than trying to re-parse history. The Forms tab still has no per-question free-text summary (a list of distinct text answers) — out of scope here, and the submissions list already shows them per person.

### ADR-048 — Registration-form field rules and a DM on each submission
**Context**: Brainstorm v2 items N6 (validate the form's inputs: name at least 2 characters, no special characters except `-`) and N11 (Telegram DM when someone fills the form in). Both sit on the private-post registration flow.
**Decision** (27.07.2026):
- **The rule lives in Core** (`RegistrationFieldValidator`, unit-tested), not in the endpoint and not only in the browser: the page script mirrors it to save a round-trip, but the server re-checks, since a form POST is trivially replayable outside the browser. Letters are tested by **Unicode category, not an A–Z range** — Cyrillic names are the normal case here, so an ASCII regex would have rejected most real submissions. Spaces and `-` pass; digits and all other punctuation don't; a value made only of hyphens and spaces fails because at least one letter is required.
- **Validation applies whenever a name was supplied, not only when the owner marked it required** — junk in an optional field still lands in the audience list the form exists to build.
- **Only the name field is constrained.** Nickname deliberately keeps its freedom (digits and underscores are what nicknames are made of), email keeps its existing `@` check, and the social link is a URL, not a name.
- **The client-side copy of the message reads `document.documentElement.lang`** instead of being interpolated per render: the blog page shell is one static template shared by both languages, so runtime lookup is the only way to keep RU/EN text without threading the language through the template.
- **N11 reuses `NotifyOwnerAsync`** (ADR-040) rather than adding a second notification path: same opt-in flag, same "log and move on" failure behaviour, so a bot that's down or an owner who never `/start`ed it can never turn a successful registration into an error for the visitor.
**Consequence**: existing `PostRegistration` rows that predate this rule are untouched — the validator runs on submission, not on read, so old junk stays visible in the owner's list rather than disappearing retroactively. Names legitimately containing an apostrophe (O'Neill) or a period (Jr.) are now rejected; that follows Marty's rule as stated ("no special characters except the hyphen") and is a one-character change in Core if it turns out to be too strict in practice.

### ADR-049 — Low-priority sweep: sorting, attention badges, seen-feedback watermark, range slider, and the paragraph-number bug
**Context**: The Low block of brainstorm v2 (N1, N3, N8, N9) plus `B12`'s real bug from the v1 list, done as one pass.
**Decision** (27.07.2026):
- **N1 — `/drafts` sorting and column resizing.** Sort state and column widths are **per-browser view state in `localStorage`**, not profile data — the same treatment `ThemeService` gives the theme, and not worth a round-trip or a schema column. Clicking a new column starts descending, since "newest / most / last touched first" is what each of these columns is usually asked for. Title stays `1fr`, so dragging any handle redistributes width instead of widening the table and reintroducing the horizontal scroll B24 fixed. Resize uses **pointer events with `setPointerCapture`**, so it works with a trackpad, a pen and an iPad finger, and survives the pointer leaving the 5px handle mid-drag.
- **N8 — one watermark, not a per-comment seen table.** `ApplicationUser.FeedbackSeenAt` (migration `AddFeedbackSeenAt`): comments and reactions created after it read as new. A row-per-comment table would answer the same question at far greater cost, given the list is date-ordered anyway. **Loading the page does not move the watermark** — hovering a row does, which is the "I read this" signal Marty asked for; otherwise merely opening the tab would erase the highlights you came to look at. The watermark is flushed **once on leaving**, not per hover, so reading twenty new comments is one request. The server only ever moves it forward, so a stale request from a tab left open overnight can't un-see feedback already read elsewhere.
- **N3 — badges read one shared count** (`CommentsService.newComments/newReactions`, root-provided) fed by a dedicated `GET /api/comments/new-count`, rather than each screen fetching the full feedback list for a number in a corner. A failed count silently renders nothing: a badge is decoration and must never surface as an error. `CountBadgeComponent` is shared (unlike this app's repeated page-chrome CSS) because it has behaviour worth centralising — it renders nothing at zero and caps at `99+` so a runaway count can't stretch the control it sits on.
- **N9 — the range is a free 7…180-day slider with magnets** at 7/14/30/60/90/180 (±4 days of pull), replacing the fixed 30/90/180 tabs. The label updates during the drag but the **fetch fires on release**, so one drag is one request rather than sixty.
- **`B12` — paragraph numbers: a real bug with a specific cause.** The CSS was correct but lived in `editor.component.css`. Angular's emulated encapsulation appends an `_ngcontent` attribute to the last compound selector, and the paragraphs being numbered are created at runtime by ProseMirror, which never carries that attribute — so `.sheet.show-para-numbers .tiptap > *::before` matched nothing, ever. Moved verbatim into `styles.scss` (global), where the rest of the TipTap-dependent styling already lives for exactly this reason. **Only the paragraph-number half of B12 was in scope**; the "ruler should overlay the writing area" half stays open.
**Consequence**: `FeedbackSeenAt` is per account, not per device — reading comments on the phone clears the badge on the laptop, which is the intended behaviour and the same choice ADR-043 made for the `/drafts` delta. Anyone whose watermark is null sees everything as new exactly once. The new-count endpoint is called on editor init and on leaving the feedback tab; it is not polled on a timer, so a badge can be stale until the next navigation — deliberate, since a poll would be a request per user per interval for a decoration.

### ADR-050 — Finishing the UI translation: what the dictionaries hold, and what stays English
**Context**: ADR-044 shipped the localization mechanism plus three screens. This closes the rest — `/posts` and its stats/comments tab bodies, Settings, the editor (the largest by far: toolbar tooltips, export modal, AI dialogs, new-draft dialog) and the debug console.
**Decision** (27.07.2026):
- **Cycling status messages became dictionary arrays.** `TRANSLATE_STATUS_MESSAGES`/`EXPORT_STATUS_MESSAGES`/`BLOG_STATUS_MESSAGES` were module-level `const`s indexed by elapsed seconds; they now live in `editor.statuses.*` as plain string arrays and are indexed the same way. The list length is free to differ per language, since the code takes `list.length` rather than a fixed count.
- **Plural forms are functions, not templates** (established in ADR-044 and used again here for request counts and connected-channel counts) — Russian needs three forms where English needs two, and `{n}` interpolation cannot express that.
- **Deliberately NOT translated**: brand and product names (Cedar Clerk, Telegram, Stripe, PayPal, YouTube, Notion…), plan tiers (Free / Pro / Pro Plus), language endonyms in the picker, and `freeAttributionText` — that last one is *published content* mirroring `Consts.Signatures` server-side, not UI chrome, so translating it would change what appears at the bottom of real posts.
- **A second `t`-shadowing bug was hit and fixed the same way as the first**: `@for (t of tagList())` in the editor shadowed the dictionary accessor, producing "this expression is not callable" at build time. Loop variables named `t` are now renamed to `tag` wherever they exist (`/drafts` and the editor), and both carry a comment saying why. Worth knowing for any future template: `t` is reserved.
**Consequence**: **Server-side text is still English** — `ErrorMessages.cs` and every `{ error }` body reaches the UI untranslated, so a Russian interface still surfaces English failure text; this is the single biggest remaining gap and needs an `Accept-Language` pass on the endpoints. `/terms` and `/privacy` remain English on purpose (unfinished `[BRACKETED]` legal drafts). The German layout requirement from B26 is still a pending CSS pass, not a third dictionary — the tab strips added since carry `overflow-wrap: anywhere` and no fixed widths, but nothing has been checked against genuinely long words. The Russian wording itself has not been proofread in a browser screen by screen.

### ADR-051 — The glossary: where terms are matched, and where they deliberately are not
**Context** (27.07.2026): idea #11, specced by Marty as "a page with all terms; add or edit a description, maybe an image; on publish the text is scanned, terms are found and highlighted; hovering or clicking shows a hint".

**Decision**:
- **Matching happens at blog render time, in Core**, not in the editor and not as a stored transformation of the document. `GlossaryScanner.Mark` takes already-escaped text and the owner's terms and returns HTML; `CedarToBlogHtmlRenderer.Render` gained an optional `glossary` parameter. The document is never rewritten, so a term renamed or deleted today changes every already-published page on its next render with no backfill.
- **First occurrence per page only.** Marking all twenty uses of a common word turns an article into a field of dashed underlines. The `MarkedTerms` set lives on the render context rather than per text node, so "first on the page" means the page.
- **Never inside code, never inside a link.** A term in a code sample is code; a tooltip span nested in an `<a>` puts two destinations under one word. Code blocks bump a suppression depth on the context; the `code` and `link` marks switch marking off for that text node.
- **Aliases, not stemming.** Russian inflects, so a canonical form alone would miss most real occurrences. A comma-separated alias list is honest about what it does; per-language stemming is a much larger commitment for a feature whose failure mode is a missing tooltip.
- **Terms are per content language.** The same word needs a different explanation depending on which language's version of a post is being read, and a Russian description under an English article is worse than no tooltip at all.
- **Images reuse the asset pipeline** and are restricted to `/media/...`, the same rule ADR's avatar work used: an arbitrary URL would let a tooltip point the blog's own chrome at someone else's server.

**Consequence**: the scanner sits in the one place `renderers.md`'s escaping invariant is hardest — it injects markup into already-escaped text — so it is a separate tested unit (19 tests) covering entity skipping (`&amp;` must not yield a marked "amp" and a split entity), attribute escaping of the description, word boundaries, and the longest-candidate-wins rule. The blog script writes the description with `textContent`, never `innerHTML`. **Telegram gets nothing**: a Blocks message has no hover surface, and linking every term to a glossary page was not asked for. The editor shows no highlighting either — deliberate, per Marty's "при публикации"; adding it later means a TipTap decoration plugin, which is its own piece of work.

### ADR-053 — FI1: the Appearance panel gets a real theme switch and an explicit Apply, reversing part of ADR-035
**Context** (27.07.2026): Marty's live feedback on the day-old Appearance panel (`docs/BACKLOG.md` FI1, 7 sub-items) — it doesn't match the rest of the app's visual language, its narrow scroll column shows a default OS scrollbar, the Light/Dark toggle is confusing, more typefaces are wanted, and there should be an explicit Apply instead of saving on every interaction. Marty also suggested a popup instead of a side panel, as a suggestion rather than a firm instruction.

**Decision**:
- **The Light/Dark toggle now switches the real theme** (`ThemeService.set(...)`, same instant call the topbar's own theme button makes). Previously `appearanceMode` was a panel-local signal that only selected *which* theme's accent the swatches below were about to edit — clicking it visibly did nothing to the app, which is exactly the "real ambiguity" the backlog note names. The accent swatches now simply follow whichever theme `ThemeService.theme()` currently is; no more separate mode state to keep in sync.

Flagged back to Marty rather than silently implemented either way.

**Consequence**: `AppearanceService.save()` no longer exists — its one caller (`AppearancePanelComponent`) is rewritten against `preview()`/`commit()`/`dirty`. `en.ts`/`ru.ts` gained `common.saved`, `settings.appearance.apply`, and lost `settings.appearance.themePalette` (the "editing the ⟨theme⟩ palette" sentence no longer applies once the buttons are real theme switches). `ng build`/`ng test` clean. Not yet live-verified in a browser.

### ADR-055 — NF5: polls, blog-only, no new form/preset entity
**Context** (28.07.2026): idea #22/NF5 — a poll content block. `docs/BACKLOG.md` recorded Marty's suggestion to build it on the existing form-preset entity, since the question/choice model already exists there. Marty's explicit decision this session: **polls render on the blog only** — no Telegram surface at all (not even a degraded link), which removes the biggest open question NF5 carried (Blocks has no native poll support).

**Decision**:
- **Not built on `RegistrationFormDefinition`/`FormPreset` after all.** That entity models a per-*draft* access-gate form (name/email/questions to unlock a private post) — a fundamentally different thing from an in-content block any reader can vote on inline, registered or not. Reusing it would have meant threading poll semantics through access-control code that has nothing to do with polls. Instead: a new TipTap node (`poll-node.ts`, `cedarclerk-web/src/app/tiptap-extensions/`) storing `id`/`question`/`options` as node attrs (no content — there's nothing here that's itself rich text), following the exact node-view pattern `toggle-node.ts` already established (hand-built DOM via `addNodeView`, patched back into the doc via `setNodeMarkup`).
- **Genuinely blog-only, enforced by omission, not a guard.** No `case "poll"` was added to either Telegram renderer (`CedarToTelegramBlocksRenderer`/`CedarToTelegramMarkdownRenderer`) or to `CedarToTelegramHtmlRenderer`. A poll node has no content, so those renderers' existing "unknown block type → render children" default (the same fallback `annotation` already relies on) naturally produces nothing at all — the blog-only behavior falls out of the node shape, it isn't special-cased per renderer.
- **Votes are a new `PollVote` table** (`DraftId`, `PollId`, `Option`, `VisitorHash`, `CreatedAt`), same anonymous-visitor-hash shape as `Reaction` (ADR-016) rather than anything tied to an account — a poll on a public blog post has to accept votes from anyone, the same way a like does. One vote per `(poll, visitor)`; changing your answer updates the row (no "unvote" — a poll has no meaningful blank state to return to, unlike a like toggle). Tallies piggyback on the existing `GET /{slug}/annotations` bootstrap fetch (a `polls` dict alongside `article`/`annotations`) rather than a separate round-trip, since every real post page already makes that call.
- **Results only show after voting**, not live before — the rendered markup ships zero-width bars and no percentages; the client script only paints real numbers once `myVote` is set. A `.zip`/`.cedar` static export still gets the same markup (a poll is post *content*, unlike the page-level reactions/comments chrome those exports never included) — the vote buttons simply have no server to call from a downloaded file, the same inherent limitation any interactive feature has in a static export, not something special-cased for polls.

**Consequence**: migration `AddPollVotes`; new route action `poll` in `BlogEndpoints.HandleRequest`'s slug-scoped dispatcher (`POST /api/posts/{slug}/poll`), alongside `react`/`comments`/`register`. `CedarToBlogHtmlRenderer` gained a `poll` case with the same "drop entirely if nothing to show" rule as an empty carousel/collage (ADR-019). `dotnet test` 353/353 (2 new `BlogHtmlRendererTests` cases, 1 new `BlocksRendererTests` case confirming the Telegram side renders nothing). `ng build`/`ng test` clean. Not yet live-verified in a browser; the migration has not been applied against production.

### ADR-057 — Appearance panel: modal, not a side panel (reverses ADR-053's "stays a side panel")
**Context** (28.07.2026): Marty, directly and forcefully, after ADR-053 had explicitly kept the panel as a side column: the permanent sliding column "breaks the design logic," and concretely, it was producing **two scrollbars** — one on the writing area, one on the browser page itself.

**Root cause of the double scroll, confirmed rather than assumed**: `.ap-body` (the panel's content) had grown taller than its flex ancestor chain in some states — the column's own `overflow-y:auto`/`max-height:100%` did not reliably contain it (percentage `max-height` inside nested flex-item chains is exactly the kind of thing that silently stops resolving against a definite height under some combinations, and this component had never been checked against browser devtools for it). The result: `.ap-panel` pushed `.main` taller than the viewport, and `html`/`body` picked up their own scrollbar on top of `.canvas`'s. Verified directly in a running browser (28.07.2026): before this change, `document.documentElement.scrollHeight` exceeded `clientHeight` with the panel open; after, `docScrollable` is `false` with the modal open, at any content length, because a `position:fixed` modal never participates in document flow at all — it cannot push the page taller by construction, which is why this fix is structural rather than a tuned CSS patch.

**Decision**:
- **`AppearancePanelComponent` now renders through `app-modal`**, opened by a new palette-icon button in the editor topbar (next to the theme toggle), instead of the permanent handle+sliding-column it used since I14. `open()` is the same signal as before; only what it gates changed.
- **The trigger lives in the topbar, not the component itself** — `editor.component.html` holds a template reference variable (`#apPanel`) on `<app-appearance-panel>` and calls `apPanel.open.set(true)` from the new button, since Angular template references resolve across the whole template regardless of DOM order.
- **Live preview while dragging a slider — ADR-035's original reason for a side panel — is the one thing this trades away.** The `prefs` signal still updates the sheet the instant any control changes (that plumbing didn't change at all), but the sheet is now hidden behind the modal's backdrop while it's open. Marty's instruction was explicit and didn't hedge on this trade-off, so it wasn't relitigated — accepted as the cost of not having a permanent layout element that fights the page's own height for good.
- **No scroll-closing risk from using `app-modal` over `app-popover`**: this app's `PopoverComponent` closes on *any* document-level scroll event (capture-phase, ancestor-scroll-only... except it can't distinguish "user scrolled the page" from "user scrolled inside my own panel," since scroll doesn't bubble but capturing still passes through `document` for both). A popover here — with this much content (theme/accent/sheet-width/typeface/size/line-height/table-size/five checkboxes/Apply, then the whole toolbar-customization section with drag-and-drop) — would have closed itself the instant anyone tried to scroll it. `app-modal`'s `.modal-body` already had working `overflow-y:auto` with no such trigger, being the same shell Export/Insert/New-draft already use without incident.

**Consequence**: `.ap-panel`/`.ap-handle`/`.ap-handle-label`/`.ap-chevron` and the 900px-width media query are gone from `appearance-panel.component.css` — dead code, nothing else referenced them. `ng build` clean; live-verified in a running browser (theme toggle switches the real theme instantly with the modal still open, typeface's 5-option chip grid wraps correctly at the modal's 440px width, `document.documentElement.scrollHeight === clientHeight` with the modal open). Not yet checked at narrow/mobile widths.

### ADR-058 — Markdown-zip import over 100MB: a local-only SSH bypass, not chunked upload
**Context** (28.07.2026): Marty tried importing a real ~148MB Notion export (design doc + ~20 images) via `/drafts`' "Import .zip". Confirmed directly, not assumed: `cedarclerk.mooexe.dev`'s Cloudflare Tunnel edge hard-rejects any request body over 100MB with a bare `413`, before the request ever reaches Kestrel — verified by `curl`-posting a 150MB dummy file straight to production and observing a 413 in under a second, after only ~1.1MB of the body went out. This is a Cloudflare Free/Pro plan limit (Business=200MB, Enterprise≈500MB practical ceiling), not an app bug: Kestrel's own cap here is already 200MB (`MarkdownZipMaxBytes`, `DraftEndpoints.cs:46`), well above what Cloudflare allows through. Marty declined Business ($250/mo, and 200MB isn't much headroom over 100MB anyway).

**Decision**: build a **local-only bypass endpoint**, `POST /api/drafts/import-markdown-local`, for one-off large imports triggered over SSH — not a shipped multi-tenant feature. Marty `scp`s the zip onto the Pi's `CEDAR_DATA_DIR/import-tmp/`, then `curl`s `http://localhost:8080/api/drafts/import-markdown-local` directly on the box; the request never crosses the tunnel, so Cloudflare's limit never applies.

**The existing `/import-markdown` handler's zip/markdown/image-matching/quota/persist logic (`DraftEndpoints.cs`, previously inline in the endpoint lambda) is extracted into a shared `private static Task<IResult> ImportMarkdownZipAsync(Stream, string ownerId, CedarDbContext, MediaPaths)`.** Both the existing `IFormFile`-based endpoint and the new local one call it — a pure, mechanical extraction (no behavior change, verified: no existing test referenced `/import-markdown` before this, and none of the checks/messages/ordering changed).

**The security-critical decision, worth writing down rather than rediscovering later**: gating this on `HttpContext.Connection.RemoteIpAddress` being loopback alone is **not sufficient**. Kestrel binds only to `http://localhost:8080` (`Consts.URLs.Localhost`), and Cloudflare Tunnel (`cloudflared`, running on the same Pi) reaches the app by connecting to that same address — so *every* request relayed through the public tunnel also arrives at Kestrel from a loopback IP, indistinguishable by IP alone from a `curl` run directly on the box. A bare loopback check would have made this endpoint reachable from the entire public internet.

The actual gate requires **both** loopback IP **and** `Request.Host.Host == "localhost"`. This is safe specifically because Cloudflare Tunnel forwards the client's *original* `Host` header rather than rewriting it — a property this exact deployment already depends on: `Program.cs`'s blog routing (`app.MapWhen(ctx => ctx.Request.Host.Host == blogHost, ...)`) only works in production because the tunnel preserves `Host`, which is direct proof this signal is real and load-bearing here, not a theoretical assumption. A real on-box `curl http://localhost:8080/...` sends `Host: localhost:8080`; a tunneled request always carries `Host: cedarclerk.mooexe.dev`. Deliberately **not** using `CF-Connecting-IP`/`X-Forwarded-For` — both are ordinary, attacker-settable headers, and no `UseForwardedHeaders`/trusted-proxy configuration exists anywhere in `Program.cs` to validate them.

Gated with `Results.NotFound()` (404, not 403) on failure — same instinct as `AdminEndpoints.cs`'s admin-only filter: an endpoint that answers "wrong, but it exists" tells a prober something it has no business knowing.

**Rejected: chunked upload.** The general-purpose fix (splits any file into <100MB pieces client-side, reassembles server-side, works for any future user regardless of file size) has zero existing scaffolding anywhere in this codebase to build on — a from-scratch session/chunk protocol, new endpoints, an abandoned-upload cleanup mechanism, and client-side retry/progress logic. Real value if bulk imports become a recurring need across users, but disproportionate for a single ~148MB personal import. Recorded as backlog idea #23, `docs/BACKLOG.md`, so it isn't lost.

**Consequence**: new `ImportTmpPaths` record (mirrors the existing `MediaPaths` pattern) resolves to `CEDAR_DATA_DIR/import-tmp` — inside the directory the nightly backup cron already covers, so a dropped zip rides along in backups if not deleted promptly after use. `dotnet test` clean. Not yet exercised against the real production import this was built for.

### ADR-059 — Anthropic auto-translate: extract/chunk/splice instead of whole-document JSON echo
**Context** (29.07.2026): a real ~47,000-character document took 1000+ seconds to auto-translate and had already 502'd once with "Model returned malformed translation output" (see `Consts.cs`'s `MaxOutputTokens` comment). Root cause: `AnthropicTranslationProvider`/`OpenAiTranslationProvider` send the entire `Draft.CedarJson` to the model and require it to echo back the **whole TipTap JSON structure** (every node/attrs/marks, in order) with only `"text"` values translated (`TranslationPromptGenerator.cs`). A large document means a large, slow output that can truncate mid-JSON — and a single failed attempt wastes 100% of its tokens for zero result, with no way to chunk since the contract requires one valid JSON document as output.

**Decision**: Anthropic's provider moves to the pattern `DeepLTranslationProvider` already used successfully: `TipTapTextNodes.ExtractTexts` pulls only the human-visible strings out, the flat list is split into chunks (`Consts.Anthropic.TranslationChunkCharBudget`/`TranslationChunkMaxStrings`), chunks are translated **in parallel** (up to 4 concurrent, own `AnthropicClient` per chunk, existing bounded overload/rate-limit retry kept per-chunk), then `TipTapTextNodes.ReplaceTexts` splices the results back into the untouched original JSON. The model never sees or reproduces document structure. A new `TranslationChunkPromptGenerator` carries this flat string-array-in/array-out contract, separate from the existing whole-document `TranslationPromptGenerator`. **OpenAI is deliberately left on the old whole-document approach** — it isn't the active provider; revisit if that changes.

**Also fixed in the same pass**: `TipTapTextNodes.Walk` only ever looked at `text`-node strings, never `attrs` — so poll question/options, footnote body text, image/video/audio captions+alt, and toggle summary were silently never translated by *any* provider, despite the LLM prompt's own rule claiming "every human-visible text." `Walk` now visits these attrs strings too, which fixes the gap for free for DeepL as well (same shared utility).

**Consequence**: `Consts.Anthropic.ChunkRequestTimeout` (short, per-chunk HTTP timeout — fails fast into the existing retry) is now separate from `Consts.Anthropic.AutoTranslateTimeout` (unchanged, still the `AiJobService` job-level ceiling across all chunks). `DraftEndpoints.cs` is untouched — still one `provider.TranslateAsync(...)` call per job. A chunk failure after retries (or the job hard-timeout) still fails the whole translation — same all-or-nothing UX as before, just far cheaper per failed attempt since only one chunk's tokens are at risk instead of the whole document's.

**Follow-up (30.07.2026), found on the first real chunk translated**: a 72-item chunk came back as "Model returned 74 translations, expected 72." A plain positional JSON array has no error-correction — if the model splits (or merges) even one entry, every index after it shifts and the whole chunk fails, even though most of it translated correctly. Fixed two ways: (1) `TranslationChunkPromptGenerator` switched from a JSON array to a JSON object keyed by input index ("0", "1", ...) — extra keys the model invents are simply ignored, and a genuinely missing key names the exact failed index instead of a bare count mismatch; (2) blank/whitespace-only strings are filtered out before ever reaching the model (no translation needed, one less thing that can come back misaligned) and restored unchanged; (3) `TranslateChunkAsync`'s retry loop now also covers `ParseResult` itself (previously only the HTTP call was retried — a malformed/mismatched response failed the chunk immediately with zero retries), so a one-off model slip on a single chunk no longer fails the entire translation.

### ADR-060 — Registration forms go multi-language: one skeleton, per-language text overlays
**Context** (30.07.2026): the FI4.1 model — one `FormPreset` row per language, each holding a completely independent form blob — turned out to answer the wrong question. Marty's actual need: author a form once in Russian, press "+", pick a language, and get a per-language text field on every question and every choice option — with "Да" and "Yes" counting as *the same answer* in the distribution charts. Under FI4.1 nothing ties two language versions together at any level: question ids are independent client timestamps, options are bare strings with no id at all, and `distribution()` groups by raw answer text. Also fixed en route: a real bug where `loadPresets()` only ran from `setTab()`, so landing on `/posts` directly never fetched the preset library and the form dropdown claimed "no saved presets yet" over a non-empty library (the exact confusion that spawned this session), plus the Export modal lacked the Posts tab's DB1 "form attached but library empty" hint wording.

**Decision — the v2 form blob.** One preset = one skeleton + per-language texts, versioned inside the same JSON columns (no schema migration):
```json
{ "v": 2, "languages": ["ru", "en"],
  "intro": { "ru": "…", "en": "…" },
  "requireName": true, "requireNickname": false, "requireEmail": true, "requireSocial": false,
  "questions": [ { "id": "q1", "type": "choice", "required": true,
      "label": { "ru": "Жанр", "en": "Genre" },
      "options": [ { "id": "o1", "label": { "ru": "Да", "en": "Yes" } } ] } ] }
```
- **Options get stable ids**, and the rendered `<option value>`/checkbox `value` is now the **id**, not the label — so a submitted answer is language-neutral and "Да"/"Yes" aggregate as one slice. Core's `RegistrationQuestion.Options` becomes `IReadOnlyList<RegistrationOption>` (`Id`, `Label`); a v1 blob parses with `Id == Label`, which keeps every already-stored answer displaying identically (the old stored values *were* the labels).
- **Single-language resolution stays the render/validation model**: `RegistrationFormSet.Pick` detects `"v": 2` on the primary blob and projects the requested language out of it (per-string fallback to the skeleton's first language), returning the same `RegistrationFormDefinition` the renderer and submit validation always consumed. The `Draft.RegistrationFormTranslationsJson` column and per-language slot writes remain only as the v1 compatibility path — a v2 write nulls the translations column.
- **Applying a preset applies every language at once** — the whole v2 blob is copied onto the post in one click (still a copy, never a link — ADR-047 stands).
- **Form auto-translate** — `POST /api/form-presets/{id}/translate` (Pro Plus + daily AI quota, same gates as post auto-translate). This **reverses the FI4.1-era note** on `FormPreset.Language` ("a machine translation of the owner's wording is not the owner's voice"): Marty explicitly asked for it, and unlike then it's now an explicit per-language button the owner presses and can edit afterwards, not something automatic. Implementation reuses ADR-059's chunk machinery via a new narrow `ITextsTranslationProvider` (flat string list in/out) implemented by Anthropic (chunked/parallel) and DeepL (its native batch); OpenAI doesn't implement it → 501. Runs synchronously — a form is a handful of short strings, one chunk, seconds.
- **No data migration**: FI4.1 multi-language blobs barely exist (confirmed with Marty). v1 blobs stay readable everywhere; the Forms editor upgrades them to v2 in memory on load and writes v2 on save.

**Consequence**: `FormPreset.Language` becomes derived metadata (`languages[0]`) kept for wire compatibility; the per-preset language dropdown is replaced by language chips (+ add / auto-translate / remove) in the Forms editor; the comma-separated options input is replaced by per-option rows with one input per active language (a comma field can't keep option ids stable across languages). Distribution charts and the submissions list map stored option ids back to primary-language labels, falling back to the raw stored value for pre-v2 rows.


### ADR-061 — Glossary terms get per-term auto-translate into the other content languages
**Context** (29.07.2026): glossary terms are per-language by design (a post is only scanned against terms in its own language — see the glossary ADR), so a six-language blog means entering the same term up to six times by hand. Marty asked for auto-translation into selected languages.

**Decision**: `POST /api/glossary/{id}/translate` with `{ targetLanguage }` — the ADR-060 form-preset shape verbatim: Pro Plus + the daily AI quota, `ITextsTranslationProvider` (Anthropic chunked / DeepL batch; a provider without it → 501), synchronous — a term is two short strings, well under one chunk.
- **Term + Description are translated; Aliases deliberately are not.** Aliases exist to cover one specific language''s inflections ("рендерер, рендерера, рендереру") — a word-for-word machine rendering of that list into another language is noise, not coverage. The owner fills them per language when needed. `ImageUrl` is copied — a picture is language-neutral.
- **Upsert, not blind insert**: if the owner already has a term in the target language whose `Term` equals the translation (case-insensitive), its `Description` is overwritten and its aliases/image are kept; otherwise a new row is created. Pressing the button twice therefore refreshes rather than duplicates.
- **"Selected languages" is a frontend loop**: the modal collects target-language checkboxes and calls the endpoint once per language, sequentially. No batch endpoint — per-language quota consumption and per-language errors stay legible, and the ADR-060 contract is reused unchanged.

### ADR-062 — Glossary gets a whole-language batch translate (amends ADR-061's "no batch endpoint")
**Context** (29.07.2026): Marty asked to translate *all* terms of the selected language into the other languages at once. Doing that through ADR-061's per-term endpoint would cost one daily-AI-quota call per term per language — 20 terms into 5 languages is 100 quota calls for what the provider could do in 5. The "no batch endpoint" line in ADR-061 was written for the per-term modal, where the unit of work really is one term; it priced in neither a whole-glossary sweep nor the quota math.

**Decision**: `POST /api/glossary/translate-all` with `{ sourceLanguage, targetLanguage }` — same gates as ADR-061 (Pro Plus, `ITextsTranslationProvider`, daily AI quota), but **one quota call and one provider call per target language**, covering every term of the source language: all term+description pairs go into a single `TranslateTextsAsync` call and the existing chunk machinery (ADR-059) splits them as needed.
- **The frontend still loops per target language, sequentially** — that part of ADR-061 stands. Per-language quota consumption and per-language errors stay legible; only the per-term loop inside a language collapsed into the batch call.
- **Upsert rule is ADR-061's, applied per term**, with one addition: existing target-language terms are loaded once up front (one query, not one per term), and terms created earlier in the same batch participate in the case-insensitive match — two source terms that translate to the same target word update one row instead of inserting a duplicate.
- **A term whose translation comes back unusable (blank or over-length) is skipped, not fatal**: the endpoint returns the upserted terms plus a `skipped` count. One garbled pair shouldn't discard a whole language's worth of paid translation.
- Aliases/image treatment is ADR-061's verbatim: aliases stay untranslated, the image is copied onto newly created rows only.


### ADR-063 — Private posts can block copying on the blog page (deterrent, not protection)
**Context** (29.07.2026): Marty asked for a per-post switch — in the Export window and the Posts manager — that forbids copying (and the context menu) on private posts' blog pages. Same motivation as the watermark (I7): discourage redistribution of something handed out per invite.

**Decision**: `Draft.DisableCopy` (bool) + `POST /api/drafts/{id}/disable-copy` — the `/listed`/`/watermark` one-concern-per-endpoint shape verbatim.
- **Only applied when `IsPrivate` is also true** (same family rule as the watermark): the flag persists independently, but `RenderPostAsync` checks `IsPrivate && DisableCopy`, so flipping a post public silently deactivates the guard without losing the setting.
- **Render-side, not renderer-side**: a `<style>` (`user-select: none` on `.post-sheet`, `user-drag: none` on its images) plus a tiny inline script blocking `contextmenu`/`copy`/`cut`/`dragstart` — injected by `BlogEndpoints.RenderPostAsync` next to the watermark, never touching `CedarToBlogHtmlRenderer` (which stays a pure document renderer).
- **Scoped to `.post-sheet` only** — the annotation/comment UI below the sheet keeps normal selection and a working context menu; readers still copy their own comment drafts.
- **Named honestly**: the entity comment, hints and this ADR all say *deterrent* — the page source is one Ctrl+U away, and the UI hint tells the owner so rather than selling fake DRM.
- UI: a checkbox in the Export modal's blog section (under "show in list anyway", visible only while Private is on) and one in the Posts manager's private-post section; both call the same endpoint, list/get DTOs carry `disableCopy`.

**Consequence**: nothing changes for public posts or any renderer test; the guard is one string in one method. If a real protection ask ever lands (image watermarking on pixels, PDF-style export), it starts from this flag but is a different feature.

### ADR-064 — Draft language is chosen per draft; publishing is guarded by revision diffs
**Context** (30.07.2026): a post may now originate in any supported content language, including English without a Russian version. Editors also need an incremental translation path, a minimal audit trail for every language, and an explicit last check before a live post is overwritten.

**Decision**:
- `Draft.PrimaryLanguage` records which language owns the canonical `Draft.Title`/`Draft.CedarJson` slot. Changing it swaps that slot with the selected `DraftTranslation` row atomically, so the storage layout stays compatible while no language is inherently Russian.
- A translation explicitly records its source language and source snapshot. Incremental translation uses the snapshot to send only changed top-level blocks plus their stable context to the provider; a full translation remains available as a deliberate fallback.
- Every content save creates an immutable `DraftRevision` carrying language, title, document JSON and a compact block-level diff summary. The same revision model records the content successfully sent to each destination.
- Before an already-published Telegram or blog target is updated, the client must request a server-calculated diff against that target's most recently published revision and show it in a confirmation modal. The actual update carries the revision id it was previewed against, so the server rejects a stale confirmation rather than publishing unseen edits.

**Consequence**: existing drafts receive `ru` as their primary language through the additive migration. Historical posts without a stored publication revision deliberately show a conservative "baseline unavailable" warning on their first update; subsequent publishes are fully diffable.

### ADR-065 — ADR-064 corrected: the publish guard becomes server-enforced, and three of its claims are withdrawn
**Context** (30.07.2026): ADR-064 was implemented in one pass and then audited before being committed. The audit (14 agents, every major finding independently re-verified against the working tree) confirmed the design but found the implementation delivered roughly half of it — including the part the ADR exists for. The findings are recorded as `docs/BACKLOG.md` T-063; this ADR records what changed as a result, because several of ADR-064's own statements were not true of the code and one of them is now deliberately deferred rather than fixed.

**Decision**:
- **The publish guard is enforced on the server, not the client.** ADR-064 said the update "carries the revision id it was previewed against, so the server rejects a stale confirmation"; in practice `ConfirmedFingerprint` was never read or sent, so the confirmation was advisory only and had a preview-to-publish TOCTOU gap. Both publish endpoints now *require* a matching fingerprint whenever a prior publication revision exists for that target, and answer `409` with a fresh diff when it does not match. The client sends the fingerprint it showed the user, and flushes any pending autosave **before** asking for the preview — previewing last-saved content and then publishing newer content is the same defect in a different place.
- **The guard covers the blog too**, as ADR-064 claimed but the code did not: `update-preview` takes a `kind` (`telegram`/`blog`), and the blog's own destination is its slug. Whether a target counts as "already published" is decided by the server's answer (`publishedBefore`), not by whether the client happens to know a public post URL — the previous client-side condition silently skipped the guard for channels with no `@username`, which is an ordinary private-channel setup.
- **Every language being published is shown, not one of them.** The previous single-preview modal showed an arbitrary language's diff while confirming the publication of all ticked languages, which could confirm "no changes" and publish a changed translation unseen.
- **`Draft.PrimaryLanguage` is the primary everywhere, or nowhere.** Static HTML export, `.zip` export, AI edit and the v1 registration-form slot still compared against the literal `ru`, so the feature's headline flow (a draft whose primary is not Russian) broke them. There is now one list of content languages (`Languages.ContentLanguages`) and one predicate (`IsContentLanguage`); `TranslationLanguages`/`IsTranslationLanguage` are gone, because "is a translation" is a per-draft question (`lang != draft.PrimaryLanguage`) that a static list cannot answer — and answering it statically is exactly what produced the duplicate-`ru` list and the shadow-translation rows.
- **A revision is only written when the content actually changed**, and `save` revisions are pruned to the most recent 50 per draft+language. ADR-064's "every content save creates an immutable revision" is unworkable as literally stated against a 1.2s-debounced autosave: it stored a full copy of the document on every pause in typing, with no deduplication and no ceiling, on a Pi whose database is backed up nightly to a microSD. Publication revisions are never pruned — they are the diff baselines the guard depends on.
- **Deleting a draft or a translation deletes its revisions.** They had no foreign key and no cleanup, so a deleted private post left full copies of its text in the production database and in all 14 backup generations. **A real FK with cascade is deliberately not added**: on SQLite that is a table rebuild, and `.claude/rules/ef-migrations.md` exists because this project has already been bitten by rebuild-shaped migrations. Explicit deletes are deterministic and need no schema change at all — this correction ships with **zero** migration, and the one Codex generated is left exactly as it was (the audit found it sound: purely additive, correct `ru` default).
- **A no-op save is a no-op.** `PUT /api/drafts/{id}` and `PUT .../translations/{lang}` return early without touching `UpdatedAt` when the incoming title and document are byte-identical to what is stored. This is also the root cause of the long-standing false-dirty bug (the old `IB3`): staleness is a timestamp comparison, and the server bumped the timestamp on saves that changed nothing — a touched title, a typed-then-undone edit, or a rename from the Posts Manager, which PUTs the unchanged body back. Relatedly, changing the primary language no longer bumps `UpdatedAt` to "now": it carries the promoted translation's own timestamp, which preserves every relative recency and therefore flips nothing to stale for what is a pure relabeling.

**Withdrawn from ADR-064**: incremental translation ("send only changed top-level blocks plus their stable context") was never implemented — auto-translate still sends the whole document. It stays a wanted feature (`docs/BACKLOG.md` T-015, with a designed approach) but is **not** something to build on today. `DraftTranslation.SourceLanguage` was a write-only column; it now decides whether a stored snapshot is offered to the client at all — a snapshot taken from a different language is withheld rather than diffed, which is the same honesty the swap applies when it nulls them.

**Consequence**: the swap now nulls the *other* translations' snapshots instead of leaving them pointing at a document in a language they were never translated from — provenance is unknown after a relabeling, and saying so costs a diff gutter rather than showing a false one. Restoring a revision is still not possible from the UI (T-016); the history modal remains read-only, so the recovery story for the 29.07 data-loss incident is unchanged by this ADR and is tracked separately (T-018).

### ADR-066 — Saves can be refused: a shrink guard, a conditional write, and a flush the tab can't kill

**Context** (30.07.2026): the 29.07 wipe was root-caused as three independent gaps that each had to hold for the post to survive, and none of them did. The 1.2s autosave honestly saved a transient empty document (deleting a table empties the doc for an instant); the server accepted it without a word; and closing the tab on iOS killed the timer carrying the restored content. ADR-065 closed the *publishing* half of this. This closes the *saving* half — `docs/BACKLOG.md` T-018.1/.2/.3/.6, T-060, T-062.

**Decision**:
- **A save that deletes nearly all the text is refused, not applied.** `CedarClerk.Core/ShrinkGuard.cs`: when the stored version has at least 200 characters of human-visible text and the incoming one keeps 20% or less of it, both save endpoints answer `409 {code:"shrink"}` and the editor asks the author. The measure is extracted text, **not** JSON length — a table becoming paragraphs rewrites most of the JSON while keeping every word, and measuring bytes would refuse ordinary editing. The thresholds are deliberately lenient: a false positive costs one click, the false negative cost a published post.
- **The refusal dialog offers "restore stored", not just "save anyway".** At the moment of refusal nothing is lost — the editor holds the new text, the server the old — and the recovery the incident had no button for is getting the stored version back. It reloads the active language directly rather than going through `openDraft()`, which refuses to reopen the draft already open and would flush the very save being discarded.
- **Writes are conditional when the client knows what it is overwriting.** A save may carry `expectedUpdatedAt`; a mismatch is `409 {code:"stale"}` with the server's current timestamp. **Optional on purpose** — the Posts manager's rename-PUT and both import paths send no baseline and behave exactly as before, and a brand-new translation row has none. This is also the prerequisite recorded against editor tabs (Q-2): without it, two tabs on one draft are two more ways to lose text.
- **A pending save is flushed when the page is hidden, with `keepalive`.** `visibilitychange`/`pagehide` fire while the page is still alive; `fetch(..., {keepalive:true})` lets the request outlive it, which `HttpClient` cannot do. Above ~30k characters the ordinary save is used instead: the browser rejects a keepalive body over 64KB outright, and a rejected request saves nothing at all. Bypassing the debug-console interceptor is the accepted price.
- **A failed save retries itself** (2s/5s/15s, then the manual button), and the status bar stays on "sync failed" the whole time rather than briefly claiming success.
- **A failed `/api/auth/me` is no longer treated as a logout.** It is retried, and only a `401` clears the session; anything else leaves the state untouched and reports "unavailable", which the login page shows as a retry instead of a password prompt. The auth ticket also gets an explicit 30-day `ExpireTimeSpan` — Identity's default is 14 days, so under a 30-day cookie the shorter one silently won and looked like a random logout (T-062).
- **DataProtection keys move under `CEDAR_DATA_DIR`** (T-074). They decrypt every auth cookie and lived in `~/.aspnet/DataProtection-Keys`, which the backup cron never saw. `SetApplicationName` is pinned to `CedarClerk.Server` — the value ASP.NET already derived implicitly — because changing it invalidates every existing cookie.

**Consequence**: **the deploy carrying this has a manual prerequisite** — copy the Pi's existing `~/.aspnet/DataProtection-Keys/*.xml` into `~/cedarclerk/data/dataprotection-keys/` *before* starting the new binaries, or every signed-in session is dropped once. The shrink guard's thresholds are a judgement call pinned by `ShrinkGuardTests`; changing one of them silently brings back the incident it exists for.

### ADR-067 — Version history becomes reachable: read a version, diff any two, restore one

**Context** (30.07.2026): ADR-065 left the history modal read-only and said so — recovering a version meant `sqlite3` on the Pi, which is a recovery story for exactly one person. `docs/BACKLOG.md` T-016/T-017.

**Decision**:
- **A row in the history opens the version** (`GET /revisions/{lang}/{revisionId}`) — its stored document, its diff against what is stored now, and whether it *is* what is stored now (the restore button is disabled in that case rather than performing a no-op that writes two revisions).
- **Any two ends can be diffed** (`GET /revisions/{lang}/diff?from=&to=`), where either end may be the literal `current`. One endpoint instead of a compare-to-current special case: the client has to pick two ends either way, and "current" is the only thing that isn't a revision id.
- **The preview is the words, not a rendering.** A second TipTap instance is a lot of machinery to answer "is this the version I lost", and the block boundaries the diff counts are exactly what makes the text readable — so `plainTextOf` emits one line per top-level block.
- **Restoring is an ordinary edit, not a rewind.** `POST /revisions/{revisionId}/restore` records the version being *replaced* first, so a restore is itself undoable through the same history, then writes the restored content and finally a `restore`-kind marker naming the point rewound to. The marker is never pruned — it is the one entry an author will go looking for later, and the 50-save ceiling would eventually sweep it away.
- The revision's own `Language` decides which slot is written; there is no language parameter on restore, because a revision belongs to exactly one language and letting the caller name a different one is only a way to write English text into a Russian post.

**Consequence**: the 29.07 incident now has a complete answer — ADR-066 stops the empty save, and this makes the older version retrievable if one ever gets through. `DraftRevision` rows are still capped at 50 saves per draft+language, so the history is a safety net measured in recent edits, not an archive.

### ADR-068 — Re-translation is incremental: only the blocks that moved are sent to the provider

**Context** (30.07.2026): ADR-064 promised incremental translation and ADR-065 withdrew it as never implemented. Re-translating a document that changed by one paragraph cost a translation of the whole document — slow, one full quota call, and it discarded every manual correction the author had made to the other paragraphs, which is the reason "re-translate" was avoided in practice. `docs/BACKLOG.md` T-015.

**Decision**:
- **A positional splice, computed on the server** (`CedarClerk.Core/IncrementalTranslationPlan.cs`). `DraftTranslation.SourceSnapshotJson` is the source as it stood when this translation was made; an LCS alignment of its top-level blocks against the current source says which blocks are unchanged. Unchanged ones are copied out of the **existing translation** verbatim, changed and new ones are sent to the provider, and the result is reassembled in the new source's order.
- **The reuse rests on "block *i* of the snapshot became block *i* of the translation"**, so the plan refuses itself whenever that can no longer be assumed: no snapshot, a snapshot taken from a different primary language (ADR-065), unparseable content, or a translation whose block count no longer matches the snapshot's — most often a translation restructured by hand. It also refuses when *every* block changed, where the splice would add bookkeeping and save nothing. Every refusal falls back to the existing full translation, so the worst case is today's behaviour.
- **The changed blocks travel as a real TipTap document**, not as a bare list of strings, so they go through the ordinary provider path — which replaces text in place and leaves structure alone (ADR-059) and therefore returns the same blocks in the same order. `Assemble` still verifies the count and throws rather than storing a document of the wrong shape; the endpoint turns that into a 502 instead of a corrupted translation.
- **Blocks are translated without their neighbours as context**, which the backlog's sketch suggested including. Sending neighbours means either paying for their translation too or asking the provider to return text it was told to ignore, and the failure mode of a mismatched count is a shuffled document. Paragraph-level blocks carry enough of their own context; if a pronoun-heavy edit ever translates badly, that is the trade to revisit.
- **Zero changed blocks means no provider call at all** — the stored translation already is the answer, and confirming that is not worth one of the twenty daily calls. **Consequence, accepted knowingly**: a source whose *title alone* changed keeps its old translated title, because the title is not part of the block diff and there is no stored snapshot of it. The title is an editable field; a migration to add `SourceTitleSnapshot` is not justified by that case.

**Consequence**: "re-translate" now preserves manual edits to untouched paragraphs, which changes what the confirmation dialog means — its wording was updated accordingly (and, en route, stopped saying "the English version" and "from Russian", leftovers from before per-draft primary languages).

### ADR-069 — The Appearance panel saves itself; server messages follow the reader's language

**Context** (30.07.2026): two separate complaints with the same shape — a control that does not say what it does. `docs/BACKLOG.md` T-041 and T-050.

**Decision**:
- **The Appearance panel has no Apply button.** It was real (it persisted the prefs) but read as decoration, and for a good reason: every control already changed the sheet live (ADR-053) *and* the toolbar half of the same panel saved itself on click, so half the panel behaved one way and half the other. The appearance half now commits on its own, debounced — which keeps the whole point of ADR-053's preview/commit split (a slider drag is one write, not one per tick) — and closing the modal flushes a debounce still in flight. What is left where the button was is a line saying saved / saving / could not save. ADR-053 and ADR-057 are unaffected: live preview and the modal both stand.
- **Server messages answer in the reader's language, without any call site passing one.** `ErrorMessages` members became properties reading `CultureInfo.CurrentUICulture`, which a middleware sets per request from the signed-in account's `UiLanguage` (Accept-Language for anonymous requests, which is what the blog's registration gate needs). Consts could never have worked here — a const is baked into the caller at compile time. The alternative, threading a language parameter through every endpoint, would have been ~130 call-site changes for the same result, and .NET already flows `CurrentUICulture` across await boundaries (pinned by a test, since the whole design fails silently if that ever stops being true).
- **Only Russian is translated**, matching the app's own dictionaries: every other UI language already falls back to English in `en.ts`/`ru.ts`, and machine-quality German error text is a worse answer than the English original.

**Consequence**: **T-050 is half done and stays open.** The centralized messages in `ErrorMessages.cs` are localized; the ~130 inline `{ error = "..." }` strings scattered through the endpoint files are not, so a Russian UI still shows a mix. The mechanism is the hard half — moving a literal into `ErrorMessages` is now mechanical and needs no call-site signature change — but until that sweep happens the mix is real, and the backlog row says so rather than claiming the item shipped.

### ADR-070 — UI verification precedes the redesign; the redesign precedes new publishing targets

**Context** (30.07.2026): Marty asked for four things in one breath — a full pass over the UI, a redesign in one modern style, reworked icons, and support for one more social network (Threads / X / Instagram). Taken as a single sprint they conflict: the project's dominant risk right now is **verification debt, not code debt** — a large amount of shipped work (the FI2 export rebuild, the FI4 forms editor, the glossary, and everything from 30.07: save guards, version history, incremental re-translation) has never been opened in a browser. Restyling on top of unverified screens destroys the ability to tell an old defect from one the restyle introduced.

**Decision** — three sequential phases, not one:

- **Phase 10 — UI Verification Sweep.** Audit first: extend `docs/UI-INVENTORY.md`, build a Playwright smoke suite, walk the live-verify checklist by hand, and record every defect as a backlog row rather than fixing it on sight. Fixes happen only against a list Marty has approved, so "what did we change" stays separable from "what was already broken".
- **Phase 11 — Design System 2.0.** Tokens v2, one icon set, screen migration, responsive and accessibility passes.
- **Phase 12 — Publishing Targets.** The publishing abstraction and the first non-Telegram network.

Four scoping calls inside that order:

- **Icons are a component of the design system, not a phase.** A separate icon pass would be a second walk through the same templates for the same files; it rides along with the screen migration. `@lucide/angular` is the incumbent and the choice of set is Q-12.
- **Mobile-responsive and the German long-word pass belong to Phase 11, not after it.** Breakpoints written during the migration cost one pass; written afterwards they cost a second full pass over markup that just moved. These are existing backlog rows (T-034, T-051), not new work — they get pulled into the phase rather than duplicated.
- **Social publishing is an architecture phase, not a UI phase, and it is blocked on Q-1.** Which network to build first follows from which audience the product is for; the cost profile differs by an order of magnitude between them (Q-13). The abstraction must also land *before* the second network exists, or it will be born shaped around Telegram.
- **The frontend has no safety net.** The 442 tests cover the backend and Core; the three frontend spec files cover two utilities. A redesign is a refactor of the entire UI with nothing that can say "this broke". The smoke suite is therefore a prerequisite of Phase 11 and, in Phase 10, doubles as the audit instrument.

**This reverses the standing "no general redesign" position** recorded in `docs/BACKLOG.md` ("дробить на конкретные боли, не монолит"). That call was made against a redesign proposed with no design direction, no inventory and no tests; it stands as written for an *unstructured* restyle, and the deferred row is updated rather than silently dropped. What makes Phase 11 a different proposition is that all three are prerequisites of it, and Q-11 must be answered before any of it starts.

**Consequence**: Phase 10 ships no visual change whatsoever — that is what makes its defect list trustworthy. Q-11 (visual direction) blocks all of Phase 11 and is Marty's to answer, not Claude Code's; Q-13/Q-14/Q-15 block Phase 12 the same way.

### ADR-071 — Visual direction: warm editorial base, one palette, two density modes (Q-11 answered)

**Context** (31.07.2026): Q-11 was the single thing blocking all of Phase 11 (T-075…T-082). Three options were put to Marty: (A) warm editorial / cabin — paper, wood, warm neutrals, serif typography in content; (B) dense product / dark-first, the Linear/Vercel school; (C) a hybrid. **Marty chose C: A as the base, with B's density borrowed on the table-shaped screens.**

The measured starting point matters more than the label, and it was checked rather than assumed. The current token set **is already warm editorial** — `--bg: #ECE9E2`, `--sheet: #FCFBF8`, `--accent: #5B6E46` (olive), `--text: #26231D` — because that is what the 08.07.2026 "Cabin" redesign built. So this decision is **not a repaint; it is systematization plus a density layer.** That materially lowers Phase 11's risk profile, and it is the honest reading of what was chosen: the direction question was answered in favour of what the app already looks like when it is at its best, against the screens that have drifted away from it.

**Decision** — five principles, which T-075 carries into `docs/DESIGN.md`:

- **One palette and one type scale across the whole product.** Density is expressed as *spacing, radius and font-size tokens*, never as a second set of colours. A second palette for "the dense screens" would be a second visual system wearing a shared name, which is precisely the failure mode option C exists to avoid.
- **Density is a mode set on a surface, not a decision made per component.** A container opts in (`[data-density="compact"]` on the page root, mirroring how `data-theme` already works on `<html>` — the mechanism exists and is proven), and the tokens inside it resolve tighter: row spacing, control padding, radius (`--radius-md` → `--radius-sm`), and border-instead-of-shadow separation. Compact is for `/posts`, `/drafts`, `/admin` and `/stats`. The editor sheet, the blog and the private-post gate stay comfortable. A component never hardcodes which mode it is in, so the same component can appear on both kinds of screen — which several already do.
- **Serif is for content, sans is for chrome.** Today everything is sans, including the blog body. Serif enters in the read surfaces (blog post body, editor sheet) and nowhere else; toolbars, tables, forms and menus stay on `--font-sans`. This is the one genuinely new visual element of option A, and it is confined to where a reader reads.
- **Light-first, dark as a peer.** Against B's dark-first premise. The light theme is the product's identity here, and the dark theme is already a full override rather than a filter — it stays that way, and every token added in v2 gets both values at the moment it is added, not afterwards.
- **The blog is inside the design system, not adjacent to it.** `BlogEndpoints.cs` carries **its own `:root` block and 21 hardcoded hex colours**, and `CedarToBlogHtmlRenderer` another 6 — a duplicate token set, hand-maintained, for roughly half of what any reader ever sees (the thirteen server-rendered surfaces inventoried in Phase 10). Tokens v2 has to reach it, or the redesign ships a product whose public face is on the old system.

**Two things this decision deliberately does not settle**: the icon set (Q-12, T-079) is still open and is the next blocker after this one; and no mockup is authorized by this ADR — T-076 draws them, starting from `_Documents_/CedarClerk/Design-Handoff-2026-07-28/` rather than from scratch.

**Consequence**: Phase 11 is unblocked and T-075 is closed by this entry plus the principles section in `docs/DESIGN.md`. The scale of the token sweep is now a measured number rather than an impression: **314 hardcoded `font-size` declarations** across component CSS against a `--fs-*` scale that has existed since 27.07 and was adopted by exactly one component (ADR-052), plus 44 hex literals in `styles.scss` and the blog's separate 27. T-077's "zero hardcoded values in components" is that list. (An earlier count in this entry said 191 — that regex matched whole pixels only, which is exactly how the next finding stayed invisible.)

**What the measurement itself found, and it is not a counting artefact**: **110 of those 314 sizes are half-pixel values** — 44×`12.5px`, 30×`11.5px`, 16×`10.5px`, 14×`13.5px`, and stragglers at 9.5/14.5/16.5. Nobody designs on half-pixels; a browser rounds them per-element at render, so two controls written as `12.5px` and `13px` can land on the same rendered size at one zoom level and differ at another. And 79% of all UI text sits in a 11–13.5px band with half-steps inside it, meaning the app's *entire* type hierarchy is expressed in about five distinguishable sizes crowded into 2.5 pixels. The v2 scale therefore collapses the half-steps to integers rather than preserving them — this is a real hierarchy problem the redesign fixes, not a formatting preference.

### ADR-072 — Icon set: Phosphor, delivered as inlined SVG through one `app-icon` component (Q-12 answered)

**Context** (31.07.2026): Q-12 was the second blocker of Phase 11 and gated T-079. The incumbent is `@lucide/angular` ^1.23.0, used as a directive on a bare element — `<svg lucideTrash2 class="icon-sm">` — with icons imported per component across 15 TypeScript files, 79 distinct icons in 203 places. Candidates were Lucide (stay), Phosphor (MIT, six weights) and Tabler (MIT).

**Decision**: **Phosphor.** Marty chose it, and the reason it fits rather than merely being a change: six weights (thin → fill) give the "larger and bolder" reading he has asked for before *without* introducing a second icon family, and its rounder, softer terminals sit with the warm-editorial direction of ADR-071 better than Lucide's uniformly geometric stroke. Tabler was declined as a lateral move — close enough to Lucide in character that migrating 203 call sites would buy nothing visible.

**Delivery mechanism** — three published packages exist and they are not interchangeable (verified on npm 31.07.2026: `@phosphor-icons/core` 2.1.1, `@phosphor-icons/web` 2.1.2, `@phosphor-icons/webcomponents` 2.1.5). The choice is **`core` (raw SVG assets) behind a single `app-icon` component**, mirroring the existing `app-brand-icon` (ADR-054) rather than inventing a second pattern:
- The **icon font** (`web`) was rejected: it ships the whole font regardless of how many icons are used, and a font glyph is a poor host for the `aria-label`/tooltip work T-080 is about to do on exactly these elements.
- The **web components** package was rejected: it needs `CUSTOM_ELEMENTS_SCHEMA` on every component that renders an icon, which switches off Angular's template type-checking for that component's whole template — a real cost paid across 15 files to avoid writing one wrapper.
- One wrapper component also means **weight and size are props bound to tokens**, so "make the icons bolder" stays a one-line change instead of a fourth sweep through 203 call sites.

**Consequence (superseded in part by ADR-073)**: T-079 is unblocked. It is not only a set swap — the same pass fixes the measured inconsistency behind it: `.icon` is declared in **9 files with three different values** (15/18/20px) and `.icon-sm` with two, which the new `--icon-sm/md/lg` tokens replace, plus **10 glyphs that are not from any icon set at all** (`☾ ✦ ◷ ⤢ ¶ ⏰ 👍 👎 ☰ ↑`) rendering in the system emoji font and therefore looking different on every OS. Lucide stays in `package.json` until the last call site moves, since a half-migrated app needs both. Because the base direction is a continuation rather than a reversal, the migration (T-081) can proceed screen by screen with the Phase 10 smoke suite green after each one, instead of needing a big-bang cutover — which is what ADR-070 built the suite for.

### ADR-073 — The editor sheet is excluded from the serif rule (narrows ADR-071 principle 4)

**Context** (31.07.2026): ADR-071's fourth principle read "serif for content, sans for chrome — blog post body and editor sheet get a serif". Migrating the editor to tokens surfaced a collision the principle was written without: **the editor sheet's typeface is already a user setting.** `AppearancePrefs.typeface` offers five system stacks including `serif` and `serifClassic`, defaults to `system` (sans), and is edited in the Appearance panel (ADR-053/057).

**Decision**: principle 4 now covers **the blog post body only**. The editor sheet keeps its user setting, default unchanged.

The reasoning Marty confirmed: a serif on the blog is what the *reader* sees, and that is a design-system decision. The editor is a working tool whose typeface the author already chose — or deliberately did not change, which is also a choice. Honouring the original wording would have meant a design sweep silently rewriting a preference every existing account already reflects, to enforce a rule about how text should look to somebody who is not looking at it.

**Rejected alternative**: applying the serif default only to new accounts. It would have been honest to existing users, but it splits accounts into two classes with different defaults — a permanent data-model wrinkle bought for one font.

**Consequence**: `docs/DESIGN.md` principle 4 is narrowed in place (that file states the current rule, not the history — this entry is the history). Nothing in the code changed: the editor already behaves this way, and the point of recording it is that the next person reading principle 4 does not "fix" the editor to match it. Q-16 is closed.

### ADR-074 — The accessibility contract of the token set: `--t3` stops being a text colour (T-082)

**Context** (31.07.2026): T-082 asked for AA contrast, focus states and 44px touch targets. Measuring first (`cedarclerk-web/tools/check-contrast.mjs`, which resolves the `color-mix()` derivations the same way a browser does) turned "improve accessibility" into a list: **32 failing token pairs** across both themes. The measurement also settled which surface binds — for dark text on a light palette the *recessed* surface `--canvas`, not the sheet, is the worst case, because contrast falls as the background darkens.

**The finding that forced a decision, rather than a fix**: raising `--t3` to 4.5:1 lands it on `#676259`, and `--t2` is `#6B655A`. **At AA, this palette has room for exactly two muted text tiers, not three.** Every option that keeps three tiers either fails the standard or repaints the warm neutrals into something else.

**Decision**: `--t3` is no longer a text colour. Its contract is **placeholder, disabled and decoration**, where the rule is 3:1 (non-text contrast, SC 1.4.11) rather than 4.5:1. Every declaration that used it to say something — 91 of the 107 in the app — moved to `--t2`. What is left on `--t3` is eight rules: three breadcrumb separators, two disabled states, a dimmed table row, a spacer and a placeholder.

The visible consequence, stated plainly because Marty will see it: **meta text across the app is darker now** — timestamps, counts, column headers, hints. The type scale still carries the hierarchy (`--fs-caption`/`--fs-meta` against `--fs-body`); colour no longer carries it twice. This is one token away from being reverted if he hates it.

**Also decided, in the same measurement**:
- `--t2`, `--accent`, `--danger`, `--ok`, `--warn` each moved one step towards black in the light theme — the smallest step that clears 4.5:1 on `--canvas`. Hue untouched; these are the same colours a shade deeper.
- **`--border` is deliberately NOT held to 3:1.** It is a hairline between cards and rows and never the only way to identify a control; at 3:1 the whole warm-paper surface reads as a wireframe. The boundary that *is* an affordance got its own token, **`--border-strong`** (3:1 on every surface, both themes), applied to fields, selects and textareas — globally, plus the 11 component rules specific enough to have overridden the global one. `--abord` is exempt for the same reason as `--border`.
- **Placeholders stay on `--t3`.** At `--t2` a placeholder reads as a filled-in value, which is the worse failure. A field whose only label is its placeholder is a defect to fix per field, not by darkening every placeholder in the app.
- **Focus** is now one global `:focus-visible` ring in `--accent`, with the editor sheet excluded (a permanent outline around the surface you are typing on is noise; the caret is the indicator). Before this, the entire app had two focus rules, both on surfaces nobody but a developer opens.
- **Touch targets** are keyed on `@media (pointer: coarse)`, not on viewport width — the device this actually broke on is an iPad in landscape, 1024px wide and entirely touch-driven. `min-height`/`min-width` rather than `height`, because a minimum beats a component's fixed `width` by property rather than by specificity, so 40-odd files did not have to be edited. Inline links (WCAG 2.5.8 exempts them), checkboxes and radios are excluded.

**Consequence**: the contract is enforced, not remembered — `e2e/12-a11y.spec.ts` fails the smoke suite if any pair regresses, and asserts on four screens that no icon-only control lacks an accessible name. The suite went 37 → 42. The blog's server-rendered surfaces were **not** covered at the time — they carried their own `:root` and stayed on the old values. Since closed: the server surfaces read the generated `DesignTokens` and this ADR's `--t3` contract reached them on 01.08.2026 (ADR-090, T-101).

### ADR-075 — The icon inventory is generated from the call sites, not maintained (T-080)

**Context** (31.07.2026): T-080 wanted `aria-label` plus tooltip on icon-only controls, and a `/dev/icons` page. The sweep itself was mechanical — all 58 icon-only controls already had a `title`, none had an `aria-label`, and a `title` alone is announced inconsistently by screen readers and not at all on touch.

**Decision**: the page's data comes from `tools/generate-icon-usage.mjs`, which reads every `<app-icon>` call site and the accessible name of the control it sits in, rather than from a hand-kept list. A hand-kept inventory answers "which icon means what here" only until the next commit; this one is wrong only if nobody re-runs it, and `npm run icons:generate` regenerates both it and the icon data together.

**What it caught immediately, and what it got wrong first**: the first run reported six meanings drawn with two icons each — Connect, Save, Disconnect and others. All six were false. A busy button swaps its icon for `arrow-clockwise` with `class="spin"`, and the analyser was reading the spinner as if it meant what the button means. Teaching it that a spinner is a state, not a meaning, dropped `arrow-clockwise` from 11 meanings to 3 and emptied the duplicate list entirely: **the app is in fact consistent here.** The remaining overloaded glyphs are `x` (12 labels), `trash` (5) and `plus` (5) — the universal actions that legitimately repeat.

**Consequence**: `/dev/icons` and `/dev/styleguide` are the first **lazy** routes in the app (`loadComponent`). They carry reference data no product screen needs, and the initial bundle is already over budget (T-092). One string was fixed on the way through: the shared modal's close button was the last hardcoded English label in the app's chrome, and it appears in every modal.

### ADR-076 — Every route is lazy, and the build budgets became a measurement (T-092, T-051)

**Context** (31.07.2026): `ng build` had warned on two budgets for long enough that the warnings were scenery — initial bundle 1.87 MB against a 1 MB budget, `editor.component.css` 27 kB against 20 kB. The backlog row said the fix was to make the threshold a decision rather than to raise it whenever it broke.

**What the measurement showed**: the app imported all thirteen page components eagerly in `app.routes.ts`, so **TipTap, ProseMirror and KaTeX were downloaded in full before `/drafts` — the landing screen — could paint**, on an app whose entire hosting is one Raspberry Pi behind a tunnel.

**Decision**: every route becomes `loadComponent`, with `withPreloading(PreloadAllModules)` in `app.config.ts`. The initial bundle went **1.87 MB → 531 kB raw, 410 kB → 127 kB transferred**; the editor's 996 kB moved into its own chunk. Preloading is what makes the split free rather than a trade: the chunks are fetched in the background once the first screen has rendered, so opening the editor still finds it in cache. Nothing else changed — same components, same guards, and the smoke suite stayed green through it.

Only then were the budgets set, against the new measurement rather than against the old failure: **initial 650 kB warning / 800 kB error** (531 kB today, so roughly 20% of headroom, and re-importing a page eagerly would trip the error rather than add a line of scenery), **anyComponentStyle 30 kB / 36 kB** (27.6 kB today — `editor.component.css` is the app's largest by a wide margin, and splitting it is separate work, not something to force with a budget). `ng build` is now **warning-free for the first time**.

**On T-051, decided in the same session**: the German layout pass got a **pseudo-locale rather than a real German dictionary** — it inflates every string ~30% and glues a real compound onto its longest word, marked with `⟦ ⟧`. A translation would have to be maintained; this measures the thing the task is actually about, which is layout under long words. It found three defects on its first run, all of the same family and none visible in English or Russian: **the page header could not shrink** (`flex: none` + `nowrap`), so every screen using it scrolled sideways and clipped its last button — the editor by 770px; **the `/drafts` column headers could not ellipsize**, because `text-overflow` does not apply to a flex container, so LANGUAGES printed over FOLDER; and a toolbar group caption could widen its group and push the next group off the row. The rule that came out of it is in `docs/DESIGN.md`: a label shrinks and ellipses, it never widens its container, and it keeps its `title` so the full text is one hover away.

### ADR-077 — Phase 12: Bluesky first, and a cross-posted post is written, not derived (Q-13, Q-14 answered)

**Context** (01.08.2026): Phase 12 (publishing targets, T-083…T-091) has been blocked on three questions since ADR-070. Marty answered two.

**Q-13 — which network first: Bluesky.** It is the only candidate that needs neither app review nor payment (X is pay-per-use since 06.02.2026 and Cedar Clerk almost always posts *with* a link, the expensive kind; Instagram needs a Business account plus 2–4 weeks of review; Threads needs Tech Provider Verification per scope). That makes it the right polygon for the abstraction: the connector can be built and thrown away without anyone else's approval standing in the way.

**Q-14 — what a cross-post is: a standalone post with a manual per-target override**, not a teaser plus a link. The author writes the Bluesky text themselves; an empty override falls back to an automatic teaser so publishing never blocks on writing a second version.

The reason this is the more expensive answer and still the right one: a teaser-and-link is an advertisement for the blog, and ADR-021 already decided that every destination is co-equal — a network that only ever receives "read this elsewhere" is not a destination, it is a billboard. It also decides the shape of T-087: that row is now **per-target text stored on the draft plus a target tab in the editor**, not merely a set of truncation rules.

Q-15 has to be answered before Instagram or Threads, not before this connector. Q-1 (audience) also stays open and no longer blocks the phase, since the network choice it was meant to inform has been made on other grounds.

**Consequence — the build order is unchanged and matters**: T-083 (what a publish target *is*), T-084 (`IPublishTarget` + the entity + encrypted per-tenant credentials), then **T-085, the Telegram refactor, before any Bluesky code exists**. ADR-070's argument holds: an abstraction extracted after the second connector is written is an abstraction shaped to the first one. T-085 changes no behaviour, which is exactly what the Phase 10 smoke suite is there to prove.

### ADR-078 — What a publish target is, and what it is not (T-083)

**Context** (01.08.2026): Phase 12's first row. Before `IPublishTarget` can be written, three things need deciding: what a publish target *is*, what it is obliged to be able to do, and what happens to everything it cannot do. Today there is exactly one publishing path — `PostEndpoints.PublishAsync`, 137 lines that load a draft, check channel ownership, compress media to Telegram's URL-fetch limit, render through `CedarToTelegramBlocksRenderer`, append signature/cross-link/hashtags, send, and then write `Draft.LastTelegramChatId`/`LastTelegramMessageId`/`LastTelegramUsername` plus a `ChannelPost` row. Every one of those steps is shaped to Telegram, including where the result is stored.

**A publish target is a (tenant, network, remote account) triple that owns credentials and can turn a rendered document into a durable remote object it can name afterwards.** The three parts each earn their place: *tenant*, because credentials are per-account and never shared (the Telegram bot is the one exception in the product and it is a bot identity, not the user's); *network*, because capabilities and rendering follow from it; *remote account*, because one owner may hold two Bluesky handles or five Telegram channels, and "which one" is not a property of the network.

**The blog is deliberately NOT a publish target.** It has no credentials, no remote account, exactly one destination per draft, and its publish action is a flag on a row this server already owns (`Draft.IsBlogPublished`). Modelling it as a target would mean an implementation whose credential is empty, whose remote id is its own primary key, and whose "send" is a local `UPDATE` — uniformity bought by making the abstraction describe something it does not describe. The blog is a first-class destination (ADR-021) and stays its own path.

**What a target must be able to do** — the whole obligation, kept deliberately small:
1. **Name its network** (`telegram`, `bluesky`), because that is what selects a renderer and a capability set.
2. **Declare its capabilities** as data, not behaviour — character ceiling, how many media it takes, which formatting survives, whether alt text exists, whether threading exists. Data because T-086 has to show the author a limit *before* the send, and behaviour cannot be displayed in an editor.
3. **Publish a prepared payload and return a receipt** — a remote id, and a public URL when the network has one (Telegram channels without a `@username` do not, which is why the URL is optional and why ADR-065 already stopped treating its absence as "never published").

**What a target must NOT be asked to do**, each because a plausible-looking extension would leak somebody's model into everyone's: it does not fetch statistics (a `ChannelStatSnapshot` equivalent does not exist for most networks and Telegram's own comes from the bot, not from a publish path); it does not delete or edit (nothing in the product offers it today, and inventing `UnpublishAsync` now would be designing for Telegram's `deleteMessage` and hoping); and it does not run its own connect/OAuth flow (Telegram's is a bot-membership discovery, Bluesky's is a handle plus an app password, Meta's is a review-gated OAuth — three shapes with nothing in common, and each already belongs in its own endpoints file).

**What happens to what a target cannot represent** — the rule, which is a continuation of the empty-media-group guard (ADR-019) rather than a new idea: **a target either renders a valid degraded form or refuses with a readable reason. It never sends something silently wrong.** Degradation belongs to the per-network renderer in `CedarClerk.Core`, the same place the Telegram and blog renderers already live, so it stays pure and unit-testable; the capability set is what the editor reads to warn first (T-086); and the author's own per-target text (ADR-077) overrides both when present.

**Where the pieces live**: capabilities and the payload model go in `CedarClerk.Core` (pure, no ASP.NET, testable — the same rule the renderers follow); `IPublishTarget` and its implementations go in `CedarClerk.Server/Publishing/`, matching `Translation/ITranslationProvider` and `Ai/IAiEditProvider`, because publishing needs an HTTP client, configuration and the database.

**Consequence and the order that follows from it**: T-084 builds the entity, the interface and the credential storage. **T-085 then moves Telegram onto it before any Bluesky code exists** — ADR-070's rule, and the reason it matters is visible above: three of `PublishAsync`'s steps write Telegram-shaped columns, so an abstraction extracted after a second connector would have been shaped around them. Telegram's `Channel` rows are *projected* into `PublishTarget` in T-085 rather than replaced by it: `ChannelPost`, `ChannelStatSnapshot` and `BotKnownChat` all key off `Channel`, and it remains the Telegram-specific detail table behind a general row.

### ADR-079 — Bluesky ships: the capability matrix, the author's own text, and a session per publish (T-086/T-087/T-089)

**Context** (01.08.2026): with the abstraction in place (ADR-078) and Telegram moved onto it (T-085), the three rows that make a second network possible were built in one pass.

**T-086 — the capability matrix is data, and the check runs before the send.** `PublishCapabilities` describes what a network takes; `PublishValidator` (Core, pure, 9 tests) answers what it will do to a given document. It returns **codes plus numbers, never sentences** — Core has no dictionaries and this app has two languages, so the wording belongs to the client. Issues are split into *blocking* (the network would refuse) and not (it accepts and quietly drops or flattens something), because those are two different things to tell an author and one of them is not a reason to stop.

**T-087 — a cross-post is written, not derived, and the writing is stored per (draft, network, language).** `DraftTargetText`, keyed by *network* rather than by target row: an author writes one Bluesky version of a post, not one per connected handle. An empty text **deletes the row** instead of storing a blank — a blank would read as an intentional empty post to every later reader of that table. Absent means "derive one", which is what keeps publishing from blocking on writing a second version.

**T-089 — Bluesky, with a session per publish.** Credentials are a handle plus an **app password**, encrypted by `PublishTargetSecrets`, and every publish opens a fresh session from them rather than storing and refreshing a JWT. The reason is failure-shaped: AT Protocol refresh tokens rotate on every use, so a rotated token that fails to save locks the account out, while an app password is revocable from Bluesky's own settings — that revocability is what makes holding one defensible at all. The connect flow verifies the credentials by opening a session **before** storing them, and the row is keyed by **DID, not handle**: a handle can be renamed and the account stays the same.

`BlueskyPostBuilder` (Core, 10 tests) builds the fallback teaser and the link facet. Two things there are impossible to notice afterwards and are pinned by tests: **facet offsets are UTF-8 byte indices, not character indices** — on a Cyrillic post every character is two bytes, so a character-based offset produces a link that silently covers the wrong words — and truncation runs on grapheme boundaries, so a family emoji is not cut into a different one.

**Consequence**: `/api/posts/publish-target` is a separate endpoint from `/export` rather than an optional field on it. Folding two different target resolutions into one endpoint is exactly how `chatId` came to mean three things.

### ADR-080 — The publish request that never came back (found 01.08.2026)

**Context**: publishing a post with a 15MB audio and a 15MB video returned Cloudflare's 502 to the browser. The logs answer what happened, and it is not what the error suggests: the request arrived, the draft loaded, and then **nothing** — no exception (the global handler logs those), no error, and the same process kept running its Quartz jobs on schedule. The server did not fail. It did not finish.

**Why**: publishing is synchronous inside one HTTP request, and the slow part is not ours. Telegram downloads every media URL **from our origin** while `SendRichMessage` blocks — 30MB over a home connection behind a tunnel — after we have already spent time compressing 20MB JPEGs into Telegram-safe derivatives. The proxy in front of the origin gives up long before that finishes, and the author is told "bad gateway" about a publish that may well still be in flight.

**What was done now, and what it is not**: T-086's validator warns about it before the send (`slow-media`, non-blocking, fired on total media bytes). That is honest — every file is *within* Telegram's limits, so nothing here is a size violation and a blocking check would be wrong — but a warning is not a fix.

**The fix is T-090** (`PublishJob`: retry, partial failures, idempotency), already scoped in Phase 12: publishing becomes a job the client polls, so the answer stops depending on a proxy's patience. It is the next row in this phase and this incident is the argument for its priority, not a new task.

### ADR-081 — Publishing became a queue, and the interesting part is what it refuses to retry (T-090)

**Context** (01.08.2026): ADR-080 recorded why a heavy post returned a proxy's 502 — publishing was one HTTP request that stayed open while Telegram downloaded 30MB of media from this server. T-090 was already scoped for partial failures across several networks; the timeout made it the next row rather than a later one.

**Decision**: a publication is a durable row (`PublishJob`), one per destination, queued by `POST /api/publish/jobs` and answered immediately. The client polls `GET /api/publish/jobs`; `PublishJobRunner` does the work, kicked in-process for immediacy and swept by a Quartz job every 15 seconds as the backstop.

**A table, not `AiJobService`'s dictionary.** The existing in-memory job service (ADR-059) is the right shape for an AI call: losing one to a restart costs a retry. A publish lost to a restart is a post that may or may not exist on someone's channel, and durability is what makes "did this go out?" answerable at all.

**One job per destination**, because a post that reaches Telegram and fails on Bluesky is a partial success, and one row per target is what lets it be reported as one rather than as a single verdict over both.

**What it will not do, which is the part that matters:**
- **A job left `Running` by a restart is never retried.** The request had already left; whether the network accepted it is unknowable from here, and retrying is how one post becomes two. It becomes `Unknown` with "check the destination before publishing again" — a status a person can act on, and the only honest one.
- **A refusal is permanent.** Only 502/503/504 are retried (three attempts, 10s then 1m) — those are failures that could not have posted. Retrying a rejected document would produce the same answer more slowly.
- **The claim is a status transition.** Pending → Running is conditional, so the in-process kick and the sweeper cannot both send the same job.

ADR-065's overwrite guard moved with the flow rather than being dropped: the queue endpoint still refuses to re-send over a live post without the fingerprint that was previewed, now per destination, and Bluesky records its own revision so the guard has a baseline there too.

**Consequence**: `/api/posts/export` still exists and still works — the scheduled-post job publishes through the same `PublishAsync` — but the editor no longer uses it. Six tests cover the runner, and the two that earn their place are the ones asserting that three sweeps produce one post and that an abandoned job produces none.

### ADR-082 — "Wrong type of the web page content" meant the post was too big for Telegram (01.08.2026)

**Context**: with the queue in place (ADR-081), publishing the design doc stopped timing out and started reporting what Telegram actually says: `Bad Request: wrong type of the web page content (code 400)`. `.claude/rules/telegram-bot.md` already records that this string means at least three different things; this adds a fourth, and it is the one nobody would guess from the wording.

**What was measured, not assumed** — every candidate was tested against the live Bot API with the real URLs:
- The 15MB audio the post carries: **sends fine**. The 15MB video: fine. Every YouTube thumbnail the renderer generates: fine.
- All 105 referenced files return real media content types over the public URL, all exist on disk, none is a 404 falling through to the SPA's `index.html`.
- A 20MB JPEG *without* a Telegram-safe derivative does fail — but with a different message (`failed to get HTTP URL content`), and no such file is referenced by this post.

**The answer came from our own check.** Running `PublishValidator` (T-086) against the real document: **44,474 characters against Telegram's 32,768 limit, and 105 media items against a limit of 10.** The document is a game design document; it is not a Telegram post and cannot become one. Telegram's error names neither fact.

**Two defects this exposed, both ours:**

1. **A refusal was retried three times.** `TelegramPublishTarget` mapped *every* `ApiRequestException` to HTTP 502, and the queue reads 502 as "could not have posted, try again". So a document Telegram had already judged was sent again twice. Telegram's own code is now what travels: 400/401/403/404 are verdicts and are final, 429 is a rate limit and is the one 4xx worth repeating, everything else stays 502.

2. **The pre-send check was advisory.** T-086 shipped hours earlier and flags exactly this document as blocking — but only in the export window, where it can be scrolled past. The queue now enforces it: a blocking issue is the network's own verdict known in advance, and queueing anyway just delays the same answer by three attempts and two minutes. `POST /api/publish/jobs` answers 422 with the issue list.

**What is not being done about it**: nothing that would make a 44k-character, 105-image document into a Telegram post. Splitting a document into a thread is real work with real decisions behind it (where to cut, how numbering reads, what happens to a table that spans a cut) and belongs to whoever wants that feature, not to a bug fix. The blog already holds documents this size, and the cross-link exists to point Telegram at them.

### ADR-083 — A long document becomes a thread, and the author decides where it breaks (T-106)

**Context** (01.08.2026): ADR-082 established that the design doc — 44,474 characters and 105 media against limits of 32,768 and ~10 — is not a Telegram post and cannot become one. Publishing refuses it honestly. T-106 is the other half: letting it go out as several messages.

**Decision: splitting is offered, never applied.** The switch is off by default, appears only when the post actually does not fit, and shows the parts before anything is sent — number, what each one opens with, its size and its media count. Turning one post into eight messages is a loud act in someone's channel, and the difference between a tool and a liability is whether the author saw it coming.

**Where the cuts land** (`TelegramThreadSplitter`, Core, 9 tests):
- **At a heading whenever one is near.** A message that ends mid-section reads like a transmission error; one that ends where a section ends reads like a chapter. So a part is closed at the next heading once it is 60% full, rather than filled to the brim and cut at an arbitrary character. This is the rule that turns "eight slices" into "eight sections", and it is why the preview is worth reading.
- **A block is never split.** A table, a code block, a list or a media group crosses no boundary.
- **Both limits count.** A hundred images will cut a thread long before its text does.
- A single block larger than the whole budget still ships as its own part: refusing there would leave a document that cannot be published and no explanation, and the network's own refusal is the better answer.

**What each message carries**: the part's own blocks, plus an `N/M` **footer**. A footer, not a heading — the first message should open with the post, not with its own bookkeeping, while a reader arriving mid-thread still learns there is more. The signature, the blog cross-link and the hashtags go on the **last part only**: repeated eight times they stop reading as a signature.

**How it hangs together**: each part replies to the previous one, so Telegram renders a thread rather than eight loose posts, and **only the first part notifies** — eight notifications for one publication is how a channel loses subscribers.

**One job per part** (extending ADR-081), and this is the decision that pays for itself: a thread that fails on part four must be resumable at part four, because retrying the whole publication would send parts one to three a second time and a channel cannot un-see them. A part runs only after its predecessor has succeeded; if an earlier part failed, the later ones are held back with "an earlier part did not go out" rather than leaving a channel with parts 1 and 3 of a document.

**A race this exposed, in code shipped hours earlier**: `Kick` is fire-and-forget, and inside a sweep it competed with the sweep's own loop — part 3 could be decided while part 2 was still running. The sweep now runs sequentially and does not kick successors; the kick exists only for immediacy, and the sweep is the deterministic path.

**Not done, deliberately**: a manual cut marker in the editor. It is the honest control for "break here" and it is a TipTap node, an authoring affordance and a rendering rule — a feature, not a detail of this one. The preview plus headings covers the case that exists today.

### ADR-084 — A reader's access travels in the link, and the cookie now proves something (T-064/T-023)

**Context** (01.08.2026): a friend of Marty's opened a private post in Telegram's in-app browser, filled in the registration form, then opened the same post in Chrome — and was asked to register again. That was T-064. Reading the code for it turned up T-023 in the same place: the access cookie's value was the string `"1"`. It proved nothing. Anyone who knew a draft's id could write `cedar_access_<id>=1` and read a private post.

Both are the same mistake seen from two sides — the grant lived nowhere but in one browser, and it was not a grant at all.

**Decision**: the cookie carries a **signed** value (DataProtection, the key ring T-074 already put under `CEDAR_DATA_DIR`), and a successful registration mints a **per-reader token** that comes back in the redirect: the reader lands on `/slug?access=…`, which is a link they can send themselves. Per registration rather than per post, which is what makes it revocable without locking out everyone else who registered.

**What this costs, stated rather than hidden**: cookies issued before today stop working. A reader who is already through the gate meets it again once, and passes it again. Keeping the old value working would have meant keeping the forgery open, and a private post whose lock can be picked by typing a cookie is not private.

**What was not built**: the owner-facing revoke button. `IsRevoked` exists and the read path honours it, so revoking is a database update away, but a control for it belongs with the submissions list and its own confirmation — a small feature, not a footnote to this fix.

The test that matters is the incident itself: one browser fills in the form, a second browser that has never seen the post opens the link and reads it, and a third with neither link nor cookie still meets the gate.

### ADR-085 — The landing page is server-rendered and reads its prices from the code (T-009)

**Context** (01.08.2026): `cedarclerk.mooexe.dev/` sent everyone to the login form. A stranger arriving at the product had no way to learn what it was.

**Decision: server-rendered HTML at `/`, not an Angular route.** This is the one page whose job is to be found and read by someone who has never heard of the product, and making them download a 531 kB application bundle to read a headline is the wrong trade. The blog already proves the pattern in this codebase. It is **middleware, not a mapped endpoint**, so a request carrying an Identity cookie falls straight through to the SPA — an author who types the address wants their drafts, and an endpoint would have to know where `index.html` lives and hand it back itself.

**Every number comes from the code that enforces it** — `PlanLimitations` for channels and storage, `Consts.Plans` for prices, `PlanLimitations.AiDailyLimit` for the AI quota. A hand-written price table is wrong the first time a limit moves, and a pricing page that lies is worse than no pricing page. The section says so out loud, which is also a small argument for trusting the rest.

**Colours come from the app's own stylesheet** through the generated `DesignTokens` (T-101), and the four card marks are real Phosphor paths from the icon set the app draws with — inlined, because a landing page that waits on a request to draw its own bullet points flickers.

**The screenshot is real.** It is generated by the audit harness from a seeded post written to be worth reading, captured on the blog page rather than in the editor: the editor's chrome carries an account email, and a marketing screenshot with `e2e-admin@local.test` in the corner is worse than none.

**Language follows `Accept-Language`**, defaulting to Russian — the product's own default, and its author's.

**A regression this shipped with, caught by the smoke suite within the hour**: the first version matched `/` on *every* host, so the blog's own index — its homepage — was quietly replaced by the marketing page. The blog host is excluded by name now, and a test asserts it. This is exactly the class of mistake that made Phase 10 build the suite.

**Not built**: an editor screenshot (its chrome is account-specific), testimonials (there are none), and a feature list longer than four items. The page says what the product does, what it costs and who makes it, and stops.

### ADR-086 — A thread part has its own character budget, far below the message limit (01.08.2026)

**Context**: the first real threaded publish of the design doc (ADR-083) produced a first message of 6,412 characters, and Telegram's client collapsed it behind a "Show more" button. The splitter's character budget was `MaxPostChars = 32,768` — the most a message *can* carry — so in practice every cut in a media-heavy document came from the 10-media limit and the character rule never fired at all. "The most Telegram accepts" and "the most a subscriber will read as one message" are two different numbers, and the splitter was using the wrong one.

**Decision: `PublishCapabilities` gains `ThreadPartCharacters`, and the splitter budgets against it** (falling back to `MaxCharacters` where a network does not set one). Telegram sets it to `Consts.Telegram.ThreadPartChars = 3,000` — chosen empirically from this incident: a 1,787-character part rendered fully, a 6,412-character one collapsed, so the threshold sits somewhere between and 3,000 leaves margin under it while still beating the old behaviour by an order of magnitude. The value is a named constant precisely so the next @testingandfun session can tune it in one place.

**What does not change**: `MaxCharacters` keeps meaning "what the network refuses" — validation (T-086) and the single-message path still use it. A single unsplit message may still exceed the comfortable size; that is the author declining to split, which ADR-083 made their call.

### ADR-087 — Telegram media URLs carry a per-send cache-buster (01.08.2026)

**Context**: the same threaded publish failed on part 3 with `wrong type of the web page content` — while every one of that part's ten images served `200 image/*` over the public URL. This is the negative-cache failure `.claude/rules/telegram-bot.md` documented on 16.07.2026: Telegram caches a *failed* fetch per URL and keeps refusing that exact URL after the origin recovers. The morning's failed whole-document attempts (ADR-082's 3×-retry, 104 media each) had poisoned some of the URLs; the afternoon's thread then died on the first poisoned one it met. The 16.07 note concluded a permanent cache-buster was "not warranted for one transient incident" — this is the second incident, and threads raise the stakes: one poisoned URL now holds back every later part of a publication.

**Decision: every media URL sent to Telegram gets a `?v=<per-send stamp>` appended** (`TelegramPublishTarget`, at the block-mapping boundary — the stored document, the blog and the `.cedar` export never see it). Each send is a URL Telegram has never fetched, so a cached failure cannot outlive the incident that caused it, and a retry after a fixed origin actually retries.

**Cost, accepted**: Telegram's fetch now always misses Cloudflare's cache and hits the Pi. Publishes are a handful of requests a few times a week against media Cloudflare still caches for every reader; the origin can carry the author's own publishes.

**Superseded**: the 16.07 "don't add a cache-buster" conclusion in `telegram-bot.md` — updated to point here.

### ADR-088 — Telegram gets media as uploaded bytes, not as URLs to fetch (01.08.2026)

**Context**: the evening's re-run of the threaded design doc (v0.9.33, with ADR-087's cache-buster live) reproduced the same failure shape with a new name: parts 1–2 (one media between them) sent, part 3 — the first part with nine images — died with `failed to get HTTP URL content`, parts 4–23 held back. Not flood control: Telegram's anti-flood answers 429 with `retry_after`, which the queue already retries. This is Telegram's *fetcher* failing to download nine files at once — and ADR-087 is complicit: the `?v=` stamp makes every fetch miss Cloudflare's cache and go straight to the Pi, whose residential upload cannot serve ~10–15MB inside the fetcher's patience. The morning's "wrong type of the web page content" was the same storm wearing its cached aftermath.

**Decision: media that lives in this server's own media directory is uploaded to Telegram as multipart bytes** (`InputFileStream`), not referenced by URL. The URL round-trip — Kestrel → tunnel → Cloudflare → Telegram's fetcher, with its timeout, its concurrency and its negative cache — existed only because the send *started* as "give Telegram a link". The files sit on the same disk as the process; handing Telegram the bytes removes the whole failure class: nothing to fetch, nothing to time out, nothing to cache-poison. Upload limits are also simply better (photos 10MB vs ~5 by URL, video/audio 50MB), and the app's own `TelegramSafeImageBytes` derivatives already sit under them.

**External media keeps the URL path** — YouTube thumbnails are the current case: tiny files on Google's CDN, exactly what URL fetch is good at. They also keep ADR-087's per-send stamp, which now applies *only* to URL-delivered media (that ADR is narrowed, not repealed: its diagnosis of Telegram's negative cache stands, and the stamp is still the defence for anything Telegram fetches itself).

**An escape hatch, not a setting**: `Cedar:Telegram:MediaDelivery` = `upload` (default) / `url` in server config flips the whole target back to URL delivery — one line in the systemd drop-in if upload misbehaves in the field, no redeploy. It is deliberately NOT an author-facing option: "which bytes should Telegram receive" has one correct answer, and a setting whose right value is always the default is UI debt.

**Resolution rule**: a media URL whose path contains `/media/` and whose trailing filename exists in the data dir's `media/` folder is uploaded; anything else stays a URL. Existence on disk is the test — a foreign URL that merely contains `/media/` falls through to URL delivery.

### ADR-089 — Upload goes through a storage chat, because SendRichMessage is JSON-only (01.08.2026)

**Context**: ADR-088's multipart upload met `can't parse InputRichBlock: media not found` on its first real send. Reflection over Telegram.Bot 22.10.2 shows why: `SendRichMessageRequest` derives from `RequestBase` — a JSON-only request — while `SendPhoto`/`SendMediaGroup` derive from the multipart-capable `FileRequestBase`. An `InputFileStream` inside Blocks serialises to an `attach://…` reference whose bytes never leave the machine. The Bot API also offers no standalone upload call (`UploadStickerFile` is sticker-scoped, as in the real API).

**Decision: pre-upload each local file once through a method that CAN carry bytes, then send Blocks by `file_id`.** The file goes out via `SendPhoto`/`SendVideo`/`SendAudio` to a **storage chat — the owner's own private chat with the bot** (`User.TelegramUserId`), silently, and the buffer message is deleted the moment its `file_id` is captured. `file_id` is bot-scoped and reusable across chats, so the real send is pure JSON — which `SendRichMessage` accepts.

**The `file_id` is cached on the Asset row** — `TelegramFileId` (a column the initial schema carried but no code ever wrote) plus new `TelegramFileIdSourcePath` naming which file (original vs. compressed derivative) the id was minted for, so a changed derivative re-uploads instead of serving stale bytes. A 23-part thread uploads each file once, and a retry — the queue's whole reason to exist — re-sends JSON only.

**Fallbacks, in order**: no linked Telegram account, or a failed upload (e.g. the owner never opened the bot chat, so the bot cannot message them) → that file falls back to ADR-087's stamped URL, logged. `Cedar:Telegram:MediaDelivery=url` still flips the whole target back.

**Accepted costs**: the owner's bot chat briefly hosts a silent, self-deleting message per new file; photos pass through Telegram's own photo re-encode (which channel display applies anyway); ADR-088's `InputFileStream`-in-Blocks path is dead code until the library grows a multipart `SendRichMessage`, at which point this ADR is the one to revisit.

### ADR-090 — Server-rendered surfaces read the app's stylesheet through generated tokens (T-101, 01.08.2026)

**Context**: ADR-071 principle 6 called the blog "inside the design system, not adjacent to it", yet `BlogEndpoints.cs` carried its own copies of the palette and the single-file HTML export (`DraftEndpoints.StaticExportHtml`) a third — which is exactly why ADR-074's contrast pass fixed the app and left the public surfaces a shade behind, on the pre-AA values. The blog half landed in the 01.08 night pass without an ADR of its own; this one records the whole mechanism.

**Decision**: one source — `cedarclerk-web/src/styles.scss`. `npm run tokens:generate` (`tools/generate-design-tokens.mjs`, the ADR-075 generated-not-maintained pattern) parses the `:root` blocks and writes `CedarClerk.Core/DesignTokens.generated.cs`; `BlogEndpoints`, `LandingEndpoints` and `DraftEndpoints.StaticExportHtml` inline `DesignTokens.Declarations()` into their `<style>` blocks. Inlined per page rather than served as a `/tokens.css`, deliberately: the export must stay self-contained in one file, and the blog saves a request on a Pi behind a tunnel. `DesignTokenDriftTests` fails the build if the generated copy and the stylesheet part ways.

**With it, ADR-074's `--t3` contract reaches the public surfaces**: the 15 blog declarations and 2 export declarations that used `--t3` as a text colour moved to `--t2`; what stays on `--t3` is decoration — the spoiler background and a hover border — which is what the token is for now. The colour literals that remain in `BlogEndpoints` are there by name and by reason (a generated avatar colour, the code block's own dark scheme, white on an accent fill — see the T-101 comment in the shell template): a theme token would go dark behind each of them and become unreadable.

**Not done with it, recorded rather than implied**: ADR-071 principle 4 (serif in the blog post body, as narrowed by ADR-073) is still unimplemented — `--font-serif`/`--fs-read`/`--lh-read` are exported but unused — and `e2e/12-a11y.spec.ts` still covers no blog surface. Both are visible-design/coverage calls for Marty, not mechanical sweeps.

### ADR-091 — The cache-buster stamps our own media URLs only (04.08.2026)

**Context**: the first publish after the disk-full recovery — a text post with one YouTube embed, no local media at all — failed with `failed to get HTTP URL content`. Verified by hand: `img.youtube.com/vi/<id>/hqdefault.jpg` answers `200 image/jpeg`, and the same URL with ADR-087's `?v=<stamp>` appended answers **404** — Google's thumbnail host refuses unknown query strings rather than ignoring them, unlike the CDN behaviour the stamp silently assumed. So the stamp, built to bust Telegram's negative cache of *our* origin, was breaking the one media class that still legitimately travels by URL.

**Decision: `TelegramPublishTarget` stamps only URLs that point into this server's own `/media/`** (the `TryLocalMediaFileName` test ADR-088 already uses for upload eligibility). External URLs go to Telegram byte-for-byte as rendered. The stamp's whole diagnosis (ADR-087) was about our origin behind Cloudflare — a fetch of a foreign CDN was never the thing being defended, and a foreign host's query-string behaviour is not ours to assume. Negative-cache poisoning of an external URL, should it ever happen, is out of our hands either way — the URL has no variant we are entitled to mint.

**Sequence note**: ADR-087 stamped everything, ADR-088 narrowed it to URL-delivered media, this narrows it to URL-delivered media *we serve* — each step shrinking the stamp toward the failure it was actually built for. With ADR-089's file_id path healthy, a stamped URL now occurs only as the per-file fallback when pre-upload is impossible.

### ADR-092 — Кошелёк кредитов: платные сети оплачивает автор, предоплаченными кредитами (04.08.2026)

**Context**: Марти решил строить X-коннектор (T-001 → Phase 12), а X с 06.02.2026 — pay-per-use: ~$0.015 за пост, ~$0.20 за пост со ссылкой (Cedar Clerk почти всегда постит со ссылкой на блог), и при shared-app модели платит владелец приложения — за посты всех тенантов. Перекладывать расход надо на автора; Марти выбрал предоплаченные кредиты (04.08.2026, три ответа: универсальный кошелёк / наценка ~2× / в планы ничего не включено).

**Decision: один универсальный кошелёк кредитов Cedar Clerk**, не счётчик «постов в X». Кредит — внутренняя валюта для всего, что стоит внешних денег: сейчас X-пост (1 кредит = 1 пост = $0.40 при себестоимости ~$0.20), позже другие платные сети и перерасход AI-квоты. Пакеты: **10 = $4, 50 = $18, 100 = $30** (Stars: 200/900/1500 ⭐ по калибровке 1⭐≈$0.02). Планы Pro/Pro Plus кредитов не включают — покупка строго отдельная, бонусы можно добавить потом, не ломая модель.

**Механика — леджер, не поле-баланс**: `CreditEntry` (OwnerId, Delta ±, Reason, Ref, CreatedAt), баланс = SUM. Плюсовые строки пишет покупка (Stripe one-time Checkout / Stars invoice — те же флоу, что планы, с дедупликацией по `Payment.ExternalId`), минусовые — успешная публикация. **Списание только за успешный пост**, идемпотентно по (Reason, Ref=PublishJob) — ретрай очереди (T-090) не списывает дважды. Недостаток баланса — читаемый отказ в окне экспорта до отправки, рядом с предупреждениями матрицы возможностей (T-086).

**Не сделано этим ADR**: PayPal-покупка пакетов (добавится по образцу, когда дойдут руки), возврат кредитов при удалении поста (пост в X уже оплачен — возврата нет), и сам X-коннектор — он получит собственный ADR при постройке (OAuth 2.0 PKCE с ротацией refresh token, подсчёт символов с t.co=23, медиа байтами).

### ADR-093 — X-коннектор: OAuth 2.0 PKCE, «сохранить до использования», текст+ссылка в v1 (05.08.2026)

**Context**: T-110. Кошелёк (ADR-092) и `XPostBuilder` готовы; сам коннектор — третья реализация `IPublishTarget`. X API v2: постинг требует user context (OAuth 2.0 Authorization Code + PKCE, scope'ы `tweet.read tweet.write users.read offline.access`); app-only Bearer постить не может. Конфиг-ключи: `Cedar:X:ClientId` / `Cedar:X:ClientSecret` (drop-in на Pi, gitignored локально — как все секреты).

**Ротация refresh token — центральный риск**: X выдаёт новый refresh token при каждом обновлении и инвалидирует старый. Для Bluesky ADR-079 ушёл от хранения токенов вообще (сессия с app-пароля на каждую публикацию) — у X такого пути нет. Правило здесь: **новый refresh token сохраняется в БД ДО первого использования нового access token**; упавший сейв — публикация не отправляется. Потерянный токен = «переподключите X» (та же деградация, что `TryUnprotect`→null из T-084), а не тихо мёртвый таргет.

**v1 постит текст + ссылку, без медиа и без тредов.** Пост в X по ADR-077 — самостоятельный короткий пост (override автора или тизер), ссылка на блог ведёт к полному документу с медиа; загрузка картинок байтами (до 4) и цепочка reply — отдельные строки бэклога, не блокирующие первый работающий пост.

**Валидатор научился сетям-тизерам** (`PublishCapabilities.DerivesShortPost`): для сети, которая сама выводит короткий пост, `too-long`/`too-many-media` — информация («будет тизер»), не блокировка. Это чинит и латентный баг Bluesky: очередь 422-ила любой документ длиннее 300 графем, хотя билдер гарантированно строит влезающий пост. Найден при постройке X, не в проде — Bluesky-путь ещё не был live-verified.

**Списание кредита — после успеха, якорь — id созданного поста** (уточнение ADR-092, где якорем назван PublishJob: id поста ещё точнее — каждый реально созданный пост стоит кредит, ретрай очереди после неуспеха создаёт новый пост и честно платит за него). Недостаток баланса — отказ **до** отправки (402, невоспроизводимый для очереди — ретраи не жгутся).

**Callback**: `GET /api/targets/x/callback` (ровно тот URI, что вбит в портал). State+PKCE verifier живут в памяти процесса 10 минут — одна нода, перезапуск роняет только незавершённые подключения.

### ADR-094 — Микроблог-треды: документ целиком в X и Bluesky цепочкой reply (05.08.2026)

**Context**: запрос Марти после первого живого X-поста. ADR-077 дал коротким сетям тизер/override — анонс со ссылкой. Тред — второй, явно включаемый режим: документ уходит в сеть целиком, частями ≤ лимита, каждая часть — reply на предыдущую. Инфраструктура тредов уже есть у Telegram (T-106: один job на часть, порядок через очередь, ReplyToRemoteId) — переиспользуется как есть.

**Решения**:
- **Тред режет текст документа, а не override.** Смысл треда — весь пост; override остаётся текстом одиночного тизера. Резка по абзацам (`CedarPlainText.Paragraphs`), переполненный абзац — по предложениям, затем по словам; счёт — родной для сети (`XPostBuilder.WeightedLength` / графемы Bluesky). Общий `MicroThreadSplitter` в Core, сеть — параметр.
- **Нумерация «N/M» в конце каждой части** (бюджет зарезервирован), **ссылка на блог — в последней части**. Часть из одной части тредом не является — нумерация и цепочка не появляются.
- **Один и тот же план у очереди и у таргета**: `/jobs` считает число частей тем же `MicroThreadSplitter`, таргет пересчитывает его же из документа (принцип T-106 — одинаковые вход и правила дают одинаковые части, синхронизировать нечего).
- **Bluesky reply требует uri+cid родителя и корня** — `RemoteId` bluesky-джоба становится `uri|cid` (публичный URL по-прежнему строится из uri); `ThreadPartRef` получает `RootRemoteId`, который заполняет runner. X reply — просто `in_reply_to_tweet_id`.
- **Тред в X стоит N кредитов** — по кредиту за каждую реально созданную часть (прямое следствие ADR-092/093: якорь списания — id поста). Баланс проверяется на старте части i как «хватит ли на оставшиеся Count−i», чтобы тред не обрывался посередине из-за денег; стоимость показана в модалке до отправки.

### ADR-095 — Подключения живут только в Настройках → Интеграции (07.08.2026)

**Context**: запрос Марти. Панель «Интеграции» существует с I12, но знает лишь три вещи: связан ли Telegram-аккаунт, жив ли бот, и сколько каналов подключено — со ссылкой «управлять в редакторе». Всё реальное подключение росло в окне экспорта: подключение Telegram-канала (N4/FI2.9 — «момент, когда нужен аккаунт, — это момент публикации»), логин Bluesky по app-паролю (T-089), OAuth-кнопка X (T-110). За три коннектора правило N4 перестало работать: окно экспорта наполовину стало окном настройки аккаунтов, а панель, которая по названию отвечает за интеграции, устарела и не показывала ни Bluesky, ни X.

**Decision: подключение аккаунта — это настройка, а не шаг публикации.** Настройки → Интеграции становятся единственным местом, где аккаунт подключается и отключается: Telegram-аккаунт, бот, Telegram-каналы (список известных чатов, ручной ввод @name/id, отключение), Bluesky (handle + app-пароль), X (OAuth), и список запланированных сетей. Окно экспорта только **выбирает** из уже подключённого и на пустом месте показывает ссылку «Подключить →» в Настройки, а не форму.

**Почему N4 отменяется, а не уточняется**: правило родилось, когда сеть была одна и «подключить» значило «вставить id канала». С тремя разными флоу (обнаружение членства бота / app-пароль / редирект на x.com и обратно) окно публикации перестало быть местом, откуда можно уйти на сторонний сайт и вернуться. OAuth-редирект — это и есть аргумент: страница уходит целиком, черновик остаётся позади, а возвращаться в модалку неоткуда.

**Следствие**: `GET /api/targets/x/callback` возвращает браузер на `/settings?tab=account&x=connected` (было `/?x=connected`, и ни один экран этот параметр не читал — подключение выглядело как «ничего не произошло»). Ошибка — `?x=error` там же.

### ADR-096 — Окно экспорта: версия → куда → параметры сети (07.08.2026)

**Context**: запрос Марти — «меню Экспорт неинтуитивное». Окно выросло из одной сети в четыре, и каждая новая приносила свою колонку со своей кнопкой публикации: Blog и Telegram уходили общей кнопкой Publish (B5), а Bluesky и X — собственными кнопками внутри своих секций. Язык выбирался чекбоксами внутри секции Telegram, хотя это свойство поста, а не Telegram. Итог: две модели публикации в одном окне и непонятно, что сделает большая кнопка внизу.

**Decision: окно читается сверху вниз как три вопроса — какую версию, куда, с какими параметрами.**
1. **Версия** — выбор языков наверху, один на всё окно. Telegram/Bluesky/X отправляют по сообщению на каждый отмеченный язык; блог публикует все существующие версии сразу (у страницы свой переключатель языка) — и говорит об этом строкой, а не молчанием.
2. **Куда** — строка карточек-назначений с чекбоксом и статусом. Неподключённая сеть не исчезает и не притворяется доступной: карточка неактивна и ведёт в Настройки (ADR-095).
3. **Параметры** — панель на каждое отмеченное назначение, свёрнутая для неотмеченных.

**Одна кнопка публикации на всё окно.** Собственные кнопки Bluesky и X убраны: чек-лист публикации (T-090) уже умеет показывать шаг на сеть и язык, и это единственное место, где параллельная отправка в четыре сети читается честно. `canPublishAll` требует хотя бы одно назначение и выполнимость каждого отмеченного (Telegram — выбранный канал, X/Bluesky — подключённый аккаунт).

**Режим короткой сети — переключатель из двух, а не галочка.** Для X и Bluesky выбор «анонс со ссылкой на блог» (ADR-077) против «весь пост тредом» (ADR-094) — это две разные публикации, а не опция одной; галочка «разбить на тред» рядом с полем текста читалась как «а текст-то тогда зачем». Сегментированный переключатель показывает ровно параметры выбранного режима: в режиме ссылки — поле текста со счётчиком лимита сети, в режиме треда — число частей (и стоимость в кредитах для X, ADR-092), а поле текста скрыто, потому что тред его не использует.

**Текст короткого поста — на язык.** Поле хранилось одно и писало override для «текущего языка редактора»; при выборе двух версий это молча отправляло один и тот же текст в обе. Теперь панель держит карту язык→текст с мини-табами, появляющимися только когда отмечено больше одной версии.

**Что осталось на месте**: сжатие фото, расписание и предпросмотр тредов Telegram — параметры своей сети и живут в её панели; приглашения и водяной знак переехали внутрь панели блога (они описывают приватную страницу блога, а не публикацию как таковую); файловые экспорты (.cedar/.zip/список файлов) — отдельная панель внизу, потому что это единственная часть окна, которая ничего никуда не публикует.

### ADR-097 — Просмотры блога по странам и языку читателя: дневной роллап, а не лог визитов (08.08.2026)

**Context**: запрос Марти — «статистика просмотров по странам (по языкам) на странице статистики». До сих пор просмотр был одним инкрементом `Draft.ViewCount` без единого измерения: ни страны, ни языка, ни времени внутри дня. Ответить на «кто меня читает» из этого нельзя ни при каком запросе — данных просто нет.

**Decision: новая таблица `BlogViewGeoDaily` — одна строка на (владелец, UTC-день, страна, язык), счётчик внутри.** Не лог визитов: страница задаёт единственный вопрос «сколько», поэтому строка на визит не купила бы ничего, кроме следа за читателем. Апсерт руками (у EF нет `INSERT … ON CONFLICT`): сначала инкремент, вставка только если корзины ещё нет, а гонку двух первых просмотров дня ловит уникальный индекс — проигравший инкрементит строку победителя, а не теряет просмотр.

**Откуда берутся измерения**: страна — заголовок `CF-IPCountry` от Cloudflare (туннель — единственный вход в приложение, см. `.claude/rules/production-environment.md`), язык — первичный subtag из `Accept-Language`. Оба нормализуются в `CedarClerk.Core.ReaderGeo` (чистые функции → юнит-тесты): всё, что не похоже на код, падает в одну честную корзину `??` — «неизвестно» это реальная доля аудитории, а не пропущенная строка.

**Язык читателя, а не язык показанной версии.** `Accept-Language` отвечает на вопрос, ради которого разбивка и заводится — «на какой язык имеет смысл переводить». Язык отданной страницы отвечал бы на другой («читают ли мой перевод») и был бы смещён: у поста без перевода выбора нет, и вся аудитория записалась бы в основной язык.

**Разбивка только у блога.** Bot API не отдаёт географию по каналу — у вкладки Telegram сюда положить нечего, поэтому блок живёт только на вкладке «Блог» и молчит на остальных.

**Считается за период, а не накопительно.** Карточки выше — running total (снапшоты), разбивка — сумма за выбранный диапазон: вопрос «кто читал меня в этом месяце», а не «сколько у меня читателей всего».

**История начинается со дня выкатки** — как у `DraftStatSnapshot` и по той же причине: `ViewCount` это итог без измерений внутри, восстанавливать разбивку не из чего. Пустой блок говорит об этом текстом, а не показывает ноль.

**Что не сделано намеренно**: `DraftId` в строке нет — это умножило бы число строк на число постов ради разбивки на пост, которую никто не просил. Города/регионы тоже нет: Cloudflare отдаёт их только на платных планах, а страна и так покрывает вопрос.

### ADR-098 — Telegram: канал выбирается на язык, а не на публикацию (09.08.2026)

**Context**: запрос Марти — заведён второй канал, англоязычная копия основного. Окно экспорта умело отправлять несколько версий поста (ADR-096, шаг «Версия»), но канал был один на всё окно: RU и EN уходили в один и тот же чат. Отправить перевод в свой канал можно было только двумя заходами — опубликовать RU, вернуться, переключить канал и язык, опубликовать EN.

**Decision: назначение Telegram — это пара (язык, канал), а не канал.** Панель Telegram показывает по строке выбора на каждую отмеченную версию; при одной версии строка ровно одна и выглядит как раньше. `canPublishAll` требует канал для **каждой** отмеченной версии — «RU выбран, EN нет» это неполный запрос, а не запрос с умолчанием.

**Почему не язык на канале (поле `Channel.ContentLanguage` в Настройках)**: это выглядело более «правильной» моделью, но отвечает на другой вопрос — «на каком языке этот канал», — а публикация спрашивает «куда уходит эта версия». Один канал может принимать обе версии (общий канал, разные дни), и модель «язык принадлежит каналу» это запрещает без всякой причины. Соответствие живёт там, где принимается решение — в окне экспорта.

**Соответствие запоминается в браузере (`localStorage`, ключ `cedar.tgChannelByLang`), а не в базе.** Это предпочтение автора, а не свойство поста: черновик, отправленный в канал X, не обязан предлагать канал X следующему черновику по причине истории, — но один и тот же человек за одним и тем же столом почти всегда шлёт EN в EN-канал. Ошибка запомненного значения ничего не ломает: канал, которого больше нет в списке подключённых, просто не подставляется.

**Следствия**: ссылка на опубликованный пост строится по каналу **того языка**, который её произвёл (раньше — по единственному `chatId`); `update-preview` (ADR-065) спрашивает про канал каждой версии отдельно, поэтому «перезапись живого поста» теперь считается по правильному чату — раньше вопрос про EN задавался про RU-канал.

### ADR-099 — Расписание — свойство публикации, а не Telegram (09.08.2026)

**Context**: запрос Марти. Блок «Запланировать отправку» жил внутри панели Telegram (ADR-096 оставил его там как «параметр своей сети»), и это было правдой ровно до того момента, пока сетей не стало четыре. Отложить пост в X или Bluesky было нельзя вообще, а галочка «разбить на тред» рядом с полем времени молча игнорировалась: запланированная отправка шла через `PostEndpoints.PublishAsync` без всякой поддержки тредов.

**Decision: расписание — отдельный шаг окна («Когда»), общий для всех отмеченных сетей.** Заданное время меняет смысл единственной кнопки Publish для каждого сетевого назначения сразу, а не для одного.

**`ScheduledPost` адресуется таргетом, а не чатом.** Строка получает `TargetId` (`PublishTarget`, ADR-078) и `Network`; `ChatId` остаётся заполненным для Telegram — по нему работает проверка владения и подпись канала в Менеджере постов, — но перестаёт быть идентичностью назначения. Строки, написанные до этой колонки, публикуются старым путём: `TargetId == null` это и есть признак «legacy», а не ошибка.

**Отправка по времени идёт через `PublishToTargetAsync`, а не через очередь `PublishJob`.** Очередь (ADR-081) существует, чтобы HTTP-запрос не ждал сеть; у Quartz-джоба этой проблемы нет — он никого не заставляет ждать. Прямой вызов сохраняет честную семантику статуса строки: `Sent`/`Failed` с настоящим текстом ошибки, а не «передано в очередь» с неизвестным исходом. Цена — у запланированной отправки нет ретраев очереди.

**Тредов в расписании нет, и окно об этом говорит.** Это не потеря: их и не было — переключатель треда просто не доезжал до запланированной отправки. Теперь при заданном времени он выключен с пояснением, а не притворяется работающим.

**Блог не планируется.** Блог намеренно не является publish-таргетом (`docs/ARCHITECTURE.md`), планировать нечего; при заданном времени отмеченный блог публикуется сразу, и шаг «Когда» пишет об этом строкой.

### ADR-100 — Язык короткого поста выбирается на сеть (09.08.2026)

**Context**: запрос Марти. ADR-096 сделал выбор версий общим для окна, и X с Bluesky отправляли **каждую** отмеченную версию: две галочки в шаге «Версия» — два твита с одного аккаунта, два кредита (ADR-092). Для Telegram это правильно (у версий разные каналы, ADR-098), для одного аккаунта в X — почти никогда.

**Decision: у панели X и Bluesky свой набор языков — подмножество отмеченных в шаге «Версия».** По умолчанию совпадает с ним целиком (поведение не меняется молча), ряд пилюль появляется только когда версий больше одной. Снятая всюду галочка запрещена — назначение отмечено, значит что-то уходит.

**Почему подмножество, а не один язык**: у аккаунта может быть двуязычная аудитория, и «оба» это законный выбор. Ограничение до одного языка сэкономило бы клик и запретило бы реальный сценарий.

**Следствие**: стоимость публикации в X (`xCreditCost`) считается по языкам **этой сети**, а не по отмеченным версиям окна — до сих пор она завышалась ровно в той же ситуации, в которой сеть отправляла лишнее.

## Модуль для инди-геймдева (ADR-101…107, 10.08.2026)

Семь решений одной сессии, принятые по брифу Марти `_Documents_/CedarClerk/Gamedev_Focused_Rework.md`. Кода в этой сессии нет намеренно: правило CLAUDE.md — сначала решение, потом код, — и разворот такого размера стоит записать до того, как первая миграция сделает часть выбора необратимой. Обзор модуля целиком — `docs/INDIEDEV.md`.

### ADR-101 — Инди-геймдев это модуль внутри одной кодовой базы, а не форк (10.08.2026)

**Context**: бриф Марти разворачивает продукт из «пиши длиннопост → публикуй в соцсети» в тулкит инди-разработчика игр, где пост — лишь один из типов документа. Соблазн развести это на два продукта реален: половина новых сущностей (задачи, ассеты, спринты) не имеет никакого отношения к публикации. Бриф отвечает на это прямо: «one codebase, one installation, the base lives as "role" or "module", not as fork».

**Decision: одна кодовая база, один процесс, одна база данных; модуль — это набор эндпоинтов и экранов за флагом, а не отдельный контекст.**
- Бэкенд: `CedarClerk.Server/Modules/IndieDev/` со своими `XxxEndpoints`-классами по существующей конвенции, регистрируемыми в `Program.cs` за флагом `Cedar:Modules:IndieDev`.
- Фронт: `cedarclerk-web/src/app/modules/indiedev/` с ленивыми маршрутами — механика уже стоит, все маршруты перешли на `loadComponent` в T-092/ADR-076, и цена выключенного модуля равна нулю: его чанки просто не грузятся.
- Флаг доезжает до клиента в ответе `/api/me`; guard прячет пункты меню, а не только страницы.

**Схема БД общая, и это не компромисс.** Второй `DbContext` дал бы отдельный набор миграций поверх того же файла SQLite — то есть два независимых `Database.Migrate()` на старте против одной базы, чего `.claude/rules/ef-migrations.md` не переживёт. Важнее другое: `Draft` обязан принадлежать проекту, а задача — ссылаться на документ. Граница между контекстами прошла бы ровно по связям, ради которых модуль и заводится.

**Что флаг НЕ делает**: он не превращает существующие экраны в другие. Редактор, `/drafts`, `/posts`, `/settings` при включённом модуле работают как работали — модуль добавляет, а не подменяет. Это условие обратимости: если бизнес-модель не сработает (бриф прямо допускает удаление ветки `indiedev_module`), выключение флага возвращает сегодняшнее приложение целиком.

### ADR-102 — Тип документа — колонка на `Draft`, а не новая сущность (10.08.2026)

**Context**: бриф вводит документы разных типов — пост, гейм-дизайн, сценарий, чейнджлог, — и «пост» становится одним из многих. Прямолинейный ход — новая сущность `Document`, куда `Draft` со временем переезжает.

**Decision: `Draft.DocumentType` (string, default `post`) и `Draft.ProjectId` (`Guid?`).** Существующие строки становятся `post` без миграции данных: значение по умолчанию и есть правда о них. `ProjectId` — plain scalar без FK и nav-свойства, ровно как `Draft.FolderId` (`Entities.cs:275`) и по той же записанной причине.

**Прецедент уже есть в коде**: `IsTemplate` (`Entities.cs:285`) — шаблон поста был заведён именно так, флагом на `Draft`, и формулировка Марти в `docs/BACKLOG.md` про «самую дешёвую честную форму» относилась именно к этому выбору. Тип документа — обобщение того же хода, а не новый приём.

**Почему не отдельная сущность**: `Draft` — это не «пост», это «TipTap-документ с автосейвом, историей версий, переводами, тегами и папкой». Всё перечисленное нужно гейм-дизайн-документу дословно. Новая сущность означала бы копию `DraftTranslation`, `DraftRevision`, автосейва с гардами ADR-065/066 и оптимистической конкурентности — то есть повторение самой дорогой и самой обожжённой части кодовой базы (инцидент 29.07 — `T-060`).

**Цена принимается явно**: `Draft` растёт примерно до 35 полей, и публикационные поля (`BlogSlug`, `IsBlogPublished`, `WatermarkText`, `LastTelegram*` и прочие) не значат ничего для документа типа `design`. Это тех-долг «вынести публикационные поля в `DraftPublishing`», заведённый строкой в `docs/BACKLOG.md`, а не повод строить вторую иерархию сейчас: сегодня нули в неиспользуемых колонках стоят дешевле, чем join на каждом чтении документа.

**Дополнено при реализации (10.08.2026, T-120):**

**Не всякий тип документа публикуется.** `DocumentTypes.IsPublishable` — чистая функция в Core: `post` и `changelog` да, `design`/`script`/`plot`/`note` нет. Гейм-дизайн-документ и сюжетный план — рабочий материал, и отправка такого в канал не бывает намеренной; честный ответ на запрос — отказ, а не пост. Проверка стоит на общем пути `PostEndpoints.PublishToTargetAsync(Draft, …)`, то есть действует сразу для всех сетей, а не для той, о которой вспомнили. Поведение существующего контента не меняется: всё, что написано до типов, — это `post`.

**Дефолт колонки обязан быть объявлен в модели, а не в инициализаторе свойства.** EF при генерации миграции **не читает** `= DocumentTypes.Post` в объявлении поля и сгенерировал `defaultValue: ""` — то есть `ALTER TABLE ADD COLUMN` заполнил бы все существующие черновики пустой строкой. Пустой тип не проходит ни `IsKnown`, ни `IsPublishable`, значит **каждый уже написанный пост отказался бы публиковаться на первом же деплое**. Лечится `builder.Entity<Draft>().Property(d => d.DocumentType).HasDefaultValue(DocumentTypes.Post)` в `OnModelCreating` — в модели, а не правкой руками в файле миграции, чтобы повторная генерация не потеряла дефолт молча. Первая миграция была удалена и сгенерирована заново; тест `A_null_type_still_publishes` держит границу.

### ADR-103 — «В проекте минимум один документ» — правило UI, а не констрейнт БД (10.08.2026)

**Context**: бриф требует, чтобы `Project` обязательно включал хотя бы один документ.

**Decision: правило живёт в создании проекта, а не в схеме.** Создание проекта одной транзакцией создаёт и стартовый документ по шаблону выбранного типа проекта; удаление последнего документа проекта запрещается на эндпоинте с внятной ошибкой.

**Почему не констрейнт**: обязательность в схеме нарушается на первом же `INSERT` — проект не может ссылаться на документ, которого ещё нет, а документ не может ссылаться на проект, которого ещё нет. Разрешается это либо отложенными констрейнтами (SQLite их так не умеет), либо nullable-полем «первый документ», которое ничего не гарантирует. То есть констрейнт всё равно оказался бы декоративным — лучше сразу держать правило там, где оно действительно исполняется.

**Следствие для UI**: создание проекта — это диалог выбора, а не поле «имя». Пустой проект в системе не существует ни секунды.

**Сужено, а затем восстановлено — в течение одного дня.** Утром 10.08 таксономия типов проекта была убрана как выдуманная: ни в брифе, ни у Марти таких категорий не было, а классификация, о которой нечего сказать, — это лишнее понятие вместо решения. Вечером того же дня Марти принёс дизайн-хендофф (`docs/design_handoff_indiedev_core_loop/`), в котором диалог создания — именно выбор **типа проекта**, с четырьмя конкретными типами и стартовым документом у каждого:

| Тип | Что это | Стартовый документ |
|---|---|---|
| `fullgame` | Весь тулкит: документы, спринты, индекс ассетов, пресс-кит | GDD (master) → `design` |
| `jam` | Дедлайн прежде всего: один спринт, план, чек-лист сдачи | Jam plan → `design` |
| `prototype` | Вопрос, на который надо ответить. Заметки и задачи, без церемоний | Hypothesis note → `note` |
| `released` | После релиза: патчи, чейнджлоги, пресса | Changelog → `changelog` |

**Это не отмена сужения, а его причина.** Сужение снимало понятие, за которым не было продуктового решения; хендофф это решение принёс. `ProjectTypes` живёт в Core рядом с `DocumentTypes` и отвечает ровно на один вопрос — с какого документа начинается проект. Больше тип проекта не ограничивает ничего: проект `prototype` волен содержать любые типы документов.

**Заголовок стартового документа сервер не придумывает.** «GDD (master)» и «Jam plan» — пользовательский текст, а у сервера нет второго языка (`ErrorMessages` переведён, контент — нет). Тип выводится на сервере как правило, заголовок присылает клиент, у которого обе локали уже есть; без заголовка используется имя проекта.

**Как это выглядит в коде**: `POST /api/projects` принимает `{ name, description, documentType, documentTitle }` и одной `SaveChangesAsync` пишет `Project` и `Draft` с проставленным `ProjectId`. Обратная сторона — удаление: `DELETE /api/projects/{id}` **отвязывает** документы (`ProjectId = null`), а не удаляет их, как это делает `FolderEndpoints` с папками, и по более сильной причине — в проекте лежит собственно написанное, и удаление контейнера не должно быть способом случайно это потерять. Отказ «нельзя удалить последний документ» стоит в двух местах: на пути модуля и в обычном `DELETE /api/drafts/{id}`, потому что правило, которое соблюдает только одна из двух дверей, — не правило.

### ADR-104 — Десктоп: Electron поверх существующего сервера как sidecar (10.08.2026)

**Context**: бриф просит десктопное приложение — прямо названа причина: «Asset management will definitely need some local application». Строка `T-010` висела в бэклоге как Low с формулировкой «на базе существующего кода» и без всякой механики. Выбор сделан Марти 10.08.2026 из четырёх вариантов (Electron+sidecar, Tauri+sidecar, только PWA, нативный Avalonia/MAUI).

**Decision: Electron-оболочка запускает существующий `CedarClerk.Server` как локальный процесс и открывает в окне тот же Angular SPA.** Ни серверный код, ни фронтенд не форкаются. Механика целиком — `docs/DESKTOP.md`.

**Почему не Tauri**: экономит ~140 МБ дистрибутива и заметную долю памяти, но приносит незнакомый Марти стек (Rust) и различия WebView между ОС — а весь смысл решения в том, что оболочка тонкая и её почти не надо разрабатывать. Экономия размера не окупает второй незнакомый инструмент в проекте, который и так тянет .NET + Angular + TipTap.

**Почему не PWA**: не решает задачу, ради которой десктоп заводится. Браузер не даёт индексировать папку Unity-проекта — File System Access API требует пользовательского жеста на каждую папку и не работает в Safari/iPad, то есть Asset Manager остался бы работать только с загруженными файлами.

**Почему не нативный клиент (Avalonia/MAUI)**: редактор — это TipTap, то есть WebView в любом случае, а весь остальной UI пришлось бы написать заново и потом вести в двух экземплярах. Это форк фронтенда под другим именем, чего ADR-101 избегает специально.

**Ключевая экономия**: `CEDAR_DATA_DIR` уже существует и уже управляет расположением SQLite и медиа (systemd-drop-in на Pi, `.claude/rules/production-environment.md`). Десктоп задаёт ту же переменную в `%APPDATA%/CedarClerk` — и по части хранения серверный код не меняется вообще. Одно исключение найдено при написании этого ADR: адрес прослушивания зашит в код (`app.Run(Consts.URLs.Localhost)`, то есть `http://localhost:8080`), а не берётся из конфигурации, поэтому `ASPNETCORE_URLS` им перекрывается. Десктопу нужен свободный порт — значит, ровно одна строка `Program.cs` становится конфигурируемой, с прежним значением по умолчанию. Бот на десктопе выключается сам, потому что без токена `TelegramBotService.IsRunning` уже возвращает false by design; это не удобство, а защита от 409 (`.claude/rules/telegram-bot.md`), которая иначе стреляла бы каждый раз, когда Марти открывает десктоп при живом Pi.

### ADR-105 — Десктоп v1 не синхронизируется с облаком (10.08.2026)

**Context**: как только десктоп держит собственный SQLite, возникает очевидное ожидание — что данные те же, что на `cedarclerk.mooexe.dev`.

**Decision: v1 не синхронизирует. При первом запуске пользователь выбирает режим: локальные данные или подключение к облачному инстансу как клиент.** В облачном режиме десктоп не поднимает свой сервер вовсе и работает как окно браузера с доступом к файловой системе.

**Почему не синк**: двусторонняя синхронизация двух SQLite с офлайн-правками — это разрешение конфликтов на уровне TipTap-документа, то есть либо CRDT, либо «кто последний, тот и прав» с потерей чужих правок. Проект уже проходил через инцидент потери текста (`T-060`, 29.07) и построил вокруг него три гарда (ADR-065/066/067); добавлять к этому нерешённый merge — прямой путь к повторению того же инцидента, но уже без возможности откатить.

**Обещание, которое не даётся, лучше обещания, которое нарушится.** Режим выбирается явно и виден в интерфейсе постоянно, чтобы «я правил на ноутбуке, где мои изменения» не мог случиться молча.

**Что это значит для Asset Manager**: в облачном режиме индексация локальных папок всё равно работает — пути уходят на сервер, файлы никуда не копируются (ADR-107). То есть главная причина существования десктопа не зависит от выбранного режима.

### ADR-106 — Задача — отдельная сущность, а не документ (10.08.2026)

**Context**: бриф просит базовый таск-трекер с полями Name, Status, Priority, Description, Assignee, связанный с остальными документами. ADR-102 только что решил, что типы документов — это колонка на `Draft`; напрашивается сделать задачу восьмым типом документа.

**Decision: `GameTask` — своя сущность с фиксированными колонками.** У задачи есть набор полей, по которым надо фильтровать, сортировать и агрегировать («что в работе», «что просрочено», «сколько осталось в спринте»). В `Draft` это жило бы внутри `CedarJson`, то есть каждый такой вопрос стал бы полным перебором документов с парсингом JSON.

**Граница между ADR-102 и этим решением проста**: если содержимое — свободный текст, а поля вокруг него — метаданные, это `Draft` с типом. Если содержимое — набор полей, а текст лишь одно из них, это своя сущность. `Description` внутри задачи остаётся простым текстом, а не TipTap-документом — задача, требующая форматирования, таблиц и медиа, это на самом деле документ, и его надо создать документом и прилинковать.

**Связи — таблица `TaskLink(TaskId, EntityType, EntityId)`, а не колонка `DraftId`.** Бриф требует, чтобы задача была «somehow linked to other documents», и на практике цеплять придётся не только документы: ассет, другую задачу, сам проект. Колонка на каждый вид связи означает миграцию на каждый новый вид; строковый `EntityType` — нет. Это сознательный отказ от FK ради расширяемости, в том же духе, что и `Draft.FolderId`.

**Спринты (`Sprint`) — отдельная сущность поверх задач, а не поле на задаче.** У спринта есть собственные даты и имя, и задача может пережить несколько спринтов.

### ADR-107 — Asset Manager индексирует пути, а не копирует файлы (10.08.2026)

**Context**: в коде уже есть `Asset` (`Entities.cs:590`) — загруженный файл, лежащий под `CEDAR_DATA_DIR/media`, считающийся в квоту плана (200 МБ на Free) и раздающийся публично через `/media/*`. Ассет игрового проекта — другое животное: он весит гигабайты, живёт в папке Unity-проекта, меняется мимо Cedar Clerk и не должен быть публично доступен никогда.

**Decision: новая сущность `AssetEntry` — метаданные и путь, без копирования байт.** Существующий `Asset` остаётся ровно тем, чем был (медиа поста), и не трогается. Индексация ходит по указанной папке, записывает имя, размер, тип, время изменения и хеш, и на этом останавливается.

**Почему не переиспользовать `Asset`**: он определяется тем, что файл лежит внутри `CEDAR_DATA_DIR` и раздаётся по HTTP. Отвязать его от этого — значит сломать квоту плана, `/media/*` и предзагрузку в Telegram (ADR-088/089) ради сущности с другим жизненным циклом. Две сущности здесь дешевле одной с двумя режимами.

**Это и есть причина, по которой десктоп в MUST, а не в MIGHT.** Веб-версия может показать только то, что в неё загрузили; индексировать `D:\Projects\MyGame\Assets` умеет лишь процесс, запущенный на той же машине. Порядок в `docs/INDIEDEV.md` следует из этого: десктоп-оболочка идёт перед Asset Manager, потому что без неё он вырождается в ту же загрузку файлов, что уже есть.

**Что не решено и решается при реализации**: превью (генерировать и класть куда — рядом с базой, не рядом с исходником), реакция на исчезнувший файл (помечать, а не удалять строку — иначе отключённый внешний диск сотрёт индекс), и объём индекса на реальной папке Unity, который может оказаться в сотнях тысяч строк и потребовать фильтров по расширениям на входе, а не на выходе.

**Реализовано 10.08.2026 (T-122), с четырьмя уточнениями:**

**1. Индексация — вторая, отдельная способность, выключенная по умолчанию.** Эндпоинт заставляет **сервер** обходить **свой** диск по запросу тенанта. На ноутбуке это и есть смысл фичи; на Pi, где один процесс обслуживает все аккаунты, это возможность перечислить `/etc` и прочитать имена файлов. Поэтому мало флага модуля: нужен `Cedar:AssetIndex:Enabled`, который выставляет только десктопная оболочка для своего однопользовательского процесса. Прод его не выставляет и отвечает 403 с внятным текстом; **просмотр уже проиндексированного при этом работает** — строки owner-scoped, а проект, проиндексированный на десктопе, должен открываться и из веба.

**2. Один корень на проект, а не `RootPath` в каждой строке.** Исходный набросок клал корень в `AssetEntry`; при десятках тысяч строк это одна и та же строка, повторённая десятки тысяч раз, а «Сменить папку» в дизайне всё равно заменяет корень целиком. Корень живёт на `Project.AssetRootPath`, в строке — только `RelativePath` с разделителем `/`.

**3. Обход написан руками, а не через `Directory.EnumerateFiles(.., AllDirectories)`.** Тот бросает исключение на первой же папке, которую не может открыть, и бросает всё, что после неё, — одна папка без прав обрывала бы скан целиком. Свой обход пропускает такую папку, считает её и идёт дальше; число непрочитанных показывается, а не проглатывается. Заодно он пропускает по имени `Library/`, `Temp/`, `node_modules/`, `.git/`, `Intermediate/` и прочие кэши движков — в них файлов больше, чем в самом проекте, и ни одного авторского.

**4. Тип файла — догадка по расширению, и интерфейс не притворяется, что это больше.** Открывать каждый файл на папке в сотню тысяч элементов нельзя. Отдельного вида «Музыка» **нет**, хотя в дизайне чип есть: отличить музыкальный трек от эмбиента по расширению невозможно, а чип, набитый угадайкой, хуже отсутствующего. Всё звуковое — один вид `audio`.

**Проверено запуском, а не чтением**: скан реальной папки (41 файл: 26 картинок, 15 текстов, рекурсия, `.exe` и `Library/` пропущены); удаление файла помечает строку и **сохраняет** её; возвращение файла снимает пометку; при выключенном флаге `POST /index` отвечает 403, а список продолжает работать.

**Дополнено 10.08.2026 (T-140/T-141): превью, метаданные и связи.**

**Миниатюры лежат под `CEDAR_DATA_DIR/thumbs/`, а не рядом с исходником.** Индексируемая папка — чужой игровой проект, обычно под контролем версий; запись файлов в неё была бы и неожиданностью, и диффом. Генерируются **по запросу**, а не при скане: скан, который декодирует каждую картинку, идёт минутами ради превью, на которые почти никто не посмотрит. Кэш инвалидируется по `ModifiedAt` файла — заменённый спрайт не показывает предшественника. Отдаются авторизованным owner-scoped эндпоинтом, **не через `/media/*`**: публичный путь — для того, что автор решил опубликовать, а индекс — для того, что лежит у него на диске.

**Метаданные читаются только у новых и изменившихся файлов.** Заголовок читать дёшево, но сто тысяч раз при каждом пересканировании — уже нет. `MetadataForModifiedAt` ставится даже когда заголовок ничего не сказал, иначе такой файл открывался бы заново вечно.

**`.blend` — свой парсер (запрос Марти).** Это главный файл множества игровых проектов и единственный, который не откроет ни одна графическая библиотека. Blender кладёт RGBA-превью в блок `TEST` внутри файла, и `CedarClerk.Core/BlendThumbnail.cs` его достаёт: 12-байтный заголовок, обход блоков, копия пикселей. Читается только первый мегабайт — блок лежит близко к началу, а сцена может весить сотни мегабайт. Строки хранятся снизу вверх (как отдаёт OpenGL), поэтому изображение переворачивается. Сжатый `.blend` (zstd с 3.0, раньше gzip) **отказывается честно**: превью там есть, но тянуть декомпрессор ради миниатюры — не та цена.

**Что считается «превью возможно» — решается по расширению, не по виду.** `image` покрывает и PNG, и Photoshop-документ: первый декодируется, второй нет. Список разрешённых расширений явный, потому что альтернатива — сетка с иконками сломанных картинок там, где декодер спасовал.

**Набор форматов расширен под реальный геймдев (запрос Марти).** Движковые файлы (`.unity`, `.prefab`, `.uasset`, `.tscn`), DCC-исходники (`.blend`, `.ztl`, `.sbsar`, `.aseprite`, `.kra`), проекты DAW (`.rpp`, `.flp`, `.als`, `.bank`), шейдеры и скрипты. Движковые остаются видом `other`: сцена Unity — не картинка и не документ, и записать её в «текст», чтобы куда-то деть, было бы ложью из удобства.

**`EntityLink` вместо `TaskLink` — уточнение ADR-106.** Та строка задумывалась как «задача → что угодно»; как только связывать понадобилось второй паре сущностей, это стали бы две таблицы, делающие одну работу. Связь задачи — это `EntityLink`, одна сторона которого задача. Пара **упорядочивается** (`LinkTargets.Order`) перед записью: без фиксированного порядка A→B и B→A — две строки об одном факте, и никакой уникальный индекс их не различит.

**Связи ставятся руками, и это не срез угла.** Проиндексированный файл лежит вне Cedar Clerk; ни один TipTap-документ не может на него сослаться — картинки редактора это загруженное медиа под `/media/`. Искать нечего, поэтому «используется в» невозможно обнаружить, можно только указать. Подпись это отражает: «Связанные документы», а не «Используется в».

**Проверено запуском (T-140/T-141)**: скан папки с фикстурами — размеры PNG (256×16, 64×32), длительность и частота WAV (2:14 · 48 кГц), превью из `.blend` и `.blend1` (128×96 и 64×64, JPEG сгенерирован), `.fbx` честно без миниатюры, `.exe` и `Library/` пропущены; связь документа с ассетом добавляется, повторное добавление не создаёт вторую строку, удаление возвращает пустой список.

**Что осталось непроверенным**: ориентация превью из **настоящего** `.blend`. Переворот сделан по документированному поведению Blender (строки снизу вверх), но проверен на синтетическом файле — у Марти есть Blender, и один реальный файл это закроет.

### ADR-108 — Десктоп спрашивает «кто ты» у Pi, но данные держит у себя (10.08.2026)

**Context**: запрос Марти после первого запуска десктопа. Он завёл локальную учётку на ту же почту, что и на Pi, и увидел, что дальше будет каша: две учётные записи с одинаковым адресом — разные, и ничто об этом не говорит.

**Decision: источник истины о личности — Pi; данные остаются локальными.** При настроенном `Cedar:Auth:Upstream` вход на десктопе проверяется на `cedarclerk.mooexe.dev`, а локальная строка пользователя заводится (или подхватывается) под удалённой личностью. Регистрация на десктопе при этом **выключается**: аккаунт создаётся на сервере, и создать второй локально нельзя — именно это и порождало кашу.

**Почему не полный облачный режим** (второй режим из ADR-105, где десктоп просто открывает сайт): тогда данные были бы одни, но **индекс ассетов перестал бы работать** — сервер на Pi не видит диск Марти, и `Cedar:AssetIndex:Enabled` там выключен by design (ADR-107). Это выключило бы ровно ту способность, ради которой десктоп и появился. Облачный режим остаётся отдельной, ещё не сделанной опцией; эта — не она.

**Личность привязывается к идентификатору, а не к почте.** `ApplicationUser.RemoteUserId` хранит id с Pi; почта может измениться, id — нет. Пока Pi отдаёт `/api/auth/me` без `id` (сборки до этой), используется почта как запасной ключ — работает уже сегодня и само уточнится, когда Pi обновится.

**Существующая локальная учётка подхватывается, а не дублируется.** При первом удалённом входе, если локально есть строка с той же почтой и без `RemoteUserId`, к ней привязывается удалённая личность вместе со всем, что к ней уже привязано. Иначе первый же вход после этой правки создал бы вторую учётку и сделал бы ровно то, чего Марти просил избежать. Подхват по почте безопасен здесь потому, что upstream-аутентификация включается только на однопользовательской машине; на общем сервере она выключена.

**Честная цена, которую надо назвать вслух: одна личность — не одни данные.** Черновики на Pi и документы на десктопе остаются разными наборами. С общей учёткой ожидание, что это одно и то же, становится **сильнее**, а не слабее, — поэтому интерфейс обязан постоянно говорить, что данные локальные. Без этой надписи решение делает кашу хуже, а не лучше.

**Офлайн**: уже выданная сессия живёт 30 дней (`Consts.AuthCookieLifetime`), так что работать без сети можно. **Новый вход требует Pi** — и говорит об этом отдельным сообщением, отличным от «неверный пароль»: «сервер недоступен» и «не тот пароль» это разные вещи, и путать их — худший вид ошибки входа.

### ADR-109 — Картинки в Bluesky отправляются, ссылка на YouTube едет текстом, X честно говорит «не приму» (10.08.2026)

**Context**: отчёт Марти после теста экспорта — «картинки не отправились, ссылка на YouTube не отправилась». Разбор по коду показал, что это не одна ошибка, а три разных, и худшая из них — не та, что бросается в глаза.

**Что было на самом деле:**

| Что | Как было | Как выглядело со стороны |
|---|---|---|
| Картинки в Bluesky | `Capabilities.MaxMediaItems = 4`, `MaxImageBytes`, `SupportsAltText = true` — но запись `app.bsky.feed.post` содержала только `text`/`facets`/`reply`, а `uploadBlob` не вызывался **никогда** | **Приложение обещало и молча не выполнило.** Предполётная проверка читает `Capabilities`, поэтому четыре картинки проходили как «всё в порядке» |
| Картинки в X | `MaxMediaItems = 0` — заявлено честно, медиа не реализовано (ADR-093, «text+link v1») | Предупреждение было, но звучало как «медиа: 3, а сеть принимает 0» — арифметика там, где нужна фраза |
| YouTube | Узел `youtube` не встречался ни в `CedarPlainText` (текст короткого поста), ни в `PublishValidator` | Видео исчезало **совсем и без единого сигнала** — ни ссылки в тексте, ни предупреждения |

**Decision, по каждой строке отдельно:**

**Bluesky получает картинки по-настоящему.** `uploadBlob` + `embed` типа `app.bsky.embed.images`, до четырёх, в порядке чтения, с alt-текстом (сеть его поддерживает и ждёт). Лимит блоба — 1 МБ, что ниже почти любого реального скриншота, поэтому используется тот же `ImageCompressor`, что и на пути Telegram. **Неудача картинки не рушит публикацию**: пост без картинки стоит несравнимо больше, чем непубликация, — но каждый пропуск пишется в лог. Картинки уходят только с **первой** частью треда: повторять одни и те же четыре снимка в каждой части — не то, как выглядит тред где бы то ни было.

**Ссылка на YouTube едет текстом.** Ни Bluesky, ни X видео не встроят, но ссылку донесут, а ссылка — это всё, что нужно зрителю. `CedarPlainText` теперь отдаёт `youtube`-узел как абзац `«подпись + watch-URL»`; подпись первой, чтобы часть треда читалась фразой, а не голым адресом. Это же чинит тред: раньше видео просто выпадало из середины документа.

**X остаётся без медиа, но говорит об этом словами.** Реализовать выгрузку в X — это отдельный механизм (media/upload с другой схемой авторизации) и отдельные деньги за пост; начинать это молча в рамках отчёта об ошибке неправильно. Заявленный ноль — правда, изменилась формулировка: «медиа: 3 — эта сеть их не принимает вовсе, они не уйдут».

**Общий вывод, который стоит дороже трёх правок**: `PublishCapabilities` — это обещание, которое читает предполётная проверка. Расхождение между ним и реализацией не даёт ни ошибки, ни предупреждения — оно даёт молча потерянный контент. Любая новая возможность должна появляться в `Capabilities` **вместе** с кодом, который её исполняет, а не раньше него.

**Что осталось непроверенным**: живая отправка картинки в Bluesky. Механизм покрыт юнит-тестами на сборку списка изображений и на текст, но `uploadBlob` против настоящего bsky.social требует учётки Марти — проверяется первым же реальным постом.

### ADR-110 — «Куда ушёл пост» читается из очереди публикации, а не из новой таблицы (11.08.2026)

**Context**: Марти опубликовал тред из 25 частей в X и сообщил две вещи — прогресса не было видно, и ссылок на созданные посты он не нашёл нигде. Проверка по продовой базе: все 25 частей `Succeeded`, у каждой записан `PublicUrl`, весь тред ушёл за **17 секунд**. То есть бэкенд отработал полностью, а оба симптома — во фронте.

**Найдено три дефекта, и ни один из них не про публикацию как таковую:**

1. **Прогресс трека не обновлялся вообще.** `awaitJobs` принимает колбэк `onProgress`, который перерисовывает чипы частей на каждом опросе — и телеграмный путь его передаёт, а путь коротких сетей (X, Bluesky) **никогда не передавал**. Чипы рисовались один раз, все «ожидает», и разом переключались в конце. Помощник `reflectJobs` к тому же умел адресовать только строки `tg-<lang>`, так что передать колбэк было и нечем — теперь он адресуется по id шага и годится любой сети.
2. **Счётчик «7/25» был невидим в обеих темах.** `.pr-count` красился в `--alt` — это токен **поверхности**, а не текста: #EFECE4 на #FCFBF8 в светлой, #2F2C23 на #2B2820 в тёмной. Автопроверка контраста этого не поймала, потому что проверяет заданные пары ролей, а не произвольные сочетания в CSS.
3. **Ссылки исчезали.** Тост с результатом живёт **внутри** окна экспорта, окно прогресса стоит поверх него, и тост удалял сам себя через 10 секунд. То есть досмотреть публикацию до конца и закрыть чеклист означало не увидеть ничего. Десяти секунд не хватает, чтобы прочитать ссылку, — их едва хватает, чтобы её заметить.

**Decision: «где лежит опубликованное» читается из `PublishJobs`, а не из новой сущности.** Каждая строка очереди уже хранит `PublicUrl`, который вернула сеть. Заводить рядом таблицу «опубликованные посты» значило бы писать второй раз то, что уже записано, и получить два источника правды, расходящихся при первой же ошибке. Новый `GET /api/publish/published` отдаёт по строке на каждое место, куда версия ушла, и его читает Posts Manager — единственное место, переживающее закрытие редактора.

**Только часть 0.** Публичный адрес треда — его голова; 25 ссылок на один тред это не список постов, а список ответов. `PartCount` едет рядом, чтобы интерфейс мог сказать «тред из 25 сообщений».

**Побеждает новейшая** запись на каждую пару (черновик, сеть, язык, аккаунт): для читателя перепубликация заменяет пост, поэтому пять попыток иначе дали бы пять ссылок на одну и ту же вкладку.

**Успех без публичного адреса в список не попадает** — телеграм-канал без `@username` опубликован, но ссылки предложить не может, и строка с пустым `href` была бы мёртвой кнопкой. Это ровно тот случай, который ADR-065 уже находил трактуемым как «никогда не публиковалось»; здесь он трактуется как «опубликовано, ссылки нет».

**Урок, который дороже трёх правок**: у публикации не было ни одного места, переживающего закрытие модального окна. Прогресс, результат и ссылки жили только в том окне — а окно закрывается. Ценность, созданная действием, обязана иметь адрес, по которому её можно найти назавтра.

### ADR-111 — Состояние спринта выводится из дат, а номер хранится (11.08.2026)

**Context**: T-124, планировщик. ADR-106 уже решил, что спринт — отдельная сущность с собственными датами и именем. При реализации всплыли два вопроса, которых тот ADR не касался.

**Decision 1: у спринта нет колонки «статус» — «текущий / запланирован / завершён» вычисляется из дат.** Хранимый статус расходится с реальностью ровно в ту секунду, когда часы переходят через `EndsAt`, и дальше требует чего-то, что его чинит: фонового задания, проверки при чтении, кнопки «закрыть спринт». Всё это — механика, обслуживающая копию факта, который уже записан в двух датах. Спринт «текущий», если сегодня внутри `[StartsAt, EndsAt]`; если таких несколько — текущим считается начавшийся позже (перекрытия не запрещены: запрет ничего не защищает, а мешает при переносе сроков).

Прямое следствие: **у спринта нет состояния «просрочен».** Просрочены задачи внутри него, и интерфейс говорит именно так — «1 просрочена», — а не красит весь спринт. Это то же правило, что уже действует на доске: красной становится только дата, никогда не карточка и не колонка.

**Decision 2: `Sprint.Number` — порядковый номер внутри проекта, выдаётся при создании и не переиспользуется.** Дизайн показывает чип `S14` на карточке задачи и строку «Sprint 14 — Ferry Terminal» на дашборде, то есть номер и имя — разные вещи: номер отвечает «какой по счёту», имя отвечает «про что он». Альтернатива — вытаскивать число из имени регуляркой — сломается на первом же спринте, названном «Полировка».

Номер не переиспользуется после удаления: дырка в нумерации честнее, чем второй `S7`, означающий другой отрезок времени.

**Decision 3: удаление спринта отвязывает задачи, а не удаляет их.** То же правило, что у удаления проекта: удаление контейнера — не просьба удалить содержимое. Задачи возвращаются в «Без спринта».

**Проверять при реализации нечего, но назвать стоит**: «завершён» здесь означает «отрезок времени кончился», а не «всё сделано». Спринт с незакрытыми задачами всё равно завершается по календарю — и планировщик показывает эти задачи, а не прячет их. Спрятать их значило бы соврать о том, что работа исчезла вместе с датой.

### ADR-112 — Глоссарий проекта — колонка, билд — сущность (11.08.2026)

**Context**: T-125 и T-126, последние два MUST фазы 13. Бриф формулирует их так: «`Glossary` пока остаётся где стоит, но должен работать глобально для постов. Я должен иметь возможность завести локальный глоссарий со скоупом проекта» и «Тегирование билдов и версий. И, соответственно, развитая система тегов».

**Decision 1 (T-125): `GlossaryTerm.ProjectId` — nullable-колонка, `null` = глобальный термин.** Ровно тот же ход, что `Draft.ProjectId` (ADR-102): у термина проекта и глобального термина одинаковая форма — слово, описание, синонимы, картинка, язык, — и различаются они одним вопросом «где он действует». Отдельная сущность означала бы вторую таблицу с теми же девятью колонками и невозможность перенести термин из проекта в общий словарь без перенабора.

**Что видит документ**: глобальные термины **плюс** термины своего проекта. Не «или»: «Unity» глобален, «паром» — про конкретную игру, и статья про эту игру нуждается в обоих. Термин проекта при этом никогда не протекает в документ вне его — иначе «локальный» ничего не значит.

**Порядок при совпадении**: если один и тот же термин определён и глобально, и в проекте, побеждает проектный. Более узкая область действия — более точное определение; ради этого локальный глоссарий и заводят.

**Decision 2 (T-126): билд — своя сущность `Build`, а не тег.** «Развитая система тегов» из брифа — это описание желаемого результата, а не механизма. У версии есть номер, дата выпуска, заметки и состав; плоская строка `Draft.Tags` не хранит ни одного из этих полей и не отвечает на вопрос «что вошло в 0.4.2» иначе как полным перебором с разбором строк. Это та же граница, что провёл ADR-106 для задачи: набор полей — сущность, свободный текст — тег.

**Связь с задачей — колонка `GameTask.BuildId`; связь с документом — `EntityLink`.** Асимметрия намеренная и объясняется вопросами, которые задают: задача выходит **в одном** билде («в каком?»), и по этому полю надо фильтровать и агрегировать — это колонка, как `SprintId`. Документ же относится к билду свободно и не обязательно однозначно: чейнджлог версии, девлог о ней, гейм-дизайн-документ, который она реализует. Заводить ради этого колонку на `Draft` — расширять сущность, у которой уже около тридцати пяти полей и записанный тех-долг на разбиение (ADR-102).

**Чейнджлог порождается как документ, а не как текст.** `POST /api/builds/{id}/changelog` создаёт в проекте настоящий документ типа `changelog` со списком закрытых задач билда — и дальше он живёт обычной жизнью документа: правится, переводится, публикуется, versioned. Отдавать вместо этого строку для копирования значило бы построить генератор, результат которого некуда положить.

**Чего сознательно не делается**: билд не связан с гитом, не читает теги репозитория и не знает о сборках. Это запись о версии, которую ведёт автор, — и притворяться интеграцией с CI, которой нет, было бы хуже, чем честно быть записью.


### ADR-113 — Деплой едет одним архивом с докачкой, а служба останавливается только на переименование каталогов (11.08.2026)

**Context**: `scp -r publish/* host:app/` раз за разом обрывался на последних процентах — `client_loop: send disconnect: Connection reset`, — и всякий раз это происходило **после** остановки службы. То есть каждый сбой связи оставлял продакшен лежать: половина файлов новая, `wwwroot` нет вовсе, `/api/health` отвечает 502. Именно в таком состоянии этот ADR и писался: 50 файлов из 174 в `app/`, служба `inactive`. Повторный запуск скрипта начинал те же 50 МБ с нуля, потому что `scp` не умеет продолжать.

**Decision 1: всё медленное происходит, пока старая версия обслуживает пользователей.** Сборка, упаковка, передача, проверка контрольной суммы и распаковка идут при работающей службе — в отдельный каталог `app.new`, которого никто не читает. Остановка нужна только для двух `mv`. Простой упал с «сколько продлится копирование» (минуты, а при обрыве — до следующего успешного запуска) до примерно секунды, и она измеряется на самом сервере и печатается в отчёте.

**Decision 2: передаётся один tar.gz, а не 174 файла.** Дело не только в скорости (50 МБ сжимаются примерно вдвое, и одна последовательная передача не тратит round-trip на каждый файл). Дело в том, что у одного потока байт есть **позиция**, а у дерева файлов её нет: оборвавшийся `scp -r` не может сказать, докуда он дошёл, а оборвавшаяся передача файла — может.

**Decision 3: докачка своя, потоком в `cat >>`, а не `scp`.** `scp` умеет только «сначала». Скрипт спрашивает `stat -c %s` у серверного файла и досылает хвост локального начиная с этого байта. Проверено на живом сервере: передача, прерванная на 2 МБ из 5, продолжилась и дала совпадение sha256. Отсюда же требование не перепаковывать архив между попытками — gzip пишет в заголовок время, и повторная упаковка того же ввода даёт другие байты, после чего дописанный хвост склеился бы с чужим началом. Поэтому артефакт кэшируется в `%TEMP%` вместе с сигнатурой каталога `publish/` (число файлов, суммарный размер, самая свежая дата), и `-SkipBuild` продолжает **тот же самый** файл.

**Целостность проверяется до того, как что-либо трогается**: sha256 с обеих сторон, наличие `CedarClerk.Server.dll` и `wwwroot/index.html` в распакованном каталоге, совпадение числа файлов. Любая из этих проверок не сошлась — деплой останавливается, и продакшен даже не знал, что что-то происходило. Это прямой ответ на то, чем кончился прошлый сбой: работающая половина сборки хуже, чем невыполненный деплой, потому что выглядит как выполненный.

**Предыдущий релиз остаётся как `app.prev`**, поэтому откат — это те же два переименования, а не повторная сборка и передача: `.\Scripts\deploy.ps1 -Rollback`. Плохую версию он сохраняет как `app.broken`, чтобы было что смотреть.

**Что скрипт удаляет на сервере**: `app.prev` (позапрошлый релиз) и чужие архивы в `staging/`. Каталога `data/` он не касается никогда — база и медиа лежат там, и ни одна операция деплоя не поднимается выше `app*`.

**Урок**: порядок шагов деплоя — это и есть его надёжность. Старый скрипт останавливал службу первым действием из трёх рискованных, и любая ошибка после этого превращалась в аварию. Новый устроен так, что всё, что может не получиться, происходит до остановки, а после неё остаются только операции, которые не умеют идти долго.

### ADR-114 — Прод переехал на DigitalOcean, и вместе с ним переехало не всё (11.08.2026)

**Context**: продакшен два месяца жил на Raspberry Pi 4 дома у Марти. Накопилось три давления сразу: диск (27 ГБ, из них свободно 6 — деплой 10.08 упал на нулевом остатке из-за 13 ГБ логов cloudflared), конец security-поддержки Raspbian Bullseye ≈август 2026 (`T-070`), и то, что публичный SaaS зависел от домашнего электричества и домашнего интернета. Чек-лист переезда был написан 11.08 по фактическому состоянию машины, в тот же день исполнен Марти целиком.

**Decision: дроплет, а не другой Pi и не PaaS.** `cedarclerk-periwinkle`, fra1, Ubuntu 24.04.4 LTS, x86_64, 1 vCPU / 2 ГБ, 48 ГБ диска. Всё, что было на Pi, воспроизведено один в один: те же пути (`~/cedarclerk/app`, `~/cedarclerk/data`), тот же юнит с тем же `ExecStart`, те же drop-in'ы с секретами, тот же Cloudflare-туннель на `127.0.0.1:8080`, тот же один процесс Kestrel на два хоста. Смены платформы приложение не заметило.

**Почему это оказалось копированием, а не портированием**: сервер публикуется **framework-dependent, без RID** — переносимый IL. Именно поэтому armhf → x86_64 не потребовал ни пересборки под другую архитектуру, ни правки кода. Это свойство существовало не ради переезда, а ради того, что Pi ничего не собирает, — и окупилось в день, когда понадобилось.

**Decision: `raspberrypi.local` больше не адрес прода.** `Scripts/deploy.ps1` по умолчанию целится в `martycow@deploy.mooexe.dev`; в правилах, `ARCHITECTURE.md`, `CLAUDE.md`, `AGENTS.md`, `DESKTOP.md` и скриптах Pi заменён на сервер/дроплет. **`CHANGELOG.md` и этот файл не правились**: там записано, как было тогда, и переписывать историю под сегодняшнюю машину значило бы потерять, почему решения принимались именно такими.

**Decision (и это самая честная часть): бэкапы стали хуже, и это записано, а не замазано.** На Pi был ночной `sqlite3 .backup` + rsync на microSD, 14 датированных копий. На дроплете нет ни crontab, ни `~/bin` — скрипт не переехал. Вместо него включён платный **еженедельный бэкап дроплета** на стороне DigitalOcean. Это не эквивалент, и разница именно в трёх местах:

1. **Окно потери выросло с суток до недели.** Сбой накануне снимка стоит шести дней постов, медиа и аккаунтов.
2. **Восстановление всё-или-ничего.** Образ возвращает машину целиком; «вернуть вчерашнюю базу, оставив сегодняшний код» физически нечем.
3. **Копия лежит в том же аккаунте, что и оригинал.** Случайный destroy, неоплата или угон логина забирают её вместе с дроплетом. Карточка в другом устройстве этим свойством не обладала — и оно потеряно, а не приобретено.

Ни один из трёх пунктов не делает ситуацию аварийной, и ни один не является причиной откладывать: `sqlite3` на дроплете стоит, ночной cron — это десять строк, выгрузка за пределы аккаунта — `T-071`, поднятый до High. **Пока это не сделано, фраза «данные забэкаплены» верна только в еженедельном, одноаккаунтном, помашинном смысле** — и любая запись о бэкапах обязана говорить, в каком именно.

**Найдено при ревизии, не сделано**: юнит стоит `disabled`. DigitalOcean перезагружает дроплеты для обслуживания хоста, и после ребута сайт не поднимется сам (`T-143`). Чинится одной командой, но она требует пароля sudo, которого у автоматики нет по устройству прав: `NOPASSWD` намеренно ограничен ровно `systemctl start|stop|restart cedarclerk`.

**Что переезд закрыл сам**: `T-070` (миграция ОС Pi ради arm64 и нового .NET) — новый хост уже 64-битная поддерживаемая Ubuntu; дефицит диска (45 ГБ свободно вместо 6); и координацию с Freenove-проектами на той же машине.

### ADR-115 — На проводе всегда UTC с `Z`, на экране всегда тихоокеанское время (11.08.2026)

**Context**: сервер переехал на дроплет, где часы стоят в UTC (ADR-114), и Марти попросил: время на сервере пусть будет UTC, а на сайтах — блоге и в приложении — пишется тихоокеанское. Проверка кода показала, что просьба задевает не только формат вывода.

**Найдено при разборе, и это баг, а не стилистика.** В базе всё пишется в UTC — `DateTime.UtcNow` встречается 125 раз, `DateTime.Now` не встречается ни разу, даты файлов в ассет-индексе берутся как `LastWriteTimeUtc`. Но SQLite не хранит `DateTimeKind`, EF читает такие значения как `Unspecified`, а `System.Text.Json` печатает их **без суффикса `Z`** — и браузер по спецификации считает такую строку **местным временем**. То есть приложение показывало UTC-числа под видом местного времени: сегодня это семь часов вперёд. Ровно от этого в двух компонентах жил помощник `utcDate()`, дописывающий `Z` руками, — но покрывал он два места из примерно двадцати.

**Decision 1: инстант чинится на проводе, а не в двадцати вызовах.** `UtcDateTimeConverter` в `ConfigureHttpJsonOptions` печатает любой `DateTime`/`DateTime?` как UTC с `Z`. Это одна точка вместо помощника, о котором надо помнить в каждом новом компоненте; забыть конвертер нельзя, а забыть `utcDate()` — можно, что и произошло восемнадцать раз.

**Decision 2: зона — `America/Los_Angeles`, а не фиксированный UTC−8.** Марти сказал «Pacific Standard Time», но буквальный PST — это зимнее время; с марта по ноябрь Лос-Анджелес живёт по PDT (UTC−7), и фиксированное смещение показывало бы час назад **прямо сегодня**. Просьба означает «моя зона», а не «эта конкретная аббревиатура», поэтому берётся именованная зона с переходами, а подпись следует реальности: PDT летом, PST зимой. Если когда-нибудь понадобится именно фиксированный сдвиг — это одна константа.

**Decision 3: зона названа один раз с каждой стороны.** `Consts.General.DisplayTimeZone` на бэкенде, `DISPLAY_TIME_ZONE` во фронтенде. Конфигом это не делается: конфиг нужен, когда значение различается между установками, а сегодня оно одно — и когда у арендаторов появится своя зона (а с многопользовательским режимом это вопрос времени), менять придётся не значение, а модель: зона станет полем пользователя. Две константы — ровно то место, куда придёт эта правка.

**Decision 4: подпись зоны есть в блоге и нет в приложении.** Блог читают из любой точки мира, и «14:05» без указания зоны там означает разное для разных людей. Приложение — рабочее место автора в одной зоне, и «PDT» у каждой даты в плотном интерфейсе это шум, который ничего не сообщает.

**Что сознательно не меняется:**
- **`pubDate` в RSS остаётся GMT.** RFC 1123 с корректным смещением — машинный формат для агрегаторов, а не текст для человека; «локализовать» его значило бы сломать сортировку у читалок.
- **Группировка постов по месяцам считается в той же зоне, что и заголовок месяца.** Иначе пост от 1 сентября 00:30 UTC (31 августа 17:30 PDT) попал бы в сентябрьскую группу под августовской датой — рассинхрон, который выглядит как потерянный пост.
- **Ввод времени планировщика остаётся в зоне браузера.** Поле `datetime-local` читается как местное время машины и переводится в UTC при отправке. Для Марти в тихоокеанской зоне это то же самое, что и вывод; расхождение появится только с ноутбука в другой зоне. Это отдельная задача (ввод, а не вывод), и делать её наполовину — молча — хуже, чем не делать: рядом с полем уже висит подсказка с временем в других зонах, и она станет врать первой.

### ADR-116 — Десктоп обновляется сам, инсталлер раздаёт наш же сервер, деплой везёт его по флагу (11.08.2026)

**Supersedes** строку «Самообновление — в v1 нет, обновление — переустановка» в таблице рисков `docs/DESKTOP.md` и часть ADR-113 («деплой не касается `data/` никогда» — теперь касается ровно одного её подкаталога, см. ниже).

**Context**: инсталлер собирался только вручную флагом `.\Scripts\build.ps1 -Installer`, лежал в `CedarClerk.Desktop/dist/` на машине Марти и никуда не уезжал. То есть у десктопа не было ни способа доставки, ни способа обновления: любая правка сервера — а сервер едет внутри установки, self-contained — означала «собери, перешли файл, поставь заново вручную». Пока установка одна и своя, это терпимо; как только их станет две, версии разъедутся молча, а рассинхрон оболочки и сервера ловится только диалогом при старте.

**Decision 1: обновление делает `electron-updater`, провайдер `generic`, а не GitHub Releases.** У проекта уже есть публичный HTTPS-origin с собственной раздачей статики; GitHub Releases потребовал бы публичного репозитория (его нет) или токена в клиенте (нельзя). `publish: {provider: generic, url: https://cedarclerk.mooexe.dev/downloads}` — и весь протокол обновления сводится к трём файлам в одной папке: `latest.yml` (манифест с версией и sha512), `CedarClerk-Setup-<версия>.exe` и `.blockmap` к нему. Никакой серверной логики: обновления раздаёт та же `UseStaticFiles`, что и медиа.

**Decision 2: файлы лежат в `data/downloads/`, а не рядом с приложением.** `app/` деплой сносит и пересоздаёт при каждом релизе — инсталлер, положенный туда, исчез бы при первом же обычном деплое, унеся с собой `latest.yml` и оставив установленные копии с манифестом, указывающим в никуда. `data/` переживает деплой по построению (ADR-113). Плата за это — то самое исключение из «деплой не трогает `data/`»: скрипт пишет **ровно** в `data/downloads/` и никуда больше, а содержимое этой папки — единственное в `data/`, что пересоздаётся сборкой, то есть его потеря стоит одного `deploy -Desktop`, а не данных.

**Decision 3: сборка и заливка — по флагу `-Desktop`, а не в каждом деплое.** `electron-builder` — это минуты работы и ~130 МБ поверх обычных ~50 МБ деплоя, по домашнему каналу вверх. Обычный деплой правит сервер и фронт, которые в десктопе всё равно приедут с ближайшей десктопной сборкой; платить за это каждым деплоем незачем. Цена решения названа честно: **версии прода и последнего инсталлера могут разойтись**, и это видно в отчёте деплоя (он печатает, какая версия сейчас в `downloads/`), а не выясняется потом.

**Decision 4: заливка идёт тем же механизмом, что и сам релиз, и `latest.yml` пишется последним.** Тот же `Send-Tail` с докачкой и та же сверка sha256 (ADR-113) — 130 МБ по каналу, который рвётся, иначе не доедут вообще. Порядок обязателен: `.exe` и `.blockmap` заливаются во временный подкаталог, проверяются, переносятся `mv` в `downloads/`, и **только потом** появляется `latest.yml`. Манифест — это единственное, что читают клиенты; пока его нет или он старый, установленные копии видят прошлую версию, а не битую новую. Обратный порядок означал бы окно, в котором `electron-updater` скачивает половину файла и падает на sha512.

**Decision 5: подписи кода нет, и это меняет модель доверия, а не только SmartScreen.** `publisherName` в конфиге не задан, поэтому `electron-updater` пропускает проверку подписи и опирается на sha512 из `latest.yml`, полученный по тому же HTTPS, что и сам файл. Практический смысл: **доверие к обновлению равно доверию к `cedarclerk.mooexe.dev`** — тот, кто может подменить ответ origin'а или DNS, может доставить произвольный exe на машину. При одном пользователе и своём домене это приемлемо; при первом внешнем пользователе desktop-сборки подпись перестаёт быть косметикой (SmartScreen) и становится границей безопасности. Записано здесь, чтобы решение принималось осознанно, а не по факту.

**Decision 6: сервер убивается до установки.** NSIS перезаписывает `resources/server/CedarClerk.Server.exe`, а он в этот момент запущен как дочерний процесс — заблокированный файл сорвал бы установку на середине. Поэтому `stopServer()` вызывается до `quitAndInstall()`, а не полагается на `before-quit`.

**Найдено на первом настоящем обновлении (Марти, 11.08.2026), и это свойство, а не частность: обновление ставит та версия, которую заменяют.** Код, выполняющий установку, — старый; новый начинает действовать только со следующего раза. Практическое следствие: любая правка пути обновления проверяется на цикле «предыдущая версия → эта», и первое обновление после такой правки всё ещё идёт по старому, сломанному пути. Обойти это можно единственным способом — поставить новую версию инсталлятором руками, минуя самообновление. Это же означает, что путь обновления — единственное место в проекте, где ошибка живёт на одну версию дольше, чем её исправление.

Конкретная ошибка была в этом же духе: `taskkill /f` отдаёт убитому процессу код возврата 1, а на `exit` сервера висел обработчик «сервер упал сам», показывающий модальный `showErrorBox`. До появления обновлений это не проявлялось — все остальные остановки происходят после закрытия окна, а обработчик именно это и проверял. Установка обновления останавливает сервер **при живом окне**, посреди последовательности выхода, и модальное окно блокировало главный процесс. Лечится тем, что намеренная остановка сначала снимает обработчик: то, о чём мы попросили сами, не может быть аварией по определению.

**Оболочка говорит по-английски.** Интерфейс приложения переведён, оболочка — нет, и переводить её наполовину хуже, чем не переводить: диалог обновления по-русски рядом с английским «Version mismatch» читается как баг, а не как забота. Решено Марти 11.08.2026, когда первый русский диалог обновления оказался единственным русским текстом в оболочке.

**Что осталось прежним**: `Scripts/build.ps1 -Installer` по-прежнему собирает инсталлер локально и никуда не отправляет — деплой его переиспользует (`-DesktopOnly -Installer`), а не дублирует логику сборки. Версия оболочки по-прежнему синхронизируется с `Consts.CurrentVersion`; новое здесь то, что деплой **отказывается** ехать с разошедшимися версиями, а не молча правит файл в рабочем дереве по дороге.

### ADR-117 — Десктоп стал клиентом облака: одна база, локальный агент только для диска (12.08.2026)

**Supersedes ADR-105** целиком (двух режимов больше нет) и **ADR-108** (upstream-аутентификация была протезом для локальной базы). **Уточняет ADR-107** в части того, кто обходит диск.

**Context**: запрос Марти. ADR-105 оставил десктопу свою базу и явный выбор режима, ADR-108 склеил личность, но не данные — и честно предупредил, что «одна личность — не одни данные» делает путаницу **сильнее**, а не слабее. Через сутки эксплуатации Марти сформулировал ровно это предсказание своими словами: «использую в десктопе одну и ту же почту, но по факту это другой аккаунт». Просьба: всё синхронизируется с облаком, но ассеты никуда не заливать — максимум авто-превью, уезжающие при индексации; на десктопе доступ к настоящим файлам, в браузере только превью с пометкой, что это отпечаток.

**Decision 1: не синхронизировать, а убрать вторую копию.** Окно десктопа грузит `cedarclerk.mooexe.dev`, база одна — облачная. Локальный режим удалён, а не оставлен вторым вариантом.

Это не отказ от осторожности ADR-105, а снятие задачи, которой тот боялся. Двусторонний merge офлайн-правок TipTap — это CRDT либо потеря чужих правок, и проект уже проходил через инцидент потери текста (`T-060`, три гарда ADR-065/066/067 вокруг него). Единственная база означает, что merge'ить нечего: править негде, кроме облака. **Правильный вывод из ADR-105 был не «синхронизация опасна», а «двух копий не должно быть»** — тогда он выбрал второй экземпляр как меньшее зло, потому что asset-индекс требовал локального процесса; теперь локальным остаётся только процесс, а не данные.

**Decision 2: локальный процесс остаётся, но становится агентом файловой системы, а не сервером.** `CedarClerk.Server.exe` с `Cedar:Agent=true` не поднимает ни Identity, ни миграции, ни бота, ни SPA — только `/agent/*`: обход папки, stat одного файла, генерация JPEG-превью.

Он остаётся .NET-процессом, а не переезжает в Node, по одной проверяемой причине: в нём уже лежит парсер превью `.blend` (прямой запрос Марти, `CedarClerk.Core/BlendThumbnail.cs`) и покрытие ImageSharp по TGA/TIFF/QOI/PBM/WEBP. Переписывание этого на JS — недели работы и второй набор форматных багов ради экономии 70 МБ дистрибутива, которые ADR-104 уже согласился платить.

**Decision 3: агент читает диск, страница отправляет.** Записи об ассетах и превью уезжают в облако запросами **страницы**, у которой уже есть cookie-сессия, а не Electron'а. Значит, агенту не нужны никакие учётные данные, а Electron не занимается авторизацией вообще. Побочная выгода важнее экономии: работа становится наблюдаемой и отменяемой обычным UI, а не невидимым фоновым процессом, о котором нельзя спросить, чем он занят.

**Decision 4: способность обходить диск исчезает с хостящегося сервера, а не выключается флагом.** `Cedar:AssetIndex:Enabled` и эндпоинты `POST/GET/DELETE .../assets/index` удалены; вместо них — импорт (`PUT .../assets/source`, `POST .../assets/batch`, `POST .../assets/sweep`).

Это **усиление** границы, которую ADR-107 (уточнение 1) держал флагом. Опасная способность была «сервер перечисляет свой диск по просьбе тенанта»; теперь её код физически существует только в агенте, то есть на проде отсутствует, а не дремлет за конфигом. Приём списка имён от владельца опасной способностью не является — это обычная запись данных. Флаг убран именно потому, что охранять больше нечего: способность решается наличием моста у клиента, а не конфигом сервера.

Открытый канал записи всё же требует потолков, и они названы числами, а не «разумными значениями»: ≤500 строк в батче, ≤200 000 строк на проект, `RelativePath` ≤1024 символов с отказом на `..` и абсолютные префиксы, ≤256 КБ на превью с проверкой magic-байтов JPEG.

**Decision 5: превью генерируются и уезжают все, без лимита для автора — но с потолком у системы.** Это отход от «по запросу, а не при скане» (ADR-107, дополнение T-140), сделанный по прямому выбору Марти после того, как цена была названа: папка с 20 000 картинок — это 20 000 декодирований и ~600 МБ.

Три вещи делают это выполнимым, и без любой из них решение было бы безответственным:
- **Проход возобновляем и идемпотентен.** `GET .../assets/thumbs/pending` возвращает то, у чего `ThumbnailForModifiedAt != ModifiedAt`, — значит, обрыв на 8000-м файле стоит продолжения, а не повторения, и догнать проход можно позже, отдельно от скана.
- **Потолок `Cedar:AssetIndex:ThumbBudgetBytes`** (дефолт 2 ГБ на владельца) отказывает с текстом, называющим цифру. «Без лимита» — это про отсутствие лимита у автора, а не про отсутствие потолка у дроплета с 45 ГБ свободного диска. Молчаливое заполнение диска было бы не щедростью, а отказом обслуживания.
- **Счётчик в интерфейсе показывает файлы и мегабайты.** Долгий проход без цифр неотличим от зависания, и это единственная причина, по которой прогресс здесь обязателен, а не желателен.

`ThumbnailForModifiedAt` переиспользована, а не продублирована: смысл «превью соответствует этой версии файла» не изменился, изменился только источник байт.

**Decision 6: доступ к диску получает удалённый origin, и это настоящая цена, а не формальность.** Раньше окно грузило `127.0.0.1`; теперь — `cedarclerk.mooexe.dev`, а SPA рендерит TipTap-документы и вставленный пользователем HTML. **XSS на домене превращается в чтение выбранной папки.** Это записано здесь как принятый риск, а не как решённая проблема.

Что его сужает, каждое по отдельному основанию:
- **`shell.openPath` в мост не входит** (выбор Марти). `showItemInFolder` подсвечивает файл в проводнике и ничего не запускает — это разница между чтением и исполнением, и она стоит того, чтобы отказаться от двойного клика по `.blend`.
- **Bearer-токен агента** — 32 случайных байта на запуск, передаётся оболочкой через окружение. Без него локальный HTTP-сервер, перечисляющий любую папку, открыт любому процессу на машине и любой странице в любом браузере. Сегодняшний sidecar был закрыт cookie Identity; агент, у которого Identity нет, нуждается в своём замке.
- **Только выданные корни.** Корень выдаётся агенту главным процессом **после** диалога ОС, то есть после жеста Марти. Скомпрометированный renderer не может попросить `C:\Users\marty\Documents`.
- **Гейт preload по origin** и блокировка навигации за пределы upstream: мост не достаётся странице, приехавшей откуда-то ещё.

**Decision 7: окно грузит `/projects`, а не `/`.** Лендинг перехватывает ровно `GET /` без cookie (`LandingEndpoints.UseLanding`), поэтому любой другой путь отдаёт SPA — и `Cedar:Desktop` для обхода лендинга больше не нужен. Это же убирает баг, который Марти нашёл 10.08.2026 (приложение открывалось на маркетинговой странице с ценами), не флагом, а выбором адреса.

**Цена, которую надо назвать вслух: без сети десктоп не работает вообще.** Локальный режим был единственным офлайновым сценарием, и он удалён. Тридцатидневная cookie спасает от повторного входа, но не от отсутствия сети. Это прямое следствие Decision 1, и приемлемо оно ровно потому, что рабочая машина Марти постоянно в сети, а альтернатива — та самая каша, из-за которой этот ADR написан.

**`ApplicationUser.RemoteUserId` остаётся колонкой-рудиментом.** Код `UpstreamAuth` удалён весь, колонка — нет: удаление колонки в SQLite означает пересборку `AspNetUsers`, а Identity трогает эту таблицу на каждом авторизованном запросе (инцидент `no such column` из `.claude/rules/ef-migrations.md`). Нулевая выгода против ненулевого риска на живой базе.

**Что это закрывает и обнуляет**: `T-121` (второй режим из ADR-105 — сделан не как режим, а как единственный) и `T-137` (у десктопной базы нет бэкапа — базы больше нет, так что строка моот, а не выполнена).

### ADR-118 — Cedar CLI: интерактивная оболочка поверх существующих скриптов, деплой инициирует только человек (12.08.2026)

**Context**: запрос Марти. Управление проектом разъехалось по пяти PowerShell-скриптам с двадцатью флагами и по десятку `ssh`-команд, которые каждый раз набираются заново. Просьба — собрать это в один интерактивный инструмент на C#/Spectre.Console с меню, промптами и насыщенной терминальной графикой. Явное условие этапа: **обёртка, а не порт логики**.

**Decision 1: CLI вызывает `.ps1`, а не повторяет их.** `deploy.ps1` — это 875 строк, каждая ветка которых написана по следу реального инцидента: докачка с байта появилась после того, как `scp -r` дважды оставил прод лежать (ADR-113), порядок `.exe` → `.blockmap` → `latest.yml` — после разбора того, что читает `electron-updater` (ADR-116), а sha256 на той стороне — потому что оборванная заливка молча выглядит успешной.

Порт этого в C# означал бы переписать проверенный в бою код и одновременно поменять интерфейс, которым его вызывают. Тогда первый же сбой деплоя стал бы вопросом «это новая логика или новая обёртка», а ответить на него можно только откатом обеих. **Меняем ровно одну вещь за раз**; порт — этап 2, и только после того, как обёртка отработает вживую.

**Decision 2: `cedar deploy` не деплоит.** Он выполняет preflight (ветка, чистота дерева, тег, связь с сервером, живая версия против собираемой), печатает сводку `0.11.0 → 0.11.1` и **готовую команду**, которую запускает Марти.

Это не осторожность ради осторожности. `deploy.ps1` монолитен: точки останова перед swap в нём нет, и чтобы «довести до рестарта и остановиться», его пришлось бы разрезать — то есть нарушить Decision 1 в первом же сценарии. Плюс правило `.claude/rules/destructive-operations.md` требует остановки перед необратимым, а деплой останавливает продакшен. Отсюда честная формулировка: CLI знает про деплой всё и не запускает его.

`cedar restart` — исключение и единственная destructive-команда этапа 1, потому что `sudo` на дроплете выдан NOPASSWD ровно на `systemctl start|stop|restart cedarclerk` и ни на что больше: способность, которую CLI получает, уже очерчена сервером, а не нами. Подтверждение по умолчанию `false`.

**Decision 3: удалённые вызовы идут shell-out на `ssh`, а не через SSH.NET.** Ключи, agent, `known_hosts` и `BatchMode` уже настроены и уже работают — библиотека потребовала бы второй, параллельной конфигурации доверия, которая расходится с первой молча. Плюс любую команду CLI можно скопировать из `--dry-run` и выполнить руками; с библиотекой воспроизводимости нет.

**Decision 4: `--dry-run` — это подмена реализации, а не `if` внутри команд.** Один интерфейс `ICommandRunner`, три реализации: настоящая, печатающая и фейковая для тестов. Условие внутри команды рано или поздно окажется не на том пути — а «сухой» деплой, который что-то выполнил, хуже отсутствия флага.

**Decision 5: всё, что рисуется, берётся с машины, а истории CLI не выдумывает.** Проверено вживую 12.08.2026, до написания кода:
- `journalctl -u cedarclerk` **читается без sudo** — служба запущена от `martycow`, и её строки принадлежат владельцу. Правило в `.claude/rules/production-environment.md` утверждало обратное и **исправлено этим ADR**. Оговорка, ставшая ограничением интерфейса: за сутки в журнале **1.49 млн строк** (EF логирует каждый запрос), поэтому `cedar logs` всегда ограничивает выборку — режима «показать всё» не существует.
- **`sysstat`/`sar` установлен и собирает данные каждые 10 минут.** Значит sparkline CPU/RAM — настоящие измерения, а не оживление статики. Дефолт окна — **24 часа (144 точки)**, а не час: часовое окно даёт шесть точек, из которых график не получается.
- `systemctl show`, `df`, `free`, `du`, `sqlite3`, `ps` доступны без повышения прав; `sqlite3` используется только на чтение (`PRAGMA quick_check`, `SELECT count(*)`).

**Decision 6: `cedar backup verify` показывает отсутствие бэкапа, а `cedar backup now` не строится.** На дроплете **нет ни crontab, ни `~/bin`, ни `/mnt/backup`** — ночная копия с Pi не переехала (ADR-114). Команде «проверить последний бэкап» нечего проверять, и правильный ответ — не убрать её, а заставить сказать вслух: единственная копия — недельный образ DigitalOcean, в том же аккаунте, восстанавливаемый только целиком.

Создание бэкапа — это `T-071`, то есть новая логика на сервере, а не обёртка над существующей. Строить её внутри сессии про интерфейс означало бы протащить серверное изменение под видом кнопки.

**Decision 7: цвет никогда не единственный носитель смысла.** Рядом с каждым цветом — символ или число. Терминалы бывают монохромными, `--no-unicode` деградирует до ASCII, и различение красного и зелёного не у всех одинаковое. Проверяется на `AnsiConsole.Profile.Capabilities`, флаг только принудительный.

**Decision 8: прогресс тестов рисуется парсингом потока, а не ожиданием кода возврата** (прямая просьба Марти — видеть, как сотни галочек зеленеют). `dotnet test`, `vitest` и Playwright печатают строку на каждый завершённый тест; `ICommandRunner` получает потоковый вариант с обратным вызовом на строку, и сетка галочек заполняется по мере прихода.

Плата названа: формат этих строк — не контракт, а вывод чужих инструментов, и он может измениться при обновлении. Поэтому **парсер обязан деградировать, а не падать**: непонятая строка не считается тестом, а вердикт прогона берётся из кода возврата, а не из числа распознанных галочек. Красивая сетка не должна становиться причиной, по которой красный прогон покажется зелёным.

**Что осталось за границей**: любые изменения в `CedarClerk.Server` и `cedarclerk-web`, новые эндпоинты (включая `/api/admin/telemetry`), автоматический деплой, CI, cron и хранение любых секретов. Конфиг CLI хранит только пути и имена хостов; аутентификация — существующий ssh-agent.

**Decision 9 (12.08.2026): ставится как .NET global tool, а не публикуется в папку на PATH.** `PackAsTool` + `ToolCommandName=cedar` в `.csproj`, установка — `Scripts/install-cli.ps1`. Причина в том, чего этот путь **не** делает: `%USERPROFILE%\.dotnet\tools` уже создан и уже в PATH самим SDK, поэтому переменные окружения не правятся руками — а значит их не придётся вычищать при удалении (`install-cli.ps1 -Uninstall`). Версия для `pack` читается из `Consts.CurrentVersion`, чтобы `dotnet tool list` не показывал число, которого нет больше нигде.

Побочный эффект, который пришлось закрыть отдельно: `ConfigStore.FindRepoRoot` ищет `CedarClerk.sln`, поднимаясь от исполняемого файла, и это работало, пока инструмент лежал в `bin/` внутри репозитория. Global tool живёт в хранилище SDK, откуда наверх идти некуда — вне рабочей папки он репозиторий не находит. Поэтому установщик записывает `RepoRoot` в `%APPDATA%\cedar\config.json` (существующий конфиг дополняется, не перезаписывается); без этого `cedar deploy` из произвольного каталога честно отвечал бы «run 'cedar config'» на каждый запуск.

**Decision 10 (12.08.2026): меню рисуется само, а не через `SelectionPrompt`.** Запрос Марти — чтобы логотип продолжал поблёскивать, пока сидишь в меню, и раз в десять секунд буквы по очереди чуть подпрыгивали. `SelectionPrompt` этого не позволяет в принципе: он владеет нижней частью экрана и перерисовывает только свой список, поэтому всё, что нарисовано выше, застывает навсегда.

Поэтому `Rendering/Chooser.cs` держит весь экран одним `Live`-кадром: логотип, шапка, пункты. Плата — свои обработчики стрелок; взамен три вещи, а не одна: логотип живёт, шапка (какая машина, какая версия) не уезжает вверх с выводом предыдущей команды, и подменю **заменяет** экран вместо того, чтобы подклеить вторую копию всего под первой.

Анимация — **чистая функция времени** (`Logo.IdleAt`), а не сопрограмма с состоянием. Меню спрашивает «как логотип должен выглядеть сейчас» и перерисовывает кадр, только если ответ изменился. Это не микрооптимизация: в покое (а покой — больше половины цикла, это проверяется тестом) цикл спит, и меню, открытое в ssh-сессии, не гонит по каналу 25 кадров в секунду.

Подскок реализован как **лишняя пустая строка сверху**: кадр на строку выше арта, и «буква подпрыгнула» — это «читать её колонки на строку ниже». Один и тот же поиск для взлетевшей буквы и для стоящей, вместо второй раскладки для особого случая. Без этой пустой строки верхний ряд `CEDAR` обрезался бы краем блока, и прыжок читался бы как потеря крышки.

Деградация обязательна, потому что инструмент владеет клавиатурой: перенаправленный вывод, отсутствие ANSI, неинтерактивная консоль **или слишком низкое окно** — и `Chooser` откатывается на прежний `SelectionPrompt`. Меню, которое нарисовало половину логотипа и съело клавиатуру, хуже простого списка.

**Decision 11 (12.08.2026): `cedar claude` открывает второе окно, а не подпроцесс.** Пункт меню и команда, запускающие терминал в папке репозитория с уже работающим `claude /remote-control` (запрос Марти). Именно **второе окно**: обе программы читают клавиатуру, и общая консоль означала бы двух читателей, дерущихся за каждое нажатие. Сессия запускается и забывается — ни пайпов, ни кода возврата, который стоило бы ждать.

Для этого в `ICommandRunner` добавлен `LaunchDetachedAsync` — отдельный метод, а не флаг у `RunLocalAsync`, потому что тот перехватывает stdout и блокируется до выхода, то есть ровно две вещи, которых интерактивная сессия делать не должна. Через интерфейс он идёт всё равно, чтобы `--dry-run` продолжал означать «ничего не трогаем», включая «не открываем окон».

Windows Terminal, если он есть, иначе просто pwsh: `wt` разбивает собственные аргументы по `;`, поэтому в его варианте `Set-Location` нет вовсе — `-d` уже ставит вкладку в нужный каталог, и в оставшейся команде точки с запятой не остаётся. На не-Windows команда печатается, а не угадывается: портируемого «открой терминал» не существует.

**Decision 12 (12.08.2026): тег `LIVE` ставится после health-check, локально, и умеет ошибаться вслух.** Запрос Марти: помечать тегом `LIVE` коммит, который сейчас в продакшене, и следить, чтобы такой коммит был один.

Второе бесплатно и полицейского не требует: имя тега по определению разрешается ровно в один объект, поэтому `git tag -f` не добавляет метку, а **переносит** её. Ни одного состояния, в котором `LIVE` висит на двух коммитах, не существует.

Полицейского требует другое — **тег, который врёт**. Он расходится с реальностью через деплой с другой машины, ручную правку на сервере или откат, о котором git не узнал. Отсюда две меры. Первая: тег двигается **только после того, как health-check получил от продакшена ту самую версию**, — раньше это намерение, а не факт, и `LIVE` на коммите, который не доехал, хуже отсутствия тега (на неверный ответ действуют, отсутствующий выясняют). Вторая: `Test-LiveTag` в preflight читает `CurrentVersion` на коммите тега (`git show LIVE:…/Consts.cs`) и сравнивает с тем, что отвечает живой сервер; расхождение — предупреждение, а не стоп, потому что деплой, который этот стоп заблокировал бы, как раз и чинит тег.

`LIVE-PREV` повторяет серверный `app.prev` **ровно на один уровень**. Сервер держит один предыдущий релиз, поэтому цепочка из двух тегов обещала бы откат, которого сервер выполнить не может. Отсюда три следствия: выходящий `LIVE` становится `LIVE-PREV` даже когда это тот же коммит (повторный деплой того же коммита делает `app.prev` этим же коммитом); при первом в жизни деплое `LIVE-PREV` **удаляется**, а не оставляется от прошлой жизни; а `-Rollback` переносит `LIVE` на `LIVE-PREV` и удаляет `LIVE-PREV` — как сервер, который после отката не оставляет за собой ничего. Если возвращаться некуда, `LIVE` снимается совсем: после такого отката запущенный коммит здесь честно неизвестен, и отсутствие тега — единственный способ это сказать.

**Тег не пушится на origin** (решение Марти). Плата названа: с другой машины и с GitHub не видно, что в продакшене. Взамен `deploy.ps1` остаётся полностью офлайновым по git — ни сетевой зависимости в скрипте, который и так делает самую рискованную операцию в проекте, ни force-push в его составе.

Ни одна из этих операций не может провалить деплой: к моменту, когда они выполняются, сайт уже живой, и уронить закончившийся релиз из-за бухгалтерии было бы хвостом, виляющим собакой.

**Decision 13 (12.08.2026): глоссарий сгруппирован по плиткам, а не по алфавиту.** Запрос Марти: «иногда не понимаю, что значат сокращения в статистике». `cedar legend`, пункт меню, и `cedar status --legend`, который кладёт панель прямо под дашборд; без флага `status` оставляет одну серую строку с указателем — иначе глоссарий это команда, о которой надо сначала узнать, чтобы её найти.

Порядок — по плитке, в которой слово встречается. Алфавитный список строится проще и требует, чтобы ты **уже знал**, какое слово тебя смутило; по плиткам читаешь экран так же, как смотришь на него: находишь коробку, потом слово в ней.

Определения — про **эту машину**, а не про аббревиатуру вообще. «rss — resident set size» это перевод, а не объяснение; строчку оправдывает продолжение: на дроплете с 2 ГБ и без свопа именно это число приводит к тому, что службу убивают. То же с `wal` (растёт — checkpoint не отрабатывает), `avail` (свопа нет, поэтому это всё, что есть) и `no autostart` (юнит disabled, ребут DigitalOcean оставит сайт лежать).

**Decision 14 (12.08.2026): сетка тестов — поле квадратов, а не галочки.** Запрос Марти: «не понравились фиолетовые галочки, круче — дофига квадратиков, заполняются зелёным, но чтобы border был виден».

Фиолетовыми они были не по вине палитры. `✔` (U+2714) входит в эмодзи-набор, поэтому Windows отдаёт его Segoe UI Emoji, который рисует собственный цветной глиф и **игнорирует ANSI-цвет целиком**. Одна галочка в строке это скрывает, стена из восьмисот — нет. Geometric Shapes эмодзи-представления не имеют и остаются того цвета, который им задали, поэтому смена символа чинит причину, а не симптом.

Три требования к глифу ячейки, и все три — следствия, а не вкус: **ровно одна колонка в обоих режимах** (в ASCII `Ok`/`Bad` были двухсимвольными — `OK`/`XX`, — и сетка, которая переносит строку по числу результатов, а не символов, молча рисовалась вдвое шире); **не эмодзи** (выше); **различимость формой, а не только цветом** (решение 7) — залитый, перечёркнутый и с точкой читаются в монохроме, три оттенка одного квадрата нет. Отсюда `□ ▣ ⊠ ⊡`. Залитый сохраняет рамку, поэтому законченная сетка остаётся сеткой ячеек, а не одной зелёной плитой.

**Поле рисуется заранее по памяти о прошлом прогоне** (`%APPDATA%\cedar\last-run.json`, ключ — набор флагов, потому что `-Backend` и `-Smoke` это разные наборы). Иначе эффекта «заполняется» не существует: сетка, которая появляется по мере поступления, заполнять нечего. Число — догадка, и обращаются с ним как с догадкой: поле рисуется по максимуму из запомненного и фактического, финальный кадр перерисовывается только по фактическому, и ни одно решение из этого числа не следует. Устаревшее число делает анимацию слегка неверной один раз и тут же перезаписывается; красный прогон зелёным оно сделать не может — вердикт по-прежнему код возврата (решение 8).

**Побочно исправлено**: `Live` прячет курсор, а на Windows при перенаправленном выводе это бросает `IOException: The handle is invalid`, — то есть `cedar test` из скрипта падал, не запустив ни одного теста. Теперь неинтерактивный вывод обходит `Live` и печатает готовый кадр один раз.

### ADR-119 — Этап 2: логика переезжает в C#, скрипты становятся тонкими обёртками (12.08.2026)

ADR-118 закончился фразой «этап 2 — отдельное решение». Вот оно. Марти: «приступай к этапу 2; самое главное, чтобы всё билдилось, тестилось и деплоилось как и раньше».

**Decision 1 (переписано в тот же день по замечанию Марти): `deploy.ps1`, `build.ps1` и `test.ps1` удаляются, а не остаются обёртками.** Входов у логики один — `cedar`.

Первая редакция этого решения оставляла три скрипта тонкими обёртками, которые зовут `cedar`, чтобы `.\Scripts\deploy.ps1` продолжал работать под старым именем. Марти спросил: «а они реально нужны? там же толком кода нет». Проверка ответила за меня — **ни один автоматический вызов их не использует**: ни CI (его нет), ни `e2e.ps1`, ни npm-скрипты, ни electron-builder. Все 30 совпадений по репозиторию — упоминания в комментариях и документации, то есть текст, который правится тем же движением, что и всё остальное.

Значит, аргумент «имя записано в CLAUDE.md и в памяти рук» держался на пустом месте: документацию я в той же сессии и переписывал, а рук ровно одни, и они попросили убрать. Оставалось бы вот что, и всё это — цена, а не польза:

- **вторая поверхность флагов**, которую надо держать в синхронности: `-SkipBuild` ↔ `--skip-build`, `-Ascii` ↔ `--no-unicode`, `-CloudHost` ↔ `--host`. Новый флаг завтра — две правки вместо одной, и забытая вторая проявится как «а почему из скрипта не работает»;
- **риск рекурсии**, которого без обёрток не существует: установленный `cedar` старее скриптов зовёт их обратно. Пришлось ставить сторожа с переменной окружения — защиту от проблемы, целиком созданной самими обёртками;
- **два имени у одной вещи** в каждой фразе документации.

Единственное, что обёртки честно давали, — запуск на машине, где `cedar` ещё не установлен, через запасной `dotnet run`. Это никуда не делось, просто переехало туда, где ему место: **`install-cli.ps1` — точка входа на свежем клоне**, и после неё всё остальное это `cedar`. Круг «скрипт работает только после инструмента, который ставится скриптом» не разрывается запасным путём в трёх местах, он разрывается тем, что установка ровно одна и она первая. Аварийный путь, если `cedar` сломан, тоже один и он документирован: `dotnet run --project CedarClerk.Cli -- deploy`.

Что остаётся в `Scripts/`: `e2e.ps1` и `install-cli.ps1` (Decision 3). Обе — настоящие скрипты, а не переадресация.

**Урок, который стоит записи**: «это же записано в документации» — не аргумент за сохранение интерфейса, когда документацию пишешь ты же и в этой же сессии. Настоящий аргумент — существующий вызывающий, которого нельзя починить. Его здесь не было, и проверить это стоило одного `grep`, который был сделан только после вопроса.

**Decision 2: `cedar deploy` теперь действительно деплоит.** Это отмена Decision 2 из ADR-118, и отменяется она вместе со своей причиной, а не вопреки ей.

Причина звучала так: у `deploy.ps1` нет безопасной точки остановки перед подменой каталогов, поэтому «дойти до последнего шага и встать» означало бы разрезать скрипт — в той же сессии, в которой менялся интерфейс, вызывающий его. Тогда первый упавший деплой был бы необъясним: новая логика или новая обёртка? На этапе 2 разрезать нечего. Логика переписана целиком и вместе с интерфейсом, то есть меняется ровно одна вещь — реализация деплоя, — и она меняется целиком.

Что осталось от старого решения и не должно исчезнуть: **человек нажимает кнопку.** `cedar deploy` показывает preflight, печатает пару версий и **спрашивает, с ответом по умолчанию «нет»** (`.claude/rules/destructive-operations.md`). `--preflight` сохраняет прежнее поведение — проверки и стоп; `--yes` нужен обёртке, чтобы `.\Scripts\deploy.ps1` вёл себя как раньше, то есть спрашивал не дважды.

**Decision 3: переезжает не всё, и границу задаёт не размер файла.** `_git-guard.ps1`, `build.ps1`, `test.ps1`, `deploy.ps1` — переезжают: это оркестрация, ветвления и отчёт, то есть ровно то, что C# делает лучше, а PowerShell — многословнее.

Остаются скриптами:
- **`e2e.ps1`** — он не оркестратор, а стенд: чистит `CEDAR_DATA_DIR`, поднимает сервер без токена бота, регистрирует аккаунт, перезапускает сервер ради admin-bootstrap, запускает Playwright и гасит сервер, что бы ни случилось. Это управление жизненным циклом процесса и переменными окружения — то, ради чего скриптовый язык и существует. `cedar test --smoke` вызывает его как фазу.
- **`install-cli.ps1`** — bootstrap. Ставить `cedar` при помощи `cedar` нельзя по определению, и попытка была бы тем самым кругом из Decision 1.

**Decision 4: `tar` остаётся внешним.** .NET 8 умеет `System.Formats.Tar`, и соблазн убрать зависимость от `tar.exe` был. Отклонено по двум причинам, и вторая важнее первой. Первая: на Windows у файла нет unix-режима, `TarWriter` пишет туда ноль, и на сервере распаковались бы файлы с правами `000` — то есть деплой, который проходит все проверки и не стартует. Обойти можно, но проверить можно только на сервере. Вторая: менять упаковщик в той же сессии, в которой меняется оркестратор, — это ровно та ошибка, от которой ADR-118 защищал этап 1. Байты на проводе остаются те же, что и вчера.

По той же логике сохранены без изменений: определение GNU tar ради `--force-local` (GNU читает `C:\...` как хост `C`), переиспользование архива по сигнатуре `файлы|байты|mtime` (gzip штампует время, поэтому повторная упаковка того же ввода даёт другие байты и убивает докачку), докачка через `cat >>` вместо `scp` (scp начинает с нуля), sha256 на той стороне, распаковка в `app.new` до остановки сервиса, подмена одним ssh-вызовом, `app.prev` для отката и порядок `.exe` → `.blockmap` → `latest.yml` для десктопа (ADR-116).

**Decision 5: шаги деплоя — данные, а не последовательность вызовов.** Каждый шаг — объект с именем, деталью и телом; исполнитель ведёт таймер, рисует живой экран и собирает отчёт. Это то, что позволило сделать интерфейс, о котором просил Марти («чем круче, тем лучше»): полоса загрузки со скоростью и ETA, **живой брайль-график пропускной способности** (тот же `BrailleChart`, что и на дашборде), счётчик простоя в миллисекундах и финальная сводка с пропорциональными полосами времени. Ни один из этих элементов не знает, что именно он измеряет, поэтому добавление шага не требует трогать отрисовку.

Правило ADR-118 о цвете действует и здесь: у каждой полосы есть число, у каждого статуса — слово, и `--no-unicode` по-прежнему снимает всю графику до ASCII.

**Decision 6: `_git-guard.ps1` удаляется.** Его единственными потребителями были три переехавших скрипта, а `GitGuard.cs` — это он же, дословно, вместе с логикой тега `LIVE`/`LIVE-PREV` (ADR-118 решение 12). Оставленный «на всякий случай» файл — это вторая реализация, которая молча разойдётся с первой.

**Что это стоит, честно.** У самого рискованного скрипта в проекте больше нет параллельной копии, к которой можно откатиться одним запуском. Откат — это git (`git show <commit>:Scripts/deploy.ps1`), и первый настоящий деплой новым кодом должен быть сделан при свидетеле. Смягчает это то, что режимы отказа остались прежними по построению: сервис не останавливается, пока архив не проверен по контрольной сумме и не распакован, `app.prev` на месте, `-Rollback` работает, а прерванная закачка продолжается с того же байта.
