# Модуль для инди-геймдева

Единая точка входа по развороту Cedar Clerk в тулкит инди-разработчика игр. Первоисточник замысла — внерепозиторный бриф Марти `Gamedev_Focused_Rework.md`. Решения — `docs/DECISIONS.md`, ADR-101…107. Устройство десктопа — `docs/tech/DESKTOP.md`. Порядок работ — `docs/tasks/ROADMAP.md`, Phase 13.

Ветка `indiedev_module` (создана от `dev`) **влита в `master` с v0.10.0 и удалена**. Обратимость, которую бриф требовал от ветки, живёт в флаге `Cedar:Modules:IndieDev` (ADR-101): выключение возвращает сегодняшнее приложение целиком. **MUST-список модуля закрыт 11.08.2026** — статус ведёт `docs/tasks/ROADMAP.md` Phase 13, открытые остатки (MIGHT + `T-127`) — борда.

## Что меняется

Cedar Clerk перестаёт быть «редактором постов с публикацией в несколько сетей» и становится платформой, где **пост — один из типов документа**, а документы живут внутри **проекта** (в терминах Марти — игры). Вокруг документов появляются вещи, которые постами не являются вовсе: задачи, спринты, индекс ассетов, референс-борды, помощники сценариста и гейм-дизайнера.

При этом ничего из существующего не подменяется. Модуль **добавляет** — редактор, `/drafts`, `/posts`, `/settings` работают как работали, и выключение флага `Cedar:Modules:IndieDev` возвращает сегодняшнее приложение целиком.

## Позиционирование

Это заодно ответ на `Q-1` в `docs/tasks/BACKLOG.md`, висевший открытым с 30.07.2026: тогда было названо четыре фокуса (блоггеры, фотографы/видеомейкеры, помощь писателям, помощь инди-геймдевам) и потеряна формулировка пятого. Бриф выбирает один — **инди-разработчик игр**, — и выбирает его по честной причине: это сам Марти, то есть единственная аудитория, чьи потребности здесь проверяются не догадкой, а собственной работой.

Важно, что аудитория при этом не сужается до «программиста». Формулировка брифа перечисляет роли одного человека: программист, гейм-дизайнер, продюсер, сценарист, звукорежиссёр, композитор, режиссёр, маркетолог, аналитик. Тулкит адресован этому набору ролей, а не типу занятости.

Рабочее имя из брифа — `Cedar Clerk For Indie Developers`. Имя продукта остаётся открытым вопросом (`Q-17`, `docs/tasks/BACKLOG.md`); рекомендация — оставить `Cedar Clerk` именем платформы, потому что переименование тянет за собой домен, имя бота, расширение `.cedar` и все сто ADR, а маркетинговую задачу решает подзаголовок.

## Модель данных

Полное обоснование каждой строки — ADR-102, ADR-106, ADR-107.

**Изменения существующего:**
- `Draft.DocumentType` — string, default `post`. Существующие строки становятся постами без миграции данных.
- `Draft.ProjectId` — `Guid?`, plain scalar без FK и nav-свойства, как `FolderId`. Null = документ вне проекта (все сегодняшние).
- `GlossaryTerm.ProjectId` — `Guid?`. Null = глобальный термин (сегодняшнее поведение), заполнен = локальный глоссарий проекта.
- `Project.AssetRootPath` / `Project.AssetsIndexedAt` — папка, которую индексируем, и когда это делали в последний раз. Корень один на проект, а не в каждой строке индекса (ADR-107, уточнение 2).

**Новое:**

| Сущность | Смысл | Ключевые поля |
|---|---|---|
| `Project` | Игра или иная работа, вокруг которой собраны документы | `OwnerId`, `Name`, `Description`, `CoverUrl?`, `CreatedAt`, `ArchivedAt?` |
| `GameTask` | Задача таск-трекера | `OwnerId`, `ProjectId`, `Name`, `Status`, `Priority`, `Description`, `Assignee`, `SprintId?`, `DueAt?` |
| `TaskLink` | Связь задачи с чем угодно | `TaskId`, `EntityType`, `EntityId` |
| `Sprint` | Отрезок планирования поверх задач | `OwnerId`, `ProjectId`, `Name`, `StartsAt`, `EndsAt` |
| `AssetEntry` | Строка индекса локального ассета — путь и метаданные, файл не копируется | `OwnerId`, `ProjectId`, `RelativePath`, `FileName`, `Extension`, `Kind`, `SizeBytes`, `ModifiedAt`, `IndexedAt`, `MissingSince?` |

Соглашения проекта соблюдаются: GUID-первичные ключи, плоский `string OwnerId` на каждой owner-scoped строке, фильтрация по владельцу в каждом эндпоинте (`docs/tech/ARCHITECTURE.md`). Сущности модуля живут в `Data/Entities.IndieDev.cs` — второй файл, а не тридцать: конвенция «всё в одном плоском `Entities.cs`» существует, чтобы не плодить файл на сущность, и разделение по модулю ей не противоречит.

**Обязательная миграция.** Любое из перечисленного трогает `Entities.cs` — значит, `dotnet ef migrations add <Name> --project CedarClerk.Server` в той же сессии, немедленно. `SchemaDriftGuardTests` уронит `dotnet test`, если про это забыть (`.claude/rules/ef-migrations.md`).

**Ловушка, на которую уже наступили (T-120):** EF **не читает** инициализатор свойства (`= DocumentTypes.Post`) при генерации миграции и подставляет `defaultValue: ""`. Для колонки, у которой пустое значение означает «неизвестный тип», это заполнило бы все существующие строки нерабочим значением. Дефолт объявляется в `OnModelCreating` через `HasDefaultValue` — тогда он попадает и в миграцию, и в снапшот модели. Проверять это в сгенерированном файле **перед** первым запуском: `Database.Migrate()` на старте выполняет миграцию молча.

## Что реализовано (T-123, 11.08.2026) — таск-трекер

- `CedarClerk.Core/TaskWorkflow.cs` — `TaskStatuses` (четыре колонки доски, порядок = порядок слева направо) и `TaskPriorities` (1–3, `Clamp`). Чистый C#, покрыт тестами.
- `Data/Entities.IndieDev.cs` — `GameTask`. Миграция `AddGameTasks`: только новая таблица, существующие не тронуты; дефолты объявлены в `OnModelCreating`, а не инициализаторами свойств (грабли T-120).
- `Modules/IndieDev/TaskEndpoints.cs` — `/api/projects/{id}/tasks` (список, создание) и `/api/tasks/{id}` (чтение, обновление, удаление, связи).
- `Modules/IndieDev/ProjectLinks.cs` — общий помощник по `EntityLink`; `AssetIndexEndpoints` переведён на него, чтобы не было двух копий логики связей.
- Фронт: `core/tasks.service.ts`, `pages/project-tasks.component.*` (доска + список + карточка-модалка), маршрут `projects/:id/tasks`, блок `tasks` в обоих словарях.
- Дашборд: рейл «Ближайшее» стал настоящим; колонки «Задачи» и «Ассеты» в списке проектов показывают числа вместо прочерков.

**Решения, принятые при реализации:**

| Что | Почему |
|---|---|
| Связи — `EntityLink`, а не отдельный `TaskLink` из ADR-106 | T-141 уже обобщил эту строку. Упорядочивание пары досталось даром; отдельная таблица была бы второй, делающей ту же работу |
| Сортировка — на сервере, в одной функции | Доска, список и рейл отвечают на один вопрос «что дальше». Три реализации — три шанса разойтись |
| Просрочка важнее приоритета | P3, просроченный неделю назад, требует ответа раньше, чем P1 со сроком через месяц. Рейл, отсортированный по приоритету, понял бы это ровно наоборот |
| Доска отдаётся целиком, без пагинации | Задач в проекте десятки, а не десятки тысяч. Колонка канбана с пагинацией врёт о собственном счётчике. Пагинация — у индекса ассетов, и это разные экраны по природе |
| «Задачи» в списке проектов — счётчик **открытых** | Иначе законченный проект показывал бы своё самое большое число в тот день, когда делать в нём стало нечего |
| `CompletedAt` хранится, а не выводится из `UpdatedAt` | Правка заголовка закрытой задачи сдвинула бы дату, когда она была закрыта |
| Спринтов нет — это T-124 | Колонка `SprintId` заведена сразу, чтобы планировщик добавлял таблицу, а не менял существующую. Карточка спринта на дашборде честно говорит «ещё не построено», а не рисуется пустой |

**Побочная находка, исправленная здесь же:** удаление проекта оставляло индекс ассетов, а удаление документа — его связи. Ни у того, ни у другого нет навигационного свойства, поэтому EF не каскадил ничего; задачи стали бы третьим сиротой. Все три пути удаления теперь убирают за собой.

Проверено: `dotnet test` **737/737**, фронтенд 11/11, контраст чистый, smoke **53/53**. Плюс на живом сервере: порядок доски, взаимная связь двух задач (одна строка — две карточки), просроченное первым в рейле, `completedAt` не сдвигается от посторонней правки и обнуляется при возврате в работу, удалённая задача забирает свои связи с чужой карточки.

- Доска: чипы фильтра по спринтам, `S`-чип на карточке, выбор спринта в карточке задачи. Дашборд: карточка спринта стала настоящей.

**Решения, принятые при реализации** (обоснование — ADR-111):

| Что | Почему |
|---|---|
| У спринта нет колонки статуса | Хранимый статус неверен ровно с той секунды, как часы прошли `EndsAt`, и требует механики, обслуживающей копию факта, записанного в двух датах |
| Спринт не бывает «просрочен» | Просрочены задачи внутри. Карточка так и говорит — «1 задача просрочена», — а не краснеет целиком. То же правило, что на доске |
| «Завершён» = дни кончились, а не «всё сделано» | Завершённый спринт сворачивается **только если внутри всё закрыто**. Осталась незакрытая — карточка остаётся открытой: спрятать её значило бы соврать, что работа исчезла вместе с датой |
| Номер спринта хранится, а не парсится из имени | Регулярка сломается на первом спринте, названном «Полировка». Номер отвечает «какой по счёту», имя — «про что» |
| Номер берётся из счётчика на проекте, а не `MAX+1` | `MAX+1` **переиспользует** номер сразу после удаления самого верхнего спринта. Поймано запуском, не чтением; тест написан после |
| Удаление спринта отвязывает задачи | То же правило, что у проекта: удаление контейнера — не просьба удалить содержимое |
| Задача может войти только в спринт своего проекта | Иначе id из чужого проекта принимался бы, и задача выпадала бы сразу из обоих планировщиков |

Проверено: `dotnet test` **752/752**, фронтенд 11/11, контраст чист, smoke **53/53**. На живом сервере: три спринта в трёх состояниях и их порядок, счётчик просроченных внутри текущего, отказ на чужой спринт, отказ на «конец раньше начала», номера после двух удалений (`S2, S4, S5` — без переиспользования), задача пережила удаление своего спринта.

## Что реализовано (T-125 и T-126, 11.08.2026) — глоссарий проекта и версии

**T-125.** `GlossaryTerm.ProjectId` (`Guid?`, миграция `AddGlossaryProjectScope`, nullable без дефолта — существующие термины становятся глобальными). `GET /api/glossary` понимает `?projectId=` и `?scope=global`; `LoadForAsync` получает проект документа, и блог рендерит пост с общими терминами **плюс** терминами его проекта. Экран глоссария получил строку области видимости, которая заодно решает, куда попадёт новый термин (и подпись под ней это говорит).

**T-126.** `Build` + `GameTask.BuildId` (миграция `AddBuilds`), `Modules/IndieDev/BuildEndpoints.cs`, экран `/projects/:id/builds`, выбор версии в карточке задачи, `LinkTargets.Build` для документов.

| Что | Почему |
|---|---|
| Область видимости термина — колонка, а не вторая сущность | У термина проекта и глобального одинаковая форма. Отдельная таблица — девять продублированных колонок и невозможность перенести термин между областями без перенабора |
| Документ видит общие **плюс** свои | Не «или»: «Unity» глобален, «паром» — про одну игру, статья про эту игру нуждается в обоих |
| При совпадении побеждает термин проекта | Более узкая область — более точное определение; ради этого локальный глоссарий и заводят |
| Билд — сущность, а не тег | У версии есть номер, дата, заметки и состав. Плоская строка `Tags` не хранит ничего из этого и не отвечает на «что в 0.4.2» иначе как перебором с разбором |
| Задача — колонка `BuildId`, документ — `EntityLink` | Задача выходит в одном билде, и по этому полю фильтруют. Отношение документа свободнее, а `Draft` уже около тридцати пяти полей с записанным долгом на разбиение |
| Чейнджлог — документ, а не текст для копирования | Дальше он живёт обычной жизнью документа: правится, переводится, публикуется. Строка была бы генератором, результату которого некуда лечь |
| Билд ничего не знает о гите | Ни тегов репозитория, ни CI, ни артефактов. Это запись, которую ведёт автор; притворяться несуществующей интеграцией хуже, чем честно быть записью |

Проверено: `dotnet test` **752/752**, фронтенд 11/11, контраст чист, smoke **53/53**. На живом сервере: глоссарий проекта не показывает термины чужого проекта, повтор версии отклонён, билд из чужого проекта отклонён, чейнджлог собран из двух закрытых задач (задача в работе исключена), задача пережила удаление своей версии.

### T-122 — Asset Manager (10.08.2026)

~~**Вторая способность за вторым флагом.** `Cedar:AssetIndex:Enabled` включён только в десктопной оболочке.~~ **Заменено 12.08.2026 (ADR-117).** Обход диска переехал из серверного эндпоинта в десктопного агента, а облако теперь **принимает** описание папки (`PUT .../assets/source`, `POST .../assets/batch`, `POST .../assets/sweep`, `PUT .../assets/thumbs`). Флаг удалён вместе с эндпоинтами обхода: способность не выключена на проде, а отсутствует там — её код живёт только в агенте. Это сильнее, чем говорил флаг. Приём списка имён от владельца опасной способностью не является; ограничивают его числовые потолки (500 строк в батче, 200 000 на проект, 256 КБ на превью, потолок объёма `thumbs/`).

**Индекс теперь общий, и это меняет экран.** Строки живут в облаке и открываются откуда угодно, поэтому чаще всего экран ассетов показывает **отпечатки**: превью и метаданные вместо файла, лежащего на другой машине. `Project.AssetRootMachineId` — то, что делает вопрос «файл здесь или его отпечаток?» разрешимым; у браузера моста нет, значит нет и id машины, значит отпечаток всегда. Подробности — `docs/tech/DESKTOP.md` §«Файл или отпечаток».

**Отступления от хендоффа §9-10, все от нехватки данных, не от лени:**

| Что | Почему |
|---|---|
| Нет чипа «Музыка» | По расширению трек от эмбиента не отличить. Всё звуковое — `audio` |
| Постранично (60), а не виртуализованный список | Виртуализация нужна на десятках тысяч строк; пагинация честно работает уже сейчас и не притворяется бесконечным списком (`T-142`) |

### T-140 и T-141 — превью, метаданные и связи (10.08.2026)

Закрывают два из трёх честных пробелов, оставленных T-122. Обоснования — в ADR-107 (дополнение).

**Превью.**
- `CedarClerk.Core/BlendThumbnail.cs` — парсер превью, которое Blender кладёт внутрь `.blend`. Запрос Марти: это главный файл проекта и единственный, который не откроет графическая библиотека. Читается первый мегабайт, картинка переворачивается (Blender хранит строки снизу вверх), сжатый файл честно отказывает.
- `Modules/IndieDev/AssetMetadata.cs` — генерация миниатюр по запросу в `CEDAR_DATA_DIR/thumbs/`, **никогда** рядом с исходником.
- Эндпоинт `GET .../assets/{id}/thumb` — owner-scoped, не через `/media/*`.
- Что превью **возможно**, решается по расширению, а не по виду: PSD, EXR и Aseprite — картинки, которых декодер не откроет, и просить у них миниатюру значит показать иконку сломанного файла.

**Метаданные.** Размеры картинок (`Image.Identify`, только заголовок) и длительность с частотой WAV (`CedarClerk.Core/WavHeader.cs`, чистый парсер). MP3/OGG/FLAC молчат: каждому нужен настоящий парсер, а неверная длительность хуже отсутствующей — «2:14» не вызывает сомнений. Читается только у новых и изменившихся файлов.

**Набор форматов расширен** (запрос Марти): движковые файлы Unity/Unreal/Godot, DCC-исходники, проекты DAW, шейдеры и скрипты. Движковые остаются видом `other` — сцена Unity не картинка и не документ.

**Связи.** `EntityLink` — обобщение `TaskLink` из ADR-106 с упорядочиванием пары, чтобы A→B и B→A были одной строкой. Ставятся **руками**: проиндексированный файл лежит вне Cedar Clerk, ни один документ не может на него сослаться, поэтому «используется в» невозможно обнаружить — только указать. Подпись сменилась на «Связанные документы».

`dotnet test` 698/698. Проверено запуском на папке с фикстурами; непроверенным осталось одно — ориентация превью настоящего `.blend` (переворот сделан по документированному поведению, но подтверждён только на синтетическом файле).
