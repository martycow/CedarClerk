# Деплой Cedar Clerk

Запускайте на Mac из корня репозитория:

```bash
bash docs/for_user/deploy.sh
```

Это **настоящий деплой на production**. Скрипт собирает сервер и веб-приложение,
загружает их на `martycow@periwinkle.mooexe.dev`, переключает приложение и проверяет
результат. Десктопные установщики в этот сценарий не входят.

## Перед запуском

- Локально нужны Git, .NET SDK 10, Node/npm, Python 3.11+, SSH и rsync.
- На дроплете: ASP.NET Core Runtime 10 в `~/.dotnet`, Python 3.12+, sqlite3,
  rsync, curl, tar, sha256sum, flock и работающий сервис `cedarclerk`.
- SSH должен входить по ключу без пароля. Ключ сервера должен быть проверен и
  сохранён в `known_hosts`; скрипт не отключает эту проверку.
- Пользователь `martycow` должен иметь право `sudo` без пароля на
  `/usr/bin/systemctl start cedarclerk` и `/usr/bin/systemctl stop cedarclerk`.
- Ветка — `master`, рабочее дерево чистое. Все изменения должны быть закоммичены.
- `CurrentVersion` в `CedarClerk.Core/Consts.cs` должен совпадать с тегом на HEAD.
  Например, для версии `0.24.0`, после коммита: `git tag 0.24.0`.
- Локальный тег `LIVE` должен указывать на коммит реально работающей версии.
  Скрипт сравнивает её номер с ответом production и требует новый номер релиза.
  Не переносите `LIVE` на новый коммит до успешного деплоя.

Проверить сборку без подключения к серверу:

```bash
bash docs/for_user/deploy.sh --build-only
```

Требования к ветке, чистоте и тегу сохраняются. Путь к архиву и логу появится
в терминале. Сам скрипт не меняет версию, не создаёт релизный тег и не делает merge.

## Что проверяется

1. Backend-тесты, frontend-тесты, иконки, контраст, плотность UI и production-сборка.
2. Публикация Linux x64 сервера, наличие DLL, runtimeconfig и веб-приложения.
   Сервер собирается из отслеживаемых Git файлов; локальные секретные настройки
   и старый `wwwroot` в архив не попадают.
3. Передача архива с частичным возобновлением и тремя попытками, SHA-256,
   количество файлов, безопасные пути архива, свободное место и текущая версия.
4. После остановки — целостная SQLite-копия в
   `~/cedarclerk/data/backups/predeploy-<запуск>.db` с проверкой целостности.
5. После запуска — активность сервиса, локальный и публичный `/api/health`,
   точная версия/коммит в `/deployment.json` и загрузка HTML страницы входа.

Проверки HTTP не заменяют ручную проверку входа через Google/Discord, публикации
в Telegram или оплаты. Скрипт не отправляет тестовые публикации и не проводит платежи.

## Если что-то пошло не так

До остановки сервиса ошибка просто прекращает деплой. После остановки скрипт
пытается вернуть предыдущее приложение и проверяет его локальный health.
База **не откатывается автоматически**: миграции и изменения при старте могут
потребовать отдельного восстановления. Не подменяйте БД, пока не выяснена причина.

Предыдущая версия остаётся в `~/cedarclerk/app.prev`, более старая — в
`app.prev.<запуск>`. Неудачный новый релиз сохраняется в каталоге staging запуска.
Скрипт не удаляет старые релизы, архивы или резервные копии.

При обрыве SSH серверный процесс продолжает работу. Посмотрите напечатанный
каталог запуска, прежде чем запускать деплой снова:

```bash
ssh martycow@periwinkle.mooexe.dev
cat ~/cedarclerk/staging/<запуск>/result
tail -n 60 ~/cedarclerk/staging/<запуск>/deploy.log
journalctl -q -u cedarclerk -n 50 --no-pager
```

`success` — проверки пройдены; `rolled-back` — прежнее приложение восстановлено;
`failed-before-stop` — сервис не останавливали; `rollback-failed` — требуется
ручное восстановление. Отсутствие `result` не доказывает, что процесс завершился.

После подтверждённого успеха скрипт переносит локальные `LIVE`/`LIVE-PREV`, не
отправляя их в GitHub. Если связь оборвалась до этого шага, сверьте публичную
версию и коммит с логом, затем обновите эти теги вручную. Не запускайте второй
деплой, пока состояние первого не выяснено.
